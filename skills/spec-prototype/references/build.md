# Build

Build in a private throwaway root with loopback preview and a decision log. Keep generated assets and production source separate. Record the exact run command, preview URL, cleanup receipt, and what the human observed before making a recommendation.

## Fidelity and medium

Throwaway means unmaintained and unshipped, not necessarily low fidelity. Make a state or flow question rich enough to drive, a visual direction finished enough to judge, and an isolated placement only as detailed as needed. Do not add production abstractions or hardening beyond runnable, and persist state only when persistence is the question. Fidelity can differ among avenues.

Use the web by default. Honor a user-named technology or a tested dimension that cannot be represented honestly in a browser; state that choice before building. If the named technology cannot express the dimension either, report the limitation. Within the preview page, use available image generation when appropriate; markup is a valid fallback only when it honestly carries the dimension. A photographic or painterly question cannot be replaced by a markup sketch. Do not introduce a second display mechanism beside the preview; a non-web medium uses its own suitable display.

## Build and compare

Recreate only what the question needs from the current product. Do not stand up the full app unless the question concerns the whole-product experience. This local Skill preserves isolated artifacts and does not edit production source for overlays; when isolated reproduction cannot answer a density/chrome question, report that limitation to the owning workflow instead of silently expanding mutation scope.

Put comparable options on one surface unless that distorts the dimension. Scroll and transition questions need full-size interactive runs, with a static comparison surface if useful. Show the relevant state after a variant or user-facing action changes. Use one child directory per question beneath the single run directory selected by the preview reference. Never delete a kept prototype merely because its code is throwaway.

## Decision capsule

Only after a human actually settles a choice, update `decisions.md` with the question, what was built, run and question paths, the winner and reason, rejected options, requested adjustments, adjustments not yet in the artifact, and open questions. Preserve the winner and agreed adjustments in the prototype where feasible. Do not ask again before recording an already settled decision, and do not invent a winner from a passing test. The capsule is continuity for brainstorm or planning, not an implementation plan; multiple unresolved choices remain explicitly unresolved.
