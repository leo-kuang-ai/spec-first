# Scoping

A prototype answers one unresolved behavior or visual question that a person can experience. Define the decision, audience, success signal, and explicit non-goals before building. Unattended pipeline work, production write-back, and prototypes without a human experience remain blocked.

## Resolve the question

Use the current conversation and any supplied brainstorm or plan. An empty invocation may use an already stated question; disclose meaningful inferences from messy history and ask only for missing information. A repo run concerns that product unless the user says otherwise. Inspect only the page, component, or flow the question touches, its current behavior, paths, and constraints; do not scan the whole tree or request an architecture summary. Perform the bounded read inline unless the current user or authorized caller explicitly requested delegation.

Before building, know the product surface, the decision, and hard constraints. Do not ask the user to invent the answer in chat. Start with the uncertainty most expensive to get wrong, combining parts when their interaction is the question. Do not rebuild a visual question the user already settled against an adequate artifact.

## Narrow or wide

- **Narrow:** compare two or three close variants of a specific control, placement, or transition on one suitable surface; do not invent unrelated mechanisms.
- **Wide:** explore three to five distinct mechanisms within the named product question, describing what the user would see or do. This is not product discovery. Let the user choose avenues or build a comparable subset, then converge against the artifacts. Do not build one idea as the presumed answer.

Resolve unclear width from context, asking once when the distinction materially changes the build. Size to the uncertainty, not to the cheapest remaining question. A coupled flow may require a larger prototype than an isolated placement decision; fidelity is a separate choice owned by the build reference.

## Before and between builds

Before a costly preview, state what you will try, why, how it is split, and any consequential inference. Honor an existing explicit go-ahead for that scope; ask only when it is missing or the proposed effects exceed it. The user can redirect the question. Do not treat silence as approval or the agent's visual judgment as the user's decision.

After a human decision, reread the capsule and reassess remaining questions. The choice may settle another question, make it irrelevant, or reveal a new one. Explain meaningful changes before the next build. If the product goal itself changes, return the learning to its owner instead of continuing an obsolete question.
