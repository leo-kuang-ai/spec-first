# 研发流程 Skill 全量内容审查方案 - Plan

## Goal Capsule

**首批把需求文档和技术方案放在一起审。** 先看业务读者能否说清“谁在什么情况下会看到什么变化”；再看研发能否指出“本期功能如何实现、质量要求如何保证、以后变化会牵动哪里”。用户转述两类文档均有读不懂的反馈；目前没有对应版本、原始反馈或样本分母，不能据此认定某个 Skill 有缺陷。

**首轮执行入口：** 选一项获准使用的需求，固定原始材料、实际交付的 PRD 和计划版本，登记本轮必验场景。全读 `spec-prd`、`spec-plan` 及实际依赖，用下表追踪同一项业务约束；这张表用于开始取证，不替代后文的全量审查。

| 审查问题 | 主判据 | 取什么证据 | 不能据此判通过的反例 |
|---|---|---|---|
| 产品和测试能否读懂变化？ | 已决定的规则容易找到，未定事项明确保留。 | 有效产品决定、对应 PRD 原句、读者独立复述及正反用例。 | 两份需求对未支付订单说法相反，审查者选一种当标准答案。 |
| 研发能否据此实施？ | 方案解释当前调用路径、改动归属及理由，覆盖本期功能、质量与未来变化。 | 源码位置、方案决策、失败路径和验法。 | 列出了文件，却没说明响应丢失后重试会不会重复发信。 |
| 从 PRD 到计划有没有丢约束？ | 同一项承诺在下游有明确责任和验法。 | 连读产品决定、PRD、计划及对应验证要求。 | PRD 承诺保留详情页入口，计划只验证新增列表入口。 |

交付结论分三栏：**本轮审查是否做完、被审对象质量如何、真实研发收益是否得到验证**。三者不互相推断，取值见文末“交付物与完成口径”。

**怎样才算说清楚？** 假设需求是“已支付订单可在列表重发电子发票”。写“优化发票流程，完善异常处理”看不出改动。换成“现在只能去订单详情重发；改后在已支付订单的列表行也能点‘重发’，失败时留在列表并可重试；详情页入口和未支付订单保持原样”，开发知道改哪里，测试也能写出用例。这是写法示例，不是本项目的真实发现。

**范围不变：** 38 个 Skill 仍然分批全审，不抽查。本文规定查什么和怎样验收；没有修改任何 Skill，也不授权外发、付费评测或实施建议。

## Product Contract

### 审什么，交给谁

给执行审查的人一份完整名册、逐内容判据和证据要求；给研发负责人一份能区分“应保留、应修正、应简化、尚不能判断”的逐 Skill 结论。全面指审查对象和内容没有缺项，不指穷尽所有模型、项目和运行环境。

### 每个 Skill：产物模板是否合理，交付后是否好用

先列出该 Skill 实际会交付什么、谁接收、接收后要做什么，再沿生成路径找到决定内容的模板或指令。独立模板、正文内嵌格式、共享模板、脚本渲染和聊天简报都算；同一 Skill 在成功、受阻或不同交付格式下有不同产物，要分别核对。没有面向人的产物，注明实际消费者和依据，不要求为机器返回值另写报告。

| 分开判什么 | 执行者怎么查 | 什么不能算通过 |
|---|---|---|
| 模板内容是否合理 | 对每个栏目问：谁凭它做什么决定？必要信息能否填出，未知能否如实保留？重复、无消费者、只在特定场景有用的栏目，分别考虑合并、移除或按需展示。 | 技术方案要求填满所有设计章节，却没给实施者交代本次具体改动的位置；或要求填写尚未确定的性能指标。 |
| 实际产物是否易读 | 看接收者真正收到的版本。检查最先看到的是结论还是编号与日志，术语是否适合读者，标题、摘要和链接能否帮助定位细节；长文不因长而扣分，短文也不因短而通过。 | 模板源文件顺序合理，但页面默认折叠关键风险；不能仅查模板就判页面易读。 |
| 读者能否独立使用 | 给目标读者一个与职责匹配的任务，不提示答案，记录能否完成、在哪一处停住及需要什么解释。例如让开发指出改动和不变项，让评审者找到放行前必须解决的问题，让接手者定位首个未完成任务及依据。 | 作者讲解后读者才知道下一步，却记为独立使用成功。纯机器产物以调用方能否正确消费状态与结果验证；若同一 Skill 另给人看摘要，摘要仍须单审。 |

每种产物分别记录**模板设计判断、实际交付文本或呈现判断、读者任务结果**，附版本及位置。只有模板时，可以指出设计缺口，实际可读性与读者效果记未验证。建议写到可修改的位置，例如“将本次行为变化放在方案开头，保留源码依据在详设章节”，而不是笼统要求“更友好”。

### 首批重点一：业务读者能否读懂需求文档

专业 PRD 先用业务语言讲清一件事，再展开规则和证据。首屏让读者知道目标用户、当前困境、本期变化与不变项；不能要求读者先解读编号、技术缩写或机器检查记录。具体内容看下面五个问题，不要求所有需求使用同一种排版。

| 读者会问 | 正文应给出的答案 |
|---|---|
| 谁遇到了什么问题，为什么值得做？ | 指出用户角色、触发场景、现状及影响；区分已观察事实与假设。写清怎样判断问题改善，未知目标值不编造。 |
| 这次到底改什么？ | 交代改前与改后、本期必须交付的行为、优先级和明确不做的事。关键术语在首次出现处用业务实例解释。 |
| 实际用起来是什么样？ | 用一个完整场景串起起点、用户操作和可见结果；再说明影响决策的权限、状态、例外及失败反馈。涉及多角色或多端时标清差异。 |
| 怎么知道做对了？ | 把关键规则写成可观察的验收例：给定什么条件，做什么，应该或不应该发生什么。影响体验、隐私或时效的质量要求写成用户能理解的约束。 |
| 哪些已经决定，哪些还没决定？ | 区分已定规则、证据来源、外部依赖、假设和待决问题；注明谁能确认、是否阻塞规划。接口选型、组件拆分和内部实现归技术方案。 |

**读者检验：** 取与反馈匹配版本的 PRD，只给业务读者看交付文本，不提示标准答案。请其复述“谁能做什么、谁不能、失败后会看到什么、本期不做什么”；再请测试依据同一文本写一个成功例和一个反例。与原始需求逐项比对，记录原句、误读位置和缺失决定。规则齐全但难找到，判表达问题；人人读懂但规则尚未确定，判需求未就绪。没有真实读者时，只能判断文本风险，不能宣称读者已看懂。

例如，同是发票需求，“支持符合条件的订单重发”仍要读者猜条件；“已支付订单可从订单列表重发；未支付订单不提供此操作；原详情页入口不变”才能让不同角色对同一行为作判断。这是写法示例，不是用户已经确认的业务规则。[PRD 输出合同](../../skills/spec-prd/references/prd-output-template.md)已有摘要、变更、需求、验收、范围和证据栏目；正式审查查实际产物写了什么，不因栏目存在就认定易读。

### 首批重点二：一份技术方案要讲清什么

**既有系统的设计从源码现状开始。** 在定方案前，沿本次需求实际经过的入口找到业务规则由谁执行、状态由谁读写、哪些调用方依赖它，再核对相关接口和测试。方案应让评审者能从关键源码位置或符号，追到一个具体判断：现有实现已经满足什么、还差什么、因此哪里要改或不改。文件清单、架构图和搜索命中只能导航，不能单独证明行为。读不到关键实现时标明未知、验证路径及其是否阻塞选型；不把“没搜到”写成“不存在”。

**怎样选改法：** 接口、业务语义与失败行为已满足需求，就直接复用；行为属于原模块职责且能保持旧约定，就在原处扩展；现有能力只缺协作，就组合它们。**抽离已有职责**要指出当前耦合及代价；**新建职责边界**要说明本期新增了什么责任、为何现有模块或组合不适合承担、谁拥有新契约。例如审计记录有独立留存要求，即使旧代码没有重复，也可能值得单独建模。两种改法都交代依赖方向、旧调用方兼容性和维护成本，不按复用率判优。

例如，若源码显示详情页已调用独立的发票重发服务，且服务自身完成鉴权和重复请求处理，新增列表入口可以直接调用它，用现有详情页和新增列表用例验证一致性。反之，若这些规则散在详情页事件回调中，直接复用回调会让列表依赖详情页状态；此时才有理由抽出两端共享的业务操作，页面各自处理展示。两种设计面向同一需求，区别来自现有实现。这是假设对照，不是仓库发现。

在此基础上，对本期功能、本期质量和未来变化三项分别给结论：

| 必答问题 | 方案中要能找到什么 | 发票重发示例（假设） |
|---|---|---|
| 本期功能性需求：要做成什么？ | 从每条必要需求追到触发条件、角色、正常及例外行为、负责模块和验收用例。明确保留的旧行为，防止只实现主流程。 | 已支付订单可在列表重发，未支付订单不能；方案指出入口、服务端校验和正反用例，详情页行为保持不变。 |
| 本期非功能性需求：在什么条件下仍然算做好？ | 选出与本次改动有关的性能、可靠性、安全、隐私、容量或可访问性要求。逐项写明适用场景、已确认的阈值或可判条件、设计措施及验证方法。缺指标时注明来源缺口、谁确认及是否阻塞，不自行填数。 | 若业务要求同一次操作不重复发信，即使发送成功后响应丢失，重试也只能产生一封。通过模拟响应丢失并核对发送记录验收，而不是写“保证高可靠”。 |
| 未来变化与可扩展性：什么可能变，变化代价在哪里？ | 区分已知演进与假设，注明依据；说明哪些规则应稳定、哪些模块可能变化、兼容和迁移代价。本期在“就地实现、保留现有边界、立即扩展”间给出理由和重评触发条件。没有可信变化信号时写明暂不扩展。 | 若后续可能增加短信，先查是否有已确认需求及第二个消费者。只有设想时，本期复用邮件发送边界，不建多渠道平台；第二个渠道获准且出现共享规则时，再评估抽象。 |

先判产物用途。PRD 负责“用户需要什么”，不因它未指定实现而扣分；待实施的技术方案负责“在这个系统里怎样做成”。以下是评审者要从方案中找到的答案，不是强制目录。低风险单点改动可用一段话覆盖适用项；高风险事项不能以“简报”为由省略。

| 审查项 | 方案应交代什么 | 哪种写法不够 |
|---|---|---|
| 1. 问题、目标与边界 | 谁在何种场景遇到什么问题，完成后有哪些可观察的变化；关联原始验收条件，写明不改什么。 | “提升体验”，看不出成功与失败的区别。 |
| 2. 现状与依据 | 现有入口、实际调用或数据流、负责模块和可复用能力；标明来自当前源码、运行观察还是待核假设。 | 画了目标架构，却没核对现有系统是否已经提供同一能力。 |
| 3. 具体改动与影响面 | 按行为列出“现在 → 改后”，落到模块、接口或数据对象；说明受影响的调用方与必须保持的旧行为。 | 列了文件名，看不出各自负责哪一项变化。 |
| 4. 设计、关键路径与取舍 | 用一条真实场景串起入口、校验、业务处理、持久化或外部调用、结果返回；说明关键决策的依据和代价。有实质备选才比较，复杂交互可用时序图。 | 只有组件框图；研发不知道状态由谁修改、失败由谁处理，评审也无法判断为何选此做法。 |
| 5. 接口、数据与兼容（触及时） | 解释请求、返回、错误语义、状态或存储变化；明确新旧客户端、消费者与存量数据如何共存。 | “新增字段，向下兼容”，但未说明旧版本遇到空值或新状态时会做什么。 |
| 6. 风险、异常与质量要求（按风险） | 围绕真实故障后果说明防护和恢复。涉及权限、隐私、并发、幂等、容量或性能时，写出约束及验证依据；未知指标不要编造。 | “失败就重试”，却没处理服务已成功、客户端超时的情况。 |
| 7. 实施顺序与集成 | 给出能落地的改动单元、前置依赖、集成点和未决事项。阻塞决策注明由谁解决；区分不可变的实现约束与可由开发自行选择的细节。 | 前后端任务各自可做，但没人负责协议切换和联调。 |
| 8. 验证与验收 | 把每项关键需求和设计风险对应到场景、预期结果及证据；覆盖正常、关键异常和旧行为回归，说明现有检查不能证明什么。 | “跑单测、全绿即上线”，但没有测试能在关键设计做错时失败。 |
| 9. 发布、观察与恢复（影响交付时） | 说明发布或迁移顺序、上线后看什么信号、何时止损、如何回退或向前恢复；不可逆操作明确恢复边界。 | “异常回滚版本”，却没解释已写入的新格式数据还能否被旧版本读取。 |

**贯穿示例（假设，不是项目发现）：** 上文的发票入口说明了用户能做什么，尚不是完整技术设计。技术评审要继续追问：列表调用已有重发服务还是新建一条发送路径？订单归属与支付状态由谁校验？若邮件已发出但客户端超时，再点一次会怎样？若业务约定“一次操作只产生一封邮件”，方案就要交代怎样识别同一次操作，以及如何用“发送成功但响应丢失”的用例验收。若业务允许主动再次发送，则必须区分新的用户意图和旧请求重试，不能一律拦截。

**首批怎样判：** 对每份纳入的技术方案逐项记录“有依据且充分 / 有缺口 / 不适用及理由”，附原文位置和受影响的研发决策。读者说得出改动，但关键接口、状态归属或验证方法仍要靠猜，判为“可读，未就绪”；设计成立但改动埋得太深，判为“设计可行，表达需修”。不按标题数打分。沿 `spec-prd → spec-plan → spec-doc-review / spec-work` 定位缺口：需求没定、规划没讲清、文档评审没识别和实施没消费是不同责任。

依据：[规划证据与现有能力规则](../../skills/spec-plan/references/planning-evidence-boundaries.md)已规定何时检查现有能力、归属与组合方式。本轮审查的是这些规则有没有改变实际设计决策。[仓库完整计划合同](../../skills/spec-plan/references/plan-sections.md)定义产品约束、技术决策、实施单元与验证责任；[轻量输出合同](../../skills/spec-plan/references/output-contracts.md)界定简报适用范围。[arc42 架构文档概览](https://arc42.org/overview)提供上下文、运行时场景、质量、部署与风险视角，按本次变更裁剪，不作为强制模板。

### 超大跨端需求：总方案怎样带读者找到各板块

**一份总方案，两种读法。** 产品、架构和测试先按用户场景横读，确认功能在各端之间能走通；前端、后端、数据等实施者再按自己的板块纵读，找到源码改动、依赖和验法。两种视图引用同一组需求、接口和验收项，不各写一份事实。只有某板块细节多到妨碍阅读、由不同团队维护或有独立发布节奏时，才把详情拆成附件；总方案仍负责范围、跨端取舍和最终验收。[大型计划的单元索引](../../skills/spec-plan/references/plan-sections.md)可以承担板块导航，无需另起一套任务编号。

| 阅读顺序 | 读者应该看到什么 | 用来决定什么 |
|---|---|---|
| 1. 首页：交付全貌 | 一段话写清用户变化、本期范围与非目标；列受影响和明确不变的端、关键风险、待决项、总负责人及板块入口。 | 本期究竟交付什么，需要谁参加哪项决策？ |
| 2. 总体设计：现状到目标 | 画出当前与目标的系统边界或关键时序，标出复用、扩展、新增、退役处。关键连线对应真实调用点、协议及版本；尚未读取的仓库写未知。 | 为什么改这些位置？为什么不改其他端？ |
| 3. 场景与板块矩阵 | 行用可独立验收的业务场景，列用实际参与的端或服务；单元格写本端具体行为或不变理由，末列写跨端结果和验收负责人。包含关键失败、重试、老版本等路径。 | 有没有两个团队都以为对方负责的步骤？各端单测通过后，用户能否完成整件事？ |
| 4. 共享契约与各板块详设 | 接口、事件、数据和状态机指向唯一权威版本，标出提供方、消费方、错误和兼容语义。分端章节只写源码入口、现状与差距、改动、取舍、依赖和验证；共用的质量目标在总方案定义，各端说明如何共同达成。 | 接口未定时，哪些工作能并行？一端变化会影响谁？未来扩展由哪层承担？ |
| 5. 集成与分阶段交付 | 按端到端能力分批，而非只列“前端完成、后端完成”；写明真实联调环境、测试数据、依赖顺序、新旧版本共存窗口、观测指标、停止与恢复条件、负责人。 | 谁在什么证据齐备后放行？一端不能同步上线时，哪些能力仍然可用？ |

**场景矩阵示例（假设）：订单退款。** 下表只示范两个场景的呈现格式，不是对正式方案实行抽查。各端现状与协议在实际项目中须回源确认。

| 场景 | 买家端（App / Web） | 运营后台 | 退款服务与支付渠道 | 整体验收与责任 |
|---|---|---|---|---|
| 买家提交，运营审核同意 | 展示“审核中”；同意后展示“退款处理中”，不提前显示到账 | 展示待审记录；同意后不能重复审批 | 服务记录审核结果，发起退款；支付确认后才进入成功状态 | 联调负责人串起同一订单，确认买家端、后台和支付结果一致 |
| 支付已成功但通知延迟，随后同一通知到达两次 | 延迟期间保留处理中；最终展示一次成功 | 可查询进度，不让客服再次发起退款 | 核对支付结果，重复通知不重复记账；服务维护业务状态，页面仅展示 | 测试负责人核对订单最终成功、资金只退一次；仅验证各端界面不算通过 |

真实方案必须区分各端差异：例如 Web 可随服务发布，旧版 App 仍在线，就应说明旧版收到新状态时展示什么，由谁验证。若契约尚未定，允许前端依据标为草案的模拟数据并行开发，但模拟通过不算真实联调通过。任务包即使另行生成，也只是执行安排，不能另定状态语义或验收条件。

### 多仓 workspace：四个研发阶段怎样使用 CodeGraph

团队把前端、后端等独立 Git 项目放在同一 workspace，分别开发、提交和发布。按[项目图消费合同](../contracts/project-graph-consumption.md)，从父目录查询 CodeGraph 时，显式把 `projectPath` 指向目标子仓；不假定父目录有一个全量索引。已配置的 workspace Graphify 合并图可做跨仓导航；只有本地子仓 CodeGraph 时，也可用 API 路由、事件名、协议版本或生成客户端连接两端的源码证据。

| 阶段 | CodeGraph 帮忙找什么 | 对当前源码核实后交付什么 |
|---|---|---|
| 需求改动分析 `spec-prd` | 各端的现有入口、业务状态、相似能力及下游消费者。 | 按仓标出已确认的影响、保持不变的行为及理由、仍待核实的端。代码描述现状，不代替产品决定范围。 |
| 技术设计 `spec-plan` | 谁定义接口，谁调用它；现有能力可否复用，改状态或字段会传到哪里。 | 对每个关键改动给出仓库、版本或工作区状态、文件及符号，解释改前改后、取舍、契约兼容和联调顺序。 |
| 代码实施 `spec-work` | 定位实际实现、相邻调用方、旧路径和可复用测试。 | 写前复读当前工作区；逐仓明确 `target_repo` 或子仓操作范围，分别记录 diff、测试和跨仓联调结果。图中发现新仓受影响，不等于已授权修改它。 |
| 代码评审 `spec-code-review` | 从被改动的符号反查 diff 外的调用方、老客户端、异步消费者和测试盲区。 | 对照各仓实际 diff、接口版本、消费行为及测试，给出位置、触发条件和后果；未拿到的仓或版本明确列为未审。 |

**贯穿例（假设）：后端新增“退款处理中”。** 后端仓查状态定义和序列化出口，Web 与 App 仓分别查响应解析和页面展示。核对它们是否消费同一路由、字段及协议版本，才能把候选列为确认影响。旧 App 可能用通用解析器，没有同名符号；须检查默认分支、旧版源码或契约测试。拿不到旧版则兼容性待核。计划据此确定发布顺序，实施分别验证，评审检查“新后端＋旧客户端”，而非仅看各仓最新版本单测。

各阶段共用同一份改动清单，保留影响结论所依据的仓库、源码位置、版本和待核项。索引缺失、陈旧或查无结果时改用直接读源码、契约和测试；“无边”不等于“无影响”。简单局部改动无需强制查图，普通开发和评审也不因此自动重建索引。

跨仓联调按**实际跑过的组合**留证：场景、提供方与消费方各自版本、契约版本、实际结果及日志。存在未提交改动时附对应差异指纹，不能只记 HEAD。前端 A 与后端 B 通过，不证明 A 与 B′ 通过；依赖变动后只需重验受影响的组合，未测旧版本单列缺口。

### 已定取舍

- **逐内容全审。**（session-settled: user-directed — chosen over 以代表性样例代替全审：遗漏一条低频授权或验证规则也可能改变真实交付。）Governs R1、R2。试点只校准方法和成本，不代表其他对象。
- **研发流程优先。** Governs R3。先审会改变需求、代码或验收结果的技能；下面的三批排序是依据源码职责提出的工作顺序，不是用户逐项批准的优先级，也不是调用频率统计。
- **多个专业视角分别给理由。** Governs R4、R5。用户要求兼顾软件工程、AI 能力和 Skill 最佳实践；一个维度的优势不能冲抵另一维度的关键缺陷。

### Requirements

**范围与覆盖**

- R1. 开始时冻结当前工作区对象清单，包括未提交的有效源码、引用、直接消费者和验证资产；每项能追溯到版本与实际内容。
- R2. 每个范围内文件及有语义的内容单元都必须有当前轮次的审查记录，未读、截断或未解释的缺口不能算作全审。
- R3. 所有 Skill 均有独立结论；研发核心优先，跨批依赖跟随消费者核对，排在后面不等于免审。

**专业判断与证据**

- R4. 每个 Skill 从下列六个视角分别作出判断；不适用要给出职责依据，材料缺失只能标为未验证。
- R5. 每条问题记录写明行为、触发条件、影响、来源与反证；同时保留有效机制、无须变更的依据和仍不确定的归因。
- R6. 每项能力声明分别记录源码合同、任务行为、运行成本和现场结果，不跨层宣称通过或收益。
- R7. 每条实际交接都要核对生产方、传递物、消费方及失败返回路径；没有共享字段不自动判错，有同名字段不自动判对。
- R8. 结项须可从总表追到当前证据并反向对账；历史报告、模型评分和执行者自述不能独立关闭任何当前发现。
- R9. 对每份被审方案，检查目标读者能否仅凭交付文本说明：现状是什么、哪里会改变、改后什么不同、什么保持不变，以及怎样知道改对了。尚待决定的事项要与已定改动区分，不因追求具体而编造细节。
- R10. 对每份声称可实施的技术方案，依首批九项判据分别检查工程充分性，单列会阻塞实现、集成、验收或安全发布的缺口，不用可读性代替可实施性。
- R11. 每份 PRD 分别记录业务读者可读性和产品规则是否足以规划；仅在有真实读者复述时作出对应的理解效果结论。
- R12. 技术方案分别对本期功能覆盖、本期质量约束和未来变化的设计代价作出判断；未来设想不能变成本期承诺，也不能掩盖本期验收缺口。
- R13. 既有系统的每个关键设计决定都应能追到当前源码行为、需求差距、改动责任和受影响的调用方，并说明用什么验证新需求及保留行为；缺少决定性证据的设计只能列为有条件建议。
- R14. 涉及多个端、服务或仓库的大需求，方案须能按场景查全链路、按板块查源码改动，并能找到共享契约、集成责任、混合版本验证和分阶段交付条件；多板块不自动要求多份文档。
- R15. 在多仓 workspace 场景，分别审查需求、规划、实施和评审能否将 CodeGraph 候选变成带仓库、版本和源码位置的影响判断，并披露未覆盖仓库与索引限制。
- R16. 38 个 Skill 逐一核对产物及其模板或生成规则，按实际读者和用途分别评价内容取舍、可读性与可用性；无独立模板不等于免审，无人类读者或无对应样本须分别说明，不混为通过。

### 逐内容审查口径

**先理解目标，再判断内容。** 每个 Skill 开审时，用自己的话说明：服务谁、解决什么研发问题、在哪些场景不该用、接收者凭什么判断目标达成。分别标出入口声明的目标和调用方或产物合同能证实的职责；两者不一致就记录分歧，不把入口自述当成质量结论。逐文件审完后再回答：这些内容合在一起能否兑现目标，哪里支持它、妨碍它或仍缺证据？

**逐文件清点，不从入口链接反推文件全集。** 冻结每个 Skill 目录的递归磁盘清单（含隐藏文件、未跟踪文件及未被引用的文件），与版本控制清单对照；共享目录另建账，实际包外依赖补入。每个路径都要有处置。孤立文件要读其内容并查可能的消费者，不得因没找到入口引用、文件很长、使用频率低或其他 Skill 有类似文件而跳过。缓存、派生副本逐件核实来源和身份；无法确认是派生物时不得据此排除。

**质量判断必须落到具体内容。** 每个实质文件记录一条可核对的解释：它在什么场景为谁提供什么，其中哪段规则、实现或示例会改变实际结果，为什么应保留、修正、合并或仍待验证。按文件职责看正确性、充分性、与上下游的一致性及对读者的负担，不要求每个文件承担整个 Skill 的目标。例如，一份失败用例若只检查回答里出现“已验证”，就应指出它可能接受未执行验证的回答；列出用例名、行数或给“高质量”评分不算解读。文件内独立分支仍按下述口径逐项判断。

每个包从入口读到所有引用和包内资产，不止读“必读”部分。正文按章节、规则、例外、触发与退出分支；脚本按实际入口、判断、错误与恢复路径；模板按字段含义与消费者；示例、夹具和判分器按输入、预期结果、误收与误拒条件。二进制或可视素材按真实格式检查内容或用途，不能打开就记缺口。没有独立行为含义的连续说明可同条登记，不能因此跳过内容。包外只沿实际依赖追至负责实现、直接消费者和相应测试；不声称全仓逐文件审计。

覆盖记录至少包含：`对象 / 路径及版本 / 行段或资源位置 / 内容职责 / 触发与结果 / 消费者 / 审查判断 / 证据 / 未覆盖项`。分段读取须对账首尾与缺口，读到文件末尾不证明中间没有被工具截断。相同字节可以共用一份本轮全文解读，但每个位置的触发上下文、引用兼容和使用后果仍要逐项检查。缓存、镜像、生成物逐件分类说明；若声称真实宿主可用，其安装态、投射差异与自然入口另验，不能靠编辑镜像修正结论。

同一段可以合读，但只要触发条件、授权、返回结果、证据要求或消费者不同，就要分别记录判断，可写在同一条记录里。例如“成功返回、失败降级、未获授权停止”有三个分支；一条覆盖整段行号的“已审返回逻辑”不能为它们结账。

### 六种视角：判什么，以什么为准

| 视角 | 必答问题 | 最小有区分力的证据 |
|---|---|---|
| 软件工程 | 从原始目标到验收是否可追溯？是否处理接口与数据兼容、跨模块集成、非功能约束、失败恢复和可维护性？按对象职责取舍，不要求 PRD 决定代码结构。 | 挑出该对象承诺的工程不变量，沿需求、设计、代码和测试追踪；明确一个“测试绿了但功能仍错”的反例会在哪里被发现。 |
| AI 能力及其变化 | 哪些是模型已具备的通用能力，哪些是它拿不到的项目事实？长上下文、摘要、工具不可用或结果不完整时会怎样？是否重复实现了宿主原生能力？ | 把“模型能自己做”写成可推翻的假设，记录实际模型、宿主版本和权限；需要删减指令时用对照和保留用例验证，不能因模型升级直接去掉约束。 |
| Skill 编写与加载 | 职责是否单一、入口能否区分近邻？正文是常用最小信息吗？何时读取哪份引用是否明确？示例是否被当成唯一解？规则应在提示、脚本还是宿主权限层？ | 对照自然触发、误触负例、显式调用及真实读取记录；检查引用是否能到达以及脚本是否真的执行。篇幅、章节数、关键词命中只作线索。 |
| 跨阶段协作 | 来源、非目标、验收、未知事项和当前状态是否完整传递？下游会不会重新访谈已定事项，或把上游建议当批准？ | 核对实际交接物和下游如何使用；同一约束能追到实现与复验，并允许合法短路径。 |
| 权限与运行可靠性 | 能否限制读写、外发、提交、真实服务与生成镜像等副作用？中断、部分成功、脏工作树和重试会不会损坏已有状态？ | 区分文字约定和实际阻断能力；核对真实命令结果与最终状态。高风险动作只设计隔离验证，不为证明风险而操作真实远端。 |
| 验证质量与研发收益 | 判分器能否拒绝伪成功、接受合法替代解？省下的时间是否转移给人工审查、集成或回滚？ | 以原始意图和最终产物独立判定；正反例校准，保留失败、无效运行和未执行项。没有现场数据不宣称团队收益。 |

业界资料用来提出可检验的问题，不替项目裁决。[Agent Skills 编写指南](https://agentskills.io/skill-creation/best-practices)用于检查领域增量、指令粒度和按需加载；[OpenAI 的 Skill 评测实践](https://developers.openai.com/blog/eval-skills)用于区分触发、过程和产物。正式审查记录使用的来源、查阅日期、适用模型及宿主；业界建议与项目约束冲突时记录原因，不照搬篇幅或样本数阈值。

### 审查流程与交接

`冻结范围 → 逐文件精读 → 按指令和分支作专业判断 → 核查生产方与消费方 → 验证能力声明 → 对账并交付`

1. **冻结。** 登记 HEAD、实际工作区内容指纹、来源、排除项、包外依赖、宿主和授权。用源码名册与治理清单双向求差。基线冻结后出现新增、删除或修改，保留旧基线并列明差异；对受影响对象重审后才能宣称结论适用于新版。
2. **首个完整审查单元。** 全读 `spec-prd`、`spec-plan` 及其依赖，先独立从原始需求提取必要条件，再跟踪 PRD 正文、摘要和计划。使用资料充足、存在产品决策缺口、长文摘要漏兼容要求三种场景检验判据；这些场景不能替代两个包的其他分支。

   **怎样复核读者反馈：** 使用获准的反馈及对应版本的文档。请未参与编写的目标读者在不看标准答案的情况下复述改动、指出依据，并举一个区分改前改后的验收例。分开记录：读者实际读出了什么；当时有效的产品决定确认了什么（注明来源、版本及取代关系）；差异出现在哪里。来源冲突、含糊且无权威裁决时，记“产品决定未闭合”，不判读者答错。决定已定、正文正确但难找，查表达；摘要与正文冲突，记文档内容错误；明确决定未进入产物，再沿输入、Skill 和模板查丢失位置，不直接归责。没有真实读者，只报告文本风险。

   **先核对已有机制：** [`spec-plan` 输出合同](../../skills/spec-plan/references/output-contracts.md)已要求聊天简报写改动摘要及原因。把反馈对应到实际交付格式（聊天、Markdown 或 HTML），核对读者看到的版本，再判断该改内容、模板、展示顺序，还是无需改 Skill。
3. **展开三批。** 逐个完成名册与分支记录，并单列五条主交接：PRD→Plan、Plan→Work、Plan→Tasks→Work、Work→Review、Review→Work→最终复验。按真实源码补齐路由、故障返回、平台验证、内部辅助、交付及知识消费等边，不把五条当作全部。
4. **验证与归因。** 先用本地脚本、当前源码和隔离用例验证可判事实；有授权再在新上下文注入源码检查执行行为，并在实际安装宿主分别检查自然选中和真实产物。相邻失败沿调用链追到责任点，允许归因为 Skill、宿主、工具、模型、判分器、混合或未知。
5. **对账与恢复。** 每批留下已读区间、已审单元、结论、缺口和下一入口。时间或预算耗尽就暂停相应验证并标明部分完成，不降为抽查。修复建议交还负责该源码的维护者，不自动修改、提交或发布。

### 效果判定与成本

- **合同层**只证明文本、脚本与消费者之间存在什么约束。**行为层**报告具体任务在指定模型和宿主上的观察。**成本层**报告实际耗时、人工投入与调用费用。**现场层**跟踪真实需求从接手到验收、返工、漏检与回滚。四层不互相补分。
- 判断 Skill 是否有增益，用同任务的“宿主原生能力”和“宿主加当前 Skill”比较；判断某次修改是否有效，用冻结旧版与候选版比较。固定输入、仓库、模型、工具权限与验收标准，保留所有尝试。校准任务与未参与调优的验收任务分开；随机行为需重复运行并报告分母与波动。
- 需求保留率按“被下游正确落实的必要要求数 / 原始必要要求数”；漏检和误报分别对已知缺陷和正确对照计数。达到可信验收的时间包括人工澄清、等待验证、修订及复验；仅有模型时长不得冒充研发总耗时。零分母、不可比数据或缺日志均标为未测。
- 阻塞级：越权写入或外发、关键验收漏做却宣布完成、数据损失风险；高影响：丢失必要需求或造成错误实现、审查漏掉关键缺陷；一般：可恢复的额外返工或有证据的维护负担。严重度与证据强弱分开；未证实的高风险列为待复核，不能伪装成已发生事故。不得以 token 节省抵消质量或安全回归。

### Acceptance Examples

| 编号 | 给定情形 | 验收时必须看见的结果 |
|---|---|---|
| AE1 · R1–R3 | 38 个入口都有摘要，但一个未被引用的文件未读；另一文件虽全文读过，记录只有“高质量” | 前者是文件覆盖缺口，后者是内容解读缺口。分别补全原文读取和带位置、用途、理由的判断；任一缺口仍在，该 Skill 均不能标为内容全审完成。 |
| AE2 · R2、R4 | 两个包复用相同模板，但一个调用方容许空值 | 允许引用同一本轮精读记录；两个调用点分别给出语义结论，不复制通过状态。 |
| AE3 · R4、R7 | 原 PRD 禁止改变旧接口，摘要漏写且计划测试全绿 | 回到正文核对计划和测试是否覆盖兼容；定位遗漏发生的位置，不凭“有测试”放行。 |
| AE4 · R5、R6 | 实际用了另一条正确实现路径，判分器只认示例命令 | 判分器误拒与 Skill 失败分开；同时用“命令出现在日志但未执行”验证不会误收。 |
| AE5 · R6、R8 | 源码注入通过，未实际安装或无真实需求样本 | 只报告该注入场景；宿主自然触发与团队收益分别记未验证。 |
| AE6 · R1、R8 | 历史报告称某缺陷已修，本轮源码或调用方已变化 | 保留历史编号，用当前字节和原始反例复核；没有当前证据不得关闭。 |
| AE7 · R5–R7 | 实现后两项测试通过，审查修复改变代码，必要验证未重跑 | 记录旧结果对应的版本，指出未覆盖义务，不将先前的绿色结果用于新版本收尾。 |
| AE8 · R5、R9 | 方案列出“优化流程”和三个文件名，却看不出用户操作有何变化 | 读者必须猜测的行为记为缺口；不能凭有“改动摘要”标题或文件列表判通过。建议须给出可核对的改前、改后和验收例，不编造业务决定。 |
| AE9 · R9、R10 | 改前改后清楚，但新旧版本并存期间，旧服务如何读取新写入的数据没有说明 | 可读性可通过，实施就绪性不能通过；指出受影响的读路径、待定的兼容决策和需要补的混合版本验证。 |
| AE10 · R10 | 只调整本地校验错误文案，已定位触发点、预期文本及回归用例，无接口或数据变化 | 不因缺架构图、迁移或回滚专章而判失败，记录这些项不适用的理由。 |
| AE11 · R11 | PRD 写“符合条件可重发”，却没定义哪些订单符合条件 | 即使摘要、需求编号与验收章节齐全，也指出产品规则缺口；若规则其实在正文，则区分读者找不到和规则不存在。 |
| AE12 · R10、R12 | 重发主流程可用，但响应丢失后可能重复发信；方案只写“高可靠，未来可扩展” | 功能主路径不抵消可靠性验证缺口；未来部分须给出有据的变化及影响，或暂不扩展的理由。没有短信需求不因未建平台扣分。 |
| AE13 · R10、R13 | 同一列表需求分别面对两种实现：已有独立业务服务，或规则仅存在于详情页回调 | 检查方案能否根据各自源码选择直接复用或有理由地拆分，指出旧入口的回归验证。允许其他有证据的解法；两种情况下都只写“抽一个公共层”不通过。 |
| AE14 · R7、R10、R14 | 前端和后端各有详设，模拟联调也通过，但旧 App 对新状态的显示未知，重复支付通知没有跨端验收责任人 | 记录具体契约、消费者和联调缺口；不能以两端分别完成判整体验收通过。总方案须能定位旧端兼容策略和不重复退款的端到端验法。 |
| AE15 · R13–R15 | 后端图中找到新状态，Web 图有同名符号，旧 App 索引没有命中 | 不因同名而认定同一契约，也不因未命中排除旧 App；按子仓核对路由、字段与消费行为，分别记录已确认影响和仍未知的兼容性。 |
| AE16 · R9、R16 | 用户反馈“技术方案看不懂”。同版计划附有完整接口表，开发却需作者解释才知道本期改哪个入口。 | 记录读者任务、卡住的位置及所见文本；对照源模板、填入的内容和最终展示，区分模板没要求写、生成时漏写、已写但难找。若只有反馈没有同版产物，保留线索，不直接认定模板有错。 |

### 交付物与完成口径

| 交付物 | 责任与内容 | 验收方式 |
|---|---|---|
| 总名册与覆盖账 | 执行者保留每个对象、文件、内容单元、分支和实际交接的稳定标识、位置、状态及证据。 | 冻结清单与已审集合双向对账，列缺项、重复项与排除依据；检查每个单元都有语义判断，不只比较数量。 |
| 逐 Skill 报告 | 首页先列“建议改什么”：每条写出位置、现状、拟改行为和验法；详情附职责、六视角判断，并按产物列出模板来源、接收者及任务、内容与可读性判断、样本或缺口。 | 逐项对照产物清单，不能用一份好读的样本替其他格式签收。维护者能定位应改哪一处、预期有何不同；无须修改和证据不足分别记录。 |
| 交接与发现台账 | 每条发现列位置、触发条件、预期与观察、影响、反证、结论强度、建议责任方、最小复验及状态。 | 同一共享根因合并追踪但保留所有受影响消费者；分别记录已证实、待证、已反驳、修复待验和复验关闭。 |
| 证据与运行记录 | 确定性日志、输入与最终产物、用例来源、环境、耗时成本和限制可复核；敏感材料留在授权位置。 | 分别报告已运行、失败、未运行和环境受阻。示例、历史轨迹和人工验收意见标明来源，不伪造当前运行。 |
| 总结与维护建议 | 负责人分别汇总覆盖、对象质量、行为、成本和收益，排序最影响可信交付的问题。 | 保留、修正、简化、迁移给宿主或暂不判断均可；每条建议附收益假设、回归风险、复验条件。 |

**内容全审完成**只表示范围内实质内容均已审、排除有据、跨对象差额清零。总结首页按既有审查流程并列报告三项结果：

| 结论 | 怎样判 |
|---|---|
| 审查执行：`complete` / `partial` / `blocked` | 对照启动时登记的范围与必验场景逐项核销；全部执行且结果可核验才是 `complete`，包括实际测出失败。必验项未跑或结果不确定则不能完成；部分已做记 `partial`，无法推进的依赖说明阻塞原因及所需条件。 |
| 被审对象：通过 / 有条件通过 / 不通过 / 证据不足 | 已确认阻断缺陷即不通过；无此缺陷但关键证据缺失则证据不足。仅有非阻断残余且有明确接受来源，才可有条件通过。 |
| 真实收益：已验证 / 未验证 / 不适用 | 已验证须有可比较的真实任务结果和成本；只读源码、读者复述或一次联调均不能证明团队收益。推广另需说明适用范围。 |

例如：全读两个包却没跑承诺的兼容场景，本轮仍是 `partial`；若所有承诺项都做完并实测出关键约束丢失，则可以是“本轮 `complete`、对象不通过、收益未验证”。两者都不能外推到其余 36 个 Skill。
