# Skill 审查执行 Workflow

版本：v2.1 · 更新日期：2026-11-04 · 维护者：本轮审查 owner

需要一次跑完全部 Skill 时，按 [全量单次审查执行方案](FULL-REVIEW-ONE-PASS.md) 执行；判定规则仍以本文件为准。

本流程用于审查当前 Skill 源码、上下游消费者、实际行为及交付证据，回答：哪些能力可靠、哪些问题成立、哪些结论尚不能作出，以及下一步应保持、修复、补证还是调整方向。

**审查执行完成、被审 Skill 通过、优化收益得到验证是三个不同结论。** 本文件是执行方法，不是已执行审查或验收通过的证明。它是项目文档，不新增 public Skill、运行器、状态机或 runtime contract。

## 1. 目标、边界与权威

### 目标与非目标

- 保留 core 的三层目标：单 Skill 有效性、阶段衔接顺畅度、端到端可信交付；完整审查必须覆盖三层，不能由局部绿色外推整体。
- 每个范围内 Skill 都有源码与适用维度记录；每个重要结论都能回到当前源码、实际产物、原始日志或明确 owner 证据。
- 允许有证据地得出保持现状、修正旧归因、暂不优化的结论；不设发现数量、改动数量、总分或固定阅读时长指标。
- 不自动修复 Skill、刷新宿主、提交、推送、发布或外发资料。当前用户已明确的对应授权可连续执行，不因换阶段重复询问。
- 不要求每个 Skill 拥有整条研发链路的能力；部署、生产运维等组织职责不因历史缺口清单自动进入本项目范围。

### 权威顺序与分工

先遵守当前用户范围、真实权限和[项目角色契约](../../../methodology/结构化项目角色契约.md)。当前有效合同规定应有行为，当前源码与运行证据说明实际行为；二者冲突记录为待判断的实现或合同问题，不能用源码现状取消合同。

- 源码：仓库根下 `skills/`、`templates/`、`src/cli/` 及实际 owning contracts/tests；Skill 从 `SKILL.md` 及其 references/scripts 开始读取，不套用历史示例中的 Python 入口。
- `.agents/skills/`、`.claude/` 等 generated runtime 仅用于投射、漂移或真实加载取证，不作为修复真相源。
- 工具准备路径、hash、文件身份、命令、exit code、测试和统计事实；LLM 判断设计意图、语义覆盖、因果归属与适用性。脚本不能用分数自动裁决是否通过。
- 旧审查、外部趋势、Graphify 和模型总结只作线索。旧测试通过只证明当时版本和对应检查；示例数据不能进入本轮样本。
- 本流程的完成规则属于文档约定，**没有运行时强制器**。报告需说明实际哪些检查由工具验证、哪些仍由 owner 判断；不得称所有 gate 已硬强制。

## 3. 启动：固定范围、来源与本轮判据

先从用户请求和现有材料确定本轮类型，合理默认继续；只在会改变关键范围或授权时澄清。

| 类型 | 必要工作 | 可作出的结论 |
|---|---|---|
| 方案评估 | 目标、边界、证据设计、可执行性 | 方案可用性；不能声称 Skill 已通过 |
| 定向 Skill 审查 | 指定 Skill 的源码、适用维度、相关交接与必要行为场景 | 仅该范围的质量结论 |
| 完整 Skill 审查 | 全部范围对象、三层检查、适用消费者与真实任务证据 | 满足第 9 节才可给完整通过结论 |
| 全量单次审查 | 全部范围对象的 `structure_contract`、`behavior_quality`、`runtime_cost`；`field_outcome` 在启动时登记为不承诺 | 按承诺范围可 complete；对象结论限于前三层证据；收益固定为未验证。执行方案见 [FULL-REVIEW-ONE-PASS.md](FULL-REVIEW-ONE-PASS.md) |
| 修复复验 | 原 finding、修改后的 owning source、回归与受影响消费者 | 对应问题是否关闭，其他历史范围不自动刷新 |

默认“新一轮 Skill 审查”采用完整 Skill 审查；先登记当前请求明确的对象。未限定对象时，清点当前 `skills/` 全部入口，以实际源码数量为准，不能沿用“38 个”或默认只查五个。所有对象都有状态；可按风险分批，批次完成不能关闭全范围。内部 helper、独立入口、public workflow 分别标注，不要求 helper 单独成为用户入口。

启动记录写入本轮报告：

- `target_repo`、用户目标、类型、范围内/范围外 Skill、owner、审查者、日期。
- 当前 Git HEAD、dirty 路径；被读源码、引用、fixture、测试与关键配置的路径和 SHA-256。未提交内容以实际字节为准；hash 绑定来源，不证明语义正确。
- 当前有效合同、读取清单、实际宿主和模型、加载方式、工具就绪情况；缺失写未知，不由名称推断模型或权限。
- 承诺检查、必需场景、适用交接、验收口径；完整审查的三层不能在看到失败后改成不适用。
- 实际授权覆盖的本地写入、评测、外部模型/资料外发、费用上限与 runtime 操作；从会话核对，不从历史文档或命令参数推导。
- 时间、调用/费用预算、停止条件和恢复点。现有授权未覆盖付费/外发时先完成本地审查与用例设计，仅等待该部分所需答案。

默认先完成一个主链路 Skill 的源码→场景→报告闭环，校准证据可采集性和成本，再展开其余批次；不以试点发现多少问题决定方法是否有效。可并行的只读复核须有当前授权与能力，缺少时 inline 完成并披露非独立；不为凑“多专家”复制同一上下文。

### 从试点推算全量规模

试点结束后、展开其余批次前，在报告中写一段规模估算，再决定按完整审查继续还是收缩：

- 用试点的实际消耗作单位成本：读取文件数、适用检查项数、行为场景数、模型调用/费用、墙钟时间。按全范围对象的规模（`SKILL.md` 与必读 references 行数、条件分支、消费者数、是否有脚本）分组外推，不按 Skill 个数平均。
- 估算列出假设和误差来源；主链路 Skill 通常重于 helper，外推不能把试点当作平均样本。
- 估算超出已登记预算，或行为场景所需的模型/宿主能力不具备时，向 owner 给出收缩选项，而不是静默缩小：按风险收缩为定向审查（例如主链路、近期改动、有已知 finding 的对象）；或保留完整范围，只对低风险对象做 `structure_contract` 层，其余标 `not-run`；或暂停等待预算。用户已明确要求完整范围时，收缩须经确认。
- 收缩后报告类型如实改为定向审查，或保持完整审查但状态为 `partial`，不能沿用“完整审查”标题。
- 需要无人值守跑完时，owner 可在启动记录中预先登记“超预算时采用哪个收缩选项”。登记后按该选项执行，视为已确认，运行中不再等待；未登记时仍须确认。预先登记必须写在任何试点结果出现之前。
- 实际消耗偏离估算超过登记的阈值时，在批次边界重估一次；不按固定工时机械停止。

## 4. 逐 Skill 审查维度

每个范围内 Skill 建立“Skill × 检查项”记录，逐行填写：适用理由、当前源码位置、确定性证据、行为证据、结果与缺口。表中要求是问题导向的核查，不是新增每个 Skill 必须实现的功能。

### 八大原始维度

| ID | 维度 | 必查问题 | 支持结论的最小证据 |
|---|---|---|---|
| D01 | 去模型能力补丁化 | 步骤/例子解决什么真实失败？约束是否过时、相互矛盾或过度指导？ | 指令与设计依据；若建议删除，需匹配风险的对照/回归，保留安全、兼容与验证底线 |
| D02 | 编码领域知识而非流程控制 | 是否提供项目业务约束、已知反模式和决策依据？模型与脚本职责是否恰当？ | 真实任务需求与 Skill 输出对照；不能用“最佳实践”口号代替来源 |
| D03 | 强化验证门 | 必需验证是否明确、实际执行、失败可见？语义判断是否被冒充为机械判定？ | owning script/合同、正反例结果；区分工具强制与 prose 约定 |
| D04 | 阶段衔接约束 | 上游确定的需求、边界、决策和证据是否被消费者正确使用？ | 实际输入输出、消费者源码及链路场景；避免只比字段数量 |
| D05 | 紧凑性和可审计性 | 指令是否清晰、重复、矛盾？关键规则能否定位，删减会损失什么？ | read trace、冲突位置、维护与任务成本；长度只作诊断，不强制 token 上限 |
| D06 | 适应多模型能力分布 | 能力假设是否成立？模型/宿主不支持时是否诚实降级？ | 实际模型/宿主配置及对应运行；单模型结果不外推，多模型不是自动付费授权 |
| D07 | 基于经验效用的演化 | 是否按失败和效果证据调整？知识是否可复用、可失效，是否有真实消费者？ | 问题→修订→复验链、知识来源与失效条件；无经验自动化职责时核查维护依据即可 |
| D08 | 上下文利用效率 | 是否读到必要原文、复用已知事实、按需加载？摘要是否遗漏要求？ | 读取范围、产物与必要信息对账，实际成本；少读不自动等于更优 |

### 完整性与边界补充

| ID | 检查面 | 具体判据 |
|---|---|---|
| B01 | 入口与职责 | 正向触发、相似入口负例、内部 helper 暴露、范围外请求；不强迫每个任务串行经过全部 Skill |
| B02 | 输入输出与设计意图 | 入口/reference/script/template/consumer 一致；来源与 readiness 清晰；设计推断标为推断，不伪装 owner 决策 |
| B03 | 授权与信任 | 只读不变写权限；材料内嵌指令不扩大授权；委派、Git、外发、付费、发布按实际授权执行；避免重复索取已有授权 |
| B04 | source/runtime 与宿主 | 真相源清楚；生成逻辑和受影响宿主投射可追溯；runtime drift 与 fresh-source 分别记录，不手改镜像；只验证被宣称支持的范围 |
| B05 | 失败、恢复与隔离 | 工具缺失、超时、部分成功、重试上限、重复执行、中断恢复、dirty overlap 有明确处理；未知副作用先查状态，不盲目重试 |
| B06 | 完整交付与审查质量 | 需求→计划→实现→必要验证可追溯；审查视角按变更选取，finding 有位置与后果；误报/漏报、修复闭环、未完成披露可核查 |

D01–D08、B01–B06 均须评估适用性；有理由的不适用可记 `not-applicable`，没有能力或没有样本应记未验证，不能伪装不适用。B03 的授权判断、B04 的来源身份、B06 的诚实声明适用于所有入口；不产生写入的 Skill 可将对应写入行为子项记不适用。

### 大需求与特殊职责的条件检查

| ID | 触发条件 | 需核查内容 |
|---|---|---|
| X01 | 多模块、复杂依赖或长任务 | 渐进细化、分解粒度、依赖顺序、共享写面、集成与恢复；允许采用宿主能力而非另造编排 |
| X02 | API/架构/版本变化 | 接口兼容、开放问题、版本/变更影响、ADR、迁移与回退；不要求所有 Skill 新增 schema |
| X03 | 高风险实现或交付 | 风险与验证对账、测试策略、必要发布/回滚检查；实际部署只有在项目范围和授权内执行 |
| X04 | 协作、跨会话或知识工作 | owner 与交接、摘要/source refs/freshness/limitations、决策保留、知识消费与失效；独立审查与自审分别记录 |

## 5. 源码深读与归因验证

对每个范围内 Skill 按实际调用路径阅读，不只查入口关键词：

1. 读取完整 `SKILL.md`、各 Phase 必读 references、相关脚本/模板/合同与直接消费者。条件分支按本轮场景展开；未读文件列路径、理由与未覆盖后果。涉及破坏性、授权、验证和交接边界的分支不能只因低频跳过。
2. 形成职责与调用关系摘要：输入、前置条件、核心判断、输出、失败路径、owner、消费者；复杂分支可绘图，简单 Skill 用表即可。
3. 用当前有效合同逐条对账实际实现：匹配、缺失、冲突、未知。分别记录确定性工具保证、LLM 语义义务和无法硬强制的约定；历史拟议合同先判是否已采纳。
4. 将真实任务阻力定位到指令/代码/消费者及调用路径，验证“机制存在但没有触发”与“机制本身缺失”的区别。对历史归因给出维持、细化、修正或证据不足。
5. 根因允许 Skill、模型、工具链、外部因素、混合或未知；“缺证据”不强塞为某一类。报告区分观察事实、因果假设和已支持的归因，统计混合原因时说明去重/分配方式。
6. 仅对成立的问题提出最小修复位置、预期影响、风险和复验方式；优先复用已有机制。保持现状同样是有效结果，ROI 估计须列假设，不冒充真实节省。

先独立读原始证据形成判断，再对照历史报告。旧分析可复用，但必须核对版本、范围、完整证据与失效条件；文件存在或旧作者自述“已读完”不能证明当前覆盖。

## 6. 消费者与链路验证

主链路在范围内时，下列交接逐项登记。选择的 Skill 涉及链外消费者时补充实际边；helper/独立入口不强套 PRD 主链路。

| ID | 交接 | 验证重点 |
|---|---|---|
| H01 | PRD → Plan | WHAT、验收、边界、已定决策、阻塞和来源完整继承，避免重复访谈 |
| H02 | Plan → Work（直接） | Goal、Verification、DoD、相关单元与验收被消费；任务包不是强制前置 |
| H03 | Plan → Tasks → Work | 来源/hash 与当前 readiness 分开核验；派生任务不能扩大 plan 范围或拥有批准状态 |
| H04 | Work → Review | 当前 diff、需求与任务上下文齐备；只对已提供范围作完整性声明；只读审查不变修复授权 |
| H05 | Review → Work → 收尾 | 复用 findings、处理 residual、修改后复验、必要证据对账；不能只凭全绿摘要关闭 |

复用 06 的场景意图，先检查 fixture 是否仍匹配当前源码；案例文件存在不等于运行完成。

| ID | 必须覆盖的主链路场景 | 观察结果 |
|---|---|---|
| ML-01 | 来源已经明确的需求与验收 | 引用事实，保留要求与非目标，不重新访谈已解决项 |
| ML-02 | PRD 有明确阻塞或不可进入计划的状态 | 不伪造 ready，同时继续可独立完成的工作 |
| ML-03 | 长 PRD 的摘要遗漏正文必要边界 | 原文要求仍被保留，不用摘要裁剪本轮范围 |
| ML-04 | 低风险计划可直接交付 Work | 不强制生成 Tasks，必要验证仍保留 |
| ML-05 | 任务包 hash 有效但计划 readiness/lifecycle 已变 | 重新核验当前状态，不以旧 hash 放行 |
| ML-06 | 一例实现漏必要边界，一例存在无关未实现项 | 检出真实遗漏，同时不误报本轮范围外事项 |
| ML-07 | findings 修复后代码变化或必要检查未跑 | 使用新验证证据，未完成如实披露 |

每条边检查生产者输出和消费者使用，而非只读两份文案。增加与本次职责有关的失败/恢复/越权负例；记录覆盖关系，单次运行可以覆盖多个检查但不增加独立样本数。

## 7. 真实行为、指标与证据层

### 四层证据分开记录

| 层 | 能证明什么 | 不能替代什么 |
|---|---|---|
| `structure_contract` | 当前文件、引用、schema、工具与合同断言符合检查 | 模型实际遵守、任务成功、现场收益 |
| `behavior_quality` | 指定模型/宿主/加载方式在该场景中的实际行为与产物 | 未测模型、常规宿主部署、长期总体效果 |
| `runtime_cost` | 实测调用/token/耗时/重试/协调成本 | 业务正确性或因果收益 |
| `field_outcome` | 真实需求的最终交付、返工、介入与观察期内结果 | 超出样本、任务类型和期间的普遍收益 |

### 场景与运行纪律

- 运行前记录输入/fixture、触发机制、预期判据、禁止行为、必需证据、模型/宿主配置、重复次数/预算和停止条件。oracle 与预期答案不注入被测 agent；只能提供它实际应读的合同。
- 正常、边界、失败/恢复、授权负例按适用风险覆盖。Review 场景同时看漏报与误报；无 dirty 争用的任务不算 worktree 行为覆盖。
- 使用新上下文读取当前 source，遵守[fresh-source checklist](../../../contracts/workflows/fresh-source-eval-checklist.md)。`skill-upper` 是宿主或用户级安装的外部 provider，不在本仓库 `skills/` 中，不作为真相源。可用时按其指引复用评测能力，并记录其来源与版本；不可用时，用 fresh-source 注入完成可执行部分，依赖 runner 的评测记 `not-run`，不假造调用。
- 显式注入 source 能验证给定合同下的行为，不能证明自然入口路由或常规 runtime 加载；入口正确性使用不点名 Skill 的请求与真实加载证据。宿主效果声明须另核对 runtime 版本与实际加载记录。
- 环境隔离避免全局 Skill 污染对照组，保护工作区、凭据和已有副作用；Windows 涉及 home 时同时检查 `HOME`/`USERPROFILE`。隔离方式和局限均留证，不据单次沙箱错误推断宿主不支持。
- 要声称相对收益，使用可比较的基线/候选，匹配任务、模型、工具、验收与计费口径，保留全部尝试、无效样本和排除原因；先校准判据与区分力，避免基线饱和后仍宣称改善。小样本观察只报观察，不默认有统计显著性。
- **基线取法**：默认同任务配对。对每个任务，分别注入改动前与改动后的 owning source，在新上下文中各运行一次。改动前的版本用改动前一个 commit 的 SHA，从 `git show <base-sha>:<path>` 取得；改动后的版本用候选 SHA，或当前工作区字节。两侧的模型、宿主、工具、输入与判据保持一致，并记录两个 SHA 和每个被注入文件的 SHA-256。历史任务数据只能作背景参考，不能替代同任务基线；只有候选侧数据时，收益结论记未验证。
- **任务与判据先固定**：任务清单、每个任务的判据、返工定义和排除规则，在运行任何候选之前写入报告，并记录写入时间或 commit。看到结果后新增、删除或替换任务，必须写明理由；被替换的任务与结果保留在报告中。能做到时，由实施者以外的人选任务，或者从按事先规则生成的候选池中选取。都做不到时，在限制中披露“执行者选任务”，并检查所选任务是否集中在改动覆盖面上。
- **判定不看版本标签**：能做到时，判定者不知道产物来自基线还是候选。做不到时，记录为非盲判定。
- **已入库的 eval case 可作先固定的场景**：`skills/*/evals/` 中在本轮开始前已提交的 case，任务与判据早于本轮，可直接作为主行为集，报告引用其提交 SHA。本轮新设计的补充场景放在 run 目录，执行前计算 hash 冻结，与主集分开统计；设计者不执行、不判定自己设计的场景。
- **eval 引擎的加载来源**：eval 配置为 `environment: none` 等非隔离运行时，引擎可能同时加载本机已安装的 runtime 副本。运行前确认被测 Skill 只来自 source；无法确认时，在每个行为结果上标注可能混入 runtime 副本。eval 失败需区分 Skill 缺陷、fixture 过期、环境差异和引擎错误，后三类不能直接作为对象不通过的依据。
- 确认越权、破坏或关键质量回归时停止相关候选的后续推广与危险测试，保留证据；其余独立只读工作继续。超预算、能力/凭据不足或连续失败无新信息时留下恢复点，不无限重跑。

### 指标必须能重新计算

报告保留分子、分母、任务 ID、采样方式、观察窗口和原始依据；缺数据用未知/未测，不能填 0。以下目标来自 core/00，作为本轮事先登记的参考，不自动形成 rollout 授权。

| 指标 | 计算与边界 | core 目标参考 |
|---|---|---|
| 端到端正确率 | 完全正确任务/全部有效观察任务；逐任务核对交付、正确、完整、必要测试、必要文档，失败/未交付不能从分母删去 | >90% |
| 端到端返工率 | 发生返工的任务/全部有效观察任务；事先定义返工事件，记录提交前与提交后修正，不靠“未提交”默认排除 | <10% |
| 用户介入 | 澄清、确认、纠正分别计数，报告总数/任务数；必要授权与无效重复分别解释，不能为降数字省略必要确认 | <3 次/任务 |
| 完成时间 | 有来源的起止与等待/执行时间；区分墙钟、人工投入和模型时长，回溯缺时间戳记未测 | 相对基线降低 20% |
| 信息丢失率 | 本次任务必须传递但消费者未使用的信息单元/全部必须传递的信息单元；先固定单元定义与清单 | <5% |
| 信息重复率 | 对已确定信息的重复询问/全部询问；零询问时记分母为零、不计算，并披露次数 | <10% |
| 验收落实率 | 有实现与必要验证证据的适用验收项/全部适用验收项；跨项同一证据允许复用但不得重复计项 | >90% |
| 输入输出匹配 | 满足当前消费者合同的实际交接/全部适用实际交接；同时披露缺失的关键字段/语义 | 100% |

“最终正确”与“首轮通过”分别报告；首轮命令失败后修复成功不得记首轮全绿。返工事件数不等于返工任务数。任务数、Skill 数、检查项数、场景数分别统计，嵌入事件不能冒充独立任务。

五类任务（小功能、跨模块、缺陷、PR 反馈、跨会话）逐类说明选取、复杂度与缺样本。历史方案的 11 个基线/5 个前向任务用于采样参考；数量达标不保证代表性。完整收益结论需可比数据与足够观察，无法取得时保留受限结论，不能合成“真实任务”。模型版本或环境改变后的数据单独分组，不混算改善。

## 8. 交付物与问题闭环

本轮使用唯一目录 `reviews/runs/<日期>-<主题>/`（相对 initiative 根），已有同名目录时使用新后缀，不覆盖旧轮。默认一份 `report.md` 加必要的 `evidence/`；范围超过 5 个 Skill 时，逐 Skill 记录拆到 `skills/<skill>.md`，由主报告和对象台账链接，并用文件数与台账行数核对全范围都有记录。复用[报告模板](ITERATION-REVIEW-TEMPLATE.md)，不另造状态数据库或固定 schema。

报告必须包含：

1. 启动记录与采用/未采用的来源、冲突处置；读取路径与源码身份。
2. 全范围 Skill 清单，每个对象的 D/B/X 适用性、覆盖与证据；H/ML 逐项对应结果。
3. 场景记录与四层证据。命令证据带工作目录、参数、时间、退出码、原始输出路径；模型证据带实际配置、输入、加载方式、工具轨迹、产物与判定依据。
4. 问题清单：ID、严重程度、触发条件、源码位置、事实证据、实际后果、归因及不确定性、最小建议、owner、状态、复验条件。
5. 三层指标与可重新计算的数据；按证据层和适用对象分别汇总覆盖，不合成一个“总体质量百分比”。
6. 最终判定、阻断项、已接受的非阻断残余及接受来源、未执行项、下一步和失效条件。

检查项结果使用 `pass`、`fail`、`partial`、`not-run`、`inconclusive`、`not-applicable`。缺能力是 `not-run`，已运行但无法判断是 `inconclusive`；`partial` 需写清已覆盖与缺失部分。所有结果都注明证据层，不能将 static pass 自动复制到 behavior/field。

问题严重性按后果判断：P0 为严重越权、破坏/安全等必须立即处置的风险；P1 为关键功能、必要验证或交付闭环失败；P2 为局部质量/效率问题；P3 为非阻断观察。严重性、置信度、是否完成审查独立，不用总分抵消 P0/P1。

去重仅在同一根因与同一修正足以解决时进行，保留所有影响对象；相反建议先回源裁决。没有足够证据的因果假设不得伪装已确认 finding；保留明确的补证问题。

修复需要既有或新增的明确授权；审查可单独完成。实施者改 owning source，复验者核对原触发场景、修改后版本和消费者回归；只有相应证据成立才能把问题标为已验证关闭。代码改了但未复验是待复验，不是已解决。高风险变更需独立验证；无能力时保留未关闭，不用同一 agent 换 persona 冒充独立。

证据应保存在可访问的持久位置，敏感内容按授权最小化留存，报告引用脱敏产物。若原始证据只能受控保存，记录受控位置与访问限制；仅有临时目录、已丢失日志或脱敏后无法复核时收缩结论。sha256 不能替代原始内容本身。

## 9. 结束、验收与后续

同时给出三个状态，不使用含混的“全部完成”：

| 状态面 | 允许值 | 判断条件 |
|---|---|---|
| 审查执行 | `complete` / `partial` / `blocked` | 全部承诺审查均已执行且结果可核验才能 complete；发现 fail 仍可完成审查；必需项 partial/not-run/inconclusive 则不能 complete |
| 被审对象 | 通过 / 有条件通过 / 不通过 / 证据不足 | 存在已确认阻断缺陷为不通过；否则关键证据缺失为证据不足；只有非阻断残余有明确接受来源才可有条件通过 |
| 收益结论 | 已验证 / 未验证 / 不适用 | 已验证需可比较的真实任务与成本证据；静态/定向审查不得推断收益，不以目标百分比替代有效性判断 |

审查执行为 complete 不意味着对象通过。方案评估/定向审查可以按其明确范围 complete，但标题和结论不得写成“全量 Skill 审查通过”。若完整审查缺行为或真实任务证据，完成已授权部分后交付 partial 报告与最小补证路径。

收尾逐项核对：

- [ ] 范围对象、读取记录、适用维度、H/ML 场景均有处置；未测不标不适用。
- [ ] 当前源码/配置身份与证据匹配；期间变化的相关部分已复验或失效标记。
- [ ] 全部关键结论可回源；原始记录与汇总数一致，失败尝试未隐去。
- [ ] 阻断缺陷、关键证据缺口没有被分数、文件数、测试总数或少量成功任务抵消。
- [ ] 复核方式如实记录：独立上下文、外部审查或 inline；多份自审不等于独立验证。
- [ ] 交付报告、证据索引和恢复点可访问；未完成项明确 owner/下一步/触发条件。

后续依据事实选择：保持现状、范围内修复、补证、调整非 Skill 根因、停止低收益投入。已授权的独立工作继续；只有新增重要动作等待授权。没有实测 ROI 不造数，也不以低频拒绝已确认的严重缺陷。

新的源码、runtime、模型/工具配置、消费者合同或反例变化会使相关结论失效。按影响面复审，复用仍有效证据，不无条件重跑全库。后续修改完成时，用本轮事实更新相关汇总入口；保留历史报告的日期和当时结论，不追写成历史已通过。

## 10. 迁移与本流程自身验收

v2 替代本文件 v1 的三种固定时长阅读路线、综合评分放行与问题数量要求；对应[启动指南](HOW-TO-START-REVIEW.md)、[模板](ITERATION-REVIEW-TEMPLATE.md)、[流程图](REVIEW-WORKFLOW-DIAGRAMS.md)同源更新。core 原文、覆盖分析和历史审查保留；有冲突的条款按第 1–2 节回源适配，不静默改写原始证据。

本流程的维护检查至少验证以下反例，且不把检查通过说成真实 Skill 行为通过：

| 输入情况 | 应得结果 |
|---|---|
| 合同测试全绿，必需行为场景未运行 | structure 可通过；完整审查 partial，对象证据不足 |
| 必需场景已充分运行并确认关键缺陷 | 审查可 complete；对象不通过，问题保持开放 |
| 5 个小任务成功，但比较基线是复杂大任务 | 报告观察值和不可比性，不能判收益已验证 |
| 只运行候选版本，没有同任务的改动前基线 | 收益结论记未验证；候选侧行为可按 behavior_quality 报告 |
| 执行者看到候选结果后才确定任务或判据 | 披露选择效应；相应收益结论不能记已验证 |
| 试点外推显示全量超预算，报告标题仍写“完整审查” | 改为定向审查或 `partial`，并列出收缩选项及确认记录 |
| 记录的 override 情况编号与判定条件数不符（如 2/5 记为“情况 3”） | 按来源规则重新标注，并记为来源冲突，不沿用错误编号 |
| 全量单次审查前三层全部完成，未做真实任务观察 | 审查执行可 complete；收益未验证；Layer 3 端到端指标 `not-run`；标题不写“完整审查通过” |
| eval case 首轮失败，复核发现是 fixture 过期 | 记为 `inconclusive`，归因工具或 fixture；不作为对象不通过的依据 |
| 补充场景在执行后才计算 hash 或被修改 | 该场景结果不计入主结论，单独列出并说明 |
| 旧报告说未深读，目录已有相关源码分析 | 核验旧分析身份与内容；不直接判已完成或未执行 |
| 首轮验证失败，修正后全绿 | 分别记录首轮与最终结果，不声称首过 |
| 没有 worktree 场景，但声称提示机制有效 | 对应行为 not-run，不能用其他任务代证 |
| 未授权外部模型、runner 不可用或付费预算不足 | 继续本地审查；依赖评测保留缺口，不伪造独立性 |
| 审查期间修改了 Skill 或消费者 | 相关旧证据失效，定向复验后才可关闭 |
| 逐项取证后没有发现缺陷 | 可按已覆盖范围通过，不为达到数量制造问题 |
