## 候选项的详细说明

### O01：spec-plan 读取优化

**优化方向**：减少重复读取，缓存已读内容

**理论依据**：
- Phase Reads 可能导致重复读取
- 如果宿主支持 context residency，可以避免重复

**Phase 0 验证点**：
- 真实任务中 spec-plan 是否有明显重复读取？
- 重复读取导致的成本是多少？
- 是否影响任务质量？

**如果确认**：参考 `archive/o01-execution-guide.md`

---

### NEW-04：spec-prd 需求审查与优化

**优化方向**：从"需求记录员"到"需求顾问"

**包含**：
1. 需求逻辑审查（一致性、合理性、可行性）
2. 隐含需求挖掘（边界、非功能、用户体验、运维）
3. 行业对标（最佳实践、反模式、参考实现）
4. 备选方案设计
5. 行业知识库（authentication、payment、data_management）

**Phase 0 验证点**：
- 真实任务中 spec-prd 是否遗漏隐含需求？
- 是否导致后期补充需求？
- 是否未主动提供行业方案建议？

**详细设计**：见 `03-phase1-execution-guide.md`

---

### NEW-08：spec-test-design（新 Skill）

**优化方向**：测试策略设计与用例生成

**为什么需要**：
- 当前只有 spec-test-browser、spec-test-xcode（特定平台）
- 缺少通用的测试策略设计能力
- 测试阶段 70% 缺口

**包含**：
1. 测试策略设计（单元、集成、端到端）
2. 测试用例生成（基于需求和边界条件）
3. 测试覆盖率分析
4. 测试优先级排序

**Phase 0 验证点**：
- 真实任务中是否缺少测试？
- 缺少测试是否导致质量问题或返工？
- 是否需要独立的测试 Skill？

## Phase 0 后的决策流程

### 步骤 1：统计候选项在真实任务中的频率

```yaml
example_result:
  NEW-03_spec-plan_边界系统化:
    affected_tasks: 7 / 11
    led_to_rework: 5 / 7
    severity: P0
  
  O01_spec-plan_读取优化:
    affected_tasks: 2 / 11
    led_to_rework: 0 / 2
    severity: P2
```

### 步骤 2：按影响面和严重程度排序

```
高频 + 高影响 → P0
高频 + 中影响 → P1
低频 + 高影响 → P1
低频 + 低影响 → P2 或废弃
```

### 步骤 3：识别新的优化方向

Phase 0 可能发现候选清单之外的问题，例如：
- 某两个 Skill 之间的衔接断裂
- 某个 Skill 的输出格式不符合下游期望
- 某个阶段完全缺少 Skill 覆盖

### 步骤 4：合并或废弃候选项

例如：
- NEW-02 + NEW-06 可能合并为一个"spec-code-review 全面增强"
- O01 如果没有发现明显机会，可能标记为 `no-opportunity`
