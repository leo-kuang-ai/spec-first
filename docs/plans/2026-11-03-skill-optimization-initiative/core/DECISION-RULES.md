# 量化决策规则

**文档版本**：v1.0  
**创建日期**：2026-11-03  
**目的**：将所有决策阈值量化，避免主观判断和灰色地带

---

## 🎯 核心原则

1. **数据驱动**：所有决策基于可测量的指标
2. **阈值明确**：每个决策点有清晰的量化标准
3. **灰色地带处理**：介于阈值之间的情况有明确处理机制
4. **可追溯**：每个决策都能追溯到具体数据

---

## 📋 决策规则总览

| 决策点 | 核心指标 | 阈值 | 灰色地带 |
|---|---|---|---|
| Phase -1 → Phase 0 | 追踪方法可行性 | 定性 | 有 |
| Phase 0 中期调整 | 模式识别度 | ≥60% | 40-60% |
| Phase 0 → Phase 1 | 5 个条件 | 全部满足 | 4/5 |
| Phase 1 路径选择 | 归因占比 | ≥50% | 40-50% |
| 止损决策 | ROI | <1 | 0.8-1 |

## 🔑 详细决策规则

### 规则 1：Phase -1 后是否继续 Phase 0？

#### 必须满足的条件（全部）

```yaml
条件 1: 追踪方法可行
  指标: 
    - 能完整追溯任务历史（Git 提交、PR、讨论）
    - 能识别各阶段 Skill 使用
    - 能记录阻力点
  
  判断标准:
    ✅ 可行: 
      - 追溯到 ≥80% 的关键节点
      - 数据质量"好"或"中"
      - 追踪时间 ≤4 小时
    
    ⚠️ 需要调整:
      - 追溯到 60-80% 的关键节点
      - 部分数据缺失但可补救
      - 追踪时间 4-6 小时
      → 调整方法（简化追踪、增加工具）
    
    ❌ 不可行:
      - 追溯 <60% 的关键节点
      - 关键数据缺失（无 Git 历史/无 PR）
      - 追踪时间 >6 小时
      → 暂停项目，重新评估方法

---

条件 2: 数据质量足够
  指标:
    - 能识别阻力点
    - 能归因根因
    - 信息完整度
  
  判断标准:
    ✅ 足够:
      - 识别出 ≥3 个阻力点
      - 每个阻力点都能归因
      - 信息完整度 ≥70%
    
    ⚠️ 勉强:
      - 识别出 1-2 个阻力点
      - 部分阻力点能归因
      - 信息完整度 50-70%
      → 调整追踪深度
    
    ❌ 不足:
      - 识别不出明确阻力点
      - 无法归因
      - 信息完整度 <50%
      → 暂停或重新设计

---

条件 3: 投入合理
  指标: Phase 0 预估时间
  
  判断标准:
    ✅ 合理: 44 小时估算仍然有效
    ⚠️ 调整: 需要 44-60 小时（+36%）
      → 评估是否值得，可能需要管理层批准
    ❌ 不合理: 需要 >60 小时（+36%+）
      → 重新评估或暂停
```

#### 决策矩阵

```yaml
情况 1: 三个条件都是 ✅
  决策: 启动 Phase 0
  置信度: 高

情况 2: 两个 ✅，一个 ⚠️
  决策: 调整后启动 Phase 0
  置信度: 中
  行动: 先解决 ⚠️ 的问题

情况 3: 一个 ✅，两个 ⚠️
  决策: 需要深入评估
  行动: 技术负责人 + 项目负责人讨论

情况 4: 任何一个 ❌
  决策: 暂停项目
  行动: 输出 Phase -1 报告，说明问题
```

### 规则 2：Phase 0 中期是否继续？

**时机**：Week 1 结束（已追踪 5-8 个任务）

#### 量化指标

```yaml
指标 1: 模式识别度
  定义: 发现的阻力点在多个任务中重复出现的比例
  
  计算:
    重复阻力点数 / 总阻力点数
  
  示例:
    - 追踪了 5 个任务
    - 发现 10 个阻力点
    - 其中 7 个在 ≥2 个任务中出现
    - 模式识别度 = 7/10 = 70%
  
  阈值:
    ✅ 继续: ≥60%（模式明确）
    ⚠️ 扩大样本: 40-60%（模式不明显，需更多数据）
    ❌ 停止: <40%（无明确模式，继续追踪价值有限）

---

指标 2: 归因一致性
  定义: 根因归因的一致性程度
  
  计算:
    主要归因类别占比
  
  示例:
    - 10 个阻力点
    - 6 个归因为"Skill 问题"
    - 3 个归因为"模型能力"
    - 1 个归因为"外部因素"
    - 主要归因占比 = 6/10 = 60%
  
  阈值:
    ✅ 继续: 主要归因 ≥50%（问题集中）
    ⚠️ 观察: 主要归因 40-50%（分散但可接受）
    ❌ 停止: 主要归因 <40%（过于分散，难以聚焦）

---

指标 3: 数据饱和度
  定义: 新追踪的任务是否还能发现新问题
  
  判断:
    最近 2 个任务是否发现了新的阻力点类型
  
  阈值:
    ✅ 未饱和: 最近 2 个任务发现 ≥1 个新类型
      → 继续追踪，还有发现空间
    
    ⚠️ 接近饱和: 最近 2 个任务只发现已知类型
      → 再追踪 2-3 个任务验证
    
    ✅ 已饱和: 连续 4 个任务无新发现
      → 可以提前结束（已找到主要模式）
```

#### 决策矩阵

```yaml
情况 1: 模式识别度 ≥60% AND 归因一致性 ≥50%
  决策: ✅ 继续标准样本（完成 11 个任务）
  理由: 模式明确，值得深入

情况 2: 模式识别度 40-60% OR 归因一致性 40-50%
  决策: ⚠️ 扩大样本到 13-15 个任务
  理由: 模式不够明确，需要更多数据

情况 3: 模式识别度 <40% AND 归因一致性 <40%
  决策: ❌ 停止 Phase 0
  理由: 无明确模式，继续追踪价值有限
  
  输出:
    - 部分完成报告
    - 结论: "当前方法未发现明确模式"
    - 建议: 
      1. 等待更多数据积累
      2. 调整追踪方法
      3. 问题可能不在 Skill

情况 4: 已饱和（连续 4 个任务无新发现）
  决策: ✅ 提前结束（无需 11 个任务）
  理由: 已找到主要模式，继续追踪边际收益低
  
  最少任务数: 7 个（确保统计有效性）
```

### 规则 3：Phase 0 后是否启动 Phase 1？⭐⭐⭐

#### 5 个必须条件（全部满足才启动）

```yaml
条件 1: 基线未达标
  指标: 端到端返工率
  
  阈值:
    ✅ 需要优化: 返工率 ≥20%
      理由: 改善空间大，值得投入
    
    ⚠️ 灰色地带: 返工率 15-20%
      → 评估改善潜力
      → 如果能改善 ≥30%（即降到 <14%），则值得
    
    ❌ 质量已达标: 返工率 <15%
      → 项目成功完成（无需 Phase 1）
      → 输出: "质量已达标"报告

  说明:
    - 为什么是 20%？
      - 低于 20%，改善空间有限
      - 即使改善 30%，也只从 18% → 12.6%
      - ROI 较低
    
    - 为什么不是 10%？
      - 10% 已经很好，优化边际收益小
      - 应该关注其他优先级更高的问题

---

条件 2: 归因为 Skill 问题
  指标: Skill 问题占所有阻力点的比例
  
  阈值:
    ✅ 强烈建议启动: ≥60%
      理由: 问题明确集中在 Skill
      置信度: 高
    
    ✅ 建议启动: 50-60%
      理由: Skill 问题占主导
      置信度: 中
      条件: 其他 4 个条件都满足
    
    ⚠️ 需要深入分析: 40-50%
      → 灰色地带处理（见下文）
    
    ❌ 不建议启动 Skill 优化: <40%
      → 问题不在 Skill
      → 建议: 调整方向
        - 如果归因为"模型能力" → 等待模型升级
        - 如果归因为"外部因素" → 改进流程/需求质量
        - 如果归因为"工具链" → 开发辅助工具

---

条件 3: 影响面足够
  指标: 受影响的任务占比
  
  阈值:
    ✅ 影响面大: ≥5/11 个任务（约 45%）
      理由: 问题普遍，优化收益大
    
    ✅ 影响面中等: 4/11 个任务（约 36%）
      理由: 问题较常见，值得优化
      条件: 其他条件都满足
    
    ⚠️ 影响面小: 3/11 个任务（约 27%）
      → 评估严重程度
      → 如果都是导致返工的严重问题，可以优化
      → 如果只是轻微影响，优先级较低
    
    ❌ 影响面很小: ≤2/11 个任务（约 18%）
      → 不建议启动 Phase 1
      → 个案问题，不值得系统性优化

---

条件 4: 预期改善明确
  指标: 基于 Phase 0 数据的改善预期
  
  计算方法:
    当前返工率 × (1 - Skill问题占比 × 预期修复率)
  
  示例:
    - 当前返工率: 45%（5/11）
    - Skill 问题占比: 65%
    - 预期修复率: 70%（保守估计）
    - 预期返工率: 45% × (1 - 0.65 × 0.7) = 24.6%
    - 预期改善: (45% - 24.6%) / 45% = 45%
  
  阈值:
    ✅ 值得优化: 预期改善 ≥30%
      理由: 显著提升，值得投入
    
    ⚠️ 边际值得: 预期改善 20-30%
      → 评估投入成本
      → 如果 Phase 1 投入 <80h，值得
    
    ❌ 不值得: 预期改善 <20%
      → 改善幅度小，ROI 低
      → 建议等待更好时机

---

条件 5: ROI >1
  指标: 预期收益 / 预期投入
  
  计算方法:
    收益 = (返工节省时间) × (团队规模) × (未来 6 个月)
    投入 = Phase 1 时间成本
  
  示例:
    假设:
      - 当前返工率: 45%
      - 预期降到: 25%
      - 节省返工: 20%
      - 平均任务时间: 20 小时
      - 团队规模: 5 人
      - 未来 6 个月任务数: 每人 10 个
    
    计算:
      收益 = 20% × 20h × 5人 × 10任务 = 200 小时
      投入 = Phase 1（假设 100 小时）
      ROI = 200 / 100 = 2.0
  
  阈值:
    ✅ 强烈建议: ROI ≥2
      理由: 投入回报比高
    
    ✅ 建议: ROI 1-2
      理由: 投入回报比合理
    
    ⚠️ 灰色地带: ROI 0.8-1
      → 考虑长期收益（6 个月以上）
      → 考虑知识积累价值
    
    ❌ 不建议: ROI <0.8
      → 成本 > 收益
      → 建议暂停或缩减范围
```

#### 决策矩阵

```yaml
情况 1: 5 个条件全部满足
  决策: ✅ 启动 Phase 1
  置信度: 高
  建议: 标准投入（48-120h）

情况 2: 4/5 条件满足，1 个条件在灰色地带
  决策: ✅ 启动试点（优化 1 个 Skill）
  置信度: 中
  建议: 
    - 选择最高优先级的 1 个 Skill
    - 投入 24-48h
    - 验证效果后决定是否继续

情况 3: 3/5 条件满足
  决策: ⚠️ 需要额外审查
  行动:
    - 召开决策会议（技术负责人 + CTO）
    - 深入分析不满足的 2 个条件
    - 评估是否有特殊情况
  
  可能结果:
    - 批准启动（有充分理由）
    - 调整 Phase 0（收集更多数据）
    - 暂停项目

情况 4: ≤2/5 条件满足
  决策: ❌ 不启动 Phase 1
  理由: 条件不满足，强行启动风险高
  
  输出:
    - Phase 0 完整报告
    - 不启动的理由
    - 替代建议（如果有）
```

### 规则 4：Phase 1 路径选择

**前提**：已决定启动 Phase 1

**决策**：选择哪个路径（或组合）

```yaml
路径 1: Skill 优化
  条件: Skill 问题占比 ≥50%
  投入: 48-120h
  
  决策:
    ✅ 优先: Skill 问题占比 ≥60%
    ✅ 包含: Skill 问题占比 50-60%
    ⚠️ 考虑: Skill 问题占比 40-50%（与路径 2 并行）

---

路径 2: 工具链增强
  条件: 工具链问题占比 ≥20%
  投入: 20-40h
  
  决策:
    ✅ 优先: 工具链问题占比 ≥30%
    ✅ 包含: 工具链问题占比 20-30%
    ⚠️ 可选: 工具链问题占比 10-20%

---

路径 3: 流程改进
  条件: 外部因素占比 ≥20%
  投入: 10-20h（文档、培训）
  
  决策:
    ✅ 包含: 外部因素占比 ≥30%
    ✅ 可选: 外部因素占比 20-30%

---

组合决策:
  情况 1: Skill 60% + 工具 25% + 外部 15%
    → 路径 1（主） + 路径 2（辅）
    → 并行执行，4-6 周
  
  情况 2: Skill 50% + 模型 30% + 外部 20%
    → 路径 1（主） + 路径 3（辅）
    → 串行执行，先 Skill 再流程
  
  情况 3: Skill 45% + 工具 35% + 外部 20%
    → 路径 1 + 路径 2（同等重要）
    → 并行执行，各占一半资源
```

### 规则 5：Phase 1 止损决策

**触发条件**：Phase 1 执行中发现效果不如预期

#### 量化指标

```yaml
指标 1: 实际进度 vs 计划
  计算: (已投入时间 - 计划时间) / 计划时间
  
  阈值:
    ✅ 正常: ≤10% 偏差
    ⚠️ 注意: 10-20% 偏差
      → 评估原因，调整计划
    ❌ 预警: >20% 偏差
      → 触发止损评估

---

指标 2: 已完成价值 vs 已投入成本
  计算: 
    已完成工作的预期价值 / 已投入时间
  
  示例:
    - 计划优化 3 个 Skill，共 90h
    - 已投入 50h
    - 完成 1 个 Skill（33% 工作量）
    - 预期价值: 33% × 总预期收益
    - 实际投入: 50h / 90h = 56%
    - 价值投入比: 33% / 56% = 0.59（低于 1）
  
  阈值:
    ✅ 良好: 价值投入比 ≥1
    ⚠️ 注意: 价值投入比 0.8-1
      → 评估是否能加速
    ❌ 预警: 价值投入比 <0.8
      → 触发止损评估

---

指标 3: 预期 ROI（重新计算）
  方法: 基于已完成部分，重新估算最终 ROI
  
  计算:
    预期收益（基于已完成部分外推） / 预估总投入
  
  阈值:
    ✅ 继续: 预期 ROI >1
    ⚠️ 评估: 预期 ROI 0.8-1
      → 考虑缩减范围
    ❌ 止损: 预期 ROI <0.8
      → 建议停止
```

#### 止损决策矩阵

```yaml
情况 1: 3 个指标都正常
  决策: ✅ 继续执行
  行动: 正常推进

情况 2: 1 个指标预警
  决策: ⚠️ 调整计划
  行动:
    - 分析原因
    - 调整范围或方法
    - 继续执行

情况 3: 2 个指标预警
  决策: ⚠️ 召开紧急评审
  行动:
    - 技术负责人 + 执行者深度分析
    - 评估 3 个选项:
      1. 缩减范围（只完成高价值部分）
      2. 调整方法（提升效率）
      3. 止损（停止 Phase 1）
    - 决策时限: 2 天

情况 4: 3 个指标都预警
  决策: ❌ 建议止损
  行动:
    - 立即上报 CTO
    - 保存已完成成果
    - 输出止损报告:
      - 已投入成本
      - 已完成价值
      - 未完成原因
      - 经验教训
    - 决策: 止损 or 追加资源
```

## 🔄 灰色地带处理机制

### 什么是灰色地带？

**定义**：指标处于决策阈值的边界，无法明确判断

### 处理原则

```yaml
原则 1: 倾向保守
  - 不确定时，倾向于"不启动"或"缩小范围"
  - 避免高风险投入

原则 2: 收集更多数据
  - 灰色地带通常意味着数据不足
  - 优先选择低成本的数据收集方法

原则 3: 试点验证
  - 小范围试点（1 个 Skill，24-48h）
  - 基于试点结果决定是否扩大

原则 4: 多方评审
  - 灰色地带需要技术负责人 + CTO 共同决策
  - 不由单人决定
```

### 常见灰色地带处理

```yaml
场景 1: 归因占比 45%（接近 50% 阈值）
  问题: 是否归因为"主要是 Skill 问题"？
  
  处理:
    - 看影响面: 如果影响 >5 个任务 → 倾向启动
    - 看严重程度: 如果都导致返工 → 倾向启动
    - 看改善信心: 如果有明确优化思路 → 倾向启动
    - 否则 → 试点验证（1 个 Skill）

---

场景 2: 预期改善 25%（接近 30% 阈值）
  问题: 25% 的改善是否值得 100h 投入？
  
  处理:
    - 重新计算 ROI
    - 如果 ROI >1 → 倾向启动
    - 如果 ROI 0.8-1 → 考虑长期收益
    - 如果 ROI <0.8 → 不启动

---

场景 3: 影响面 36%（4/11 个任务）
  问题: 是否影响面足够？
  
  处理:
    - 看问题严重程度:
      - 4 个任务都返工 → 严重，倾向启动
      - 只是轻微不便 → 不严重，优先级低
    - 看问题一致性:
      - 都是同一个 Skill 问题 → 易修复，倾向启动
      - 问题分散 → 难修复，谨慎

---

场景 4: ROI = 0.9（接近 1）
  问题: 0.9 是否值得投入？
  
  处理:
    - 考虑计算误差（±20%）:
      - 实际可能是 0.9 × 1.2 = 1.08 → 值得
      - 实际可能是 0.9 × 0.8 = 0.72 → 不值得
    - 考虑长期收益:
      - 6 个月 ROI = 0.9
      - 12 个月 ROI = 1.8 → 值得
    - 考虑知识价值:
      - 首次系统性优化 Skill → 学习价值高
      - 后续优化会更高效
    
    决策:
      - 如果是首次优化 → 倾向启动（学习价值）
      - 如果是常规优化 → 不启动（ROI 不足）
```
