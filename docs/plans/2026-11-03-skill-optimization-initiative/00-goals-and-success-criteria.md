# 目标与完成标准

日期：2026-11-03  
版本：v4（研发流程导向）

---

## 🎯 优化目标（一句话）

**让需求到可信交付的整条研发链路更顺畅、更自主、更可靠**

**不是**：优化 Skill 的性能指标（token、速度）  
**而是**：让真实任务能高质量、完整地交付

---

## ✅ 完成标准（三层）

### Layer 3：端到端交付质量（最重要）

这是最终目标，其他层级为此服务。

| 指标 | 基线（Phase 0 前） | 目标 | 度量方法 |
|---|---|---|---|
| **端到端正确率** | 待测量 | **>90%** | 完全正确的任务数 / 总任务数 |
| **端到端返工率** | 待测量 | **<10%** | 需要返工的任务数 / 总任务数 |
| **用户介入次数** | 待测量 | **<3 次/任务** | 平均每任务的澄清、确认、修正次数 |
| 端到端完成时间 | 待测量 | 基线 -20% | 从需求到交付的总时间 |

**质量评估标准**：

```yaml
任务交付质量（5 项全部 true 才算完全正确）：
  delivered: true      # 有交付物
  correct: true        # 功能正确
  complete: true       # 包含所有需求功能点
  tested: true         # 有测试验证
  documented: true     # 有必要文档

overall_score: 5/5
```

---

### Layer 2：阶段衔接顺畅度

检查 Skill 之间的协作是否流畅。

| 指标 | 目标 | 度量方法 |
|---|---|---|
| **信息丢失率** | **<5%** | 上游已确定但下游未使用的信息条数 / 总信息条数 |
| **信息重复率** | **<10%** | 下游重复询问上游已确定信息的次数 / 总询问次数 |
| **验收条件落实率** | **>90%** | Work 实现的验收条件数 / Plan 中的验收条件数 |
| 输入输出匹配度 | 100% | 上游输出是否符合下游输入期望 |

**四类衔接问题**：

1. **信息丢失**：Plan 定义了边界条件，Work 未实现
2. **信息重复**：PRD 已确定"每页 20 条"，Plan 又询问
3. **验证缺失**：Work 声称"已完成"，但未运行测试
4. **衔接断裂**：Plan 说"用 Redis"，Work 不知道具体配置

---

### Layer 1：单个 Skill 有效性

检查每个 Skill 本身是否合理。

| 维度 | 通过条件 |
|---|---|
| **指令清晰度** | 无歧义、无矛盾、模型能明确理解 |
| **无过时约束** | 约束仍然有效且必要 |
| **必要性** | 每个步骤都有明确目的，无不必要工作 |
| **完整性** | 关键验证点未遗漏 |

**度量方法**：
- 人工审查 Skill 源码
- 对比官方最佳实践
- 对比研发最佳实践

## 🔍 检查方法

### Phase 0：真实任务流程追踪（当前阶段）

**目的**：识别真实痛点，不预设优化范围

```
选择 11 个代表性真实任务（已完成的）
  ↓
重建端到端流程（从第一条消息到最终交付）
  ↓
标注四类阻力点（信息丢失/重复/验证缺失/衔接断裂）
  ↓
统计三层指标（Layer 3 → Layer 2 → Layer 1）
  ↓
定位问题 Skill + 决定优先级
```

**11 个任务的类型**：
- 3 个小功能开发
- 2 个跨模块需求
- 2 个缺陷修复
- 2 个 PR 反馈处理
- 2 个跨会话续做

**统计示例**：

```yaml
# Layer 3（整体）
端到端正确率: 3/11 = 27%  # ❌ 不合格（目标 >90%）
端到端返工率: 8/11 = 73%  # ❌ 不合格（目标 <10%）
平均用户介入: 2.8 次       # ✅ 合格（目标 <3 次）

# Layer 2（衔接）
信息丢失率: 7/11 = 64%     # ❌ 不合格（目标 <5%）
信息重复率: 6/11 = 55%     # ❌ 不合格（目标 <10%）
验收条件落实率: 30%         # ❌ 不合格（目标 >90%）

# Layer 1（定位）
发现问题：
  - spec-plan 缺少边界系统化检查
  - spec-work 未验证 Plan 的验收条件
  - spec-prd 未主动挖掘隐含需求
```

---

### Phase 1：优化实施（Phase 0 后）

**前提**：基于 Phase 0 数据决定优化哪些 Skill

**何时优化一个 Skill？必须同时满足：**

1. **Layer 3 有明确问题**（整体交付有问题）
2. **Layer 2 追查到具体衔接问题**（阶段之间有断裂）
3. **Layer 1 定位到该 Skill 的根因**（该 Skill 确实有问题）

**优先级排序**：

```
优先级 = 影响面 × 严重程度

影响面 = 受影响的任务数 / 总任务数
严重程度:
  导致返工 → P0
  影响效率但不返工 → P1
  仅浪费少量时间 → P2
```

**示例**：

```
spec-plan 边界遗漏:
  影响面 = 7/11 = 64%
  严重程度 = P0（导致 5 个任务返工）
  → 优先级 = P0（立即优化）

spec-runtime-setup 重复检查:
  影响面 = 6/11 = 55%
  严重程度 = P2（仅浪费 5 分钟，未导致返工）
  → 优先级 = P2（暂缓）
```

### Phase 2：验证与推广（Phase 1 后）

**在 5 个新任务中试用优化后的 Skill**

#### 验证标准（三层门）

```
第一层：质量硬门（零容忍，任一不通过立即拒绝）
├─ Layer 3 指标下降 → 立即拒绝
├─ Layer 2 衔接问题恶化 → 立即拒绝
└─ Layer 1 引入新问题 → 立即拒绝

第二层：改善门（至少一项通过才能推广）
├─ Layer 3 至少一项指标改善 ≥20% → 通过
└─ Layer 2 至少一项指标改善 ≥30% → 通过

第三层：成本门（附加考虑，不阻断推广）
├─ 开发时间增加 <20% → 可接受
└─ Token 消耗增加 <10% → 可接受（如果质量改善）
```

#### 验证清单

**Layer 3 改善**：
- [ ] 端到端正确率提升（5 个任务的正确率）
- [ ] 端到端返工率下降（5 个任务的返工率）
- [ ] 用户介入次数保持或下降

**Layer 2 改善**：
- [ ] 信息丢失率下降（统计 5 个任务）
- [ ] 信息重复率下降（统计 5 个任务）
- [ ] 验收条件落实率提升（统计 5 个任务）

**Layer 1 改善**：
- [ ] 指令清晰度提升（主观评分）
- [ ] 过时约束已移除（检查清单）
- [ ] 不必要工作已消除（对比前后）
- [ ] 遗漏检查已补充（检查清单）

## 📊 标准的层级关系

### 为什么从 Layer 3 → Layer 2 → Layer 1？

```
❌ 错误思路：
优化单个 Skill → 希望整体变好

✅ 正确思路：
整体交付有问题（Layer 3）
  ↓ 追查原因
阶段衔接断裂（Layer 2）
  ↓ 追查原因
单个 Skill 有问题（Layer 1）
```

**示例**：

```
发现：端到端返工率 73%（Layer 3 ❌）
  ↓ 为什么返工？
追查：Plan → Work 信息丢失率 64%（Layer 2 ❌）
  ↓ 为什么丢失？
定位：
  - spec-plan 缺少边界系统化检查（Layer 1 根因）
  - spec-work 未验证验收条件（Layer 1 根因）
```

---

## ⚠️ 常见误区

### ❌ 错误的做法

1. **只看性能指标**
   ```
   "spec-plan 的 token 降低了 20%"
   → 但端到端返工率反而上升了
   ✗ 优化方向错误
   ```

2. **预设优化范围**
   ```
   "必须优化这 12 个 Skill"
   → 但真实任务的痛点在其他地方
   ✗ 可能优化了不痛的点
   ```

3. **只看局部改善**
   ```
   "spec-plan 优化后很完美"
   → 但 Plan → Work 衔接仍然断裂
   ✗ 整体交付质量未改善
   ```

### ✅ 正确的做法

1. **从整体到局部**
   ```
   Layer 3（整体）有问题
     ↓
   Layer 2（衔接）找原因
     ↓
   Layer 1（单个）定位根因
   ```

2. **质量优先**
   ```
   质量改善 > 效率保持 > 成本附加收益
   ```

3. **数据驱动**
   ```
   真实任务追踪 → 统计阻力点 → 决定优化范围
   ```

## 📋 自查清单

### Phase 0 是否合格？

- [ ] 选择了 11 个代表性真实任务（5 种类型）
- [ ] 每个任务都完成了端到端流程追踪
- [ ] 标注了四类阻力点（信息丢失/重复/验证缺失/衔接断裂）
- [ ] 统计了 Layer 3 指标（正确率、返工率、用户介入）
- [ ] 统计了 Layer 2 指标（丢失率、重复率、落实率）
- [ ] 定位了 Layer 1 的具体问题（哪些 Skill 有问题）
- [ ] 给出了基于数据的优先级建议

### Phase 1 优化是否合格？

- [ ] 基于 Phase 0 的数据决定优化范围（不是预设）
- [ ] 每个优化都有明确的 Layer 3 问题作为动机
- [ ] 每个优化都追查到了 Layer 2 的衔接问题
- [ ] 每个优化都定位到了 Layer 1 的根因
- [ ] 在 5 个新任务中验证了改善效果
- [ ] 三层指标都有改善或保持
- [ ] 无质量回归

## 📝 总结

### 目标

**让需求到可信交付的整条研发链路更顺畅、更自主、更可靠**

### 完成标准

| 层级 | 核心指标 | 目标 |
|---|---|---|
| **Layer 3** | 端到端正确率 | **>90%** |
| **Layer 3** | 端到端返工率 | **<10%** |
| **Layer 3** | 用户介入次数 | **<3 次/任务** |
| Layer 2 | 信息丢失率 | <5% |
| Layer 2 | 信息重复率 | <10% |
| Layer 2 | 验收条件落实率 | >90% |
| Layer 1 | 指令清晰度 | 无歧义、无矛盾 |
| Layer 1 | 必要性 | 无不必要工作 |
| Layer 1 | 完整性 | 无遗漏检查 |

### 检查方法

**Phase 0**：11 个真实任务的端到端流程追踪 → 统计三层指标 → 定位问题 Skill  
**Phase 1**：基于数据优化 → 5 个新任务验证  
**Phase 2**：三层门验证 → 推广或回退

### 优化决策

**基于数据**：影响面 × 严重程度 = 优先级

### 质量门

**第一层（零容忍）**：Layer 3 指标下降 → 立即拒绝  
**第二层（改善门）**：Layer 3 至少一项改善 ≥20% → 通过  
**第三层（成本门）**：开发时间增加 <20%、Token 增加 <10% → 可接受
