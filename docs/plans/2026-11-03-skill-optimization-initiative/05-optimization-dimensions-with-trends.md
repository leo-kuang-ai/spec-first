# Skill 优化维度分析 - 基于 AI 大模型能力发展趋势

日期：2026-11-03  
版本：v4（研发流程导向 + 模型能力趋势）

---

## AI 大模型能力发展的三大趋势

### 1. 模型能力快速提升

**2026 年现状**：
- Claude Opus 5.5 在 SWE-bench Verified 达到 80.8%
- Claude Sonnet 5.5 已接近前代 Opus 水平（79.6%）
- 上下文窗口扩展到 1M tokens，输出可达 300K tokens
- 长上下文理解和多步推理能力显著增强

**对 Skill 的含义**：
- **曾经需要 Skill 补偿的模型能力缺陷，现在可能已不需要**
- **Skill 应该编码领域知识和工作流，而不是补丁模型推理能力**
- **过度详细的步骤指导可能反而限制模型发挥**

---

### 2. 从 Prompt Engineering 到 Harness Engineering

**范式转变**：
```
2023-2024: Prompt Engineering
  - 精心设计单个 prompt
  - Few-shot examples
  - Chain-of-thought
  - Role-playing

2025-2026: Harness Engineering + Agentic Workflows
  - 执行环境和编排逻辑
  - 状态机和多步工作流
  - 工具调用和外部集成
  - 验证门和质量闭环
```

**对 Skill 的含义**：
- **Skill 不应该是"一次性长 prompt"，而是工作流编排**
- **重点从"怎么说"转向"怎么验证、怎么衔接、怎么回退"**
- **确定性约束和语义判断的分工更重要**

---

### 3. 自演化和自优化能力

**新兴范式**：
- SkillOpt（微软）：Skill 作为可训练参数，基于轨迹自动优化
- SkillRevise：基于执行轨迹的条件性 Skill 修订
- SkillMOO：多目标优化（质量、成本、延迟）

**核心原则**：
- **领域知识优先于性能补丁**：编码工作流和机构知识的 Skill 持久有效；补丁模型能力缺陷的 Skill 会随模型进步而贬值
- **紧凑且可审计**：通过有界文本编辑、验证门、拒绝编辑反馈避免不受控的 prompt 漂移
- **独立验证门**：基于真实任务的经验效用测量，而不是主观评分

---

## 当前 Skill 需要关注的 8 大优化维度

### 维度 1：去模型能力补丁化（优先级 P0）

**问题**：
许多 Skill 在 2024-2025 年编写时补偿了当时模型的能力缺陷，现在可能已过时。

**检查项**：
- [ ] Skill 是否包含过度详细的推理步骤？（模型现在可以自主推理）
- [ ] Skill 是否包含"你必须..."/"务必..."之类的强制性约束？（可能限制模型发挥）
- [ ] Skill 是否提供了大量 few-shot examples？（长上下文模型可能不需要）
- [ ] Skill 是否手把手教模型如何推理？（Sonnet 5.5+ 已具备强推理能力）

**优化方向**：
```
❌ 旧范式（2024）：
"你必须按以下步骤分析代码：
1. 首先读取文件
2. 然后识别函数
3. 接着分析依赖
4. 最后输出结论
每一步都要详细说明..."

✅ 新范式（2026）：
"分析代码的架构和依赖关系，重点关注：
- 模块边界是否清晰
- 依赖方向是否合理
- 是否存在循环依赖"
```

**验证方法**：
- 删除过度详细的步骤，在 5 个真实任务中对比质量
- 如果质量保持或提升，说明步骤是不必要的

---

### 维度 2：编码领域知识而非流程控制（优先级 P0）

**问题**：
Skill 应该是"领域专家的知识"，而不是"AI 助手的操作手册"。

**检查项**：
- [ ] Skill 是否编码了行业最佳实践？
- [ ] Skill 是否编码了团队的机构知识？
- [ ] Skill 是否编码了已知的反模式？
- [ ] 还是只是在告诉模型"先做 A，再做 B"？

**优化方向**：

**类型 1：领域知识型 Skill（持久有效）** ✅
```yaml
skill: spec-prd
domain_knowledge:
  authentication_best_practices:
    - OAuth 2.0 / OpenID Connect
    - 多因素认证（MFA）
    - 密码策略（NIST 指南）
  
  authentication_anti_patterns:
    - 明文存储密码
    - 简单的 MD5 哈希
    - 无失败锁定机制
  
  payment_best_practices:
    - 幂等性设计
    - 异步处理
    - 对账机制
  
  payment_anti_patterns:
    - 浮点数计算金额
    - 同步扣款
    - 无对账机制
```

**类型 2：流程控制型 Skill（容易过时）** ❌
```yaml
skill: spec-plan
steps:
  - step: 1
    action: "读取需求文档"
  - step: 2
    action: "询问用户确认"
  - step: 3
    action: "设计方案"
  - step: 4
    action: "输出计划"
```

**为什么领域知识型更好？**
- 模型能力提升后，流程控制型会限制模型自主决策
- 领域知识型提供判断依据，让模型在更高层面工作
- 领域知识不会因模型升级而贬值

---

### 维度 3：强化验证门而非指导步骤（优先级 P0）

**问题**：
Skill 告诉模型"怎么做"不如告诉模型"什么时候不能继续"。

**检查项**：
- [ ] Skill 是否定义了明确的验证门？
- [ ] 验证门是否可机械判定？
- [ ] 验证失败是否阻断流程？
- [ ] 还是只是"建议"模型验证？

**优化方向**：

**类型 1：建议型（弱）** ❌
```markdown
## spec-work

实施代码时，建议：
- 尽量编写测试
- 注意边界条件
- 考虑性能优化
```

**类型 2：验证门型（强）** ✅
```markdown
## spec-work

### 验证门（不通过禁止交付）

**门 1：Plan 验收条件落实**
- [ ] Plan 中的每个验收条件都已实现
- [ ] 每个验收条件都有对应的测试验证
- 不通过：返回 Plan，标注未落实的条件

**门 2：边界条件覆盖**
- [ ] 空输入处理
- [ ] 极值处理
- [ ] 并发场景处理
- 不通过：补充边界处理和测试

**门 3：代码质量基线**
- [ ] 无明显的代码坏味道
- [ ] 关键逻辑有注释
- [ ] 复杂函数已拆分
- 不通过：重构后再提交
```

**为什么验证门更好？**
- 模型可以自主决定"怎么做"，但必须通过验证
- 验证门是确定性约束，可机械判定
- 符合"Gate the exits, not the thinking"原则

---

### 维度 4：阶段衔接约束而非独立优化（优先级 P0）

**问题**：
单独优化每个 Skill 容易遗漏阶段衔接问题。

**检查项**：
- [ ] Skill 是否定义了对上游输出的期望？
- [ ] Skill 是否定义了对下游的输出承诺？
- [ ] 是否有机制防止信息丢失？
- [ ] 是否有机制防止信息重复？

**优化方向**：

**独立 Skill（容易断裂）** ❌
```markdown
## spec-plan
输出：技术方案

## spec-work
输入：Plan
输出：代码
```

**带衔接约束的 Skill（顺畅）** ✅
```markdown
## spec-plan

### 输出承诺
必须包含：
- 验收条件（具体、可测试）
- 边界场景（至少 3 个）
- 技术选型（具体到库/框架/版本）
- 数据结构（具体字段定义）

格式：
```yaml
acceptance_criteria:
  - condition: "..."
    test_method: "..."

boundary_cases:
  - case: "..."
    expected_behavior: "..."

tech_stack:
  - component: "..."
    choice: "库名@版本"
    reason: "..."
```

---

## spec-work

### 输入期望
必须从 Plan 中读取：
- 验收条件（逐条实现）
- 边界场景（逐个处理）
- 技术选型（严格遵守）
- 数据结构（精确实现）

### 衔接验证
- [ ] Plan 的每个验收条件都有对应实现
- [ ] Plan 的每个边界场景都有对应处理
- [ ] 技术选型与 Plan 一致
- 不一致：说明原因并更新 Plan
```

### 维度 5：紧凑性和可审计性（优先级 P1）

**问题**：
过长的 Skill 难以维护、难以审计、容易 prompt 漂移。

**业界共识**（SkillOpt, SkillMOO）：
- **紧凑优于冗长**：minimal, focused content
- **可审计**：bounded text edits, versioning
- **渐进式披露**：progressive disclosure

**检查项**：
- [ ] Skill 长度是否超过 2000 tokens？（过长）
- [ ] Skill 是否包含大量重复内容？
- [ ] Skill 是否可以拆分为多个更聚焦的 Skill？
- [ ] Skill 的每个部分是否都必要？

**优化方向**：

**类型 1：臃肿 Skill（难维护）** ❌
```markdown
## spec-plan (5000 tokens)

包含：
- 需求分析步骤
- 技术选型步骤
- 架构设计步骤
- 任务拆分步骤
- 风险评估步骤
- 成本估算步骤
- 时间规划步骤
- ...
```

**类型 2：聚焦 Skill（易维护）** ✅
```markdown
## spec-plan (800 tokens)

聚焦：技术方案设计
- 输入：PRD
- 输出：可执行方案 + 验收条件
- 验证门：方案可行性、边界覆盖

---

## spec-estimate (600 tokens)

聚焦：成本和时间估算
- 输入：Plan
- 输出：工作量估算
- 验证门：估算依据充分
```

### 维度 6：适应多模型能力分布（优先级 P1）

**问题**：
不同模型能力不同，Skill 应该适应能力分布。

**2026 年模型能力分布**：
```
Opus 5.5    ████████████ 最强，适合复杂推理
Sonnet 5.5  ███████████░ 接近 Opus，性价比高
Haiku 5.5   ████░░░░░░░░ 快速，适合简单任务
```

**检查项**：
- [ ] Skill 是否假设模型能力固定？
- [ ] Skill 是否可以根据模型能力调整？
- [ ] Skill 是否可以优雅降级？

**优化方向**：

**类型 1：固定假设（脆弱）** ❌
```markdown
## spec-code-review

必须执行深度分析（假设 Opus 级别能力）
```

**类型 2：能力自适应（健壮）** ✅
```markdown
## spec-code-review

### 基线审查（所有模型）
- [ ] 语法错误
- [ ] 明显的逻辑错误
- [ ] 代码坏味道

### 深度审查（Opus/Sonnet 5.5+）
- [ ] 架构合理性
- [ ] 行业反模式
- [ ] 长期演化性

### 审查策略
- 简单变更：基线审查
- 复杂变更：深度审查
- 如果当前模型能力不足，标注需要人工审查
```

### 维度 7：基于经验效用的自演化（优先级 P1）

**问题**：
Skill 应该基于真实任务的效果自动优化，而不是主观修改。

**业界方案**：
- **SkillOpt**：基于执行轨迹的自动优化
- **SkillRevise**：条件性 Skill 修订
- **独立验证门**：重新执行候选并测量经验效用

**检查项**：
- [ ] Skill 是否有明确的成功指标？
- [ ] Skill 是否有失败案例记录？
- [ ] Skill 修改是否基于真实任务反馈？
- [ ] 还是凭主观感觉修改？

**优化方向**：

**类型 1：主观修改（危险）** ❌
```markdown
修改记录：
- 2026-10-01: 感觉步骤太复杂，简化了
- 2026-10-05: 觉得应该加强验证，增加了检查
- 2026-10-10: 看起来不够详细，补充了说明
```

**类型 2：数据驱动修改（安全）** ✅
```markdown
修改记录：
- 2026-10-01: 基于 10 个任务的追踪，发现边界遗漏率 60%
  - 原因：Skill 未要求系统化检查边界
  - 修改：增加边界系统化检查清单
  - 验证：5 个新任务，边界遗漏率降至 10%
  - 结果：推广

- 2026-10-05: 基于 8 个任务的追踪，发现验收条件落实率 30%
  - 原因：Work 阶段未读取 Plan 的验收条件
  - 修改：增加输入期望和衔接验证
  - 验证：5 个新任务，落实率提升至 85%
  - 结果：推广
```

### 维度 8：上下文利用效率（优先级 P2）

**问题**：
长上下文窗口（1M tokens）带来新机遇，但也需要优化利用效率。

**趋势**：
- **从"压缩上下文"到"选择性加载"**
- **从"避免重复读取"到"智能缓存和复用"**
- **从"精简 prompt"到"按需展开"**

**检查项**：
- [ ] Skill 是否充分利用了长上下文能力？
- [ ] Skill 是否避免了不必要的上下文浪费？
- [ ] Skill 是否使用了渐进式披露？

**优化方向**：

**类型 1：固定加载（低效）** ❌
```markdown
## spec-plan

每次都读取：
- 所有 reference 文档（50 页）
- 所有示例（30 个）
- 所有最佳实践（100 条）
```

**类型 2：按需加载（高效）** ✅
```markdown
## spec-plan

### 基线上下文（必读）
- PRD
- 项目架构概览

### 按需上下文（根据任务类型）
- 认证需求 → 加载 authentication_best_practices
- 支付需求 → 加载 payment_best_practices
- 数据处理需求 → 加载 data_management_best_practices

### 渐进式披露
- 首次遇到问题 → 加载相关 reference
- 问题仍未解决 → 加载详细示例
- 复杂场景 → 加载完整指南
```

## Phase 0 需要增加的检查项

### 检查 1：过时约束识别（维度 1）

对每个 Skill：

## Phase 1 优化策略调整

### 原 Phase 1 策略

基于 Phase 0 数据，优化影响面大、严重程度高的 Skill。

### 新增策略（结合 8 大维度）

**对每个待优化 Skill，按以下顺序检查**：

1. **去除过时约束**（维度 1）
   - 删除过度详细的步骤
   - 删除不必要的强制约束
   - 在 5 个任务中验证质量保持

2. **补充领域知识**（维度 2）
   - 识别该 Skill 负责的领域
   - 补充行业最佳实践
   - 补充已知反模式
   - 提供判断依据而非操作步骤

3. **强化验证门**（维度 3）
   - 定义明确的验证门
   - 验证门可机械判定
   - 验证失败阻断流程

4. **定义衔接约束**（维度 4）
   - 定义输入期望
   - 定义输出承诺
   - 建立防信息丢失机制
   - 建立防信息重复机制

5. **精简内容**（维度 5）
   - 目标：<2000 tokens
   - 删除重复内容
   - 拆分过大 Skill

6. **建立演化机制**（维度 7）
   - 定义成功指标
   - 记录失败案例
   - 建立数据驱动修改流程

## 业界参考方案总结

### SkillOpt（微软，2026）

**核心原则**：
- Skill 作为可训练参数
- 基于执行轨迹自动优化
- 独立验证门（重新执行候选并测量经验效用）
- 有界文本编辑（避免不受控的 prompt 漂移）

**对我们的启发**：

## 总结

### 8 大优化维度

| 维度 | 核心思想 | 业界依据 |
|---|---|---|
| 1. 去模型能力补丁化 | 模型能力提升后，补丁型指令应移除 | Red Hat 2026 |
| 2. 编码领域知识 | 领域知识 > 流程控制 | Red Hat, SkillOpt |
| 3. 强化验证门 | Gate exits, not thinking | Harness Engineering |
| 4. 阶段衔接约束 | 防止信息丢失/重复 | Agentic Workflows |
| 5. 紧凑性和可审计性 | Minimal, focused, bounded edits | SkillOpt, SkillMOO |
| 6. 适应多模型能力 | 能力自适应和优雅降级 | Sonnet 5.5 趋势 |
| 7. 基于经验效用自演化 | 数据驱动修改 > 主观修改 | SkillOpt, SkillRevise |
| 8. 上下文利用效率 | 渐进式披露、按需加载 | 1M context 趋势 |
