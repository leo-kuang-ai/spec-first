## ⚠️ 发现的问题（6 个）

### 问题 1：Phase 0 可能遇到的执行困难 ⚠️⚠️

**问题描述**：
- 真实任务可能难以重建完整流程（记录不完整）
- 某些任务可能跨多个会话，上下文难以完整追溯
- 阻力点识别可能存在主观性

**影响**：可能导致 Phase 0 数据质量不足

**建议缓解措施**：
1. 优先选择记录完整的任务（有 Git、PR、文档）
2. 对于上下文不清晰的部分，标注为"无法确认"
3. 阻力点识别使用双人复核（如果可能）
4. 前 2-3 个任务作为试点，验证追踪方法

---

### 问题 2：11 个任务可能不足以覆盖所有场景 ⚠️

**问题描述**：
- 11 个任务可能无法覆盖所有 Skill 的使用场景
- 某些低频 Skill 可能在 11 个任务中未使用
- 样本量较小，统计结论可能有偏差

**影响**：Phase 0 后的优先级建议可能不全面

**建议缓解措施**：
1. Phase 0 报告中明确"仅基于 11 个任务"的局限性
2. 对于未覆盖的 Skill，标注为"无数据"
3. Phase 1 执行后，如果发现新问题，可以补充追踪更多任务
4. 考虑增加到 15-20 个任务（如果时间允许）

---

### 问题 3：三层指标可能难以精确度量 ⚠️

**问题描述**：
- "完全正确"的定义可能有主观性（5 项全 true）
- "返工"的边界不清晰（code review 修改算不算返工？）
- "用户介入"的定义可能有争议（哪些算介入？）

**影响**：指标度量可能不一致

**建议缓解措施**：
1. 在 Phase 0 执行前，明确定义每个指标的度量规则
2. 提供具体示例（哪些算返工，哪些不算）
3. 对于边界模糊的情况，采用保守原则（疑似问题算问题）
4. 度量规则写入 Phase 0 执行指南

---

### 问题 4：优化效果可能难以验证 ⚠️⚠️

**问题描述**：
- Phase 1 优化后，需要新的 5 个任务验证
- 5 个任务可能不足以证明改善（样本量小）
- 新任务与 Phase 0 任务可能不可比（复杂度不同）

**影响**：优化效果可能无法确信

**建议缓解措施**：
1. Phase 1 验证使用"A/B 对比"：
   - 选择 10 个新任务
   - 5 个使用优化前的 Skill
   - 5 个使用优化后的 Skill
   - 对比三层指标差异
2. 设置最小显著差异：改善至少 30% 才算有效
3. 长期跟踪：Phase 1 后继续监控后续 20-30 个任务

---

### 问题 5：资源投入可能超出预期 ⚠️⚠️⚠️

**问题描述**：
- Phase 0：36 小时
- 假设发现 5 个 P0 Skill 需要优化
- 每个 Skill：分析（4h）+ 设计（4h）+ 实施（8h）+ 验证（8h）= 24h
- **Phase 1 总计**：5 × 24h = 120 小时
- **Phase 0 + Phase 1 总计**：156 小时（~20 个工作日）

**影响**：实际投入可能远超预期

**建议缓解措施**：
1. Phase 0 完成后，根据数据严格控制 Phase 1 范围
2. 只优化影响面 >50% 且导致返工的 P0 Skill（可能只有 2-3 个）
3. Phase 1 分批执行：先做 1-2 个最重要的，验证后再做其他
4. 设置止损点：如果前 2 个优化无明显效果，暂停项目重新评估

---

### 问题 6：缺少"不优化"的退出条件 ⚠️

**问题描述**：
- 文档中未明确"Phase 0 后决定不优化"的条件
- 如果 Phase 0 发现当前质量已经很好（正确率 >90%），是否还要优化？
- 缺少项目成功/失败的明确定义

**影响**：可能陷入"为了优化而优化"

**建议缓解措施**：
1. 增加 Phase 0 的"退出条件"：
   - 如果端到端正确率已 >90%，返工率 <10%，用户介入 <3 次
   - 则项目成功完成，无需 Phase 1
2. 增加 Phase 1 的"止损条件"：
   - 如果前 2 个优化无明显改善（<30%）
   - 或优化后指标反而下降
   - 则暂停项目，重新评估方法论
3. 明确"成功"定义：达到三层指标目标，而非"优化了 X 个 Skill"

### 建议 2：细化指标度量规则

创建 `phase0-results/measurement-rules.md`：

```markdown
# Phase 0 指标度量规则

## Layer 3 指标度量

### 1. 端到端正确率

**度量公式**：完全正确的任务数 / 11

**"完全正确"定义**（5 项全 true）：
1. delivered: 有可运行的代码或功能
2. correct: 无 bug，功能符合需求
3. complete: 实现了所有需求功能点（PRD 中列出的）
4. tested: 有测试（单元测试、集成测试或手动测试记录）
5. documented: 有必要文档（至少有代码注释或 README）

**边界情况**：
- code review 发现 bug 后修复 → 仍算 correct: false（因为初次交付有 bug）
- 测试只覆盖主流程，未覆盖边界 → 算 tested: true（有测试即可）
- 文档只有代码注释，无单独文档 → 算 documented: true

### 2. 端到端返工率

**度量公式**：需要返工的任务数 / 11

**"返工"定义**：
- ✅ 算返工：因 bug、遗漏功能、测试不通过而修改代码
- ✅ 算返工：PR 合并后发现问题需要修复
- ❌ 不算返工：code review 中的代码风格调整
- ❌ 不算返工：正常的迭代增强（非遗漏）

### 3. 用户介入次数

**度量公式**：总介入次数 / 11

**"用户介入"定义**：
- ✅ 算介入：用户澄清需求（因为理解有偏差）
- ✅ 算介入：用户确认方案（因为有多种选择不确定）
- ✅ 算介入：用户修正错误（模型理解错了）
- ❌ 不算介入：用户最初提供需求（正常输入）
- ❌ 不算介入：用户 approve PR（正常流程）

## Layer 2 指标度量

### 1. 信息丢失率

**度量公式**：发生信息丢失的任务数 / 11

**识别方法**：
- 对比上游输出和下游输入
- 检查是否有"上游已确定，下游未使用"

### 2. 信息重复率

**度量公式**：发生信息重复的任务数 / 11

**识别方法**：
- 检查是否有"上游已确定，下游又询问"

### 3. 验收条件落实率

**度量公式**：已落实的验收条件数 / Plan 中的验收条件总数

**计算方法**：
- 在 Plan 阶段，统计明确列出的验收条件数（X）
- 在 Work 阶段，检查代码实现了多少个（Y）
- 落实率 = Y / X
```

## Phase 1 范围控制策略

### 严格筛选原则

**只优化满足以下所有条件的 Skill**：
1. Layer 3 有明确问题（导致返工）
2. Layer 2 有衔接问题（信息丢失/重复/验证缺失/衔接断裂）

4. 影响面 ≥50%（至少 6/11 个任务受影响）
5. 导致返工 ≥30%（至少 4/11 个任务因此返工）

### 优先级排序

**优先级 = 影响面 × 导致返工占比 × 100**

示例：
- Skill A：影响面 64%（7/11），导致返工 45%（5/11）
  - 优先级 = 0.64 × 0.45 × 100 = 28.8
- Skill B：影响面 55%（6/11），导致返工 36%（4/11）
  - 优先级 = 0.55 × 0.36 × 100 = 19.8

### 范围控制

**Phase 1 第一批**：
- 只优化优先级最高的 2 个 Skill
- 每个 Skill 预计 24 小时（分析 4h + 设计 4h + 实施 8h + 验证 8h）
- 总计：48 小时（6 个工作日）

**Phase 1 后续批次**：
- 前 2 个验证通过后，再考虑其他 Skill
- 每批最多 2 个 Skill

### 止损条件

**如果前 2 个 Skill 优化后**：
- 三层指标改善 <30%
- 或任何指标反而下降

**则**：暂停 Phase 1，召开复盘会议，重新评估方法论
