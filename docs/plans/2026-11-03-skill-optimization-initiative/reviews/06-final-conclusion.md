## 最终判断

**这项优化值得推进，流程导向和质量优先的目标成立；当前文档已形成有价值的源码基线，但尚未形成一致、证据充分、可直接整体实施的方案。**

建议继续开展范围明确的诊断与验证，处理已确认的独立缺陷；暂不将新增 Contract/Protocol 和实施路线图作为全面建设依据。当前最需要补齐的是**真实失败证据、根因定位和改动效果验证**。

## 一、项目目标正确，应保留三个观察层面

“让需求到可信交付的整条研发链路更顺畅、更自主、更可靠”，符合 spec-first 缩短可信变更周期、提高有效研发产出的使命。

三个观察层面各有明确用途：

| 观察层面 | 主要问题 | 用途 |
|---|---|---|
| 单个 Skill | 指令是否清晰、必要、充分？ | 定位局部机制问题 |
| 阶段衔接 | 需求、决策、验收和证据是否正确传递？ | 发现跨阶段遗漏与重复 |
| 端到端结果 | 交付是否正确，返工、等待和用户纠正是否减少？ | 判断改进是否产生实际价值 |

它们应作为互补的诊断视角，不能规定成必须成立的因果链。确定性的局部缺陷可以直接修复，不必先证明跨阶段问题或凑齐 11 个历史任务。

项目范围应聚焦现有研发主链路及其必要支撑。新增发布编排、生产运维等能力需要独立论证；不能仅因缺少同名 Skill，就认定 spec-first 存在产品缺口。

## 三、实施前必须纠正的核心问题

### 1. 根因尚未确认，不能直接认定需要新增协议

[协议文档](08-skill-contract-protocol.md)将“缺少明确的 Contract 和 Protocol”认定为根本原因，但源码基线已经记录了需求保留、交接、验收、审查和验证收尾约定。

真实问题可能发生在不同位置：

| 失败位置 | 对应处理方向 |
|---|---|
| 规则没有定义 | 补充必要约定 |
| 规则存在但未加载 | 修复发现、加载或上下文传递 |
| 已加载但执行错误 | 调整指令、工具支持或任务组织 |
| 执行结果有误但验证未发现 | 改进检查方法与证据要求 |
| 环境、模型或外部依赖失败 | 在相应边界处理 |

应通过具体任务确定失败位置。已有契约不代表机制有效；存在失败也不自动意味着需要更多契约。

### 2. 新协议缺少与现有输入路径、产物和消费者的兼容设计

新协议要求 Plan 接收 PRD，Review 接收完整上游材料，并提出新的 YAML、FR/AC 标识和输出结构。当前 [Plan intake](../../../skills/spec-plan/references/intake.md)支持直接需求输入，已有 unified plan 及稳定标识；[Review](../../../skills/spec-code-review/SKILL.md)也允许独立审查。

如果将新要求作为全局规则实施，会与这些合法路径冲突。若限定适用场景并提供兼容方式，则可以避免冲突。

实施设计必须明确：

- 哪些任务适用，哪些任务可以跳过。
- 哪个现有产物是唯一事实源，哪些内容只是派生视图。
- 新字段由谁生产、谁消费、如何验证。
- 旧产物如何兼容，失败如何降级，变更如何回滚。
- source 变化如何投射到相关宿主。

优先复用或扩展现有约定，新增平行 schema 必须有现有机制无法承担的明确理由。修改应落在 source，generated runtime 通过生成机制更新。

### 3. 结构覆盖与语义正确必须分开

协议已有需求 ID 集合差检查，可以发现部分需求引用遗漏，不能将其描述成只有数量检查。

但以下条件仍不能证明业务正确：

- 验收数量达到要求。
- 所有需求 ID 都有关联。
- 状态填写为 `implemented`。
- 证据字段非空。
- 当前测试全部通过。

它们分别证明形式覆盖、声明存在或特定检查通过。验收是否表达正确、边界是否充分、证据是否支持完成，仍需要语义判断。

因此，应保留有价值的结构检查，取消缺乏依据的通用数量门槛，例如所有需求都必须具有“空输入、单条、多条”三个边界。边界应来自具体业务、风险和系统行为。

脚本负责结构、引用、版本、命令结果和证据新鲜度；LLM／审查者负责语义充分性。自动检查可以支撑质量判断，不能直接把“测试通过”提升为“整体正确”。

### 4. 自动门禁尚缺真实执行与阻断机制

文档提出“Skill 完成时自动运行”“失败阻止提交”，但伪代码和 Skill 指令本身不能证明宿主存在对应的强制能力。

需要明确触发位置、执行者、失败传播方式、受控出口和宿主差异。没有可验证的阻断能力时，应如实标为约定执行或降级状态。

这不否定自动化检查的价值，而是要求准确区分：**已经实现的硬门禁、依赖模型遵循的约定，以及尚待实施的设计。**

### 5. 收益和 ROI 目前不能用于投资或推广决策

[实施路线图](09-implementation-roadmap.md)将示例中的返工率等数字列为基线，并据此计算改善幅度和 ROI。当前没有真实任务数据支持这些基线；不同口径的返工率、误判风险和工具收益也不能直接相加。

这些内容应改为明确的假设或情景估算，并写出来源和条件。实际投入决策应考虑：

- 减少了多少纠错与返工时间。
- 是否提高必要需求和验证的完成率。
- 增加了多少执行、审查和维护成本。
- 改善在哪些任务、模型和宿主条件下成立。

目标可以先提出，收益不能提前认定。

### 6. 实验要求应与结论范围匹配

11 个任务适合诊断，5 个案例可以发现缺陷、验证局部修改，但不能自动证明总体稳定收益。“改善超过 30%”也不等于统计显著。

同时，不应因样本少而阻止局部改进。适当的验证强度是：

- 确定性缺陷：复现、针对性修复和回归检查。
- 行为优化：固定任务、源码、模型、宿主和工具条件，进行可比实验。
- 扩大推广：补充独立任务和相应环境中的验证。

样本应包含失败、停滞和被放弃的任务，避免只选已完成任务。调优案例与独立验证案例应分开。

指标也需明确口径：必要澄清和授权确认不能与无效重复询问混算；任务完成时间要区分实际工作与等待；聚合正确率目标不能允许单个任务遗漏必要需求后仍宣称完成。

## 四、文档应先收敛权威关系，避免继续叠加建议

审查范围内同时存在主方案、执行清单、多份审查、优化建议和新路线图。它们在样本选择、投入、优先级和实施前提上不完全一致。审查时 README 顶部三个执行链接已经失效，也说明重组后的导航检查没有闭环。

建议明确：

- 一个当前有效的执行主文档。
- 源码基线与证据目录负责承载已确认事实。
- 候选清单保留待验证假设。
- 历史审查与方案作为参考，不自动产生执行优先级。

已有“10/10”“专家认可”“可执行”等评价不能替代验收证据。[趋势文档](05-optimization-dimensions-with-trends.md)中的外部模型指标和研究结论尚未核验，也不能成为删除现有约束的直接依据。

## 五、建议采用的最小落地顺序

1. **统一当前执行口径。** 修正文档冲突、失效链接和示例数据的身份，明确已确认事实与待验证假设。
2. **选择一个高价值失败假设。** 可以从基线已有的长需求交接、任务包新鲜度、审查后复验等场景中选择，不预设必须改哪个 Skill。
3. **运行当前版本并留存证据。** 记录输入与源码版本、关键上下文加载、实际产物、失败位置、验证结果和限制。
4. **修改拥有根因的最小位置。** 优先复用现有能力；未发现问题时允许保持现状。
5. **验证目标问题与相邻正常路径。** 同时检查直接输入、小任务、可选 Tasks 等路径是否被误伤。
6. **根据结果决定扩大、保留、调整或回滚。** 新增协议、工具和 Skill 都应由具体证据驱动。

首轮完成标准应是：**确认或排除一个高价值失败假设；若实施修改，证明对应问题得到处理，并检查相邻路径没有出现已知回归。** 结论仅覆盖实际验证范围。

项目负责人应继续承担完整目标和证据责任，但不以修改 Skill 数量、增加协议数量或文档数量衡量进展。

**最终建议：推进这项优化，先统一方案并验证具体问题；已有确定性缺陷及时处理，新增框架与整体收益承诺等待相应证据。**
