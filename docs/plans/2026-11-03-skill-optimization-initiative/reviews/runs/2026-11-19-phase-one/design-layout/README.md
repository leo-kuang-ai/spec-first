# 传统技术方案目录试点：内容不变，比较能否找到答案

先读[传统目录版](notification-design-review.md)。同一个技术问题，在[原目录中文版](notification-control.md)使用「产品契约、规划契约、实施单元」查找，在传统目录版使用「现状、总体设计、详细设计、兼容、验收、上线」查找。两份都是评审材料，不是可执行计划。两份试读稿保持不变；其来源是 `9250dcdec` 的通知计划。[现行通知计划](../../../../../../../skills/spec-plan/evals/fixtures/consumer-replay/implementation-ready.md)已补充读取失败验例，不应替换任一份盲读材料。

**反馈与归因。** 用户本轮明确指出，不熟悉的是技术方案的组织方式，不只是摘要措辞。这是用户对问题的澄清；以下一次重排尚不能证明已解决。两份稿用同一份中文译写，补充的来源限制也完全相同，删除目录、标题和文件头后，13 个正文段落（含列表项）按内容比对完全一致。它是目录分组与顺序的对照，不是原版英文对中文版、也不是新稿少写了细节。两稿均未补写生产实现、发布参数及新的验收用例。

## 怎么使用

明确请求「把这份方案按传统目录写成给研发评审的 Markdown 稿」时，`spec-plan` 源码入口加载[人读模板](../../../../../../../skills/spec-plan/references/technical-design-review.md)；不额外生成执行计划。需要正式拆任务、实施或流水线交接时，仍使用统一计划。文档评审读取方根据人读稿的类型和正文采用已有技术设计审查视角，不把它误判为 PRD，不要求为了交接补空标题。当前未刷新宿主，本段说明源码合同，并非宣称安装态已经切换。

## 怎么验可读性

把[题卡](reader-task.md)和其中一份稿单独交给未参与编写的研发或测试人员，**不要给本页**。分别安排阅读两种布局，避免同一人先看答案再看另一个版本；记录所见版本、角色、原始回答、卡点与澄清次数。不以作者自查或模型代答代替读者。单个读者的反馈支持定位卡点，不足以推广到所有团队。

| 题目 | 核对答案用的依据（不给受试者） |
|---|---|
| 开发改哪里 | 新增投递协调逻辑，沿用事件接入、偏好查询、消息发送、结果记录。不得新建订阅权威或策略。没有生产文件名。 |
| 能不能验 | 禁用和读取失败都应零投递；当前验例只明列禁用，遗漏「模拟偏好读取失败后核对实际发送次数」。在规则段找到预期结果不能替代在测试中找到用例。 |
| 客服查什么 | 查同一事件、所选渠道、结果与重复处置原因，核对实际累计发送次数；投递记录不是订阅状态。 |
| 能否上线 | 按需扩展记录，再接通发送链路，验证正常和重试/变更流程，才启用；灰度阈值、回退手段均未知。 |

## 兼容与放行条件

本轮本地验证：规划合同、质量、引用、消费回放与交接判分 5 套 79 项，文档评审合同 1 套 47 项，合计 126 项通过；仓库 `lint:skill-entrypoints` 通过。系统 `skill-creator` 的通用 `quick_validate.py` 对两个包均拒绝已有的 `argument-hint` 字段；基线已有此字段，本次未改它。未派发独立模型或刷新宿主，真实读者结果尚未采集。

| 已验证的事实 | 可以判断什么 |
|---|---|
| 对原始计划运行 `spec-first tasks hash` 退出 0，对两份带 `status: draft` 的 Markdown 样稿均退出 2、`tasks-source-plan-non-active`。 | 正确生成的草稿不能经此 CLI 编译入口冒充可执行输入。不是所有宿主的执行拦截；去掉状态的旧式文件可能走另一分支，不应剥掉文件头。 |
| `tests/unit/spec-plan-handoff-judge.test.js` 中保留相同的可执行元数据、返回包和轨迹，仅把标题换成传统目录；原生成判分器先接受旧结构，再因缺 `Goal Capsule` 拒绝新结构。 | 改标题确实会破坏这条读取链，不是翻译所有旧标题就能兼容。判分器检查章节不能证明读者理解。 |
| 已复跑既有 Markdown/HTML、需求稿/实施稿的消费合同测试。 | 旧格式未因本次试点改变。新七章稿没有宣布能供 Tasks、Work 或自动交接执行；没有将 Markdown 的结论外推到 HTML。 |

**切换默认前，按以下顺序推进：**（1）拿到实际读者作答，定位新结构是否减少错找，并确认没有把「没写」答成「已经验证」；（2）对真实消费位置逐一解耦标题与章节身份：`spec-write-tasks/SKILL.md` 的来源提取、`spec-work/references/work-intake.md` 的章节定位、`spec-code-review/references/intent-and-plan.md` 的完整性比较、`spec-plan/references/plan-handoff.md` 的 goal 交接以及判分器生成源。旧结构与候选结构应提取相同的需求、约束、单元与验证义务，缺项应指出缺项，不能回传空成功；（3）在 Markdown 和 HTML 分别测旧稿仍可读、需求稿不能执行、上游需求原文保留，并验证已有任务包的来源身份；通过后才修改默认生成结构。不批量重写历史计划或重绑旧哈希。当前只能推荐**人读评审稿试用**。
