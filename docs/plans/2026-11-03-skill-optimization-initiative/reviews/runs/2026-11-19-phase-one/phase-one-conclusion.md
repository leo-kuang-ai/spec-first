## 技术方案与需求文档的可读性

**审查后的进展（不回写冻结结论）：** 用户已澄清，技术方案难读首先是因为目录不符合研发习惯。已制作[传统技术方案样稿](design-layout/notification-design-review.md)及[同正文对照和验证记录](design-layout/README.md)。此后对 `spec-plan`、`spec-doc-review` 的改动属于新增试点，不计入第 87 次的 412 项或 15 份变更。

首屏最有用的不是「涉及哪些文件」，而是「用户以前怎么做、这次从哪里做、什么不能变、用哪个例子区分」。例如历史方案中的两项实际变化是**旧版安装用户更可能在原有命令看到升级提醒，安装尾部增加来源指引**，不是「重做 doctor」或「自动升级」。这能从成品找到；读者本人能否找到并未观察。

对可实施设计用九项核查，不用标题计分。下表按同一九问读[历史成品](../../../../2026-06-01-001-feat-install-version-visibility-plan.md)和通知夹具；两种通知格式分别检查，其他限定用途的文档不冒充完整设计。

| 九问 | 安装提醒（历史 Markdown） | 通知投递（实施版 Markdown / HTML） |
|---|---|---|
| 目标和边界 | 旧安装用户看不到提醒；不新增自动升级或触发命令。 | 两版均要求按当前偏好投递，不另建订阅状态。 |
| 现状和依据 | 第 43–51 行定位超时、接入点与当时现场测量；不是今天的网络基线。 | 两版点名事件、偏好、投递职责，未给可复核的真实生产调用点。 |
| 具体改动 | 延长等待、允许覆盖、补安装引导；帮助与版本查询不变。 | 两版都能定位新增编排与投递证据，HTML 单元可导航、关键决定无专属锚点。 |
| 路径与取舍 | 复用现有提醒，失败静默，避免重复检查。 | 用事件标识去重，组合已有能力；不把策略塞进编排层。 |
| 接口与兼容 | 环境变量非法回退；无存储协议变化，须保留主命令出口。 | 同一事件重试语义明确，证据不是订阅权威；不凭夹具确认现网接口。 |
| 质量与异常 | 更长等待是代价，CI 可调小；需测查询失败后的主命令。 | 两版都声明读取失败不发送，正好与成功读到禁用构成不同条件。 |
| 顺序与集成 | U1、U2 独立，分别落到运行提醒和安装尾部。 | 先完善证据记录，再组合投递，最后整链验证。 |
| 验收 | 原需求 R3 要求原命令照常完成、退出码不变；第 122 行的函数断言不足。 | 两版都漏读取失败的实际验证。重试期望一次，禁用及读取失败均应零次，需分例。 |
| 发布与恢复 | 无格式迁移；超时可配置，安装文案随包检查。历史文档不证明实际发布。 | 写明验证后再启用；真实开关、上线观察及恢复未提供，不能据此放行生产。 |

其他包内文本按本来用途判断：月汇总 Markdown 指出入口与无数据情形，但只验 JSON 形状不能证明金额正确；同名 HTML 只有单元描述，不继承 Markdown 的验法。Work 的现役月份夹具说明可选过滤及无参旧路径，未定非法输入行为；Tasks 的轻量月份方案则明确非法格式返回 400，不能相互补全。已结束方案只验证拒绝重开，不凭「已上线」验收。订单导入和跨租户导出是需求稿：前者上限在连续失败时仍有歧义，后者把跨租户资格留给产品是正确的，不扣缺少架构图。积分 PRD 有已定比例与未定过期时点；导出 PRD 有明确的编码阻塞；同一就绪措辞不能覆盖两者。双格式需求夹具不能因为没有实施单元被扣分。详细文本位置见台账第 3、12–14、24–29、45–48 次。均无目标读者独立作答。
