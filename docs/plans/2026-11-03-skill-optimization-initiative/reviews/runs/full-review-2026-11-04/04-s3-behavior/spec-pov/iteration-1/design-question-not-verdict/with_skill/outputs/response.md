## 裁决：表单和列表放**同一个页面**

**结论先行：** 对 MiniLedger 现在这个阶段，同页是明显更优解——记一笔账后立刻在列表里看到它出现，是这类应用的核心循环，同页一次交互完成；分开页面则给每一次录入都加一次页面跳转。

**项目事实（已验证，引用）：**
- 项目目前**没有任何前端**——唯一源文件是 `src/server.js`，只有两个 JSON API（`src/server.js:16-18` 的 `GET /entries` 只返回 JSON）。这是净新增 UI，集成点就是加一个 `GET /` 页面路由。
- 数据是单用户内存数组，条目仅 4 个字段 `{id, amount, note, ts}`（`src/server.js:3,11`）——列表短期内不会复杂到需要独立页面。
- README 自己声明的痛点就是**录入摩擦**："adding an entry requires five fields typed by hand"（`README.md:8`）。分页设计会把额外导航成本精确加在这个已声明的痛点上。
- 项目约定是零依赖、单文件极简风（`package.json` 无任何依赖）——同页只需一个 HTML 路由；分页需要第二个路由加导航机制，超出这个体量。

**候选集处置（全部冻结候选）：**
- **同页** — 推荐，理由如上。
- **分开页面** — 否决。它成立的触发条件（表单字段很多、列表需要筛选/分页、录入与对账是不同用户的不同任务）在当前代码里一个都不成立。
- **维持现状（无 UI）** — 不作为选项，本问题预设要建 UI。

**条件（何时翻案）：** 当 README 里点名的 categories / summary view 真正落地、或列表需要筛选分页时，把"历史/汇总"拆成独立页面才开始划算。到时再拆是一次有界重构——这正是本题属于 Tier 1 两向门的原因：现在选错的回退成本很低。

**交接（一句话）：** 这个选择已经足够明确，需要的话我可以下一步直接给出同页版的最小实现方案。
