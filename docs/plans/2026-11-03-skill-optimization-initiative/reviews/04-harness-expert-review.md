## 📋 审查框架

### Harness 核心理念

1. **"Gate the exits, not the thinking"**（门在出口，不在思考）
2. **验证门是第一公民**
3. **可观测性优于预防性控制**
4. **快速失败优于慢速成功**
5. **数据驱动优于经验驱动**

---

## ✅ 契合的最佳实践（8 个）

### 1. ✅ 验证门设计 - Layer 3 作为最终门 (9/10)

**Harness 最佳实践**：
> "验证门应该在输出端，而非流程中。让 AI 自由探索，在交付前验证质量。"

**方案体现**：
```yaml
# 方案设计
Layer 3（端到端质量）作为最终验证门：
  - 端到端正确率 >90%
  - 端到端返工率 <10%
  - 用户介入次数 <3 次/任务

# 这是典型的 "gate the exits" 模式
```

**契合度**：9/10

**优点**：
- ✅ 以最终交付质量为标准
- ✅ 不在中间流程设置过多约束
- ✅ 符合 Harness "gate the exits" 理念

**改进建议**：
- 可以更明确地表述"验证门"概念
- 增加自动化验证门的实施细节

---

### 2. ✅ 三层观测体系 - Layer 1/2/3 (10/10)

**Harness 最佳实践**：
> "建立分层观测体系：结果层 → 过程层 → 细节层，从结果追溯根因。"

**方案体现**：
```yaml
Layer 3: 端到端交付质量（结果层）
  ↓ 如果有问题
Layer 2: 阶段衔接顺畅度（过程层）
  ↓ 如果有问题
Layer 1: 单个 Skill 有效性（细节层）
```

**契合度**：10/10

**优点**：
- ✅ 完美体现 Harness 分层观测理念
- ✅ 从结果追溯根因，而非预设问题
- ✅ 符合 "可观测性优于预防性控制"

---

### 3. ✅ 数据驱动决策 - Phase 0 先行 (10/10)

**Harness 最佳实践**：
> "优化决策必须基于真实数据，而非假设或经验。先观测，后优化。"

**方案体现**：
```yaml
Phase 0: 真实任务追踪（观测）
  ↓ 收集数据
决策: 优化哪些 Skill（基于数据）
  ↓ 只优化有证据支持的
Phase 1: 执行优化
```

**契合度**：10/10

**优点**：
- ✅ Phase 0 先行，不预设优化范围
- ✅ 所有候选项 pending Phase 0 数据
- ✅ 完全符合 Harness "数据驱动" 理念

---

### 4. ✅ 快速验证 - 最小样本先行 (9/10)

**Harness 最佳实践**：
> "快速失败优于慢速成功。用最小成本验证假设，避免大规模投入后发现问题。"

**方案体现**（优化方案）：
```yaml
阶段 1: 最小样本（5 个任务，10 小时）
  ↓ 决策点：是否继续
阶段 2: 标准样本（11 个任务，20 小时）
  ↓ 决策点：是否扩展
阶段 3: 扩展样本（15-20 个任务，可选）
```

**契合度**：9/10

**优点**：
- ✅ 分阶段验证，快速失败
- ✅ 避免一次性投入 36 小时后发现方法不可行
- ✅ 符合 Harness "快速验证" 理念

**优点**：

### 6. ✅ 验证优先 - Layer 2 验证缺失识别 (10/10)

**Harness 最佳实践**：

```yaml
四类阻力点之一：验证缺失

  - 典型场景：
    - Work 声称代码完成，但未运行测试
    - Work 声称处理边界，但未验证边界
  - 追踪方法：检查是否有测试记录
```

**契合度**：10/10

**优点**：
- ✅ 将"验证缺失"作为核心阻力点类型
- ✅ 明确定义和识别方法
- ✅ 完全符合 Harness "验证优先" 理念

### 7. ✅ 最小约束原则 - Skill 复杂度预算 (10/10)

**Harness 最佳实践**：
> "给 AI 最小必要约束，而非最大可能约束。过度约束限制创造性。"

**方案体现**（优化方案）：
```yaml
Skill 复杂度预算：
  - 原则：用最少的约束达到目标
  - 优化方向：优先精简，而非增加
  - 验证方法：A/B 对比（简化版 vs 详细版）
  - 如果简化版效果相同，使用简化版
```

**契合度**：10/10

**优点**：
- ✅ 明确提出"最小约束"原则
- ✅ 挑战"更详细就更好"的假设
- ✅ 完美契合 Harness 理念

**这是方案中最有 Harness 专家思维的部分！**

### 8. ✅ 问题归因 - 4 类根因分析 (10/10)

**Harness 最佳实践**：
> "区分 Skill 问题、模型能力、外部因素。不要把所有问题都归因为 Skill。"

**方案体现**（优化方案）：
```yaml
4 类根因归因：
  1. Skill 问题（可优化）
  2. 模型能力问题（需升级模型）
  3. 外部因素（不可控）
  4. 工具链问题（需增加工具）

优化决策：
  - 只优化归因为"Skill 问题"的项
  - 避免把模型能力问题误判为 Skill 问题
```

**契合度**：10/10

**优点**：
- ✅ 区分不同根因类型
- ✅ 避免"一刀切"归因为 Skill
- ✅ 完全符合 Harness "精准归因" 理念

**影响**：中等

**建议补充**：
```markdown
## 自动化验证门设计

### 验证门 1：代码正确性
- 触发时机：Work 完成后
- 自动检查：
  1. 运行单元测试（pytest / jest）
  2. 运行集成测试
  3. 静态代码分析（pylint / eslint）
- 判断标准：所有测试通过 → correct: true

### 验证门 2：需求完整性
- 触发时机：Work 完成后
- 自动检查：
  1. 对比 PRD 需求列表
  2. 检查每个功能点是否实现
- 判断标准：100% 覆盖 → complete: true

### 验证门 3：测试覆盖
- 触发时机：Work 完成后
- 自动检查：
  1. 运行覆盖率工具（coverage.py）
  2. 检查是否 >80%
- 判断标准：覆盖率达标 → tested: true
```

### 2. ❌ Skill Contract（Skill 合同）机制 (3/10)

**Harness 最佳实践**：
> "每个 Skill 应该有明确的 contract：输入、输出、验证门、失败处理。"

**方案缺失**：
```yaml
# 方案追踪了 Skill 的输入输出
stage: 3_planning
  skill_used: spec-plan
  input: "PRD"
  output: "Plan 文档"

# 但未定义 Skill Contract：
- spec-plan 的输入格式要求？
- spec-plan 的输出格式保证？
- spec-plan 的验证门？
- spec-plan 失败时如何处理？
```

**影响**：高

**建议补充**：
```markdown
## Skill Contract 定义

### spec-plan Contract

**输入 Contract**：
- 必须：PRD 文档路径
- 可选：技术栈约束
- 格式：Markdown 或 YAML

**输出 Contract**：
- 必须包含：技术方案、验收条件、实施步骤
- 格式：Markdown，结构化
- 存放位置：docs/plans/

**验证门**：
1. 验收条件数量 ≥3
2. 技术方案明确（不能是"使用 Redis"这种抽象描述）
3. 实施步骤可执行

**失败处理**：
- 如果验证门不通过，重新生成
- 最多重试 2 次
- 仍失败则人工介入
```

### 3. ❌ Skill 间协议（Inter-Skill Protocol）(2/10)

**Harness 最佳实践**：
> "Skill 之间的数据传递应该有明确协议，避免隐式依赖。"

**方案缺失**：
```yaml
# 方案识别了"衔接断裂"
stage: 3_planning
  output: "使用 Redis 缓存"（抽象）
    ↓ [衔接断裂]
stage: 4_implementation
  期望输入: 具体的 Redis 配置

# 但未定义协议：
- PRD → Plan 的数据传递协议？
- Plan → Work 的数据传递协议？
- 如何强制执行协议？
```

**影响**：高

**建议补充**：
```markdown
## Inter-Skill Protocol 定义

### Protocol 1：PRD → Plan

**PRD 必须提供**：
1. 功能需求列表（结构化）
2. 边界条件列表（空输入、单页、多页等）
3. 验收标准（可测试的）

**Plan 必须消费**：
1. 检查清单：PRD 的每个需求是否在 Plan 中体现
2. 边界条件：Plan 的方案是否考虑了所有边界
3. 验收标准：Plan 的验收条件是否覆盖 PRD 的验收标准

**协议执行**：
- spec-plan 开始时，自动检查 PRD 是否符合协议
- spec-plan 完成时，自动检查是否消费了所有 PRD 信息

### Protocol 2：Plan → Work

**Plan 必须提供**：
1. 具体技术方案（不能是抽象描述）
   - ✅ "使用 Redis 作为缓存，配置 maxmemory 1GB，过期策略 LRU"
   - ❌ "使用 Redis 缓存"
2. 验收条件列表（结构化）
3. 实施步骤（可执行）

**Work 必须消费**：
1. 实现所有验收条件
2. 遵循技术方案
3. 完成所有实施步骤

**协议执行**：
- spec-work 开始时，自动检查 Plan 是否符合协议
- spec-work 完成时，自动检查是否实现了所有验收条件
```

## 🎯 Harness 专家的核心建议

### 建议 1：补充 Skill Contract（P0，关键）

**为什么关键**：
- Skill Contract 是 Harness 的基石
- 定义了 Skill 的输入/输出/验证门
- 避免隐式依赖和模糊接口

**实施建议**：
1. 为主链路的 5 个 Skill 定义 Contract
   - spec-prd
   - spec-plan
   - spec-work
   - spec-code-review
   - spec-commit-push-pr

2. Contract 包含：
   - 输入格式和要求
   - 输出格式和保证
   - 验证门定义
   - 失败处理策略

3. 在 Phase 0 追踪时，检查 Contract 是否被遵守

---

### 建议 2：定义 Inter-Skill Protocol（P0，关键）

**为什么关键**：
- 方案已识别"衔接断裂"是高频问题
- Protocol 是解决衔接断裂的根本方法
- 强制 Skill 间的数据传递标准化

**实施建议**：
1. 定义 3 个关键 Protocol：
   - PRD → Plan
   - Plan → Work
   - Work → Review

2. Protocol 包含：
   - 上游必须提供什么
   - 下游必须消费什么
   - 如何验证 Protocol 被遵守

3. 在 Skill 中增加 Protocol 检查：
   ```python
   # spec-plan 开始时
   check_prd_protocol(prd_path)
   
   # spec-plan 完成时
   check_plan_output_protocol(plan_path)
   ```

---

### 建议 3：引入自动化验证门（P1，重要）

**为什么重要**：
- 方案定义了很好的验证标准
- 但缺少自动化执行
- 人工判断容易不一致

**实施建议**：
1. 为 Layer 3 的 5 项指标设计自动检查：
   - delivered: 检查是否有代码/PR
   - correct: 自动运行测试
   - complete: 对比需求列表
   - tested: 检查测试覆盖率
   - documented: 检查文档存在性

2. 在 spec-work 完成时自动触发验证门

3. 验证门失败时，阻止提交并给出反馈

---

### 建议 4：Phase 0 扩展 - Harness 能力评估（P1）

**为什么重要**：
- 当前 Phase 0 只评估 Skill
- 但问题可能在 Harness 能力不足
- 应该同时评估 Harness

**实施建议**：
在 Phase 0 追踪时，增加维度：
```yaml
harness_capability_issues:
  - issue: "缺少自动测试运行工具"
```
