## 🔍 GLM-5.3 执行建议

### 发挥 GLM-5.3 的优势

**1. 代码理解能力**
```bash
# 让 GLM-5.3 深度分析代码变更
# 在 zcode 中查看 Git diff
git show [commit-hash]

# 要求 GLM-5.3：
# - 理解这次变更的意图
# - 识别可能的问题
# - 判断是否符合 Skill Contract
```

**2. 多轮对话能力**
```
利用 GLM-5.3 的上下文理解：
- 第1轮：概述任务背景
- 第2轮：详细追踪流程
- 第3轮：深入分析阻力点
- 第4轮：归因根本原因
- 第5轮：提出优化建议
```

**3. 推理能力**
```
要求 GLM-5.3 进行因果推理：
- 现象 → 直接原因 → 根本原因
- 不要停留在表面现象
- 挖掘深层设计问题
```

---

### 注意 GLM-5.3 的局限

**1. 可能的幻觉（Hallucination）**
```bash
⚠️ 验证关键信息
- 检查 GLM-5.3 提到的代码行号是否真实存在
- 验证归因分析是否有证据支持
- 对比 Git 历史确认时间线

# 验证命令
git show [commit-hash] | grep "关键代码"
```

**2. Contract/Protocol 理解**
```bash
⚠️ 明确传达 Contract 定义
- 每次分析前，先给 GLM-5.3 看相关的 Contract
- 明确验证标准
- 不要假设 GLM-5.3 记住了所有 Contract

# 提供 Contract
cat core/08-skill-contract-protocol.md
```

**3. 归因倾向**
```bash
⚠️ 警惕归因偏见
- GLM-5.3 可能倾向于某类归因
- 要求提供证据支持每个归因
- 使用 4 类根因强制分类
- 多角度验证
```

## 📝 GLM-5.3 特定 Prompt 建议

### 任务追踪 Prompt

```
你现在是一个经验丰富的软件工程师，正在追踪一个真实任务的完整流程。

任务信息：
- PR链接：[链接]
- 完成日期：[日期]
- 任务描述：[描述]

请你：
1. 分析这个任务的完整流程（需求→PRD→Plan→Work→Review→提交）
2. 识别每个阶段使用的Skill
3. 识别阻力点（信息丢失、信息重复、验证缺失、衔接断裂）
4. 分析根本原因（4类：Skill问题、模型能力、外部因素、工具链）

重要：
- 基于实际Git历史和PR讨论，不要臆测
- 每个结论都要有证据支持
- 明确区分"直接原因"和"根本原因"
```

## 🔧 遇到问题怎么办？

### 常见问题及解决

**问题1：GLM-5.3 给出的归因过于表面**
```
解决方法：
1. 使用"5个为什么"技术
   - 为什么会X？→ 因为Y
   - 为什么会Y？→ 因为Z
   - ...（继续追问5次）

2. 要求对比设计意图
   - Skill设计时想解决什么？
   - 实际表现如何？
   - 差距在哪里？

3. 强制使用4类根因
   - 明确要求归入4类之一
   - 不接受模糊归因
```

---

**问题2：追踪耗时超出预期**
```
解决方法：
1. 简化追踪模板
   - 只记录核心信息
   - 减少可选字段
   - 聚焦高频问题

2. 批量处理
   - 先收集所有Git历史
   - 再统一分析
   - 避免重复工作

3. 调整任务选择
   - 选择信息更完整的任务
   - 避免信息缺失的任务
```

---

**问题3：数据质量不足**
```
解决方法：
1. 增加验证环节
   - 每个任务完成后自我验证
   - 使用check-quality.sh检查
   - 人工审查关键归因

2. 交叉验证
   - 多个任务的相同问题
   - 不同视角分析
   - 寻找矛盾之处

3. 及时调整
   - Week 1中期评审
   - 发现问题立即调整
   - 不要等到最后
```
