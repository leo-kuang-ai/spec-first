# 决策权限矩阵

**文档版本**：v1.0  
**创建日期**：2026-11-03  
**目的**：明确项目各阶段的决策权限，避免决策延误和混乱

---

## 🎯 核心原则

1. **分级决策**：不同级别的决策由相应层级的人员做出
2. **明确责任**：每个决策都有明确的负责人（Accountable）
3. **透明沟通**：所有利益相关方都被适当知会（Informed）
4. **快速响应**：明确的决策时限，避免拖延

---

## 📋 RACI 矩阵总览

**RACI 说明**：
- **R (Responsible)**：执行者，负责具体工作
- **A (Accountable)**：决策者，最终负责（每个决策只有 1 个 A）
- **C (Consulted)**：需要征询意见的人（双向沟通）
- **I (Informed)**：需要被告知的人（单向沟通）

### 关键决策点 RACI 矩阵

| 决策点 | 项目负责人 | 技术负责人 | CTO/VP | 执行者 | 团队 |
|---|---|---|---|---|---|
| **启动 Phase -1** | A | C | I | R | I |
| **Phase -1 后决策** | C | A | I | C | I |
| **启动 Phase 0** | C | A | C | R | I |
| **Phase 0 中期调整** | C | A | I | C | I |
| **启动 Phase 1** | C | A | A | C | I |
| **Phase 1 预算超支 <20%** | C | A | I | C | - |
| **Phase 1 预算超支 >20%** | C | A | A | C | - |
| **优化后 Skill 推广** | C | A | I | C | I |
| **项目终止** | C | A | A | I | I |

## 🔑 详细决策矩阵

### 决策 1：是否启动 Phase -1 试点？

**决策者（A）**：项目负责人

**决策依据**：
- 资源可用性（4 小时投入）
- 团队认可"数据驱动"方法
- 不需要管理层批准（投入小）

**决策流程**：
```yaml
步骤 1: 项目负责人评估资源（1 天）
  - 执行者是否有 4 小时可用？
  - 工具是否准备好？

步骤 2: 与技术负责人沟通（C）
  - 技术可行性如何？
  - 有无技术风险？

步骤 3: 决策
  - ✅ 启动：通知执行者和团队（I）
  - ❌ 不启动：说明理由，调整方案

决策时限: 1-2 天
```

**升级**：
- 无需升级（小投入，低风险）
- 如果技术负责人强烈反对 → 需要进一步讨论

---

### 决策 2：Phase -1 后是否继续 Phase 0？

**决策者（A）**：技术负责人

**决策依据**（Phase -1 结果）：
- 追踪方法是否可行？
- 数据质量是否足够？
- 44 小时投入是否合理？

**决策流程**：
```yaml
步骤 1: 执行者提交 Phase -1 报告（半天内）
  - 可行性评估
  - 发现的问题
  - 建议（继续/调整/暂停）

步骤 2: 技术负责人评审（1 天）
  - 征询项目负责人意见（C）
  - 征询执行者意见（C）

步骤 3: 决策
  - ✅ 继续：启动 Phase 0，通知团队（I）
  - ⚠️ 调整：修改方法，再次试点
  - ❌ 暂停：说明理由，项目暂停

决策时限: 2 天
```

**升级**：
- 如果需要额外资源（超出预期）→ 上报 CTO（C）
- 如果团队有重大分歧 → 技术负责人 + 项目负责人共同决策

---

### 决策 3：是否启动 Phase 0？

**决策者（A）**：技术负责人

**决策依据**：
- Phase -1 成功
- 资源可用（2 周，44 小时）
- 其他项目可以暂停/委托

**决策流程**：
```yaml
步骤 1: 确认资源（RESOURCE-PLAN.md）
  - 执行者已确定
  - 时间已预留
  - 其他工作已协调

步骤 2: 与管理层沟通（C）
  - 知会 CTO/VP
  - 说明 2 周投入
  - 强调数据驱动价值

步骤 3: 决策
  - ✅ 启动：正式启动 Phase 0
  - ❌ 延后：等待合适时机

决策时限: 3-5 天
```

**升级**：
- 如果管理层有顾虑 → 技术负责人需要说服或调整方案
- 如果资源冲突 → 技术负责人 + CTO 共同决策优先级

---

### 决策 4：Phase 0 中期是否继续？

**决策者（A）**：技术负责人

**时机**：Week 1 结束（22 小时后）

**决策依据**：
- 是否发现明确模式？
- 数据质量如何？
- 是否值得继续投入？

**决策流程**：
```yaml
步骤 1: 执行者提交中期报告（1 小时）
  - 已追踪 5-8 个任务
  - 初步发现的模式
  - 建议（继续/扩大样本/停止）

步骤 2: 技术负责人评审（半天）
  - 征询项目负责人意见（C）
  - 判断是否有价值

步骤 3: 决策
  - ✅ 继续：完成剩余任务
  - ⚠️ 扩大样本：如果模式不明显
  - ❌ 停止：如果无明确发现

决策时限: 1 天
```

**升级**：
- 通常无需升级（内部调整）
- 如果决定停止 → 知会 CTO（I）

---

### 决策 5：是否启动 Phase 1？⭐⭐⭐

**决策者（A）**：技术负责人 + CTO/VP（共同决策）

**时机**：Phase 0 完成后

**决策依据**（Phase 0 数据）：
- 基线是否达标？
- 归因为 Skill 问题的占比？
- 预期 ROI？
- 资源可用性？

**决策流程**：
```yaml
步骤 1: 执行者提交 Phase 0 完整报告（1 天）
  - 基线数据（返工率、用户介入等）
  - 根因归因分析
  - 建议（4 种退出条件之一）
  - 如果建议启动 Phase 1：
    - 需要优化的 Skill（2-3 个）
    - 预期改善（相对基线）
    - 预估投入（48-120h）
    - 预期 ROI

步骤 2: 技术负责人初审（2 天）
  - 评估技术可行性
  - 评估资源需求
  - 准备决策材料

步骤 3: 决策会议（技术负责人 + CTO + 项目负责人）
  - 时长: 1 小时
  - 议程:
    1. Phase 0 结果汇报（15 分钟）
    2. Phase 1 方案说明（15 分钟）
    3. 讨论和 Q&A（20 分钟）
    4. 决策（10 分钟）

步骤 4: 决策（4 种可能）
  - ✅ 启动 Phase 1：批准资源，开始执行
  - ✅ 质量已达标：项目成功完成（无需 Phase 1）
  - ⚠️ 调整方向：问题不在 Skill（建议其他改进）
  - ❌ 暂停项目：成本 > 收益

决策时限: 1 周
```

**升级**：
- 如果技术负责人和 CTO 意见不一致 → 工程 VP 或 CEO 决策
- 如果涉及其他团队资源 → 扩大决策会议

### 决策 6：Phase 1 预算超支如何处理？

**场景 1：超支 <20%**

**决策者（A）**：技术负责人

**决策流程**：
```yaml
触发条件: 
  - 预估剩余时间超出预算 <20%
  - 执行者上报

决策:
  - ✅ 继续：在权限范围内批准
  - ⚠️ 调整：减少范围或优化效率
  - ❌ 止损：如果效果不如预期

知会: CTO（I）

决策时限: 1-2 天
```

---

**场景 2：超支 20-50%**

**决策者（A）**：CTO/VP

**决策流程**：
```yaml
触发条件:
  - 预估剩余时间超出预算 20-50%
  - 技术负责人上报

决策流程:
  1. 技术负责人准备说明（1 天）
     - 为什么超支？
     - 已完成的价值？
     - 继续的必要性？
  
  2. CTO 评审（2 天）
     - 与技术负责人讨论
     - 评估投入产出比
  
  3. 决策
     - ✅ 批准延期：追加资源
     - ⚠️ 有条件批准：缩减范围
     - ❌ 止损：停止 Phase 1

决策时限: 3-5 天
```

---

**场景 3：超支 >50%**

**决策者（A）**：CTO/VP + 项目负责人（共同评估）

**决策流程**：
```yaml
触发条件:
  - 预估剩余时间超出预算 >50%
  - 这是重大偏差，需要重新评估项目

决策流程:
  1. 召开紧急评审会（1 周内）
     - 参与者: CTO, 技术负责人, 项目负责人, 执行者
     - 议程:
       1. 分析超支原因
       2. 评估已完成价值
       3. 评估继续的必要性
       4. 评估替代方案
  
  2. 决策
     - ✅ 重新规划：制定新计划，追加预算
     - ❌ 项目终止：保存成果，终止项目

决策时限: 1 周
```

### 决策 7：优化后的 Skill 如何推广？

**决策者（A）**：技术负责人

**时机**：Phase 1 完成后

**决策流程**：
```yaml
步骤 1: Phase 1 完成验证（1 周）
  - A/B 对比测试
  - 确认改善 ≥30%
  - 无关键指标下降

步骤 2: 制定推广计划（2 天）
  - 试点团队（1-2 个团队，2 周）
  - 培训计划（内部分享会 + 文档）
  - 全面推广时间表

步骤 3: 与团队沟通（C）
  - 说明优化内容
  - 收集反馈
  - 解答疑问

步骤 4: 决策推广方式
  - 渐进式推广：先试点，再全面
  - 立即推广：如果改进明显且风险低
  - 可选推广：团队可选择使用新/旧 Skill

决策时限: 1 周
```

**升级**：
- 如果团队有重大反对意见 → 技术负责人需要调整方案
- 如果涉及跨团队推广 → 知会 CTO（I）

### 决策 8：是否终止项目？

**决策者（A）**：技术负责人 + CTO/VP（共同决策）

**触发场景**：
1. Phase 0 发现质量已达标（无需优化）✅ 这是成功
2. Phase 0 发现问题不在 Skill ✅ 调整方向
3. Phase 1 效果不达预期 ⚠️ 需要评估
4. 资源不足或优先级变化 ⚠️ 外部因素
5. 关键人员离职，无人接手 ⚠️ 不可抗力

**决策流程**：
```yaml
步骤 1: 触发者提出终止建议
  - 项目负责人或技术负责人
  - 说明终止理由
  - 评估已完成价值

步骤 2: 决策会议（3 天内）
  - 参与者: CTO, 技术负责人, 项目负责人
  - 议程:
    1. 终止理由说明
    2. 已完成工作价值评估
    3. 是否有替代方案
    4. 决策: 终止 / 调整 / 继续

步骤 3: 如果终止
  - 保存所有数据和分析
  - 输出"项目总结报告"
  - 知会所有团队成员（I）

决策时限: 1 周
```

**终止不等于失败**：
- 场景 1 和 2 是成功的终止（达成目标）
- 数据驱动决策本身就是价值

## 🚨 紧急决策机制

### 触发条件

```yaml
紧急情况定义:
  1. 项目完全阻塞，无法继续
  2. 发现重大技术风险
  3. 关键人员突然离职
  4. 管理层要求立即停止
  5. 外部环境重大变化
```

### 紧急决策流程

```yaml
步骤 1: 触发者立即上报
  - 上报对象: 技术负责人 + CTO
  - 方式: 电话 + 邮件
  - 期望响应: 当天

步骤 2: 紧急评估（1 天内）
  - 评估影响和紧急程度
  - 识别可选方案

步骤 3: 紧急决策（2 天内）
  - 决策者: CTO
  - 可选方案:
    - 立即暂停（保护成果）
    - 调整方案（降低风险）
    - 继续执行（风险可控）

步骤 4: 执行和沟通
  - 立即执行决策
  - 通知所有相关方
```
