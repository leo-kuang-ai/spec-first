## 结论与证据边界

下一阶段优先优化“选得准、读得少、执行有弹性、结果可验证”，暂不批量重写 Skill。建议以小范围试点（Trial）证明收益后再推广。

Claude 官方实践明确区分模型自行判断的指引与宿主确定性执行的规则：模型负责理解目标和判断方法；Skill 提供项目特有知识与流程；必须保证的约束交给宿主权限、脚本和测试。随着模型和宿主能力增强，重复讲通用工程方法的价值会下降，项目知识、边界和验证闭环的价值会上升。

### 每项工作与交付规则

1. 读取当前source、对应消费者和既有证据，确定本项具体机会与不可变边界。
2. 按下文实验卡冻结可比较的输入、基线、验收标准与有界候选。已有证据确认没有机会或收益不足时记录`no-change`；证据缺失时记录`pending-evidence`，不得混同，也不得先改再寻找收益依据。
3. 候选在独立worktree中仅修改本项拥有的源码，按需补真正能发现失败的反例。验证前不写回正式工作区的Skill源码；不手改generated runtime，不新增中央调度器或通用规则引擎。
4. 完成必要静态/确定性检查和独立fresh-source复核。评测配置加载、判据校准、模型行为和真实宿主结果分开记录。
5. 回填本表及下文证据索引：实际diff、命令/结果、复核、收益是否验证、剩余缺口。候选有回归则拒绝该候选，保留证据；清理只针对本项拥有的改动，不影响他人文件。
6. 当前项可独立完成的工作处理完后进入下一项。缺模型/平台证据只阻塞依赖它的候选或推广，不用该缺口跳过其他项的本地调查，也不把待验收项标完成。

每项状态区分：待开始、核查中、候选已修改、确定性验证通过、真实行为待验收、收益已验证、no-change、pending-evidence。只有匹配其验收范围的证据齐全才称优化完成；不按文件数或测试数累计“优化完成率”。

### 候选隔离与进入正式源码的条件

“正式源码”指当前交付工作区中后续任务将消费的`skills/`及其关联source，不代表已发布。隔离候选仍修改source；隔离不授权刷新真实宿主runtime。每次实验记录baseline commit、worktree位置和候选文件hash；比较臂使用相同任务快照与环境，不能从上一项未验证候选派生下一项基线。

只有以下条件全部成立才可将本项diff应用到正式工作区：本项实验卡预先定义的质量门和收益标准通过；独立fresh-source复核完成；实际模型/宿主证据覆盖本项声称改善的行为；依赖来源未漂移。静态测试、配置加载或文案变短不能代替行为与收益证据。应用后运行受影响的确定性检查；如目标source已变化，先重新绑定基线并重验相关比较，不直接复用旧结论。

证据不足时保留隔离候选或保存可恢复的patch及hash后清理本项worktree，正式基线保持不变。质量失败记`reject/rollback`，证据不足记`inconclusive`并在总表保留`pending-evidence`；二者均不得推广。实验完成的本地应用不等于commit、push或runtime更新，这些动作仍按会话实际授权执行。

仅为当前准备实施的项目填写，不预建12套空模板。卡片写在该项证据索引中，复用既有runner、案例和合同，不新增schema或评测框架。

| 固定案例 | 可执行输入/fixture路径、预期产物或决策、正反例及相邻流程案例；开发集与独立验收集的用途 |
| 执行与判据 | 实际命令、runner版本、checker/rubric、模型/宿主/effort/cache及权限条件；未知项明确标缺失 |
| 质量门与收益 | 关键越权、虚假完成、source/runtime误写零新增回归；普通质量与主要收益指标的计算方法、样本/重复数及明确通过阈值 |

### 调查顺序与验证依赖

按O01–O12推进可独立完成的调查和准备；某项受阻不阻止后续独立调查。关键修复回归是涉及同一行为的候选推广前置条件，不是全部12项调查的统一前置条件。

- O01、O04、O05涉及已有授权与需求边界，O03/O06/O07涉及既有执行与审查边界，O09–O12涉及知识及Git副作用：各自实验卡必须指向相关修复记录，并在修复后的baseline验证这些保护行为。若baseline不通过，先移交原修复owner处理，优化不掩盖或接管未定位缺陷。
- O02入口规则及其他项目的description变化可能改变相邻Skill的实际加载。相关消费者实验须冻结入口与目标Skill的完整来源身份；入口或描述变化后，重跑受影响的路由案例，并重新判断原行为/成本比较是否仍有效。
- O08的handoff产物或其他共享合同发生变化时，重验实际消费者；无相关依赖变化的项目不要求全量重跑。
- 尚未通过门禁的候选不能成为后续baseline。已经推广的变更可以成为新baseline，但后续实验必须记录其版本，不能跨基线合并样本或沿用旧收益结论。

首轮仅考虑同上下文内完整、可观察且未失效的非关键出口材料。上下文压缩或恢复、截断、来源版本变化、owner/scope 改变及关键授权/完成出口，仍须按既有合同重新核实。不能假设文件曾被读过就一定仍可可靠使用。

### 2. 保留项目特有知识，实测通用过程指引的边际价值

值得保留的内容包括：

- 哪份文件拥有最终定义权、哪些目录是生成产物。
- 用户已有的决策与授权、项目特有的业务约束。
- 经验证的命令、常见失败及恢复方式。
- 完成必须提供什么证据。

通用分析套路、重复角色宣言、固定数量的视角和无条件审查步骤，应逐项用对照实验判断是否值得保留。模型能力增强本身不足以证明可以删除它们。

脚本负责可机械判定的事实与不变量；需求理解、架构取舍和语义充分性仍由 LLM 判断。避免把精简 Prompt 变成更复杂的规则引擎。

### 3. 优先消费宿主能力，减少重复建设

本次读取的 Claude 官方文档已介绍原生任务持续执行、上下文压缩、子代理及运行验证能力。项目应优先消费这些能力，把自身重点放在跨宿主的需求、计划、证据和知识连接上。

文档描述不证明本机版本已支持或实际启用了某能力。不能因为某个宿主支持，就假设所有宿主都能等效执行。Claude 专有 frontmatter 与 Codex metadata 应由对应适配层处理；源码资产仍是 source of truth，generated runtime 不作为手工修复入口。

## 推荐执行顺序与验收

1. 按O01–O12调查并填写当前项实验卡；相关修复的真实回归列为该候选推广依赖，受阻时继续后续独立调查。需要新增费用或平台配置的部分，沿用当前授权边界，不能从历史预算推导新授权。
2. O01先校准读取基线与测量方式，满足既有C1准入后才构造隔离候选；证据不足则保留pending-evidence。
3. O02检查相邻Skill的触发描述，冻结入口/目标来源，使用正例、负例和混淆例验证；变更影响后续实验时按依赖规则重验。
4. O03及后续项按同样的隔离、测量和推广门逐项推进；小任务流程优化保留风险升级条件和必要验证出口。

验收以任务正确率、关键边界、完成时间和返工量为主，token 消耗为辅。按模型和宿主分层比较；静态合同、模型行为、运行成本和真实任务结果分别报告。出现关键边界回归或质量下降时，不用成本收益抵消，应回滚候选或继续调查。

暂不做全量 Prompt 瘦身，不新增中央流程引擎，不把某一模型的效果推广到全部模型。未完成真实评测前，以上均为待验证建议。
