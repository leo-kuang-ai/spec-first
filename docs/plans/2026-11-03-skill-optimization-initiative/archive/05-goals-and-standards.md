# Skill 优化 - 目标与检查标准

日期：2026-11-03  
版本：v4（研发流程导向）

---

## 最终目标

**让需求到可信交付的整条研发链路更顺畅、更自主、更可靠**

**不是**：优化 Skill 的性能指标  
**而是**：让真实任务能高质量、完整地交付

---

## 三层检查标准

### Layer 1：单个 Skill 是否有效

检查每个 Skill 本身是否合理。

| 维度 | 检查标准 | 度量方法 | 通过条件 |
|---|---|---|---|
| **指令清晰度** | 无歧义、无矛盾、易理解 | 人工审查 Skill 源码 | 模型能明确理解要做什么 |
| **无过时约束** | 没有已废弃的规则 | 对比官方最佳实践 | 约束仍然有效且必要 |
| **必要性** | 不做不必要的工作 | 对比官方最佳实践 | 每个步骤都有明确目的 |
| **完整性** | 包含必要的检查 | 对比研发最佳实践 | 关键验证点未遗漏 |

**示例问题**：
- ❌ spec-runtime-setup 重复检查已存在的配置（不必要的工作）
- ❌ spec-plan 的指令中包含"必须询问用户确认"，但实际应该自主决策（过时约束）
- ❌ spec-work 没有要求验证 Plan 的验收条件（完整性缺失）

**度量指标**：
- 指令清晰度：主观评分 1-5 分
- 过时约束数量：0 个为合格
- 不必要步骤数量：0 个为合格
- 遗漏检查数量：0 个为合格

---

### Layer 2：阶段之间是否衔接顺畅

检查 Skill 之间的协作是否流畅。

| 维度 | 检查标准 | 度量方法 | 通过条件 |
|---|---|---|---|
| **信息丢失率** | 上游已确定，下游未使用 | 统计任务中的信息丢失次数 | <5% |
| **信息重复率** | 上游已确定，下游又询问 | 统计任务中的重复询问次数 | <10% |
| **验收条件落实率** | Plan 的验收条件在 Work 中实现的比例 | 统计 Plan → Work 的传递 | >90% |
| **输入输出匹配度** | A 的输出是否符合 B 的输入期望 | 人工审查阶段衔接 | 100% |

**四类衔接问题**：

1. **信息丢失**
   ```
   stage: 3_planning
   output: "边界条件：数据为空、只有一页"
     ↓ [丢失]
   stage: 4_implementation
   input: Plan
   实际实现: 未处理边界条件
   ```

2. **信息重复**
   ```
   stage: 2_requirement
   output: "每页 20 条"
     ↓ [重复询问]
   stage: 3_planning
   action: 又询问用户"每页多少条？"
   ```

3. **验证缺失**
   ```
   stage: 4_implementation
   output: "代码已完成"
   实际状态: 未运行测试，未验证边界
   ```

4. **衔接断裂**
   ```
   stage: 3_planning
   output: "使用 Redis 缓存"（抽象描述）
     ↓ [不匹配]
   stage: 4_implementation
   期望输入: 具体的 Redis 配置、数据结构、过期策略
   ```

**度量指标**：
- 信息丢失率 = 丢失的信息条数 / 总信息条数
- 信息重复率 = 重复询问次数 / 总询问次数
- 验收条件落实率 = 实现的验收条件数 / Plan 中的验收条件数

---

### Layer 3：整个任务是否真正完成

检查端到端的交付质量。

| 维度 | 检查标准 | 度量方法 | 通过条件 |
|---|---|---|---|
| **端到端正确率** | 任务声称完成且实际可交付 | 统计任务完成质量 | >90% |
| **端到端返工率** | 需要重做的任务比例 | 统计返工任务数 | <10% |
| **用户介入次数** | 用户需要澄清、确认、修正的次数 | 统计用户交互 | <3 次/任务 |
| **端到端完成时间** | 从需求到交付的总时间 | 统计 wall-clock 时间 | 基线 -20% |
| **交付完整性** | 是否包含所有需求功能点 | 对比需求与交付 | 100% |

**端到端质量评估**：

```yaml
task_quality:
  delivered: true/false     # 是否有交付物
  correct: true/false       # 功能是否正确
  complete: true/false      # 是否包含所有需求
  tested: true/false        # 是否有测试
  documented: true/false    # 是否有文档
  
  overall_score: 5/5  # 全部 true 才是 5/5
```

**度量指标**：
- 端到端正确率 = 完全正确的任务数 / 总任务数
- 端到端返工率 = 需要返工的任务数 / 总任务数
- 平均用户介入次数 = 总介入次数 / 总任务数
- 平均完成时间 = 总时间 / 总任务数

## 成功标准的层级关系

### 优先级

```
Layer 3（整体交付质量）← 最重要
  ↑ 由此决定
Layer 2（阶段衔接）
  ↑ 由此决定
Layer 1（单个 Skill）
```

### 为什么这样排序？

**错误的思路**：
```
优化单个 Skill → 希望整体变好
```

**正确的思路**：
```
整体交付有问题 → 追踪阶段衔接 → 定位到单个 Skill
```

**示例**：

```
Layer 3 发现：端到端返工率 73%（不合格）
  ↓ 追查原因
Layer 2 发现：Plan → Work 信息丢失率 64%（不合格）
  ↓ 追查原因
Layer 1 发现：
  - spec-plan 缺少边界系统化检查
  - spec-work 未验证 Plan 的验收条件
```

## 检查方法

### Phase 0：真实任务流程追踪

**方法**：选择 11 个代表性真实任务，端到端追踪

#### 步骤 1：重建完整流程

对每个任务：
1. 从第一条用户消息到最终交付
2. 记录每个阶段的：
   - 使用的 Skill
   - 输入与输出
   - 用户介入点
   - 等待时间
   - 遇到的问题

#### 步骤 2：标注问题

标注四类阻力点：
- 信息丢失：哪些信息在哪个阶段丢失了
- 信息重复：哪些信息被重复询问
- 验证缺失：哪些阶段声称完成但未验证
- 衔接断裂：哪些阶段之间输入输出不匹配

#### 步骤 3：统计指标

```yaml
# Layer 3 指标
端到端正确率: 3 / 11 = 27%  # ❌ 不合格（目标 >90%）
端到端返工率: 8 / 11 = 73%  # ❌ 不合格（目标 <10%）
平均用户介入: 2.8 次/任务   # ✅ 合格（目标 <3 次）

# Layer 2 指标
信息丢失率: 7 / 11 = 64%    # ❌ 不合格（目标 <5%）
信息重复率: 6 / 11 = 55%    # ❌ 不合格（目标 <10%）
验收条件落实率: 30%          # ❌ 不合格（目标 >90%）

# Layer 1 指标（根据上述问题定位）
spec-plan:
  - 缺少边界系统化检查（完整性问题）
  - 重复询问 PRD 内容（不必要工作）
spec-work:
  - 未验证 Plan 的验收条件（完整性问题）
```

## 优化决策标准

### 何时优化一个 Skill？

**必须同时满足**：

1. **Layer 3 有明确问题**
   - 端到端返工率高
   - 端到端正确率低
   - 用户介入次数多

2. **Layer 2 追查到具体衔接问题**
   - 信息丢失
   - 信息重复
   - 验证缺失
   - 衔接断裂

3. **Layer 1 定位到该 Skill 的根因**
   - 指令不清晰
   - 有过时约束
   - 做了不必要的工作
   - 缺少必要的检查

### 优先级排序

```
影响面 × 严重程度 = 优先级

影响面 = 受影响的任务数 / 总任务数
严重程度 = 导致返工 ? P0 : 影响效率 ? P1 : P2

示例：
spec-plan 边界遗漏:
  影响面 = 7/11 = 64%
  严重程度 = P0（导致 5 个任务返工）
  优先级 = P0

spec-runtime-setup 重复检查:
  影响面 = 6/11 = 55%
  严重程度 = P2（仅浪费 5 分钟，未导致返工）
  优先级 = P2
```

## 验证标准

### 优化后如何验证？

**在 5 个新任务中试用优化后的 Skill**：

#### 验证 Layer 1 改善

- [ ] 指令清晰度提升（主观评分）
- [ ] 过时约束已移除（检查清单）
- [ ] 不必要工作已消除（对比前后）
- [ ] 遗漏检查已补充（检查清单）

#### 验证 Layer 2 改善

- [ ] 信息丢失率下降（统计 5 个任务）
- [ ] 信息重复率下降（统计 5 个任务）
- [ ] 验收条件落实率提升（统计 5 个任务）

#### 验证 Layer 3 改善

- [ ] 端到端正确率提升（5 个任务的正确率）
- [ ] 端到端返工率下降（5 个任务的返工率）
- [ ] 用户介入次数保持或下降

### 推广标准

**三层门**：

```
第一层：质量硬门（零容忍）
├─ Layer 3 指标下降 → 立即拒绝
├─ Layer 2 衔接问题恶化 → 立即拒绝
└─ Layer 1 引入新问题 → 立即拒绝

第二层：改善门
├─ Layer 3 至少一项指标改善 ≥20% → 通过
└─ Layer 2 至少一项指标改善 ≥30% → 通过

第三层：成本门（附加）
├─ 开发时间增加 <20% → 可接受
└─ Token 消耗增加 <10% → 可接受（如果质量改善）
```

## 常见误区

### ❌ 错误的检查标准

1. **只看 Layer 1**
   ```
   "spec-plan 的 token 降低了 20%"
   → 但端到端返工率反而上升了
   ```

2. **只看成本**
   ```
   "总成本降低了 15%"
   → 但端到端正确率只有 60%
   ```

3. **预设优化范围**
   ```
   "必须优化这 12 个 Skill"
   → 但真实任务的痛点在其他地方
   ```

### ✅ 正确的检查标准

1. **从整体到局部**
   ```
   Layer 3（整体）有问题
     ↓
   Layer 2（衔接）找原因
     ↓
   Layer 1（单个）定位根因
   ```

2. **质量优先**
   ```
   质量改善 > 效率保持 > 成本附加收益
   ```

3. **数据驱动**
   ```
   真实任务追踪 → 统计阻力点 → 决定优化范围
   ```

## 总结

### 优化目标

**让需求到可信交付的整条研发链路更顺畅、更自主、更可靠**

### 检查标准（三层）

1. **Layer 1**：单个 Skill 指令清晰、无过时约束、不做无用功、包含必要检查
2. **Layer 2**：阶段衔接信息不丢失、不重复、验收条件落实、输入输出匹配
3. **Layer 3**：端到端正确率 >90%、返工率 <10%、用户介入 <3 次

### 检查方法

**Phase 0**：11 个真实任务的端到端流程追踪 → 统计三层指标 → 定位问题 Skill

### 优化决策

**基于数据**：影响面 × 严重程度 = 优先级

### 验证标准

**三层门**：质量硬门（零容忍）→ 改善门（≥20%）→ 成本门（可接受）
