# spec-first 下一阶段开发顺序与批次执行指南

> 开发主线：最小测量与证据基线 -> Astra 核心指令修订 -> 真实任务对照 -> 按瓶颈优化上下文与接续 -> 知识复用、消融与成本收敛。

本文是后续开发的顺序入口，负责批次、依赖、范围与进入条件。后续收到“按本文开发”的任务时，从 S0 核对当前事实并收敛当批实施输入，再由对应 owner 执行；不重新研究全部战略，也不把所有候选一次展开。

本文不是整包 `implementation-ready` 代码计划。`execution: knowledge-work` 表示本文是协调与规划文档；`status: completed` 表示方案 owner 已确认线下验证通过并完成收口。具体批次形成范围有限的代码计划或明确修复输入后，才进入实施；各批实际状态按下方记录与原 workflow 证据核对。

这是研发排序，不是新增 runtime 状态机。某条直接缺陷已有充分复现和局部验证时（最低证据标准：命中条款的源码行级引证加覆盖该行为的合同测试，行为复现可加强但不强制），可以提前修复并记录理由；缺少某个外部 cohort 或昂贵实验不阻止独立的本地确定性工作，但不得据此宣称整个批次验证完成或候选已有相对收益。

同时最多推进两个实质工作项，由 S0 owner 登记工作项、冲突面和串行顺序；共享 `skills/spec-plan/`、`skills/spec-work/`、根指令、renderer、公共 tests、CHANGELOG 或同一评测环境时串行集成。任务并行不等于获得子代理权限，是否委派仍按当前宿主与用户授权执行。

## 3. S0：锁定首批开发输入

目标是让下一会话可以直接准备首批实施，不再把“选什么任务”留成无期限研究。

1. 重新读取 Git HEAD、staged/unstaged/untracked 状态和命中的 source。记录已有修改与本批交集，保留当前用户与其他会话改动。HEAD 相同不表示工作树相同。同时为四份上游来源文档与本文保留内容已持久化、可定位、可恢复、可比较的版本快照，使第 12 节 SHA-256 锚点具备可 diff 的版本基线。已有提交可直接引用；未提交内容可使用持久化副本或 git blob，记录原路径、内容摘要、快照位置或对象标识，并回读核对。使用 blob 时还须记录可达引用或独立备份，避免对象被回收；仅有 hash 不算完成冻结。提交按实际授权执行，不是来源冻结的必要条件。
2. 默认从 `docs/validation/skill-evals/routing-audit-20260902/run_routing.py` 入手，复核当前是否仍存在逐次重试记录、环境分类和汇总覆盖缺口。已经修好的部分只保留回归，不重新实现。
3. 首批限定上方四项路由测量器修复及其必要回归、消费者兼容和说明；核心指令行为在 S2/S3 处理，不同时新增业务 feature、宿主或公共 schema。后续真实业务仓库在 S4 扩大试点时再选；不阻塞公开或合成样本准备。
4. 选定首批测试 owner 和后续行为执行器候选，将第 4.4 节能力核验安排到 S1 期间。模型场景必须支持所需的多轮答复、工具事件和最终状态检查；调用 Skill 名称正确不能代替能力核实。候选尚不可用时记录缺口，不阻塞首批无模型修复。
5. 确定模型任务数、重复次数、并发、timeout、费用上限与停止预算。未有付费授权时，只做本地无模型回放、场景准备与 source 核查，不启动收费调用。
6. 从本节及 S1/S2 收敛首批代码计划或具体修复输入。已知故障由 `spec-debug` 承接；已收敛的实施由 `spec-work` 承接。Skill 改造沿用项目 source owner，通用作者工具与评测工具不重新开启需求访谈。

当批输入至少包含：目标及非目标、目标仓库、当前 source 身份和已有修改、具体修改路径、需求到验收场景、必要验证、预算、回退、产物消费者。跨模块或合同变更形成有限实施计划；原子修复可用具体修复输入，不为每个小项生成重复文档。

**出口条件：** 已形成可执行的 S1 输入：目标任务与非目标、owner、source 快照、允许路径、验证入口、预算上限、隔离方式、回退与产物消费者均已记录；模型身份、费用或外部数据权限缺口单独标记，只阻断依赖它们的动作。S0 不要求提前修改测量器，也不能伪造预算、授权或试点参与者。

本批另有以下四项实验准备要求，缺任一项不得进入 S1 的模型消耗动作；不阻断已明确范围的本地无模型校准：

1. 预注册主指标、次指标、最小可检测效应、置信区间方法、难度分层、重复次数与停止/重跑规则。
2. 生成机读 `experiment_manifest.json`（provider/model、API snapshot、system prompt hash、tool schema hash、temperature/seed 或其不可控记录、依赖版本、数据集 hash、时间窗、runner revision）。
3. 冻结 S4 任务设计：随机化/交叉顺序、匹配难度、抽样框、holdout 与其 hash，并记录防调优泄漏方式。
4. 为能力不足的 runner 定义局部升级、受限 degraded mode、退役/停止三档判据与 owner；连续两批仍无法满足关键合同则复审，不能无限期保持准备中。

无付费授权时，第 1、3 项只需冻结设计本身，不要求先有模型结果；第 2 项的 manifest 由当批实验 owner 写入 run-owned 产物目录，并在 S0 记录路径、最小 schema、source snapshot 引用和缺字段判定；manifest 允许把依赖运行时才可得的字段（provider/model 实际标识、API snapshot、seed 可控性）记为待补，但字段位必须存在且在首次收费调用前补齐，不得以“待补”状态开始比较。

manifest 与运行结果逐一绑定。已准入比较中的非预定身份漂移由测量器标记 invalid，整组重跑或保持未完成；候选按计划产生新版本时，按 5.3 建立新准入，不覆写旧身份。首次预算须覆盖每个比较对自己的 A/A、对照组和候选组调用，不能假定早期基线可直接复用而漏计费用。

本节是目标模型验收边界的唯一规定位置：GPT-6 Astra 行为验证通过前，候选可做源码检查、受限 fresh-source 审查，并按上表在已通过对应行为验证的替代模型上开展 degraded / alternative-model-only 的受限内部 S4；不得进入默认投射、Astra 结论或推广。目标模型行为检查本身按 5.3 的准入与授权执行。这里是计划级完成与使用约定，不表示已有 runtime blocking primitive；若实际宿主不能强制，必须记录未强制范围，不宣称已有机械 hard gate。本批的 fresh-source 审查须由新会话的独立 agent 或人工 owner 执行，记录 source revision、评审主体、问题清单与 fresh timestamp；同会话缓存调用不计独立审查。

仅有源码结果时将本批记录为“候选已准备，行为验收未完成”，不能关闭为核心行为已修复。缺少必需独立审查时仍按第 10 节记录未执行及受阻范围。保留失败候选及原因；仅字数下降不作为推广依据，任何一层通过均不宣称普遍提效。

S3 行为证据至少记录：`source_revision`、`scenario_ids`、`fresh_context`、`host/model`、`tool_events`、`final_state`、`result`、`limitations` 和 `reviewer_identity`。无法获得独立 reviewer 时固定记录 `independent_review: not_run`，状态保持“源码候选已准备，行为验收未完成”。

## 7. S4：真实任务对照与主宿主验证

对应 OPT-05、OPT-09，并兑现 OPT-03/04。先作者/维护者自用，再考虑外部参与者。

1. 选择未参与候选调优的匹配任务，覆盖跨模块修复、业务交付或接续中的实际目标场景。不得把 S1 中已熟悉的同题重做当成工具提效；采用交叉顺序或匹配任务并记录熟悉程度。
2. 比较相同模型、工具、权限和可接受范围下的结果，记录主动人工投入、墙钟与等待、review 修改轮次、返工、缺陷、实际运行费用、未完成任务与退出。默认将 `native_project`（宿主原生 + 必要项目事实与安全约束）、冻结的 `current_full` 和已通过 S3 对应模型行为验证的 `candidate` 三组绑定到独立实验身份，在同一预先冻结的匹配任务设计中执行，分别估计现有 harness 相对原生的收益、本次候选相对现有版本的变化；不与 Astra 三组合并为一次四组测评。
3. 先验证实际可用主宿主的首次发现/调用、失败不能报通过、恢复/显式交接旅程。声明 Claude 与 Codex 均支持某一能力前，需要对应版本旅程；其他宿主按本批影响做生成、清理及 ownership 回归，不冒称八宿主现场全测。
4. 涉及真实私有数据时，先落实总方案 OPT-05 的采集、访问、保留和撤回约定。原始输出留仓外私有目录；获准脱敏派生日志才进入原 workflow 的仓内 logs，继续使用现有校验。原始、派生数据和元数据均覆盖清理，删除后收缩相关 claim。
5. 外部参与者、其他仓库访问、收费资源或报告外发缺授权时，停止对应动作并继续公开/合成或已授权内部范围。作者自用与外部采用分开。

比较矩阵固定为下列三对，其余组合不成立；预算仅支持两组时，在观察结果前固定比较问题和组名：`native_project` 对 `current_full` 只评估现有 harness 整体增量；`current_full` 对 `candidate` 只评估本次修订增量；`native_project` 对 `candidate` 只评估候选整体效果，不能拆分现有机制与本次修订的贡献。缺少的比较保留为未完成；后续补组需重新核验模型、匹配任务、输入与时间窗的可比性，不能用 S2/S3 固定行为场景补成真实任务三组结果。

预算不足时按“减少未开始的重复次数，再减少场景，最后暂停新增组”降级；不得事后改分母。任一组出现环境失败率超过预先阈值、模型身份无法核实或冻结条件失效时停止拼接并标记不可比。


**出口条件：** 至少一类真实任务在预先声明的比较范围内有可比较的完整结果，能够指出下一瓶颈。结果状态必须明确标为 exploratory_complete（探索性/样本不足）、internal_comparison_complete（预注册比较范围完整）、three-group-complete（三组及三对比较完整）或 not_complete / blocked；替代模型结果只能进入前两类，不能生成 Astra 或生产结论。每类任务至少 5 个独立任务并按类型分层报告，样本不足只报探索性结果；结果保留有效样本、缺失、区间和效应量，不能用重复执行代替独立任务。关键语义结果使用冻结 `gold_set`、双 Judge 或盲评人工 reviewer，生成模型不独自裁决，记录 agreement、分歧队列与升级处理；无独立裁决时只能报告自动评分观察，不能据此关闭语义验收。成本账本拆分 input/output token、API、工具等待、重试、人工 review 与协调成本，主指标同时报 quality-adjusted cost。

**条件验证与运行边界：**

- 涉及多 agent 时，先跑单 agent baseline 再比较最多两个 agent；记录协调 token/费用、等待、冲突、返工、共享状态污染和成功率，明确角色、worktree/index 与 handoff 隔离，异常时停止受影响动作。只有质量调整成本改善才可声称增量价值。单 agent 任务不为满足此项而引入第二个 agent。
- runner 固定 wall-clock/token/tool-call/重试/循环检测/kill-switch/checkpoint、幂等恢复与预算耗尽收尾，超限产出 `degraded`；预算和停止事件须可审计，部分输出或进程仍存不算完成。能力缺口按 S0 的三档判据处理，不默认为已强制。
- 涉及真实私有数据时，建立 data card、脱敏/重识别检查、访问审计、保留期限、撤回与删除证明；沿用本节第 4 项的存储和清理边界，无审计证据不能声称治理闭环。公开或合成数据记录来源，不要求提供不存在的私有数据删除证明。
- 仅在已获现场试点授权时开展 shadow/canary，记录 accept/rework/revert、回滚触发、用户反馈和长期失效监测；无持续现场证据时，claim ceiling 限定为内部实验，不阻止完成该内部比较。

两组结果可完成该受限内部试验，但不代表战略三组完成；只有三组及对应比较均满足冻结条件才声明三组对照完成。得到无收益结论也可结束候选，不为满足进度推广。20% 周期、25% 人工投入降幅仍只是候选讨论目标，未获预先冻结与实测支持前不变成验收承诺。
