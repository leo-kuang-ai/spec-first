### 1.1 目标

- G1. 一次真实变更能够把意图、实现范围、验收、运行证据和审查结果连接起来。
- G2. 不再依赖入口名称、结构评分、模型自报或少量演示推断实际收益。
- G3. 常驻指导和任务上下文保持最小充分，减少不必要的读取、确认、路由停顿和重复产物。
- G4. 会话或宿主变化后，可以恢复目标与进展，并识别已经失效的事实和证据。
- G5. 已验证经验在后续任务中产生可观察价值，并可被纠正、降级和撤销。
- G6. 模型、宿主和工程环境变化后，能有依据地调整机制，而不持续堆积旧补偿逻辑。

### 1.2 非目标

- 本期不建设通用 Agent runtime、中央流程引擎、大规模 Agent 调度平台或强制状态机。
- 不以新增宿主、Skill、schema、指标平台、知识数据库和文档数量作为交付指标。
- 不删除当前安全与授权约束来追求“零指导”；不直接修改 generated runtime。
- 不批量迁移全部历史计划和知识，不将语义充分性变成关键词规则或机械审批。
- 不承诺 90 天内所有优化点都进入默认路径；无收益、证据不足或低频项目可以继续 opt-in 或退役。

## 4. 优化点详细方案

### OPT-01 建立可信的原生与候选对照基线

**问题与依据。** 当前 benchmark 可以用于特定代码生产观察，但“无额外 Skill”与“无其他项目指导”尚未严格区分。业界 AGENTS.md、SkillsBench 和机制消融研究也说明，比较对象与输入差异会改变结论。

**推荐方案。**

1. 定义 A 为宿主原生加必要项目事实，B 为冻结版本的当前 spec-first，C 为仅改变一个机制的候选。先声明本次比较的是整体增量还是单项机制，再冻结两组共用的任务、业务验收、安全约束和必要项目事实；目标 Skill 的 description、正文、references、runtime 投射及替代摘要均属于待比较的增强，不能意外进入对应无增强组。
2. 将实验放在独立、可恢复的工作区，使用宿主支持的隔离选项；核查实际继承的全局/项目指导、Skill、hooks、MCP 和配置。
3. 记录实际模型标识、宿主/工具版本、source snapshot、预算和任务输入；无法观测的加载项记为未知，不用 Agent 自报填成 confirmed。
4. 将代码生产、完整验证交付、长任务接续分为不同测量任务，不用禁止执行的试验评价完整交付能力。
5. 在看到候选结果前冻结主指标、最小有意义收益、不可退化项、重复次数、交叉或随机执行顺序、缺失处理和停止预算。先做小规模 A/A，再开始 A/B/C；保留易任务和无收益任务，不按 candidate 是否获益筛选样本。

**源码身份与变化边界。** 当批协议分别记录三个对象，不使用一个无指代的 source hash 混合判断：

| 对象 | 用途 | 变化如何处理 |
| --- | --- | --- |
| harness/目标 Skill 的冻结版本 | 定义每组正在比较的机制 | 各组预先声明的版本差异属于实验设计；运行中发生非预定变化使相应比较失效 |
| 任务初始源码快照与允许修改范围 | 保证同一任务的比较起点与权限边界 | 每次试验开始前核对；未声明的初始差异或输入污染使相应比较不满足条件 |
| 任务最终源码及其验证引用 | 记录 Agent 产出的实际结果 | 范围内的正常代码修改属于任务结果，不因变化本身判为实验漂移；验证前后及尾部变更按 OPT-04 判断，越界修改另按权限和任务结果记录 |

**最小试验与判定。** 先选一个有已知验收结果的任务校准执行器与 grader，确认正确参考结果通过、明确错误结果失败，且未执行不会继承 fixture 的通过状态。之后才比较真实 Agent；A/A 超出预先约定噪声或输入加载不可核实时停止对应比较，不事后放宽门槛。涉及人工操作的对照，应交叉安排顺序或使用匹配任务，记录先前接触情况，避免第二次做同题的熟悉度被误算为工具收益。

**源码落点。** `benchmarks/agentic/run.py`、`benchmarks/agentic/tasks.py`、目标 Skill 的 `evals/`。采用 `spec-optimize` 的 measurement-only 模式时，复用 `skills/spec-optimize/scripts/measurement-admission.cjs` 和 `skills/spec-optimize/references/measurement-only-calibration.md` 的身份、A/A 与预算校验；它只负责测量准入，不拥有候选修改、选择或推广。正式修改 runner 的已知故障时由 `spec-debug` 承接；本点不执行修复。

**产物与消费者。** 复用实验 run 记录与现有 field protocol，保存分组输入、加载事实和失效条件，供 OPT-02/05/06/10 比较。

**验收场景。** A/B 仅预定输入不同；全局指导或目标 Skill 的替代摘要意外进入时，被识别为实验不满足比较条件；正确/错误参考结果能验证 grader 区分力；运行中冻结的 harness/目标 Skill 发生非预定变化使相应比较失效，任务初始快照不匹配时不开始比较，获准的任务代码修改仍作为结果接受判定；超时和 API 错误不会生成成功值。采用 measurement-only 时遵循其原生 broken-run 口径，同时另报任务完成率与覆盖，不能只用有效测量子集代表用户成功率；局部代码结果不表述为现场收益。

**回退与边界。** 无法可靠隔离时保留受限观察，停止相对收益 claim；不改用户全局配置，不移除真实项目安全规则。先加强既有 runner，不新增统一评测平台。

### OPT-02 分离环境错误、任务失败和覆盖缺口

**问题与依据。** 既有路由 runner 曾将限流输出回显的提示模板误解析为路由结果；最新有效样本准确率也掩盖了一个类别无有效样本的事实。

**推荐方案。**

1. 分别记录任务正常结束后的行为结果、环境失败、未执行与解析不可判定；它们的含义由评测协议明确，禁止互相静默折算。
2. 同时给出计划样本、有效样本、环境错误、缺失任务类别和每类别结果。样本准确率与有效覆盖率同时呈现。
3. 解析只消费明确的最终结果区域，拒绝 prompt 回显与错误日志中的示例标签；双语等价输出与格式合规分开评价。
4. 重试次数、预算、缺失处理与停止规则在运行前冻结；为所有 attempt 保留获准的状态、耗时、费用与证据可用性记录，不只留下成功尝试。原始轨迹按 OPT-05 的数据处理约定采集与保留，不为维持样本完整而无限期保存敏感内容。
5. 完整覆盖是声称“全套通过”的前提；允许报告受限结果，但必须列出未测部分。

**源码落点。** `docs/validation/skill-evals/routing-audit-20260902/run_routing.py`、`benchmarks/agentic/run.py`、`docs/validation/skill-evals/README.md`。外部 skill-up 的结果采用其原生合同，本仓只做必要映射。

**产物与消费者。** 既有 result/report 中的事实汇总与重判记录，服务评测 owner、OPT-05 和默认路径的推广决定。

**验收场景。** 429+示例 ENTRY 不计成路由；某类别全部失败时明确覆盖空缺；中文标签可判语义正确但单列格式差异；同一试验重判可追溯到原结果和判定版本。

**回退与边界。** 在获准保留范围内不覆盖原始结果，重判生成可追溯的新结果；到期或撤回导致证据删除时标记证据不可用，不伪装为仍可复核。环境长期不稳时停止效果判断，不循环扩预算。优先完成现有补强的验证，不重复实现已有过滤逻辑。

### OPT-03 连接需求验收、实现和实际结果

**问题与依据。** 结构化需求、计划、review 和验证资产已经存在，但它们是否帮助用户识别漏项，需要在真实任务中闭环验证。测试通过本身也不能覆盖所有业务接受条件。

**推荐方案。**

1. 从一类业务变更或跨模块修复开始，沿用原有需求 ID 和 source refs，明确每个关键验收条件的可观察行为。
2. 同时保留成功路径、边界/失败路径、兼容与非功能要求；主观体验和业务价值由明确 reviewer/owner 判断。
3. 沿用上游需求标识建立“需求/验收条件 → 当前实现 source refs → 实际检查或观察结果”的关系；命令结果引用 verification-run-summary 中的对应检查。业务验收和覆盖是否充分仍由 LLM/reviewer 判断，引用存在不等于验收通过。
4. code review 同时检查需求遗漏、实现正确性、回归与残余风险，不把单元数、文件数或同名函数当成完成依据。
5. 未满足或未验证的条目保持可见；需求改变返回 owning producer，不能通过修改验收条件来适配失败实现。

**源码落点。** `skills/spec-prd/SKILL.md`、`skills/spec-plan/SKILL.md`、`skills/spec-work/SKILL.md`、`skills/spec-code-review/SKILL.md` 及其按需 reference。需求验收复用 code review 的 `Plan discovery (requirements verification)` 和后续需求完整性检查，消费原有需求标识、source refs 与实际验证结果。`docs/contracts/workflows/review-closure-traceability.md` 仅用于“审查 finding → 承接整改的 plan”的引用，不承担需求到实现、检查的映射；两条关系分别由既有 owner 维护，不新建中心需求库。

**产物与消费者。** 原有 plan 和 review 输出承载需求验收关系，verification summary 提供实际命令结果；已有审查 finding 的整改关系独立引用对应计划。开发者、reviewer 和 OPT-04/05 分别消费所需关系，不以整改记录代替业务验收。

**验收场景。** 测试绿色但关键交互缺失时仍暴露未满足条目；失败路径未测时不得全量完成；审查整改引用齐全但关键需求未满足时，需求完整性检查仍报告缺口；requirements-only 文件只能作为意图，不能用于实施单元完整性判定；上游 Product Contract 保持 owning boundary。

**回退与边界。** 首期通过现有模板和引用在试点中使用；若没有减少漏项或审查负担，不把详细表格推广为所有任务强制产物。脚本不判业务语义。

### OPT-04 强化运行证据与最终源码绑定

**问题与依据。** 当前 recorder、claim validator 和工作树指纹具备基础机制，但 recorded、consistent、实际执行、最终代码状态与业务接受仍需清晰连接。

**推荐方案。**

1. 首先保持现有合同语义：单项 consistent 是关系一致；不将其提升为独立业务验证，不擅自修改 `overall` enum。
2. 试点优先引用已有 CI 或宿主运行记录，保留命令、退出、工具/环境、日志与 source identity；不能用人工构造的 JSON 证明进程已运行。
3. 复用 working-tree-fingerprint 的 canonical 实现，在必要验证前后记录变化事实；验证期间或之后出现相关 mutation 时，原结果不能直接支持最终源码。指纹是整个工作树的保守漂移信号，不能直接判断某项变更是否影响验证，也不覆盖被 Git 忽略的依赖安装结果、数据库和远端状态；这些输入按当前检查所需范围另留非敏感环境事实，由 workflow/reviewer 判断适用性。
4. 继续保护全量检查聚合：引用通过子集不能隐藏 failed/not-run/degraded；必要检查未跑必须出现在收尾。
5. 业务代码和随任务交付的文档先完成，必要检查随后运行；收尾消费的日志与摘要使用既有 owner 的证据路径，试点私有原始输出按 OPT-05 的派生日志约定衔接。收尾前再次核对工作树，确认没有未处理的尾部变更。检查本身会改源码时不能静默接受前后不同的状态；证据产物是否进入指纹必须由既有路径与排除规则确认，不临时忽略业务文件来让指纹相等。
6. 只有试点确认现有回执无法支撑目标 claim，才单独设计最薄的执行观察补充；不在首期建立通用监督 runner。

**最小试验与判定。** 对一项已有验证入口的变更，分别检查正常收尾、验证后 tail edit、并发修改、运行环境改变四种情形。正常链能够回到实际命令与适用源码；其余情形应显示需要重新验证或收缩结论的范围。文件 hash 一致只支持其实际覆盖的字节事实，不能替代进程执行证据或业务接受。

**源码落点。** `src/cli/helpers/verification-run-summary.js`、`src/cli/helpers/honest-closeout.js`、`src/cli/helpers/spec-work-run-artifact.js`、`skills/spec-work/scripts/working-tree-fingerprint.cjs` 及对应 contracts。

**产物与消费者。** 继续使用各 workflow 自有 summary/ref 和 validator 输出；只有 spec-work 按现有条件写 work run artifact。review、debug 不接管 work-owned 状态。

**验收场景。** 验证前后被测源码不同或验证后 tail edit，不能直接复用旧结果；仅依赖/数据库环境变化而工作树 hash 不变时，也不能推断旧验证仍有效；只有 green 子集不能完成整体收尾；缺失、错误归属或越界日志被拒绝。证据写入不能制造未被解释的指纹变化，纯引用一致性不能被解释为真实业务通过。

**回退与边界。** 无可靠回执时保留诚实的受限记录，不补写真实性。若需 schema 变更，先固定兼容、版本和 consumers，再实施；旧记录保持原证据上限。

### OPT-05 建立真实用户试点和收益度量

**问题与依据。** 本轮读取的 field 对照链仍为空；现有机制、使用者感受与业务收益尚不能在同一口径下比较。

**推荐方案。**

1. 先完成作者/维护者的完整真实任务，再扩到 2-3 个愿意参与的团队；不把作者自用当外部采用。
2. 场景优先为跨模块修复、业务需求交付、会话/宿主接续。对可比较的任务固定模型、工具、权限、复杂度与接受标准。
3. 使用原生与当前 spec-first 对照，记录主动人工时间、墙钟时间、review 修改轮次、返工、缺陷与实际运行成本。
4. 初始每类 6-10 对仅用于探索；样本不足或方差过大时不作普遍提效结论，扩大规模需重新估算成本。
5. 记录拒绝参加、未完成、环境失败与任务选择，避免只观察成功用户；并发等待与人工投入分开计时。
6. 区分同类旧任务提效与新增任务价值；新增工作必须有真实 consumer 和接受结果。

**试点数据处理约定。** 真实仓库试点采集前，由数据 owner 在试点协议中明确以下规则；约定不完整时先使用公开或合成样本，不采集参与者的真实轨迹。

- 采集范围只包含验证所需的最少任务与结果数据；凭据值和无关个人信息不采集、不落日志，私有源码默认以受控 source ref 和 hash 引用。确需保留片段时，先明确该片段的用途、访问者与授权。
- 原始轨迹、命令输出和身份映射保存在仓库外的 owner 私有目录，仅向获准人员开放，不进入 Git，也不直接放入共享报告或知识库。
- 收尾记录器确需仓内日志时，由数据 owner 授权并在写入仓库前完成内容脱敏核查，再由原 workflow owner 将最小派生日志写入既有 workflow/run 的 logs 证据路径，默认不进入 Git。不得先复制原始输出再脱敏，也不通过符号链接或放宽路径校验引用仓外原件；`gitignore` 不代替访问控制。
- 私有记录保留原始输出与派生日志的对应关系；派生日志及摘要中的命令、路径等元数据一起纳入访问、保留和撤回清理约定。脱敏不得改写实际退出码或检查状态；原始或派生证据删除、不可用，或脱敏后不足以支持某项判断时，按实际剩余证据收缩对应 claim，不补写成功证据。
- 可共享报告独立生成并先脱敏，检查源码片段、路径、账号和其他可识别信息；共享或发布仍需 owner 授权。只提供检查结果或数据 hash 不能代替对报告内容的脱敏核查。
- 协议写明最长保留期限、可访问人员、撤回联系责任人，以及本地副本、备份和已授权接收方副本的清理方式；无法执行约定时不启动真实数据采集。
- 到期或参与者撤回时按协议删除原始数据，只保留另获准的匿名统计或撤回标记；记录缺失并重新评估受影响结论，必要时降级或撤回，不再宣称已删除的证据可回源。

**落点。** 复用 `docs/validation/ce-localization/field-validation/` 中现有 protocol/tasks/results 的设计经验；该目录仍归 CE 验证链，不将新试点结果冒写为 CE 结果。新试点使用独立验证报告，首期不新增公共 schema。

**产物与消费者。** 试点协议、逐任务证据、人工时间与成本记录、汇总/局限，供负责人决定推广，供 OPT-06/07/10/12 识别真实瓶颈。

**验收场景。** 失败与退出都进入获准的统计；任务变简单不能计成 harness 提效；观察窗内发现回归会修订判断；没有真实外部 cohort 时报告仍明确自用性质。模拟凭据、个人信息或私有源码片段不得随采集输出进入共享报告或 Git；未经授权者不能访问原始轨迹。仓外原始日志不能直接交给 recorder，获准的仓内脱敏派生日志能够沿用现有校验，残留敏感内容仍被拒绝；元数据一并核查，退出码和检查状态不因脱敏改变。撤回或到期清理同时覆盖原始和派生记录，证据可用性与关联结论同步更新。用于这些测试的合成 fixture 可按测试资产管理，不与真实参与者数据混用。

**回退与边界。** 招募、访问用户仓库、模型费用、外发与发布由相应 owner 授权后执行，访问仓库不自动授权保留或共享其中数据。数据处理约定未落实时不采集真实轨迹；无法招募时继续内部试验但收缩 claim。无需等待新指标平台。

### OPT-06 按任务加载最小充分项目上下文

**问题与依据。** context-bundle 已有路径与预算管理，图工具和知识 recall 也存在；“提供了上下文”尚不等于“相关、及时、足以支持当前决定”。

**推荐方案。**

1. 将输入分为稳定项目约束、当前任务的直接事实、条件展开的历史决策与方法。每项任务先取得目标、变化范围、适用约束、实际代码与验证入口；是否展开由下一步决定和证据义务驱动，不默认加载完整目录说明。
2. 常驻指导只保留不能轻易从源码推断的项目约束、关键命令与边界；详细例子和方法保留在 owning Skill reference。
3. 继续 summary-first 与 full-read-trigger；当缺少共享调用方、验收细节、现行约束或关键反例时展开对应 source。达到当前决策所需的充分性后停止扩张；不能为满足预算隐藏缺口，也不能为证明充分而无限遍历。
4. 图输出、索引和历史知识只产出候选；关键决定必须回到 current source、tests、logs 或 owner evidence。
5. 比较“无上下文增强”“当前输入”“按需候选输入”的任务结果、人工补充次数、漏项、耗时和 token，避免只统计文件大小。

**最小试验与判定。** 选一个有共享调用路径的修复任务或一个需要历史决策的计划任务，对照相同输入下的读取与结果；同时用“缺关键约束”和“加入无关材料”两种反例检查是否正确展开或保持聚焦。记录必要信息是否被正确使用、用户补充次数、重复读取和调用成本；更少 token 但遗漏关键约束不能保留候选。

**实现边界。** 当前 context-bundle helper 对 caller 给定路径做包含、排除与预算处理，不承担语义检索、相关性排序或充分性证明。路径选择与展开理由仍由 LLM/workflow 负责；它输出的预算状态或 confidence 不能被解释为信息质量已确认。图为空也不能证明不存在依赖，保留直接回源路径。

**源码落点。** `src/cli/helpers/context-bundle.js`、`docs/contracts/context-bundle.md`、`docs/contracts/context-governance.md`、`skills/spec-project-rules/`、`skills/spec-plan/` 与 `skills/spec-debug/` 的对应按需 reference。

**产物与消费者。** 复用 context-bundle、artifact summary、source refs；由 planning/work/debug/review 消费，不建立平行项目画像真相。

**验收场景。** 遗漏关键约束时触发展开；加入无关材料不应迫使全量阅读；图陈旧、为空或不可用时能够直接回源；预算不足时明确缺口而不宣称充分；runtime mirror 不混入普通 source context；减少 token 但任务质量变差时候选失败。

**回退与边界。** 保留直接读取路径；不默认增加 embedding、知识图数据库或统一上下文总线。检索范围与授权一致，不能为丰富上下文静默读取相邻私有仓库。

### OPT-07 降低入口、确认和首次使用摩擦

**问题与依据。** quickstart 已存在，用户需要的改善是从安装、发现入口到完成真实任务的体验；路由和多次确认也可能变成额外人工工作。

**推荐方案。**

1. 首次体验沿“安装/初始化 → 宿主实际发现 → 当前任务所需能力就绪 → 完成可检查结果”走查，并分别记录各阶段的阻力。按用户真实任务选择入口，不强制所有用户先生成同一种文档；无需的 optional provider 不应成为当前任务的前置条件，真正必需能力缺失时仍按既有边界处理。
2. 对已授权、范围明确的工作持续推进；问题集中于会改变产品行为、目标范围或副作用权限的未决点，避免重复索取已有信息。
3. 保持现有 failure/debug、显式 workflow、review-only 等边界。在 owning workflow 内缩短不必要环节，不通过绕开边界追求快。
4. skill description 和入口说明只消除真实误解；近邻辨析按需读取，避免把完整路由知识常驻给每个请求。
5. 增加“正确持续推进”“没有无效打断”的行为验证，同时保留必须停下询问或拒绝副作用的正例。

**最小旅程与判定。** 对新会话各走查一项明确本地任务和一项只读审查，并加入一个确需新授权的副作用变体。逐次记录用户是否提供了新信息、确认是否改变范围或权限、由此产生的主动操作时间。目标是减少重复确认和无效转交，不是把提问数降到零；观察到安全/验收退化时停止候选。

**实现边界。** quickstart 当前只衔接环境探测与 init，不能从独立 CLI 进程假装执行宿主会话 workflow。初次使用的优化应明确告诉用户哪个阶段已经完成、实际下一步在哪里发生；不新建隐藏后台编排来掩盖宿主尚未发现入口。

**源码落点。** `src/cli/commands/quickstart.js`、`src/cli/commands/init-output.js`、`src/cli/lang-policy.js`、`skills/using-spec-first/`、`docs/05-用户手册/01-快速开始.md` 及命中的 workflow owner。

**产物与消费者。** 首次旅程记录、摩擦清单、已改动的入口/按需说明，服务真实新用户与长期使用者。

**验收场景。** 用户明确要求生成本地方案时可以直接交付；已明确的参数不重复确认；init 成功但宿主未发现入口时不得报首次任务完成；不相关 optional provider 缺失不冒充当前任务阻塞；需要新外发/发布权限时停止对应动作；review-only 发现问题仍不擅自修复；修复请求仍进入 owning debug 路径。

**回退与边界。** 减少提醒后若发生错路由、越权或完成遗漏，恢复对应必要规则；不建设关键词路由器，不为“低打扰”新增静默副作用。

### OPT-08 加强跨会话接续与陈旧状态识别

**问题与依据。** handoff 已规定 summary、source_refs、freshness 与 limitations，但真实中断和工作树变化后的恢复仍需任务级验证。

**推荐方案。**

1. 原生会话恢复与 compaction 留在当前任务中，保留目标、当前范围、未完事项、决策依据、最后验证与脆弱环境事实；继续工作仍遵守当前有效授权和用户最新指令。
2. workflow 内部需要持久化的状态由原 owner 按既有条件写入；普通继续、状态总结和返回 caller 不触发 `spec-handoff`。“状态需要持久化”本身不构成显式交接的调用条件。
3. `spec-handoff` 仅在用户明确要求创建交接、转到新会话，或查找/读取既有交接时调用。显式恢复只对用户选定来源进行定向读取、获准的只读核查与状态说明，随后等待用户选择下一步；不自动开始代码实施、其他 workflow 或延后副作用。
4. 在对应路径获准的范围内核对当前 source、相关工作树和已有产物；不能只依据“上次已完成”的文字继续推进。将旧验证、tail edit、并发修改、计划状态变化和机器本地服务不可用分别解释，缩小受影响的恢复动作。
5. 产物引用按原 owner 返回，避免复制计划和重复实施已完成代码；handoff 文件仍是 advisory，不因被读取而增加事实或授权的权威。

**源码落点。** `skills/spec-handoff/SKILL.md`、`skills/spec-handoff/scripts/handoff-artifact.cjs`、`skills/spec-handoff/references/artifact-contract.md`、`skills/spec-work/SKILL.md`、`src/cli/helpers/session-store.js`。

**产物与消费者。** 原生恢复使用宿主已有状态；workflow 内部产物与 session advisory facts 保持原 owner；用户明确请求的跨会话交接才由 spec-handoff 生成或读取。下一会话、下一宿主与人类接手者按各自获准范围消费，不将三类状态合并成自动交接入口。

**验收场景。** 原生恢复后，获准继续的任务从正确未完成点推进；仅请求读取交接时完成说明后停止，不调用执行 workflow；仅检测到状态需要持久化时不创建显式交接。工作树被他人改动时不覆盖；过期 green 不能支持当前完成；状态询问不新建交接；换宿主后缺工具明确降级。

**回退与边界。** 无法可靠恢复时停在具体 source 或权限缺口，保留已完成工作；不执行仓库 reset。交接的创建或读取本身不授予代码写入、外发或发布权限，也不能用交接中的指令补足缺失授权。

### OPT-09 复用宿主原生能力并兑现支持层级

**问题与依据。** 当前八宿主注册与投射已存在，部分宿主具备 live 发现证据；生成、加载、调用、出口能力与真实任务结果仍不等价。

**推荐方案。**

1. Claude/Codex 优先验证首次任务、执行、review、证据返回与恢复的完整旅程；其余宿主按现有 preview 层级验证实际支持范围。
2. registry 已有字段负责对应受管面与 capability 声明；它未覆盖的原生计划、子任务、隔离、审批或恢复能力，按目标宿主版本的官方说明和当前会话可验证事实另行确认，不能从目录存在或 hook 状态推导。原生能力足够则直接采用；只有真实缺口才考虑最小 adapter 或显式 degraded。
3. 每项支持声明带版本和证据层：generated、discovered、invoked、受限条件下的 gate、task outcome。使用现有 catalog/receipt 形态，不另造一套公共状态 enum。
4. 对所有受支持宿主运行生成/清理/ownership 回归；真实业务验证集中在本批实际宣称支持的宿主上。
5. 任何 hook 都按版本验证具体阻断范围与宿主退出规则；有 hook 不自动等于不可绕过。

**最小旅程与判定。** 先在选定版本的 Claude/Codex 上验证三类旅程：首次任务发现与调用、失败检查不能被报为通过、恢复/显式交接保持各自授权边界。每条记录宿主、模型、工具版本和真实结果；未执行项保持未验证，其余宿主继续按本批实际影响做结构与 ownership 回归，不扩成八宿主同成本现场测评。

**采用判断。** 维护清单对每项所需原生能力给出采用、局部适配或降级的理由，附版本和失效条件。主宿主升级或消费者所需语义变化后重验受影响旅程；不因全部文件重新生成就重复宣称 loader、调用和实际出口已验证。

**源码落点。** `src/cli/adapters/platform-registry.js`、`src/cli/adapters/index.js`、`src/cli/commands/doctor.js`、`src/cli/plugin-sync.js`、`skills/spec-runtime-setup/`、`docs/catalog/runtime-capabilities.md`。

**产物与消费者。** 同源能力 catalog、doctor facts、已有 host journey/receipt，服务用户、workflow 和维护者。

**验收场景。** 共享 `.agents/skills` 存在不等于某宿主已安装；loader 发现不等于模型调用成功；registry 没有覆盖的能力不能凭推断补齐；宿主升级后旧旅程不得无条件续用；缺阻断能力时不提升 claim；某宿主 clean 不删除另一宿主或用户拥有的资源。

**回退与边界。** 不以本方案删除宿主支持；如有收缩建议，单独提出迁移与 owner 决策。实现仅改 canonical source，需要时用 `spec-first init` 投射并验证。

### OPT-10 用任务结果驱动 Skill 与模型适配

**问题与依据。** 已有较完整 Skill eval 与近邻路由资产；主要提升方向是测实际任务完成与成本，并在模型变化时确认补偿机制仍然有用。

**推荐方案。**

1. 保留结构、行为、运行成本、现场结果四轴，拒绝以总分抵消关键失败。
2. 每个重点 Skill 从真实缺陷和高频任务形成少量代表样本，包括显式调用、隐式调用、近邻负例、正常不触发和实际结果检查。候选改写前冻结受保护行为、共同 case/rubric、development/holdout 分离和原生基线；前置保护不能等到第三批消融时才建立。
3. 确定性 grader 检查文件状态、测试结果与副作用；LLM/reviewer 判断语义和质量；两者不互相冒充。
4. 为多种正确表达和实现留出空间，不把固定入口措辞、固定调用次序当成所有场景的唯一答案。
5. 模型或宿主重大升级后，先用旧 Skill source 在新模型/宿主上取得基线，再与同环境的新候选比较；旧模型仍可用时才补旧环境对照，防止把模型提升归因于文案修改。入口冗余、探索深度、审查角色、reset、任务拆分逐项消融，不同时改变多个变量后猜测原因。
6. holdout 与开发集分开；先聚焦回归，再在需要时扩大，保存失败与弃用候选。

**最小试验与判定。** 优先承接既有 `docs/plans/2026-08-27-001-perf-skill-runtime-context-pilot-plan.md` 对 spec-code-review/spec-plan 的候选投资门，先确认哪一项有真实冷上下文和受保护行为覆盖。未通过原 pilot 投资门时保留原实现，不用本总方案绕过或改写它的范围。首次消融仅改变一个已明确的条件加载点，比较任务结果、实际读取、用户修正与总运行成本。

**处置规则。** 任务正确性、授权与必要验证先满足，再看预先约定的实际收益。只在特定模型/场景有效时保持定向使用；只有结构 bytes 变化则报告结构结果；测量不确定时保持实验状态。删减机制和保留机制都要有证据，不让 rule-maturity 的观测次数直接产生默认推广。

**源码落点。** 目标 `skills/<name>/evals/`、`docs/validation/skill-evals/`、`benchmarks/agentic/`、`docs/contracts/workflows/fresh-source-eval-checklist.md`。治理观察复用 `src/cli/helpers/rule-maturity.js`，不自动提升规则 stage。

**产物与消费者。** 模型/宿主/source 绑定的比较报告与能力处置结论，服务 Skill owner、OPT-06/07/09 和默认路径决策。

**验收场景。** 文案更短但 reference/tool 调用与人工修正增加，必须反映总成本；回答入口正确但实际任务失败或越权，仍不能通过；新模型配旧 Skill 已取得的提升不计入候选收益；holdout 未参与候选调优；无充分收益证据的机制不自动推广为必经步骤，用户问题变体仍能保持正确行为。

**回退与边界。** 不创建自动改写并发布 Skill 的循环；候选保留或退役由明确验证结果和 owner 取舍决定。脚本只统计事实，不自动决定架构与价值。

### OPT-11 让工程知识产生可撤销的复用收益

**问题与依据。** docs/solutions、recall 与 promotion 已有边界；需要证明其是否让后续不同任务少返工，而不只是产生更多知识文件。

**推荐方案。**

1. 从已验证任务中提取可复用的项目约束、决策和失败模式，按条目增量更新，避免不断重写整份长摘要。
2. 保留来源、适用范围和 invalidation condition；同次生成、自检和总结不互相提升权威。
3. 新任务将 recall 视为 advisory，回到当前源码和验证事实确认适用性。
4. 在当前任务的获准证据中记录引用了哪条经验、回源检查了什么、它是否改变决定、结果是否被接受，以及误召回和修正成本；只有命中或模型声称“有帮助”不算有效复用，不新增全局知识评分库。
5. 模型/工具版本、依赖、业务约束或原始证据发生相关变化时，先记录变化事实并检查适用性；hash 变化是复核线索，不让脚本自动决定语义失效。新反例或证据不足时收缩使用范围，由 compound-refresh 的 owner 决定修订、替换或撤销。

**最小试验与判定。** 选一条有真实消费者且依赖明确环境条件的经验，在另一项任务中检查回源与复用，再用条件已变化的任务检查是否停止盲目沿用。`docs/solutions/skill-simplification-patterns.md` 这类依赖旧模型与 benchmark 条件的经验可作为复核候选，先核对原始测量与外推范围，不因本次讨论就自动改写或退役。

**收益与隐私边界。** 保留“正确复用、无关未使用、陈旧被拒绝、错误应用后纠正”的实际案例，并比较用户补充、重复调查和返工。只有在必要验证满足且新任务受益时才宣称复用价值；试点私有源码、身份或原始轨迹不能随 learning 进入共享知识库，继续遵守 OPT-05 的数据约定。


**源码落点。** `skills/spec-compound/`、`skills/spec-compound-refresh/`、`skills/spec-compound/references/schema.yaml`、`docs/contracts/knowledge/knowledge-harness.md`、`docs/solutions/`。

**产物与消费者。** 经确认的候选增量和已验证 learning，由后续 plan/debug/work/review 消费。

**验收场景。** 一条旧经验在适用条件变化后不能直接沿用，无关变更也不能被脚本直接判作语义失效；无证据的总结不能晋升；修改既有 learning 时检测并发漂移；新任务必须有回源和结果证据，命中数不代替有效复用；私有轨迹不能混入共享 learning。

**回退与边界。** 无效经验降级或撤销，不为“保持知识量”保留；不默认建设向量平台或批量补写全部 legacy 字段；高风险知识仍承担相称的复核。

### OPT-12 收敛重复产物并外显真实项目价值

**问题与依据。** 项目已有大量战略、计划、验证和知识资产；新增文档如果不被消费，会提高查找和维护成本，也容易把旧计划误当当前事实。

**推荐方案。**

1. 重要产物说明 producer、consumer、当前用途与失效条件；已有来源可引用时不重复生成一份正文。
2. 区分策略、需求、实施计划、验证记录和知识，明确哪个文件拥有对应决定；后续行动引用稳定 ID。
3. 先检查引用和消费者，再标记 superseded/历史快照；归档、删除和移动单独确定范围，不按天数机械删除证据。
4. 用 OPT-05 的真实结果制作少量可复核案例：任务、输入、实际运行、人工投入、结果、限制和复用方法。
5. README/用户手册只宣称证据支持的范围，演示、作者自用、外部试点和可重复收益分开表达。

**落点。** `docs/plans/`、`docs/validation/`、`docs/strategic-review/README.md`、`docs/05-用户手册/`、`README.md`、`README.en.md`、`README.zh-CN.md`；实现时按选定消费者限定文件集合。

**产物与消费者。** 有明确指向的索引与状态说明、基于真实任务的使用案例，服务维护者、首次用户和采纳决策者。

**验收场景。** 新用户能找到一条真实使用路径；旧候选方案不会被表述为已上线；不存在证据的提效比例不进入介绍；归档后引用仍可解析且关键验证可追溯。

**回退与边界。** Git 只保存获准的脱敏产物，原始试点轨迹按 OPT-05 的私有存储和保留约定处理，不以保留历史为由拒绝到期或撤回清理。归档前预览路径与影响；不在本方案写作阶段执行清理。对外发布按 owner 授权执行。

## 5. 共同架构与产物边界

### 5.1 职责分工

| 层 | 拥有的职责 | 不拥有的职责 |
| --- | --- | --- |
| 宿主 | Agent loop、工具执行、会话/压缩、实际 sandbox/approval primitive | 项目业务验收与长期知识权威 |
| scripts/tools | source/path/hash、schema、运行与环境事实、引用和机械不变量 | 产品优先级、语义影响面、review 充分性、知识价值 |
| LLM/workflow | 意图理解、方案、上下文选择、语义覆盖、风险解释 | 伪造命令执行、环境结果与 owner 授权 |
| 项目 owner/reviewer | 产品取舍、关键授权、真实接受、推广范围 | 用主观感受替代确定性事实 |

### 5.2 现有产物优先

| 信息 | 首选承载 | 消费者 | 新增约束 |
| --- | --- | --- | --- |
| 需求与验收 | owning Product Contract/plan | plan/work/review/owner | 不复制第二份产品真相 |
| 上下文与内部状态 | context-bundle、artifact summary、owner 自有状态 | 下游 workflow/当前任务 | 保留 source refs、freshness、limitations；不因需要持久化而调用显式交接 |
| 显式跨会话交接 | 现有 spec-handoff 产物 | 用户选定的新会话/接手者 | 用户明确触发；恢复仅定向读取与说明，不自动执行下一步 |
| 检查结果 | verification-run-summary | debug/work/review closeout | 实际结果与来源、范围清楚 |
| 一致性判断 | honest-closeout 输出 | 当前 workflow/用户 | 不是第二份 durable closeout artifact |
| work 运行记录 | 现有条件式 spec-work-run-artifact | work/caller | 不扩大到其他 owner 的状态 |
| 规则观测 | rule-maturity shadow 记录 | owner/质量评估 | 不自动 promotion |
| 长期经验 | docs/solutions 的现有结构 | 后续任务 | 回源、适用范围、失效和更新纪律 |
| 试点收益 | 独立脱敏报告与私有原始记录分开保存 | 获准负责人/参与者 | 按 OPT-05 限定采集、访问、保留与清理；原始轨迹不进入 Git，外发单独授权 |

### 5.3 新机制的条件

首期允许做已有 owner 内的局部实现、测试补强与试点 instrumentation。若需要新公共字段、receipt、脚本或持久存储，提案必须同时说明当前哪项能力无法承载、真实 consumer、失败方式、兼容方案、验证和退役条件。

这不是“零新增代码”的承诺，也不把一次性脚本当成没有维护成本。新边界的成本应在决策时显式列出。

## 6. 最小执行顺序与交付批次

### 6.1 第一批：可信比较与首条交付链

**范围：** OPT-01/02 的最小校准，加 OPT-03/04 的一条真实任务；OPT-05 仅内部试点。

**建议首任务：** 选择已有复现与明确验收的跨模块修复，或一项范围清楚的业务 feature。优先选择已具备测试入口、可以回滚、没有未经授权外部依赖的任务。

**协议准备：** 比较前按 OPT-01 分别明确冻结机制、任务初始快照和最终结果的身份；真实私有数据接入收尾记录器前，按 OPT-05 落实原始输出到脱敏派生日志的授权、路径、访问和清理关系。这不阻塞公开或合成样本的校准，不新增公共 schema，也不放宽现有 validator。

**交付清单：** 分组输入和环境事实；冻结机制与任务初始快照；最终 source/变化范围；验收到检查的映射；实际命令/结果及日志可用性；涉及私有数据时的日志派生与清理约定；review 反馈；人工时间与成本；未完成和限制。

**完成标准：** 第三方能够据记录理解任务、复核关键结果，并区分未执行、失败与完成；环境错误不会被记为模型成功；不要求此时已经证明普遍提效。

### 6.2 第二批：现场反馈驱动的使用与上下文优化

**范围：** OPT-05 在数据处理约定落实后扩展至授权参与者，按第一批主要瓶颈选择 OPT-06/07/08，OPT-09 负责对应主宿主旅程。相关 Skill 候选开始修改前，先完成 OPT-10 的受保护行为、baseline 与共同评测输入冻结；任何更早批次若改 Skill，同样适用。

**交付清单：** 正常任务与失败样本、首次使用路径、接续案例、人工补充与无效打断记录、候选对照。

**完成标准：** 候选在新任务上仍保持正确与边界，不将节省的时间转移给 reviewer；缺能力宿主明确降级。

### 6.3 第三批：可复用能力与成本收敛

**范围：** OPT-10 在前置基线与回归基础上进行集中消融、模型适配和处置，OPT-11 处理已有重复使用/失败证据的经验；OPT-12 清理本次实际涉及的重复指向与介绍。第三批不是首次建立 Skill 质量保护的时点。

**交付清单：** Skill/模型消融报告、学习条目在另一任务中的复用、退役候选和案例材料。

**完成标准：** 能区分哪些机制值得常驻、按需、继续实验或退役；不因默认路径变短而削弱关键验收或授权。

### 6.4 90 天建议节奏

| 时间 | 主要动作 | 核心验收 | 继续条件 |
| --- | --- | --- | --- |
| 第 1-2 周 | 样本/输入校准、真实任务选定、首链准备 | 比较条件可靠，业务验收和 owner 明确 | 有可以实际运行并审查的任务 |
| 第 3-6 周 | 第一批闭环、内部对照、授权小规模试点 | 实际结果、人工时间、review 和成本齐备 | 真实问题被定位或存在值得继续验证的收益 |
| 第 7-10 周 | 改主要上下文/使用/接续瓶颈，重点回归 | 新任务上质量与边界保持，成本不转嫁 | 至少一类场景出现可重复的净改善 |
| 第 11-12 周 | 消融、知识复用、处置与案例 | 默认/opt-in/暂缓/退役各有依据 | owner 接受证据范围与推广方式 |

研发线默认最多同时推进两个实质性工作项；无交叉写面、无需同一评测环境的只读研究可独立开展。不是所有优化必须等待外部试点，也不能让无消费者的新机制占满首期带宽。

### 7.1 执行强度

- 文档-only：核查本次引用、数字、状态和范围，不启动代码回归或昂贵模型评测。
- CLI/脚本：最窄 unit/contract 加命中集成路径；共享行为变化才扩大到相关主链。
- Skill prose：新会话 fresh-source 行为验证；不能用当前已缓存 Skill 调用证明新定义生效。
- runtime generation：所有受支持宿主的结构与 ownership 检查；真实能力只宣称已测版本和旅程。
- 默认路径或普遍价值 claim：需要跨任务 holdout、成本观察和相称的 field evidence。

`npm run typecheck`、`npm run lint:skill-entrypoints`、`npm run test:unit`、`npm run test:integration`、`npm run test:smoke`、`npm run build` 按改动面选择。已知既有失败、环境失败和本次引入的问题分别报告，不把局部通过表述为全量通过。

## 8. 成功指标与度量口径

| 指标 | 采集与定义 | 判断方式 |
| --- | --- | --- |
| 可信变更周期 | 任务确认至必要验证和 reviewer 接受；墙钟与排队/返工分段 | 匹配任务比较中位数、长尾和未完成数，未完成任务不能从分母消失 |
| 主动人工投入 | 澄清、操作、审查、纠错与恢复时间 | 与 Agent 等待、并发工作分账 |
| 接受与质量 | 首次接受率、修改轮数、约定观察窗内缺陷/回滚 | 关键退化阻止推广，不被速度抵消 |
| 证据与授权边界 | 假完成、旧证据、缺失关键验证、越权/范围偏离 | 按严重度及实际环境结果判断，零观测不等于零风险 |
| 有效复用与持续使用 | 自愿继续使用，经验在新任务中回源并改变决策，误召回与修正 | 不把调用、命中、下载或文档数量当作收益 |

token、调用次数、加载 bytes、CPU/内存、运行费用与评测耗时作为诊断与成本数据，不单独代表价值。`quality-adjusted throughput` 只计满足质量与接受条件的变更，并同时披露人工与运行成本。

基线建立后由 owner 冻结目标。可信周期下降约 20% 或人工投入下降约 25% 可作为讨论起点，但必须报告不确定性和质量条件；本方案未将其标记为实测收益或已批准承诺。

## 9. 分工、资源与成本控制

| 责任 | 工作 | 关键边界 |
| --- | --- | --- |
| 研发负责人 | 选择首要场景、排序、资源和停止决定 | 不以机制完成代替价值验收 |
| 工程 owner | 当前 source 核查、局部实现、回归与兼容 | 不接管其他 workflow/仓库的真相 |
| 评测 owner | 输入隔离、固定协议、样本覆盖、结果与成本 | 不删除失败样本来改善分数 |
| 使用者/reviewer | 业务验收、人工负担、缺陷与采用反馈 | 真实接受与主观感受分别记录 |
| 维护者 | 发布、runtime、历史产物与知识更新 | 只在实际授权范围内执行副作用 |

角色可由同一人承担，但应声明独立性上限。外部参与者、模型费用、数据访问和发布资源在对应阶段落实；不足时缩小试点，不伪造独立验收。

每个实验运行前固定任务数量、重复次数、并发、timeout 与费用上限。先验证少量可运行样本，发现测量错误先修判定；只有出现新证据、失败或明确覆盖需要时再扩大，不无条件反复全量跑。

## 10. 兼容、迁移与回退

1. **Source/runtime。** 所有实施先改 source；根指令的受生成 slice 由 owning generator 同步。需要更新 runtime 时使用 `spec-first init`，保留预览和受管范围。
2. **Schema。** 首期沿用现有 schema。确需扩展时列出 writer、reader、CLI 输出、旧记录行为和测试；不把未知旧记录自动升级为更强证据。
3. **用户流程。** 优化确认和路由不改变既有权限来源；不能把推荐、只读审查或计划批准自动转换为 commit/push/发布授权。
4. **旧产物。** 优先加引用与状态说明，不批量覆写；归档前检查消费者，获准保留的关键证据保持可访问。试点原始数据的到期或撤回按 OPT-05 执行，删除后更新证据可用性及受影响结论。
5. **候选回退。** 候选使用隔离工作区或可撤销补丁；失败时撤回本批范围，保留原始测量和失败结论，不覆盖并行用户改动。
6. **默认推广。** 先在目标场景 opt-in，跨新任务与目标宿主验证后再转默认；不将一台机器或一个模型的结果扩展为八宿主承诺。

## 11. 风险与决策触发

| 风险 | 早期信号 | 应对与停止条件 |
| --- | --- | --- |
| 优化方案再次成为文档堆积 | 没有首条真实任务，持续新增协议 | 暂停新增机制，优先完成 OPT-03/05 |
| 测量被配置/网关污染 | A/A 不稳定、某类无有效样本、加载来源未知 | 停止相对收益 claim，处理实验条件 |
| 速度转嫁成本 | Agent 更快，review/返工更慢 | 不推广；按总人工与质量判断 |
| 低打扰变成越权 | 不询问但扩大 scope 或外发 | 阻断对应副作用，恢复必要边界 |
| 试点原始数据暴露或超期保留 | 敏感内容进入共享产物、访问者超出约定、清理责任未落实 | 停止采集或共享，按 OPT-05 处理访问、脱敏与清理，并更新证据和结论 |
| 过度压缩上下文 | 关键约束漏读、反复澄清 | 恢复必要内容，先满足语义充分 |
| 过度编排 | Agent 数增加但锁、等待和冲突上升 | 降低并发，比较最小分工与原生路径 |
| 旧经验污染 | 新 source 与学习不符仍被沿用 | 降级/撤销并记录失效，回源确认 |
| 外部收益不成立 | 用户不愿继续用或看不到改善 | 缩小目标场景或退役相应机制 |
| 兼容维护失控 | 新宿主持续占据主链验证带宽 | 保持分级，先保障实际用户旅程 |

以下选择在对应工作启动前确认即可，不阻塞本方案交付：首个业务仓库和任务、参与者与数据权限、费用/时间预算、首批宿主版本、推广目标；涉及公共 contract 或新增 durable mechanism 时，再由该能力 owner 决定版本与兼容方案。
