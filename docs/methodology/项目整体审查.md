默认中文输出。

# 一、审查目标

本次审查不是普通代码 Review，而是从以下视角判断 `spec-first` 是否真正具备企业级 AI Coding Harness 能力：

1. 是否不是零散 Prompt / Skill 集合，而是具备 Harness 架构。
2. 是否形成 PRD → Context / Graph → Spec → Plan → Work → Review → Evidence → Knowledge 的完整闭环。
3. 各个 Skill 的逻辑是否正确、执行是否标准化、产物是否高质量。
4. 是否具备执行约束、质量门禁、证据链、评测反馈、知识回流和团队治理能力。
5. 是否能支撑团队级 AI Coding 落地，而不是只适合个人使用。
6. 是否能真正提升工程效能，包括需求澄清效率、开发效率、Review 效率、Bug 修复效率、返工率和知识复用率。

核心判断公式：

```text
Harness = 流程编排 + 执行约束 + 证据验证 + 评测反馈 + 知识回流 + 团队治理
```

# 二、审查范围

请完整审查项目中的以下内容：

1. README、官网说明、架构文档、使用文档。
2. skills 目录下所有 Skill。
3. agents 目录下所有 Agent。
4. docs 目录下所有流程、规范、设计文档。
5. scripts、commands、配置文件、示例文件。
6. CHANGELOG、贡献规范、版本说明。
7. 与 PRD、Spec、Plan、Work、Review、Evidence、Knowledge、bug-fix 相关的所有产物模板和流程说明。
8. 项目中体现 Context、Execution、Review、Evidence、Knowledge、Governance 能力的内容。

如果项目中某些目录或文件不存在，也要明确记录为缺失项，不要忽略。

# 三、基本原则

审查过程中必须遵守以下原则：

1. 先理解项目定位，再审查实现细节。
2. 先审查主流程，再审查单个 Skill。
3. 先判断是否具备 Harness，再判断工程化成熟度。
4. 不只看“有没有”，还要判断“是否正确、是否稳定、是否可执行、是否可验证”。
5. 所有结论必须尽量基于源码、文档、目录结构、模板内容或示例产物。
6. 不要只给抽象评价，必须输出具体问题、影响、证据、建议和优先级。
7. 不要修改源码，除非用户明确要求。
8. 如果发现文档与源码不一致，必须单独列出。
9. 如果发现核心流程无法闭环，必须标记为 P0。
10. 如果某项能力只有概念描述，没有实际示例、模板、脚本或可执行路径，应标记为“概念具备，工程化不足”。
