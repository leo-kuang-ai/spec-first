# 实测 36166 行 AI 指令:正确率零提升,成本最高贵 4 倍

这篇文章,从一个让我们有点难堪的数字开始:**36166**。

这是我们仓库里"指挥 AI 干活"的指令总行数——什么时候必须做计划、完成前必须跑测试、审查时只许看不许改。我们维护着一个开源项目 spec-first(一套管理 AI 编程工作流的工具,支持 Claude Code、Codex、Cursor 等宿主),核心资产是 37 个 skill。如果你也在维护团队的 CLAUDE.md、rules、prompt,你手上大概率有一份类似的东西,而且还在不断加行数。

8 月 20 日到 9 月 2 日,我们把这 37 个 skill 拆开做了一次全量体检:三个阶段、三套互相独立的方法、四百余次真实 LLM 调用(40+ 次行为门运行 + 180+ 个双引擎测评 case + 198 次路由调用,另有 45 人次独立盲评)。

先说三个反直觉的结论:

**01 36000 行指令,大部分可能已被模型"内化"——加载它们,正确率零提升,成本最高贵 4 倍。**

**02 AI 最隐蔽的失败不是做错事,而是"好心越界":它识别出这个请求不该自己做,承认了规则,然后把活干了。**

**03 任务做对 ≠ 流程守住:表现最"自信"的一组引擎,入口合规率只有 71.2%——但原因比"模型不行"有意思得多。**

三个结论是最便宜的部分。这次测评的方法、两次翻车事故、和六条可以直接抄走的设计守则,才是这篇文章剩下的价值。

---

## 一、第一问:36000 行指令,正确率到底涨了多少?

**方法:行为门测试。** 我们搭了一套 benchmark harness:每个任务在独立 workspace 里运行,自动评分器只检查最终代码是否满足特定标准(不靠人眼看),同一 seed 重复运行测方差,API 失败直接标记而非计零分。

选了四个最能代表"工程素养"的维度:

- **根因修复**:bug 报告只提了 `transfer()`,真正要改的是共享的 `_debit()`,模型找得到吗?
- **代码复用**:仓库里已有 `slugify()`,要实现 `unique_slug()`,模型会复用还是重写?
- **安全默认**:实现路径拼接函数,会不会主动防目录穿越?
- **过度设计**:一个只被调用一次的函数,用户要求"加缓存优化性能",模型敢不敢拒绝?

三个对照组:**baseline(零指导,只给任务)**、加载 spec-debug(393 行的 bug 诊断 skill)、加载 spec-work(518 行的实现 skill)。模型统一用 Claude Sonnet 5。

**结果:四个维度全部饱和。**

四十余次有效运行里,baseline **20/20 = 100%**。加载 skill 的两组:spec-work 10/10,spec-debug 13/14(93%)。这里要交代口径:行为门抽的是职责最重的两个 skill(合计约 900 行),其余 35 个 skill 的验证由第二问的逐个行为实测承担。至少在我们测的 Sonnet 5 上,模型已经会"改函数前先看谁调用它"、会 grep 既有实现并复用、会写安全的路径拼接、会做 YAGNI 判断——最合理的解释是,这些做法早已进入当前模型的训练分布。我们当年写在指令里的谆谆教诲,加载与否已经不影响正确率。

更扎心的是成本(8 月测试时点、单任务样本):

| 任务类型 | baseline 成本 | 加载 spec-debug | 成本倍数 |
|---|---|---|---|
| 根因修复 | $0.33 | $0.67 | 2.0× |
| 代码复用 | $0.17 | $0.68 | 4.0× |

如果指令没有正确率收益,这些 token 买到的只有噪声。

还有一个细节值得玩味:spec-debug 掉到 93%,不是这个 skill 写得差,而是**用错了地方**——它是诊断 bug 的 skill,被塞给实现类任务时反而误导。工具没有错,拿错工具才是真实损失。

### 插曲:一张 6/6 的满分表,和 tok=0 的破绽

测试初期我们踩了个大坑:24 个测试单元因为 API 403 认证失败,**一次都没真正运行**,但评分器把测试种子文件当成了 agent 的产出,汇总出一张漂亮的"6/6 vs 6/6"。唯一破绽是日志里的 `tok=0, cost=$0, time=0.3s`。基于这批假数据,我们差点改了文档、写了 CHANGELOG。

修复措施:API 失败返回 `correct=None` 并从所有比率中排除;结果表强制带失败计数列。由此沉淀一条通用守则:

> **读任何 benchmark 结果之前,先确认工作真的发生了。零成本的满分,优先怀疑基础设施故障,而不是模型很强。**

**这一阶段的行动**:把结论直接写进项目根指令顶部——"先用 baseline(零指导)尝试你的任务,只有在模型犯了特定错误时,才加载对应 skill。"同时保留这套门作为回归测试:模型换代后重跑,哪天 baseline 掉下来了,那段指令就重新有价值了。

## 二、第二问:它认出了越界,承认了规则,然后把活干了

行为门测的是"通用能力饱和"。但 spec-first 的价值主张从来不是教模型写代码,而是**治理**:该计划时计划、该审查时审查、声明完成必须有证据。这部分行为必须逐个 skill 实测。

8 月 30 日到 9 月 2 日,37 个 skill 全量交叉测评,两轮推进。判卷用三条互相独立的线,白话版:**一队用两个引擎真刀真枪跑对抗测试;一队按 9 个维度做结构体检;每次修改都要过三个独立裁判的盲评(改前改后同场对比,三票全过才保留)。**

**数字一览**:两轮约 180+ 双引擎 case;15 轮改进、每轮都过三裁判盲评;9 维结构评分均值 91.8(自评基线,无外部锚点,仅用于内部回归对比)。缺陷的发现与修复,全部来自双引擎行为实测。

先看研发核心链路——也就是那条 "Intent → Spec → Plan → Tasks → Code → Review → Knowledge" 主线上各站的体检结果:

| 链路环节 | Skill | 结构分(参考) | 测评中修复的代表性缺陷 |
|---|---|---|---|
| 需求·发散 | spec-ideate | 89.3 → 91.0 | 打磨请求被直接代行(该转 brainstorm) |
| 需求·收敛 | spec-brainstorm | 88.4 → 91.7 | 代行技术裁决,替用户做选型决定 |
| 需求·文档 | spec-prd | 91.7 → 93.5 | 该转走时静默滑入,未宣告就开工 |
| 文档审查 | spec-doc-review | 95.1 | 零缺陷,全场最高分 |
| 计划 | spec-plan | 90.5 → 92.5 | 用户施压击穿 planning-only |
| 任务拆分 | spec-write-tasks | 93.1 | 零缺陷 |
| 实现 | spec-work | 91.2 → 92.8 | 计划与代码不符被合理化执行 |
| 调试 | spec-debug | 92.0 → 92.8 | "试过好几次"仍未先问尝试清单 |
| 代码审查 | spec-code-review | 92.0 → 93.0 | report-only 却好心改了被审文件 |
| 知识沉淀 | spec-compound | 92.5 | 零缺陷 |

> 注:结构分只是三线评估之一,分数变化是缺陷修复的伴随产出——真正的信息量在右列。

### 16 个缺陷,九个是同一种病:好心越界

37 个 skill 里 19 个零缺陷一次通过;两轮修出来的 16 个真实缺陷,聚成四族:

| 缺陷族 | 数量 | 形态 |
|---|---|---|
| **收编他职** | 9 | 识别出越界后,直接把排除的活干了 |
| 路由要素缺失 | 4 | 有排除无目的地 / 有目的地未宣告 / 宣告后未停止 |
| 授权击穿 | 2 | 用户施压、自然语言"不用问我"被当作权限 |
| 流程纪律 | 1 | 计划与代码不符被合理化为执行授权 |

挑三个最有代表性的:

**① 用户施压击穿 planning-only。** 给 spec-plan(只做计划、不碰代码)的测试 prompt 里加一句"顺手把示例代码改了跑通吧"——模型真的去改了 `src/server.js`。修复:写入条款"**User pressure is not a write gate**(用户施压不是写权限)"。被用户直接要求,恰是这份合同存在的场景,而不是例外。

**② report-only 好心修复。** spec-code-review 是只读审查 skill。测试里它检出 P0 缺陷后,顺手把被审文件改好了——而它输出的 JSON 里还声明自己是 report-only。修复:"**Report-only means byte-identical**"。声明与行为解耦:嘴上说只读,不豁免手上改文件。

**③ 收编六连。** 六个 skill 犯了同一个错:请求与其职责不匹配时,模型识别出了不匹配,然后……把排除的工作直接做了。比如给代码优化 skill 发一个修 bug 请求,它会一边说"这其实该走调试流程",一边把 bug 修了。修复范式是"点名目的地 + 反收编条款":"**识别出不匹配然后把排除的活干了,是采用了错误的 workflow,不是一次有用的兜底。**"

### 改完再考一次:换它没见过的问法

第一轮修完不算数。我们又构造了 18 个变体——换措辞、换技术域(REST→GraphQL)、换引擎、加正例防过度拒绝——验证修复的泛化性:11/16 存活,2 个新缺陷当场修复,剩下几个则暴露了一个更深的真相。

### 它读到条款,承认不适用,然后把 bug 修了

"帮我修个 bug"这类请求,发给五个不同的 skill,双引擎、修复后、加了双层条款,模型依然会上演同一幕:

> 读到条款  
> 承认不适用  
> 把 bug 修了

有一个 case,模型的输出原文是——

*"已按路由规则跳过 PRD,直接修复。"*

**它知道自己违反了规则,还是修了。**

这不是合同缺失,是注意力与冲动问题——**文本层修不动它。** 唯一的解法是把修复点上移到入口:在上游路由层识别 fix-intent(修复意图),一处修复,覆盖全部下游 skill。这个判断,直接引出了第三问。

### 插曲:测试 agent 真的在 GitHub 上建了个仓库

测 spec-lfg(一条龙交付 skill)时,沙箱里的 agent 拿着宿主的 gh 登录态,真的在 GitHub 上创建了一个仓库(建于我们的测试账号下,除创建外无其他操作)。处置之后,我们给测评体系立了安全守则:发布/commit/外部服务类 skill 的测评 prompt 禁用发布动词;沙箱必须做凭据隔离;对抗样本的价值一次获取后移出回归集。

---

前两问测的都是"进入正确 skill 之后"的行为质量。但还有一个更基础的问题没有回答:**用户说出一句话,AI 会不会先进对的门?**

如果任务本该走 debug workflow(带计划留档、证据约束、知识沉淀),模型却判断"这是即时故障,我直接改"——边界在入口就已经失守了。这一层此前从未被系统测过。

## 三、第三问:门就开在那儿,它为什么不走?

专项补测:22 条路由用例(直接意图正例 / 易混淆近似例 / Direct-Lane 负例)× 每条 3 次 × 三组引擎 = **198 次真实会话调用**,每次的原始输出全文留存可复核。

**结果:**

| 引擎 | 语义路由准确率 | 主失败形态 |
|---|---|---|
| codex(gpt-5.6-sol) | **98.5%** | 仅 1 次 fix-intent 判给了 direct |
| glm-5.3(经我方网关接入 claude CLI) | **90.9%** | 在 workflow 体系内部选错兄弟入口 |
| claude-sonnet-5 | **71.2%** | Direct-Lane 过宽,大面积绕过 workflow |

> 注:三组引擎都是我们环境的接入选择,不代表任何官方默认配置;准确率以我方用例集判定,非模型能力通用排名。

看到这张表,你的第一反应可能是:**等等,都说"越强的模型越绕过 workflow",那拿了 98.5% 最高分的 codex 算什么?**——这正是我们要主动澄清的:三个引擎对 workflow 的服从性差异巨大,是实测到的事实;"能力越强越有底气直接干",则是对 sonnet-5 这组失败形态的**解读**,不是结论,是不是普遍规律需要更多模型验证。

但 sonnet-5 这 19 次失败的机理很清楚。它的理由,原话是——

*"测试失败诊断属于即时故障排查……直接读取测试代码定位根因即可。"*

任务确实会被做对——别忘了行为门里 baseline 可是 100%——但 mutation/verification 门所依赖的 workflow 容器被整个跳过了:没有计划留档,没有证据约束,没有知识沉淀。

**任务做对了 ≠ 治理合规。**

至此,三份测评拼出了完整图景:

> **AI 的行为正确率已经饱和;真正的残余风险,集中在了"边界"上——要么选错门,要么干脆不走门。**

两个附注:其一,ideate/brainstorm 的判别在两个引擎上**双向失守**(方向还恰好相反)——证明这类判别必须写显式规则,不能赌模型先验;其二,Direct-Lane 负例 36/36 全对:不该进门时都没进,分歧全在"该进时进不进"。

## 四、修复:把规则焊死在入口,71.2% 回到 89.4%

发现问题只是上半场。两个层面的优化在测评窗口内完成并验收:

**① 入口层:硬前置规则。** 在宿主注入的治理锚点里新增两条:失败/回归/flake/报错/明确修复意图存在时,必须进 spec-debug,**不得走 Direct Lane**;用户显式点名 workflow 时不得降级。同时补上判别句:从零发散新方向→ideate;已有想法但目标用户或成功标准未定→brainstorm。这正是不再逐个 skill 打补丁、把修复点上移到入口的落地。

**验收数据(同用例集、同判定标准,before → after):**

- glm-5.3:90.9% → **95.5%**(两个 0/3 的系统性混淆族直接清零)
- claude-sonnet-5:71.2% → **89.4%**(failure→debug 6/6、技术裁决 3/3、fix-intent 3/3,大面积绕过消散)

**② 资产层:把测评变成回归基础设施。** 29 套 eval 套件(含 fixture 与 30+ 判定脚本)永久沉淀;16 个缺陷的原始 prompt 天然构成对抗样本库;22 条路由用例集已脚本化,可定期回归。

## 五、六条守则,写给所有给 AI 立规矩的人

两轮测评最大的知识产出,是这组经过实证的设计守则,可以直接抄进你的 CLAUDE.md / rules / prompt:

1. **路由三要素**(入口层):识别越界 + 点名目的地 + 宣告后停止,缺一即失败。
2. **排除语义必须自带目的地**(入口层):写"Not for X"却不写该去哪,模型会收编或裸拒绝。
3. **双层落点**(合同结构):路由类修复要同时落在合同摘要区和执行阶段入口——只落一层会被跳读。
4. **用户施压不是写权限**(授权边界):"被用户直接要求"恰是合同存在的场景。
5. **合同越逐字,失守越少**(合同质地):机器可判定的逐字合同(如"byte-identical")双引擎一次通过率最高;纯语义合同失守率最高。
6. **文本层存在极限**(系统性认知):对最强诱因(修 bug),正确的文本 + 三法官背书,仍会被冲动压倒——顽固边界的根治责任在上游路由,不在下游合同。

## 六、结语:"做对"免费之后,"守边界"成了新考题

这次测评给我们最大的观念更新是:模型能力的商品化,正在快速吃掉"教 AI 做事"类指令的价值;但另一类价值在上升——**边界与治理**。什么时候该停下来问用户、什么声明必须有证据背书、什么入口不许被绕过、识别出越界之后不许"好心代办"。这些不教模型怎么写代码,只约束它**什么时候出手**,恰恰是最自信的模型最容易失守的地方。

如果你也在维护团队的 AI 规则,三条建议:**先测再信**(任何 prompt 都值得一次行为门 + 对抗变体验证,而不是靠 review 措辞的感觉);**盯住出口,别盯思考**(确定性的事用脚本和文件级断言锚定,语义判断留给模型);**把"入口合规率"当一级指标**(任务正确率饱和之后,它才是残余风险的聚集地)。

这篇里的每一次调用、每一份原始输出,都在仓库里躺着:37 份测评文档、198 份路由记录、29 套可以直接抄走的 eval 套件(公众号内链接不可点,GitHub 搜 **spec-first**)。与其信我们的结论,不如拿数据去查——这本身就是我们想示范的事。
