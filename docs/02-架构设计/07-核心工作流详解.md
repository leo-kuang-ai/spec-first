# 核心工作流详解

> spec-first 的端到端工程与证据闭环链路

```
Codebase → Spec → Plan → Tasks → Code → Review → Knowledge
```

共 7 个节点，代表一次**可信变更**从意图到沉淀的完整路径。每个节点可以独立使用，也可以串联形成端到端流水线。

---

## 1. Codebase — 理解现有代码基

**定位：** 一切变更的起点。在写任何新代码之前，先建立对现有系统的上下文理解。

**对应 skill：** `spec-runtime-setup`（环境准备）、`spec-debug`（现有问题诊断）

**核心动作：**
- 读取当前代码结构、模式、约定
- 检查 git 状态、分支、远程仓库
- 确认 host runtime 状态（`spec-first doctor`）
- 验证源文件与 generated runtime 的一致性

**关键原则：** 不做假设。所有对当前系统的声明必须有源可查，provider 输出（如 code-graph）只作 advisory 线索，重要结论必须回源确认。

---

## 2. Spec — 把意图转化为结构化需求

**定位：** 把模糊的想法、零散笔记或已有的低质量 PRD，转化为一份**可执行的 What/Why 文档**。只回答"要做什么、为什么做"，不回答"怎么做"。

**对应 skill：** `spec-prd`、`spec-brainstorm`、`spec-ideate`

**核心流程（以 `spec-prd` 为例）：**

```
Input → 分类/路由 → 输入清理 → 当前系统快照 →
需求分析门 → 产品专家镜头 → 需求拷问 →
写前关闭决策 → PRD 编写 → 就绪透镜 + 定稿 → 交接
```

**关键设计：**

- **Brownfield first** — 先建立当前系统快照，再写新行为
- **WHAT not HOW** — 产品行为、验收条件、范围边界属于本阶段；数据库表、API 字段、任务拆分属于后续阶段
- **Grill-with-docs** — 一题一题追问需求，直到达到法律停止点：
  1. **叶子问题** — 无剩余子决策
  2. **源码解决** — source/docs/tests 可以关闭
  3. **Owner 封顶** — 所有者明确说"够了"
  4. **Pushdown** — HOW 推给 plan 阶段
- **确定性出口门** — `write_mode`、`readiness_outcome` 等 receipt 字段由脚本拥有，LLM 只拥有最终意图
- **四类法定停止点** — 分支默认持续拷问，只允许在四种情况下停止，否则挡在 `final-prd` 外

**产出：** `docs/brainstorms/*-requirements.md`（PRD 级需求文档）

---

## 3. Plan — 制定可执行的技术方案

**定位：** 把 spec 中的 What/Why 转化为 How——技术方案、架构决策、实施单元、风险分析。

**对应 skill：** `spec-plan`

**核心流程：**

```
Phase 0: 输入分类（resume / deepen / approach-altitude / domain split）
Phase 1: 上下文收集（本地研究 → 外部研究 → 综合）
Phase 2: 解决规划阶段问题（架构抉择）
Phase 3: 结构化计划（实施单元、U-ID、KTD）
Phase 4: 编写计划文档
Phase 5: 定稿审查 + 置信度检查 → 文档审查 → 交接
```

**关键设计：**

- **Evidence-grounded** — 每项决策锚定在来源文档或研究中
- **U-ID 稳定规则** — 实施单元分配唯一 ID，永不重编号，支持跨计划编辑的稳定引用
- **Three-depth 体系** — Lightweight（2-4 单元）、Standard（3-6 单元）、Deep（4-8+ 单元，可分组为 phases）
- **Deepen（加深）机制** — 自动或交互式地对薄弱部分做第二轮审查
- **三重确认门**：
  1. 写前 scope 合成确认（Phase 0.7 / 5.1.5）
  2. 置信度检查（Phase 5.3）
  3. `spec-doc-review` 文档审查（Phase 5.3.8）
- **可选格式** — markdown（默认）或 HTML（交互式浏览）

**产出：** `docs/plans/YYYY-MM-DD-NNN-<type>-<name>-plan.md`（统一计划文档）

**关键哲学：** Plan 是决策制品，不是执行脚本。不是任务列表，不是进度状态，不存储 per-unit progress。

---

## 4. Tasks — 可选的任务包层（Derived Layer）

**定位：** 对于大或依赖复杂的计划，可选地把 plan 编译为一组任务包，供执行时按波次（wave）组织。Plan 始终是单一真相源。

**对应 skill：** `spec-write-tasks`

**核心流程：**

```
输入分类 → 验证计划身份/repo 范围 → 分支选择
  ├─ compile（编译任务包）
  ├─ skip（直接执行更简单）
  ├─ return-to-plan（范围不明确）
  ├─ draft-only（草稿轮廓）
  └─ validate-only（验证已有任务包）
```

**关键设计：**

- 任务包不改变 scope、验收标准、产品决策
- `Task Pack Contract` 是机器可读的确定性验证块（JSON 格式）
- Execution waves 组织波次执行
- 高复杂度任务包自动触发 `spec-doc-review`
- Deterministic 验证：`spec-first tasks validate <task-pack-path> --json`

**产出（可选）：** `docs/tasks/<name>.md`

---

## 5. Code — 执行变更

**定位：** 按计划实施代码变更，驱动最小的反馈循环，完成验证。

**对应 skill：** `spec-work`

**核心流程：**

```
Phase 0: 输入分诊（plan / task-pack / bare prompt / blank 最新 plan 自动发现）
Phase 1: 快速启动（读计划 → 执行边界 → 创建任务列表 → 选引擎）
Phase 2: 执行循环（每单元：预检 → 反馈循环 → 实现 → 测试 → 提交检查点）
Phase 3-4: 质量关（代码审查 → 修复 → 残余工作门）
```

**关键设计：**

- **Plan 不编辑** — 执行期间不改 plan 正文；进度在 git commit 和 task tracker 中
- **反合理化红旗** — 内置注意力提醒机制，防止常见执行偏差：
  - "测试大概会过，先声明完成" → 跑真实验证
  - "计划写了 new wrapper，照着建就行" → 先查 current source
  - "相邻代码顺手清理" → 回到 active scope
- **Return-to-Caller 模式** — 供 LFG 等编排者调用的标准化返回结构（JSON 格式，包含 `changed_files`、`verification_results`、`blockers` 等）
- **Scope-changing 发现必须回退** — 发现改变验收条件、公有契约、架构时停止，回到 plan/task owner
- **三种引擎** — Inline（默认）、Goal mode、Worker dispatch（需显式授权）

**产出：** 变更的源码、测试更新、`spec-work-run-artifact/v2` 运行制品

---

## 6. Review — 结构化的代码审查

**定位：** 对照意图、测试、标准和风险维度审查代码变更。默认 report-only，仅在明确要求时 apply-fixes。

**对应 skill：** `spec-code-review`、`spec-doc-review`

**核心设计：**

- **Persona 体系** — 根据 diff 规模和风险自动选择审查角色（正确性、安全、可维护性、测试、架构等）
- **`mode:agent` 输出 JSON** — 供编排者消费的标准格式
- **`depth:full` 强制全审查** — 当用户明确要求"深入审查"时
- **Grouping 分组** — 按主题组织发现项，方便 triage
- **Small-diff lite 路径** — 小、低风险的 diff 自动缩简审查阵容
- **Lite roster** — 小 diff 用简洁阵容；**Full roster** — 标准/高风险用完整阵容

**关键原则：**
- Review 是两步过程：**审查 → 修复**。`spec-code-review` 只审查，不 checkout、不 apply、不 commit
- `mutation_policy: apply-fixes` 只授权本地的、review-owned 的修改
- 缺乏确定性强制能力时降级为"响亮约定"并说明

**产出：** markdown 或 JSON 格式的审查报告（发现项列表）

---

## 7. Knowledge — 可复用的工程知识沉淀

**定位：** 在问题解决后立即记录，形成可检索、可失效的工程知识。

**对应 skill：** `spec-compound`、`spec-compound-refresh`

**核心流程：**

```
上下文分析 → 解决方案提取 → 相关文档发现 →
（可选）会话历史 → 领域术语 → 验证 → 编写 → 发现性检查
```

**关键设计：**

- **一次只学一件事** — 每次运行只记录一个学习，不批量
- **失效驱动** — 知识附带适用范围和失效条件（invalidation condition），新的反例触发降级
- **验证门** — 脚本验证 frontmatter、claim（路径/commit/link）、不残留草稿脚手架
- **`CONCEPTS.md` 引导** — 作为 domain term 的副产品更新，不独立创建
- **Promotion gate** — 只有已验证、可回源、可复用并带适用范围的知识才能进入 durable knowledge
- **两种模式** — Interactive（默认，交互式发现性检查）和 Headless（自动化，静默修复）

**产出：** `docs/solutions/<category>/<name>.md`、`CONCEPTS.md`（领域术语表）

## 哲学贯穿

整个链路被三条核心原则统一约束（来自 `docs/10-prompt/结构化项目角色契约.md`）：

| 原则 | 含义 |
|------|------|
| **Light contract** | 契约只保留会改变决策的 durable invariants；条件流程和实现细节按需披露。上下文追求最高 **decision sufficiency per token** |
| **Deterministic floor, semantic judgment** | 脚本/工具强制可机械判定的不变量并准备事实；LLM/agents 判断意图、方案、风险与语义充分性。任何一方不得伪造另一方的权威 |
| **Gate the exits, not the thinking** | 硬 gate 只守五个出口：mutation、verification claim、source/runtime、handoff/context reset、knowledge promotion。推理路径保持开放 |

### 可信变更公式

```
可信变更 = 清晰意图 × 有效上下文 × 有界执行 × 可核验证据 × 可失效学习
```

任一项接近零，更多 agent、工具或自动化只会更快放大问题——这正是整个链路想要避免的核心风险。

### 架构定位

spec-first 的定位：

- ✅ workflow harness
- ✅ project intelligence layer
- ✅ skill/agent/tool coordination layer
- ✅ spec/plan/task/review/knowledge 的结构化连接层
- ✅ AI coding 的证据闭环

spec-first 的定位之外：

- ❌ prompt collection
- ❌ agent collection
- ❌ 强状态机
- ❌ 中心化流程引擎
- ❌ 复杂规则引擎
- ❌ 无边界脚本堆
- ❌ 替代 LLM 判断的硬编码专家系统

## 典型使用路径

### 完整变更

```
spec-ideate → spec-plan → spec-write-tasks → spec-work → spec-code-review → spec-compound
```

### 只审不改

```
spec-code-review（基于当前 diff）
```

### 只写需求不落地

```
spec-brainstorm → spec-prd
```

### 知识快速沉淀

```
spec-compound "刚刚解决了 XXX 问题"
```

### 全自动流水线

```
spec-lfg（自动完成 plan → work → review → PR → CI 全流程）
```

每个 skill 独立可用，路径灵活组合，不强制走完整链路。
