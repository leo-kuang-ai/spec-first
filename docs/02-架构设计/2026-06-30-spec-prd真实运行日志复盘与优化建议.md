### PRD-LOG-002：设计稿与需求文档冲突时，不能默认 `source-resolved`

**证据**

日志发现真实冲突：

```text
Pre-Market / Post-Market / 24H
vs
盘前/盘中/盘后/夜盘/休市
```

最终 PRD：

```text
closure_disposition: source-resolved
以设计稿为 UI 权威
```

证据：最终 PRD 第 210 行、第 224 行。

**问题**

`source-resolved` 适用于 source 直接回答事实，例如“代码里入口类是谁”“接口字段有哪些”。但当两个 product/design sources 冲突且改变 WHAT/acceptance/scope 时，选择 source authority 是 owner-owned 决策。

这类冲突不能由模型自行裁决：

```text
需求文档 says A
Figma says B
模型 says Figma wins
```

更深一层的风险不是 `source-resolved` 这个词本身，而是 provenance laundering：

```text
需求文档 says A
Figma says B
模型没问 owner
模型写成 owner-answered / owner-accepted-assumption
```

这种写法同样错误。当前 checker 只能验证 owner-* OQ 是否绑定到 Owner Decision Trace row，不能证明这条 row 真的来自 owner round-trip。因此该规则必须写在 skill prose/eval/review 里，而不是假装能由 checker 语义判定。

**当前落地状态**

已在 `design-source-evidence.md`、`prd-readiness-lens.md`、`prd-output-template.md` 和 eval fixture 中加入明确规则：

```text
When design-source evidence contradicts product requirements, owner decisions, or API/source contracts in a way that changes WHAT, acceptance, scope, source-of-truth, fallback display, analytics, or user-visible interaction, it is not source-resolved. It must be carried as checkpoint/OQ unless the run shows a specific owner question and answer for that conflict. Owner-* dispositions are valid only when the trace row binds to that exact conflict and reflects an actual owner answer, not a model-written authority preference.
```

**允许的非阻塞情况**

- 视觉稿只是补充布局细节，不改变行为或验收。
- 设计稿和需求文档是同义表达。
- 输入材料或 owner 已明确说明“设计稿优先”，且该 authority 说明本身有可引用证据。

**host provenance ceiling**

这项修复不能宣称“已机械证明 owner 真的回答”。checker 只能检查 Owner Decision Trace 结构存在和 OQ 绑定关系，不能证明 trace row 来自真实 owner round-trip。真正的 guardrail 是：

- skill prose 要求 owner-answer fidelity。
- eval 覆盖 fake `source-resolved` / fake `owner-*` closure。
- review 或 fresh-source eval 看到 product/design authority conflict 时，必须检查运行中是否有针对该 exact conflict 的 owner 问答证据。

**已覆盖/仍需观察的测试面**

- 已覆盖：需求文档写五时段、Figma 写三时段时，不得输出 `source-resolved` ready；也不得输出未证明 owner round-trip 的 `owner-*` ready；必须 ask-owner 或 checkpoint。
- 仍需观察：后续真实运行是否还会伪造 Owner Decision Trace row。如果发生，应补 review/eval 样本，而不是让 checker 裁决语义真实性。

**问题**

但真实运行显示，模型仍可能先写 PRD，再让 finalize 发现问题。

**当前落地状态**

```text

design_source_inventory:

    read_status: read | partial | unread | degraded

    extracted_design_what:

design_vs_requirements_conflicts:
  - conflict:
    affected_prd_write_targets:
    owner_authority_needed: yes/no
owner_accepts_degraded_design_ref: <trace row / none / not-needed>
```

如果存在 unread / partial / degraded item，且它可能改变 UI structure、state、interaction、acceptance、scope 或 source authority，并且没有 owner acceptance，那么 ready exit 必须阻断，第一次 durable PRD write 应是：

```text
write_mode: checkpoint-prd
can_enter_spec_plan: no
next_owner_question: ...
```

如果设计源不影响本次 PRD write target、只是重复/背景材料，或 owner 已接受 degraded risk，可以继续普通 draft/final 路径，但必须把 Design Source Coverage residue 写清楚，避免 planning 误以为视觉事实已 confirmed。

**边界**

这不是让脚本决定 UI 语义充分性；脚本只准备 evidence/readiness facts，LLM 判断是否影响 WHAT。已落地方案优先改 `SKILL.md` / `prd-output-template.md` 的 Phase 1 guidance 和 eval case，避免生成新的 design readiness contract。

**防隐藏状态机校准**

PRD-LOG-003a 分两层：

- script/checker-owned deterministic facts：是否存在 design refs、是否声明 `design_source_inventory`、是否列出 read/unread/degraded、是否有 Design Source Coverage 机器字段。
- LLM-owned semantic judgment：某个 unread/degraded item 是否 load-bearing，是否会改变 page structure/state/interaction/acceptance/scope/source-of-truth/fallback/analytics。

ready exit 只卡“已声明 unresolved load-bearing design impact 且无 owner acceptance / residue”的情况，不卡探索路径，不要求所有设计源都读完才允许写 checkpoint，也不把 Phase 1 变成强状态机。

**采纳/回退信号**

这项 P0 已落地，但应继续观察 interruption cost。如果 replay 或真实运行显示它主要增加无意义 checkpoint / owner interruption，而没有提前暴露 load-bearing design gap，应收紧阻断条件，只保留 inventory telemetry。

### P1/P2：OQ closure state 语义与 self-check 可不一致

**证据**

最终 PRD 中：

```text
OQ-1 closure_disposition = owner-accepted-assumption
closure_state = open
```

但 Readiness Self-Check 写：

```text
Outstanding 闭合...
```

证据：最终 PRD 第 206 行、第 232 行。

**判断**

机器层面这次通过是可以理解的：OQ-1 的 owner trace 存在，`blocks_planning=no`，指标明确不入本版。但文档语义上，“owner accepted deferred/open” 与 “全部闭合”容易让下游误读。

**建议**

收敛 OQ closure state vocabulary，但要保持字段边界：

- `closure_disposition` 说明“为什么不阻塞 planning”，例如 `source-resolved`、`owner-answered`、`owner-capped`、`owner-accepted-assumption`、`implementation-only-how-pushdown`。

建议 `closure_state` vocabulary：

```text
closed
owner-deferred
deferred
accepted-deferred
blocked
```

对于 ready/final：

- `closure_state=open` 不应与 `blocks_planning=no` + `owner-*` 混用。
- 若确实延期，写 `accepted-deferred` 或 `owner-deferred`。

**是否 blocking**

建议先做 advisory 或 template guidance，不立即 P0 blocking。原因是现有 checker 已有 OQ closure blocker，贸然阻断可能影响合法延期。

## 10. 最终判断

这次真实运行支持当前 `$spec-prd` 的方向：用 deterministic floor 卡住错误出口，让 LLM 在事实地板之上做语义判断。但它也暴露了一个已观察到的治理缝：

```text
hard gate 已经能卡 final 出口
但模型仍会在 hard gate 之间压缩语义路径
```

因此下一步优化不应变成“加一个大型状态机”，而应继续沿着现有哲学推进：

```text
gate exits, not thinking
scripts enforce deterministic invariants
LLM owns semantic adequacy
owner owns product/design authority conflicts
```

最小可维护修复已经落到当前 source：补 mutation guard 的缺口，前置 design evidence intake，并把设计稿/需求文档冲突明确归入 owner adjudication，而不是让模型自行裁决。剩余工作不是继续加状态机，而是用 replay、fresh-source review 和小样本信号判断：哪些语义问题需要下一批 P0，哪些只是 UX friction 或 artifact quality。
