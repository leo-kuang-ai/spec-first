## 1. 定位

`spec-prd` 是 brownfield PRD requirements workflow，是 **analysis-first** 的 workflow 脊柱，不是外部 skill 链或持久 artifact 拓扑（SKILL.md:12）。

心智模型（一句话）：材料 → 跑成 run-local 的「需求分析地图」→ 地图找出不确定/矛盾点 → Product Expert Lens 排出哪些产品/设计/技术决策必须 grill → Requirements Grill 关闭或显式背负 load-bearing 的 WHAT 缺口 → 写进标准 PRD 模板 → Readiness Lens 问「planning/work 是否还得自己编产品行为」。

核心目标不是「写更长的 PRD」，而是 **降低下游 planning invention**：让 `spec-plan` 规划 HOW 时不必发明 WHAT。

核心边界：

```text
Codebase -> Spec/PRD -> Plan -> Tasks -> Code -> Review -> Knowledge
```

`spec-prd` 只负责 Spec/PRD 节点的 WHAT / WHY / acceptance / scope / evidence / business constraint；不负责 implementation plan、task breakdown、schema、API 字段或具体文件改动（SKILL.md:78，WHAT not HOW）。

默认 artifact 不变量：Markdown requirements 写入 `docs/brainstorms/*-requirements.md`，`artifact_kind: prd-requirements`。不创建 `docs/prds/`、不写代码、不写实施计划、不编辑 generated runtime mirror（SKILL.md:16）。

### Phase 摘要（SKILL.md:137-219）

- **Phase 0 分类意图与输入模式**（:139）：紧凑决策树。① route-out/bypass（0-1 探索、一致性审计、plan/task、debug、impl-ready 转走对应 workflow，不强上 PRD ceremony）；② 操作 `create`/`refine`/`validate`（`code-align` 是 validate 姿态，不是第四个公开 intent）；③ 输入姿态 `resume-prd`/`reference-claims`/`wrong-stage`/`pure-text`/`no-input`；④ 超大初始 PRD 先推荐语义拆分边界，owner 确认后才写。
- **Phase 1 当前状态分析**（:148，最重）：PRD Sanitization（混了「已批决策 + 原始讨论」时，只有 ratified 决策和确认源能定范围/验收）→ 收集 scope-appropriate 证据 → **Requirement Analysis Gate**（run-local 地图，:170）→ **Product Expert Lens**（:172，风险只控问的顺序，不控是否继续 grill）→ **Pre-Write Closure Gate**（:174）+ **Closure-disposition razor**（:176）→ **Push-Right owner Brief**（:178）。
- **Phase 2 Change Delta 与领域语言**（:186）：确认增量 `keep/extend/replace/remove/unknown`，不让当前状态发现悄悄扩范围；术语/源-用户矛盾先 source-first，浮现矛盾而非静默归一。
- **Phase 3 起草/精炼/拆分**（:196）：先定 `output_shape`，用 `prd-output-template.md`；refine 先产 `原文→建议→理由→写入目标`，durable 产物是重写后的 PRD，不是独立批评报告。
- **Phase 4 就绪与交接**（:206）：强制 producer-local gate，详见 §5。

## 3. 贯穿线 A：Run-Local Decision Card

一张 scratch 卡片（SKILL.md:107），**不是持久 artifact / schema / gate / 用户可见 section**，只在「能减少 planning invention」时才把片段抄进 PRD：

```text
intent · input_posture · output_shape · primary_topology · surface_lens
evidence_depth · quality_diagnosis · pre_prd_clarification_status
owner_question_progress · write_mode · highest_risk_gap · next_owner_question
question_delivery · clarification_evidence · readiness_outcome
```

关键字段约束（SKILL.md:129）：

- `write_mode=final-prd` 只在**每条 load-bearing 分支都到了合法停点**时用。
- `write_mode=ask-owner-first` 表示「继续 grill 最高风险分支」，**不是**「问一个问题就停止起草」。
- `write_mode=checkpoint-prd` 是 relentless fallback（owner 无 cap/continue 信号）或 true large-input/headless 恢复点，**不是 final PRD**。
- `clarification_evidence=skipped` 是 violation 标记，不是合法 fallback；`final-prd` 要求 `clarification_evidence` 合法且非 `skipped`。

## 4. 贯穿线 B：Canonical 四个合法停点

单一真相源（SKILL.md:131）。其它 reference 只能 by-reference 指向这里，不得重述这个 four-tuple。一个 load-bearing 分支 **默认 keep grilling**，只能停在：

| 停点 | 含义 | 字段映射（Light contract） |
|------|------|---------------------------|
| ① **leaf** | 无剩余会改 产品行为/验收/范围 的子决策 | `owner_question_progress=closed` |
| ② **source-resolved** | 源/docs/tests/glossary/旧 PRD 关闭（仍 source-first） | 既有 `source-resolved` |
| ③ **owner-capped** | owner 明说「够了」（含 soft-cap offer 后选 cap） | 新增 `owner-capped`（唯一新增值） |
| ④ **how-pushdown** | 实现 HOW 带理由推给 plan（路由语义，非 grill 闭合） | 既有 `route-out` |

**不是停点（只影响问的顺序）**：「够写一段 PRD 了」、「已问一个关键问题」、「问得太长了」、「不影响当前 release slice」、「gap 还绑不到 `PRD_write_target`」。

**一个 fallback**：owner 无 cap/continue 信号（absent/headless，或 soft-cap offer 后沉默，同一可观测信号）→ 停在 `write_mode=checkpoint-prd` + `can_enter_spec-plan: no` + `next_owner_question`，记 `pre_prd_clarification_status=checkpoint-blocked`，**绝不静默 emit `ready-for-planning`**。

**anchor 缺失 / broad discovery** → 仍是 `route-out`。

## 5. Phase 4 强制 finalize gate 细节

Phase 4 是 **mandatory producer-local gate，不是可选 closeout**（SKILL.md:208）。没真跑 readiness lens、（有 artifact path 时）没执行 producer-local finalize，就**不准**声明 PRD done、写 ready 字段、或提议 `/spec:plan`。自我声明就绪 = Phase 4 violation。

执行链路：

1. 有 artifact path 时跑 `node skills/spec-prd/scripts/finalize-prd-artifact.js <prd-path> --inputs <input-path>`（`--check-only` 可预览不写）。
2. finalize 调 `check-prd-artifact.js` 产确定性 closeout count 和 trace 事实。
3. `source_inputs:` frontmatter（及 legacy alias `prd_input:`）由 Claude Stop hook 读取传入 `--inputs`，使 input-side Figma/design-source 核算不依赖模型记忆。
4. checker 命中任一 BLOCKING reason_code → Phase 4 **不准** `ready-for-planning`；要么补合法声明重跑，要么降级到 `revise-prd`/`ask-owner`/`route-out`（SKILL.md:218 列出完整 reason_code 表）。
5. `status: ready-for-planning` / `write_mode=final-prd` / `can_enter_spec_plan: yes` **必须有当前 machine-owned finalize receipt**；handoff 没命名 finalize/checker receipt = 没通过 Phase 4。

核心锚定约束：checker 用 canonical English token 锚定 core section（如 `## Summary`）；本地化 PRD 必须在每个 core-section 标题保留该 token（可加 gloss 如 `## Summary（文档概要）`），否则报 `core_section_missing`。

## 6. 硬 gate vs 软判断分层

这是全流程的关键分层，也是「Scripts prepare, LLM decides」哲学的落点：

```text
                        Scripts prepare              │        LLM decides
                    (确定性事实,可硬卡)             │      (语义判断,轻合同)
  ──────────────────────────────────────────────────┼──────────────────────────────
  Claude PreToolUse guard(prd-prewrite-guard):       │  grill是否充分/owner是否真回答
  首次 Write docs/brainstorms/*-requirements.md       │  哪些问题必须逐条深问到停点
  时已自称 ready/final 或带 machine receipt            │  问到什么程度才算收敛
  → 阻断 direct-Write shortcut                         │  readiness_outcome 最终裁决
                                                     │
  Phase 4 checker:30个 BLOCKING reason_code          │  Phase 0 意图分类 / route-out判断
  artifact文本结构在场性:                             │  Phase 1 哪些决策是load-bearing
   ✅ OQ 必须有合法 closure_disposition + 证据        │  grill到什么程度算关闭
   ✅ owner-* OQ 必须逐行绑定 Owner Decision Trace   │  风险多大 / 该不该叫owner
      row(verbatim question 或点名 OQ id)            │
   ✅ design_* / ready_receipt / core_section 锚点  │  ❌ 不能硬:grill是否充分/是否问全/
  → 命中即阻断 ready-for-planning                     │     Figma 是否真读/owner决策是否
                                                     │     被改写(底物=会话语义事件,
                                                     │     hook/checker看不见
                                                     │     → R12 host-provenance天花板)
  prose forcing(SKILL.md anti-pattern):              │  doc-review(人工审计):
  checkpoint-as-escape 明令禁止问1轮就停             │  审计shallow grill/决策改写/
  owner-answer fidelity 要求忠实记录owner答复         │  OQ静默降级等checker看不见的
                                                     │  语义问题
```

**底物决定一切**：`check-prd-artifact.js` 是 finalize 阶段读**事后 PRD artifact 文本**的 deterministic checker，看不到会话里 grill 事件、Figma 内容是否进过上下文、问题 surface 的时间顺序。所以「写出来的 OQ 必须合法闭合」能硬卡（底物 = artifact 文本），但它拦不了「写之前是否真的 grill」。本次新增的 Claude `prd-prewrite-guard` 改变的是另一块底物：`PreToolUse` 能看到即将执行的 `Write` 路径与内容，因此可以硬拦「首次直接写入 ready/final PRD」这个控制流违规形态。

但这个 guard 仍不做产品语义判断：它不能证明 owner 真回答、不能证明 grill 充分、不能证明 Figma/API 真的读过。要硬卡这些语义事件，需 host runtime 产出结构化 question-receipt（`transcript_path` 已在 Stop hook payload 中确证可用，但把它做成 block 判据仍撞 KTD2「gate the exits, not the thinking」，deferred 到有 per-question verified receipt primitive 就位时）。Codex 或没有 pre-tool guard 的 host 仍降级为响亮约定；不得宣称已机械强制。

**防御纵深三层**（能封死的都已封死，余下靠这两层）：
- **prose forcing**：SKILL.md `Checkpoint-as-escape anti-pattern` 明令"问 1 轮就写 checkpoint"是违规；`Owner-answer fidelity` 要求 trace row 忠实记录 owner 实际答复，不得 soften/reverse；doc-review 触发信号明文写进 Phase 4。
- **eval 夹具**：`one-round-scoping-then-checkpoint-rejected`（failure 案例） + `checkpoint-after-full-grill-accepted`（positive 案例）固化失败模式，每次改 spec-prd 都跑回归。

## 7. 失败映射：16:46 真实运行

把流程图对回一次真实失败运行（2026-06-26 16:46 日志）：

- **应然**：grill 先于 write（Phase 1 Pre-Write Closure Gate 在 durable write-in 之前），所有 load-bearing OQ 收敛后才写 PRD。
- **实然**：16:46 运行里模型只问 2 个 scoping 问题就直接写 PRD，把 OQ-2（接口可用性）/ OQ-3（中台持仓降级）用散文标「非阻塞」，等 Phase 4 checker 拦了才回头；最新运行日志又出现“读完材料和代码现状后直接 `Write(docs/brainstorms/...-requirements.md)`”的同类 direct-Write shortcut。
- **根因**：SKILL.md prose 规定了 grill-first，但 **prose 不是 checker 能强制的 enforcement**（缺机器约束时 prose gate 降级为「响亮约定」，最易被静默放行）。Phase 4 checker 能在 artifact 文本上拦「写出来的 OQ 没合法闭合」，但看不到 `Write` 发生前的控制流。
- **修复**：两层收口。第一层是已有 Phase 4：`check-prd-artifact.js` 的 bullet-OQ 兜底（commit `1036f26f`）让「散文标非阻塞的 load-bearing OQ」也被拦下（复用 `outstanding_question_closure_undeclared`，不新增 presence/ceremony code，`BLOCKING_REASON_CODES` 严格守 30）。第二层是本次新增 Claude `prd-prewrite-guard`：在 `Write` 前看到新 PRD 已自称 `ready-for-planning`、带 machine receipt 字段或 checker facts 显示 ready/final intent 时直接 `exit 2`，迫使流程回到 Requirements Grill 或写非 ready checkpoint。discovery 侧“是否问全”仍走 `product-expert-lens.md` 双座位 forcing-function 和 fresh-source eval，不加语义 discovery checker。

## 8. 一句话读图

grill（语义判断，prose 规定 relentless + 先于 write）在 **Phase 1 的 Pre-Write Closure Gate** 收敛 load-bearing WHAT；Claude `PreToolUse` guard 硬拦“直接 `Write` ready/final PRD”的控制流捷径；Phase 4 checker 再在 artifact 文本底物上拦「写出来的东西没合法闭合」。语义事件（是否真 grill / 是否问全 / owner 真伪）仍不被脚本裁决，靠 prose forcing-function + fresh-source eval 防御纵深兜底，收口于 R12 host-provenance 天花板。
