## 1. 定位

`spec-prd` 是 brownfield PRD requirements workflow，是 **analysis-first** 的 workflow 脊柱，不是外部 skill 链或持久 artifact 拓扑（SKILL.md:12）。

心智模型（一句话）：材料 → 跑成 run-local 的「需求分析地图」→ 地图找出不确定/矛盾点 → Product Expert Lens 排出哪些产品/设计/技术决策必须 grill → Requirements Grill 关闭或显式背负 load-bearing 的 WHAT 缺口 → 写进标准 PRD 模板 → Readiness Lens 问「planning/work 是否还得自己编产品行为」。

核心目标不是「写更长的 PRD」，而是 **降低下游 planning invention**：让 `spec-plan` 规划 HOW 时不必发明 WHAT。

核心边界：

```text
Codebase -> Spec/PRD -> Plan -> Tasks -> Code -> Review -> Knowledge
```

`spec-prd` 只负责 Spec/PRD 节点的 WHAT / WHY / acceptance / scope / evidence / business constraint；不负责 implementation plan、task breakdown、schema、API 字段或具体文件改动（SKILL.md:78，WHAT not HOW）。

默认 artifact 不变量：Markdown requirements 写入 `docs/brainstorms/*-requirements.md`，`artifact_kind: prd-requirements`。不创建 `docs/prds/`、不写代码、不写实施计划、不编辑 generated runtime mirror（SKILL.md:16）。

### Phase 摘要（SKILL.md:137-219）

- **Phase 0 分类意图与输入模式**（:139）：紧凑决策树。① route-out/bypass（0-1 探索、一致性审计、plan/task、debug、impl-ready 转走对应 workflow，不强上 PRD ceremony）；② 操作 `create`/`refine`/`validate`（`code-align` 是 validate 姿态，不是第四个公开 intent）；③ 输入姿态 `resume-prd`/`reference-claims`/`wrong-stage`/`pure-text`/`no-input`；④ 超大初始 PRD 先推荐语义拆分边界，owner 确认后才写。
- **Phase 1 当前状态分析**（:148，最重）：PRD Sanitization → 证据收集 → **Requirement Analysis Gate**（:170，run-local 地图）→ **Product Expert Lens**（:172）→ **Pre-Write Closure Gate**（:174）+ **Closure-disposition razor**（:176）→ **Push-Right owner Brief**（:178）。
- **Phase 2 Change Delta 与领域语言**（:186）：确认增量 `keep/extend/replace/remove/unknown`。
- **Phase 3 起草/精炼/拆分**（:196）：先定 `output_shape`，用 `prd-output-template.md`；durable 产物是重写后的 PRD。
- **Phase 4 就绪与交接**（:206）：强制 producer-local gate，详见 §5。

## 3. 贯穿线 A：Run-Local Decision Card

一张 scratch 卡片（SKILL.md:107），**不是持久 artifact / schema / gate / 用户可见 section**，只在「能减少 planning invention」时才把片段抄进 PRD：

```text
intent · input_posture · output_shape · primary_topology · surface_lens
evidence_depth · quality_diagnosis · pre_prd_clarification_status
owner_question_progress · write_mode · highest_risk_gap · next_owner_question
question_delivery · clarification_evidence · readiness_outcome
```

关键字段约束（SKILL.md:129）：

- `write_mode=final-prd` 只在**每条 load-bearing 分支都到了合法停点**时用。
- `write_mode=ask-owner-first` 表示「继续 grill 最高风险分支」，**不是**「问一个问题就停止起草」。
- `write_mode=checkpoint-prd` 是 relentless fallback（owner 无 cap/continue 信号）或 true large-input/headless 恢复点，**不是 final PRD**，不能洗掉未 grill 的事实。
- `clarification_evidence=skipped` 是 violation 标记；`final-prd` 要求 `clarification_evidence` 合法且非 `skipped`。
- `clarification_evidence=asked-owner` 只有在收到 owner 真实答复后才合法——问了问题但没收到答复不算。

## 4. 贯穿线 B：Canonical 四个合法停点

单一真相源（SKILL.md:131）。其它 reference 只能 by-reference 指向这里，不得重述这个 four-tuple。一个 load-bearing 分支 **默认 keep grilling**，只能停在：

| 停点 | 含义 | 字段映射（Light contract） |
|------|------|---------------------------|
| ① **leaf** | 无剩余会改产品行为/验收/范围的子决策 | `owner_question_progress=closed` |
| ② **source-resolved** | 源/docs/tests/glossary/旧 PRD 关闭（仍 source-first） | 既有 `source-resolved` |
| ③ **owner-capped** | owner 明说「够了」（含 soft-cap offer 后选 cap） | 新增 `owner-capped`（唯一新增值） |
| ④ **how-pushdown** | 实现 HOW 带理由推给 plan（路由语义，非 grill 闭合） | 既有 `route-out` |

**不是停点（只影响问的顺序）**：「够写一段 PRD 了」、「已问一个关键问题」、「问得太长了」、「不影响当前 release slice」、「gap 还绑不到 `PRD_write_target`」。

**一个 fallback**：owner 无 cap/continue 信号（absent/headless，或 soft-cap offer 后沉默） → 停在 `write_mode=checkpoint-prd` + `can_enter_spec-plan: no` + `next_owner_question`，记 `pre_prd_clarification_status=checkpoint-blocked`，**绝不静默 emit `ready-for-planning`**。

**anchor 缺失 / broad discovery** → 仍是 `route-out`。

## 5. Phase 4 强制 finalize gate 细节

Phase 4 是 **mandatory producer-local gate，不是可选 closeout**（SKILL.md:208）。没真跑 readiness lens、（有 artifact path 时）没执行 producer-local finalize，就**不准**声明 PRD done、写 ready 字段、或提议 `/spec:plan`。

执行链路：

1. 有 artifact path 时跑 `node skills/spec-prd/scripts/finalize-prd-artifact.js <prd-path> --inputs <input-path>`（`--check-only` 可预览不写）。
2. finalize 调 `check-prd-artifact.js`，内部走三阶段链：`parseStructure(target, text)` → `computeFacts(structure, inputPaths, options)` → `deriveFindings(facts, structure, oqAnalysis, inputPaths)`；`gateReadyClaims(facts, oqAnalysis)` 集中全部 claimsReady-gated findings。
3. `source_inputs:` frontmatter（及 legacy alias `prd_input:`）由 Claude Stop hook 读取传入 `--inputs`，使 input-side Figma/design-source 核算不依赖模型记忆。
4. checker 命中任一 BLOCKING reason_code（共 30 个，见 §8）→ Phase 4 **不准** `ready-for-planning`；要么补合法声明重跑，要么降级到 `revise-prd`/`ask-owner`/`route-out`。
5. `status: ready-for-planning` / `write_mode=final-prd` / `can_enter_spec_plan: yes` **必须有当前 machine-owned finalize receipt**；handoff 没命名 finalize/checker receipt = 没通过 Phase 4。

**finalize closeout 三态出口**（`lib/reason-codes.js` 控制分类）：

| 出口 | 条件 | `can_closeout` |
|------|------|----------------|
| `finalize-closeout`（fully ready） | BLOCKING 全通过 + receipt 当前有效 | `true`，`can_finalize=true` |
| `checkpoint-closeout`（合法 checkpoint） | `write_mode=checkpoint-prd` + `can_enter_spec_plan=no` + 非 ready；RECEIPT_ONLY(2) / CHECKPOINT_EXEMPT(2) 码豁免 | `true`，`can_finalize=false` |
| 阻断 | 有非豁免 BLOCKING 码 | `false`，`should_block_closeout=true` |

核心锚定约束：checker 用 canonical English token 锚定 core section（如 `##    Résumé`）；本地化 PRD 必须在每个 core-section 标题保留该 token，否则报 `core_section_missing`（BLOCKING）。

### 6.1 check-prd-artifact.js 三阶段拆分（P2）

原 `buildReport`（260 行，53 个局部变量，20 处 `claimsReady` 引用）已拆为四个纯函数 + 薄外壳：

```text
buildReport(target, text, options)          ← 19行薄外壳，public接口不变
  │
  ├─▶ parseStructure(target, text)          ← 纯文本解析，无I/O
  │     returns: {lines, frontmatter, headings, missingCoreSections,
  │               requirementIds, writeModeValue, claimsReady,
  │               readyReceiptPresent, designUnread, ...全部文本派生字段}
  │
  ├─▶ computeFacts(structure, inputPaths, options)  ← I/O + OQ分析
  │     returns: {facts(全部50+字段), oqAnalysis}
  │     ·  findProjectRootFromTarget / scanInputDesignRefs / computeInputsHash
  │     ·  analyzeOutstandingQuestions(lines, headings, {claimsReady})
  │
  ├─▶ deriveFindings(facts, structure, oqAnalysis, inputPaths)  ← 全 findings
  │     ·  基础结构 findings（frontmatter / core_section / path / placeholder）
  │     ·  readiness 声明 findings（write_mode / clarification / preflight）
  │     ·  design source findings
  │     ·  input scan findings（含 MAX_INPUT_COUNT advisory）
  │     └─▶ gateReadyClaims(facts, oqAnalysis)  ← claimsReady-gated findings 集中点
  │           ·  preflight_sweep_closure_blocked
  │           ·  ready_receipt_absent / ready_receipt_stale
  │           ·  oqAnalysis.reasonCodes（OQ 剃刀结果）
  │           ·  design_unread_without_owner_acceptance
  │           ·  design_partial_coverage_unaccepted
  │           ·  checkpoint_claims_ready
  │           ·  preflight_closure_contradicted（通过 isClosureBlocker 分类器）
  │
  └─ blockingReasons = findings filtered by BLOCKING_REASON_CODES
```

四个阶段函数全部导出，可被 in-process 单测直接调用。

## 7. 硬 gate vs 软判断分层

「Scripts prepare, LLM decides」哲学的落点：

```text
Scripts prepare（确定性事实，可硬卡）            │  LLM decides（语义判断，轻合同）
──────────────────────────────────────────────┼──────────────────────────────────
Claude PreToolUse guard (prd-prewrite-guard): │ grill 是否充分 / owner 是否真回答
首次 Write docs/brainstorms/*-requirements.md  │ 哪些问题必须逐条深问到停点
时已自称 ready/final 或带 machine receipt       │ 问到什么程度才算收敛
→ 阻断 direct-Write shortcut                   │ readiness_outcome 最终裁决
                                               │
Phase 4 checker (check-prd-artifact.js):      │ Phase 0 意图分类 / route-out 判断
lib/reason-codes.js BLOCKING 30 个             │ Phase 1 哪些决策是 load-bearing
·CLOSURE_BLOCKER(8): preflight_closure_        │ grill 到什么程度算关闭
  contradicted 触发子集；                      │
  isClosureBlocker() 分类器取代内联数组         │ ❌ 不能硬卡：grill 是否充分/是否问全/
· OQ 必须有合法 closure_disposition + 证据     │   Figma 是否真读/owner 决策是否被
· owner-* OQ 必须逐行绑定 Owner Decision Trace │   改写（底物=会话语义事件，hook/
  row（verbatim question 或点名 OQ id）        │   checker 看不见→R12 host-provenance
· design_* / ready_receipt / core_section 锚  │   天花板）
→ 命中即阻断 ready-for-planning               │
                                               │ doc-review（人工审计）：
prose forcing（SKILL.md anti-pattern）：        │ 审计 shallow grill/决策改写/
checkpoint-as-escape 明令禁止问 1 轮就停        │ OQ 静默降级等 checker 看不见的
owner-answer fidelity 要求忠实记录 owner 答复   │ 语义问题
eval 夹具：closure-contract sentinel cases     │
固化 blocks_planning=no 自声明 /              │
owner-answer-reversal 失败模式                 │
```

**底物决定一切**：`check-prd-artifact.js` 读**事后 PRD artifact 文本**，看不到会话里 grill 事件、Figma 内容是否进过上下文、问题 surface 的时间顺序。`prd-prewrite-guard` 改变的是另一块底物：`PreToolUse` 能看到即将执行的 `Write` 路径与内容，可以硬拦「首次直接写入 ready/final PRD」这个控制流违规形态。但两层 guard 均不做产品语义判断。

**防御纵深三层**：
