# spec-first/brainstorm 深度质量改进分析

文档日期：2026-03-23
分析对象：
- `/Users/kuang/xiaobu/spec-first/brainstorm`
- `/Users/kuang/.codex/superpowers/skills/brainstorming`

## 1. 结论先行

`spec-first/brainstorm` 已经具备了很强的“先问清楚再开始”的能力，但它现在的强点更偏向**会把问题聊明白**，还没有把**把问题聊到足够可靠**这件事做成系统性的质量门槛。

superpowers 的价值，不在于它“更会问”，而在于它把很多质量控制动作前置成了流程：

- 先挑战前提，而不是默认问题定义正确
- 先给多个方案，再给推荐
- 先分段确认，再写完整设计
- 先做轻量审查，再进入执行
- 先定义完成标准，再说“已经可以推进”

如果把这套思路吸收到 `spec-first/brainstorm` 里，最直接的收益不是“更像 superpowers”，而是：

1. 讨论更不容易跑偏。
2. 设计文档更不容易变成单一路线的自说自话。
3. 后续 `/plan-ceo-review` 和 `/plan-eng-review` 的输入质量会明显更高。

## 2. 当前 `spec-first/brainstorm` 的质量基础

先说清楚它已经做对了什么。

### 2.1 已有的强项

`spec-first/brainstorm` 不是一个泛泛的闲聊技能，它已经有几个很明确的质量设计：

- **单轮单问**：不会一口气把用户问乱。
- **Startup / Builder 分流**：知道自己是在做产品判断还是轻量创作。
- **设计文档产出**：不是只聊想法，而是落到可继续推进的文档。
- **项目级上下文发现**：会去找已有设计文档，避免重复造轮子。
- **Completeness Principle**：倾向完整而不是“差不多就行”。
- **AskUserQuestion 格式约束**：要求重述项目、简化问题、推荐方案、列出选项。

这些已经是很好的基础。

### 2.2 现有短板

但从“质量提升”的角度看，当前还缺几种更强的收敛机制：

- 对前提的显式挑战不够强。
- 方案比较有，但不够结构化。
- 对证据和推断的边界没有强制分离。
- 设计过程里缺少阶段性确认点。
- 文档完成后缺少轻量 adversarial review。
- “完成”的定义不够像一个可以验收的门槛。

这些缺口不一定会让设计失败，但会让设计更容易出现以下问题：

- 看起来聊得很完整，实际上问题定义偏了。
- 方案只有一个方向，没有真正比较。
- 事实、猜测、建议混在一起。
- 文档写完了，但后续执行者还要重新问同样的问题。

## 3. 最值得借鉴的质量机制

下面这些是我认为最值得从 superpowers 借进来的，而且是直接能提升质量的部分。

### 3.1 把“问题是不是问对了”变成显式阶段

这是最重要的一项。

superpowers 在进入方案前，会强制挑战前提：

- 这是正确的问题吗
- 不做会怎样
- 现有能力已经覆盖了多少
- 有没有更小、更大的、或不同角度的切法

这一步的价值很高，因为很多设计失败，不是方案差，而是**问题定义错了**。

#### 为什么这能提升质量

如果前提没被挑战，后面的所有讨论都可能建立在错误起点上。  
这类错误通常最贵，因为它不会在早期暴露，只有到实施、联调、上线之后才发现方向偏了。

#### 对 spec-first 的意义

`spec-first/brainstorm` 已经会问问题，但可以更明确地加一层：

- 这个需求是不是正确的切口
- 这个问题是否值得拆
- 有没有更小的 wedge
- 有没有更简单的替代表达

这能把 brainstorm 从“澄清需求”升级为“校正问题”。

### 3.2 强制给出 2-3 个方案，并写清 trade-off

superpowers 的方案生成不是“列几个想法”，而是要求：

- 至少 2 个方案
- 最小可行方案
- 理想架构方案
- 必要时再补一个创意路径
- 每个方案都要写 pros / cons / reuses / risk

#### 为什么这能提升质量

很多设计文档的问题，不是结论错，而是结论来得太快。

当你只给一个方案时，文档往往会默认：

- 这个方向是自然正确的
- 其他路径不值得提
- trade-off 可以留给后面再说

但后面往往没有“再说”的机会，或者再说时成本已经很高。

#### 对 spec-first 的意义

`spec-first/brainstorm` 如果吸收这一点，会让文档更像真正的决策材料，而不是单一路线说明书。

最有价值的落点是：

- 最小改动路径
- 长期最优路径
- 可折中路径

这会让 `/plan-ceo-review` 更容易做 scope 取舍，也让 `/plan-eng-review` 更容易看出架构风险。

### 3.3 把“证据”和“观点”拆开写

superpowers 很强调：

- 看到什么
- 听到什么
- 观察到什么
- 推断出了什么

这是很强的质量习惯。

#### 为什么这能提升质量

很多设计失败，是因为文档把猜测写得像事实。

比如：

- “用户需要更简单的 onboarding”
- “这个流程一定太重”
- “大家肯定会喜欢这个方案”

这些话如果没有证据支撑，就只是观点。

#### 对 spec-first 的意义

建议把 brainstorm 输出中的内容至少拆成三类：

1. **事实**
2. **推断**
3. **决策**

这样后续人读文档时，能一眼知道：

- 哪些是已确认信息
- 哪些是暂时判断
- 哪些是最终决定

这会大幅提高文档的可审查性和可继承性。

### 3.4 在设计过程中加入“段落级确认”

superpowers 要求每个 section 写完都要确认一次，这一点很适合借鉴。

#### 为什么这能提升质量

设计质量差，经常不是“最后总结错了”，而是某个中段已经偏了，但没人及时纠正。

段落级确认的价值是：

- 早发现偏差
- 早发现歧义
- 早发现范围膨胀
- 早发现用户其实不同意前提

#### 对 spec-first 的意义

可以考虑把设计对话切成几段：

- 问题定义确认
- 目标用户 / 场景确认
- 方案比较确认
- 成功标准确认

这样输出会更稳定，不容易出现“最后一页看起来很完整，但前面其实已经错位”的情况。

### 3.5 加一个轻量 adversarial review

superpowers 的文档流程里有一个很实用的设计：先自我审查，再进入正式输出。

#### 为什么这能提升质量

设计文档通常会犯几种典型错误：

- scope creep
- 逻辑自洽但与问题无关
- 约束遗漏
- edge case 漏掉
- 方案对比失真

一个轻量的 adversarial review 能在很低成本下，提前把这些问题挑出来。

#### 对 spec-first 的意义

不一定要一开始就引入重型子代理审查，但至少可以加一个简化版清单：

- 有没有漏掉最关键前提
- 有没有把一个方案当成结论
- 有没有把事实和推断混在一起
- 有没有过度设计
- 有没有明显不可行点

这会显著提高 brainstorm 输出的“可执行性”。

### 3.6 把“完成标准”写得像验收条件

superpowers 很在意 done / done with concerns 这类边界。

#### 为什么这能提升质量

如果没有清楚的完成标准，设计就容易变成：

- “差不多了”
- “再补一点就能用”
- “应该没问题吧”

这些说法对执行者没有帮助。

#### 对 spec-first 的意义

`spec-first/brainstorm` 最好明确这些问题：

- 什么状态可以交给 `/plan-ceo-review`
- 什么状态只能算草案
- 哪些问题不清楚就不能往下走

这会让整个链路的质量更可控。

## 4. 不建议直接照搬的部分

superpowers 不是全都适合原样搬进来。

### 4.1 不建议把 spec-first 的产品语境抹平

superpowers 的风格更通用，适合任何创意工作前的设计澄清。

但 `spec-first/brainstorm` 的优势，恰恰是它更产品化：

- 有 startup / builder 分流
- 有产品价值判断
- 有更强的 spec-first 下游链路

所以不要把它改成“纯通用设计模板”，否则会丢掉自己的定位。

### 4.2 不建议把流程做得过重

superpowers 的流程很完整，但如果全部硬搬，可能会让 `brainstorm` 变得太长、太重。

`spec-first/brainstorm` 的目标应该是：

- 提高判断质量
- 不明显增加使用负担

所以更适合**吸收关键质量机制**，而不是复制全部流程细节。

### 4.3 不建议把“强势措辞”照搬到所有场景

superpowers 的 diagnostic 风格很强，有些地方甚至偏“逼问”。

这个风格适合 founder diagnosis，但不一定适合 spec-first 所有用户。

spec-first 的定位更需要：

- 质量严格
- 语气可控
- 产品判断清晰

而不是单纯更强硬。

## 5. 推荐的改进优先级

如果目标是“致力于提升质量”，我建议按这个顺序做：

### P0：马上该加

1. **前提挑战**
2. **2-3 方案对比**
3. **事实 / 推断 / 决策分离**

这三项最直接提升输出质量，而且不会把流程变得特别重。

### P1：很值得加

4. **段落级确认**
5. **轻量 adversarial review**
6. **更明确的完成标准**

这三项会显著减少后期返工，让输出更可审查。

### P2：可以渐进增强

7. **修订链路**
8. **更强的下一步行动定义**

这两项主要改善长期可维护性，不是最先要做，但很有价值。

## 6. 对 `spec-first/brainstorm` 的最终建议

最理想的方向不是“变成 superpowers”，而是：

- 保留 spec-first 的产品判断和 startup/builder 语境
- 吸收 superpowers 的质量控制机制
- 让 brainstorm 从“问清楚”升级成“问清楚 + 问对 + 问到可执行”

换句话说：

- **spec-first 负责方向**
- **superpowers 负责质量门槛**

如果两者结合得好，brainstorm 就不只是一个前置对话技能，而会变成一个真正能提高设计可靠性的产品决策入口。

## 7. 一句话总结

`spec-first/brainstorm` 已经解决了“别急着写代码”的问题。  
下一步最值得从 superpowers 借鉴的是：**别急着接受问题定义、别急着只走一条路、别急着把观点写成事实、别急着说自己已经完成了**。
