# spec-prd 跨场景研究并入主需求边界说明

## 0. 结论

当前应并入主需求的不是整份跨场景研究方案，而是其中已经能稳定增强主需求边界的底层原则。跨场景研究仍是 sibling research-proposal，里面关于 `operating_context` preset、segment skill split、跨场景样本矩阵、T2-D 采纳前提探针等内容还没有完成验证，不应整体升级为主需求 P0/P0.5。

主需求当前定位是“研发侧 PRD intake / 需求澄清 / planning-readiness workflow”，核心目标是阻止 `spec-plan` 发明 WHAT。跨场景研究最值得并入的点，是把这个核心目标表达得更稳：**closure 是不变量，owner round-trip 是场景条件项**。也就是说，进入 plan 前必须关闭所有 load-bearing WHAT gap；但关闭 gap 的方式不一定总是外部 owner 一问一答，也可以是 source-resolved、leaf、how-pushdown，或在 owner 与执行者同体时留下显式 self-decision 证据。

建议当前只并入 5 个点：

1. closure 与 owner round-trip 解耦。
2. anti-rubber-stamp 护栏。
3. 低 ceremony 不等于低风险。
4. 暂不按 segment 拆公开入口。
5. self-decision 最小留痕。

一句话原则：**并入的是底层边界，不是把跨场景研究整体升级为主需求。**

## 1. 判定原则

### 1.1 只并入已能增强主需求的稳定边界

主需求已经有 `intake_mode`、`clarification_budget`、`review_gate_mode`、`clarification_risk_tier`、Requirement Interaction Analysis、Owner Question Packet、Right-Size Budget、Handoff Context Slice 与 `spec-plan` 消费端复验等节点。这些节点已经足够承接“不同场景下轻重不同”的问题。

因此，跨场景研究中只有当某个点能让这些已有节点更不容易被误用，才适合现在并入主需求。相反，如果某个点需要新增公开 skill、schema 维度、checker token、样本矩阵或用户研究结论，它就还处在研究或 plan 阶段，不应进入主需求主链路。

### 1.2 区分不变量、场景条件项与研究假设

- **不变量**：所有场景都必须守住。例如进入 `spec-plan` 前不能让 planning 发明 WHAT；load-bearing gap 必须有合法 closure；ready receipt 只证明 machine invariants，不证明语义充分性。
- **场景条件项**：不同协作拓扑下实现方式不同。例如外部 owner 一问一答、异步 Push-Right Owner Brief、开发者 self-decision，都是 closure 的不同证据形态。
- **研究假设**：需要样本或 owner 决策确认。例如 solo/small-team 是否会因为 ceremony 降低而更愿意采纳、是否需要拆 `spec-prd-solo`、preset 默认值如何设计。

当前主需求只能吸收前两类，第三类应保留在研究文档或后续 plan 中。

### 1.3 不扩大 deterministic checker 的语义职责

主需求已确立 `Scripts prepare, LLM decides`。跨场景研究里的新边界也必须遵守这个原则：脚本最多验证字段存在、receipt freshness、OQ 与 Owner Decision Trace 的结构一致性、ready 自证风险；不能让脚本判断“这个 self-decision 是否真的深思熟虑”“solo 场景是否充分澄清”“是否应该拆 skill”。

所以，当前并入主需求时，表达应落在 LLM readiness、doc-review、fresh-source eval、人审和样本验证层，不能新增 BLOCKING reason_code。

## 2. 当前应并入主需求的 5 个点

### 2.1 closure 与 owner round-trip 解耦

#### 问题

主需求当前强调 `Requirements Grill / Owner Decision Brief`，容易被理解成：只要存在 load-bearing gap，就必须通过外部 owner 一问一答来关闭。这在大厂协作场景成立，因为 PM / stakeholder 与研发分离；但在 solo 或小团队场景里，开发者常常就是 owner，强行要求外部 owner round-trip 会把主链路变成不必要的 ceremony。

如果不解耦，就会出现两个坏结果：

- 对 solo / 小团队来说，流程显得过重，用户会绕过 `$spec-prd`，失去防止 AI 发明 WHAT 的价值。
- 对主需求来说，真正的不变量被误写成某一种交互形式，导致后续 plan 容易把“有没有问人”误当成“有没有 closure”。

#### 为什么现在要并入

这个点不依赖跨场景 preset 或样本矩阵，它是对主需求已有 Phase 5 的边界校正。主需求已在 Phase 5 里要求判断所有 load-bearing gap 的 closure status，并区分 `no_load_bearing_gap`、`source_answerable_gap`、`owner_owned_gap`、`too_many_owner_gaps`、`unclear_product_direction`。这说明主需求本来就不是“无条件问 owner”，而是“每个影响 WHAT 的 gap 必须找到合法关闭方式”。

跨场景研究只是把这件事说得更准确：**closure 是不变量，owner round-trip 是场景条件项。**

#### 应并入主需求的表达

建议在主需求 Phase 5 或 `可以跳过提问式 grill 的条件` 附近补充：

```text
Phase 5 的不变量是 load-bearing WHAT gap closure，而不是外部 owner round-trip 本身。owner round-trip 只是 owner 与研发分离时的 closure 证据形态。若 gap 已由 source/docs/design/prior PRD 关闭，或需求决策者与执行者同体且留下显式 self-decision 证据，也可以形成合法 closure。任何 closure 形态都必须说明 why planning will not invent WHAT。
```

#### 不应并入的内容

不要现在把 `owner-capped` 全面重命名为 `decided`，也不要新增 `self-capped` checker token。跨场景研究的 T1-C 已指出 `self-capped` 与现有 checker `OWNER_DISPOSITIONS` 的映射还未决，当前最小路径是保持主需求语义层表达：dev=owner 时可复用 owner decision trace 的证据形态，但不改机器 token。

#### 建议落点

- 主需求 §8.1.1 Mermaid 图后补一句“不变量是 closure，不是固定交互形态”。
- 主需求 Phase 5 分支说明中，把 `owner_owned_gap` 的描述从“必须提问式 grill”收敛为“必须获得有决策权者 closure；外部 owner 场景用 Owner Brief，self-owner 场景用显式 self-decision 证据”。
- 主需求 §8.1 `可以跳过提问式 grill 的条件` 中，补“跳过提问式 grill 不等于跳过 closure”。

### 2.2 anti-rubber-stamp 护栏

#### 问题

在外部 owner 场景，主要风险是模型篡改或误解 owner 答复，所以主需求关注 owner-answer fidelity。到了 solo 场景，owner 与开发者同体，篡改他人答复的风险下降，但出现另一个风险：AI 先替开发者填关键 WHAT，开发者没有真正思考就顺手接受，最后以“owner 已接受”的形式进入 `spec-plan`。

这不是普通的轻量化问题，而是直接破坏 closure 的问题。它和主需求已识别的 `checkpoint-as-escape`、`direct-write-after-read` 是同构失败：都把“未真正决定”伪装成“已 closure”。

#### 为什么现在要并入

主需求已经强调 `recommended answer` 和 Owner Question Packet，这会提高 owner 回答效率，但也会带来 rubber-stamp 风险。尤其在 self-owner 场景里，recommended answer 可能从“辅助决策”滑成“模型代替决策”。

因此，anti-rubber-stamp 不是跨场景研究的可选增强，而是主需求当前 `Owner Question Packet` 的配套安全边界。只要主需求允许 recommended answer，就需要明确：recommended answer 不能把关键 WHAT 的 owner 决策变成默认接受。

#### 应并入主需求的表达

建议补充：

```text
Owner Question Packet 可以给 recommended answer，但 recommended answer 不得成为模型默认填充关键 WHAT 的捷径。对会改变 WHAT、验收、scope、数据/权限/发布边界的决策，owner 接受推荐答案时必须留下显式决策痕迹，说明接受的是哪个决策、影响哪个 PRD write target、若不确认 planning 会发明什么。self-owner 场景同样适用，且需要额外防止 rubber-stamp。
```

#### 不应并入的内容

不要把 anti-rubber-stamp 做成 checker gate。脚本无法判断开发者是否真的思考过，只能验证是否存在某些字段或 trace 行。这个护栏应归 LLM readiness、doc-review、fresh-source eval 或人审判断。

也不要现在要求每个 solo 场景都必须经过独立 reviewer。跨场景研究提出独立 fresh-source reviewer 是验证 `self-capped` 是否被滥用的评估手段，不应变成主需求 P0 的每次运行成本。

#### 建议落点

- 主需求 R-19 `Owner question 应升级为 decision-ready packet` 的 Acceptance 中补 anti-rubber-stamp 约束。
- 主需求 §8.2 `Push-Right Owner Brief` 后补“recommended answer 的边界”。
- 主需求风险章节补“recommended answer 被 rubber-stamp”的风险与 mitigations。

### 2.3 低 ceremony 不等于低风险

#### 问题

主需求已经引入 `intake_mode`、`clarification_budget` 和 `right-size budget`，目的是防止小需求被完整 PRD 流程放大。但跨场景研究提醒了一个关键误用风险：用户可能把 `quick`、`compact`、`solo`、`small-team` 理解成低风险，从而跳过 privacy、auth、compliance、data authority、financial ledger、state machine 等高风险澄清。

这会造成 fail-open：一个独立开发者做受监管工具、资金流水、权限系统或个人数据处理时，组织协作规模很小，但 WHAT 出错成本很高。如果按“solo = 跳过合规 overlay”处理，就会削弱主需求要守住的 planning-readiness。

#### 为什么现在要并入

主需求已有 `clarification_risk_tier: low | medium | high | regulated` 和 R-12/R-13。现在需要补的不是新机制，而是优先级规则：**right-size 只能降 ceremony，不能降 risk posture。**

这条规则可以直接提高主需求质量，而且不依赖跨场景 preset 是否落地。

#### 应并入主需求的表达

建议补充：

```text
`intake_mode`、`clarification_budget`、`review_gate_mode` 只调制表达体量、owner 交互方式和 review ceremony，不得降低 `clarification_risk_tier`。当需求涉及 governance_need、artifact_longevity、what_error_cost、auth、PII、financial ledger、compliance、public API、state machine 或不可逆用户影响时，即使是 solo/quick/compact 场景，也必须 fail-safe 触发相应风险 overlay 或记录显式不适用理由。
```

#### 不应并入的内容

不要现在引入跨场景研究里的完整 `operating_context preset` 表，也不要要求主需求新增 `governance_need / artifact_longevity / what_error_cost` 三个正式字段。当前主需求只需要吸收 fail-safe 原则，并把它挂到已有 `clarification_risk_tier` 与 R-12/R-13。

#### 建议落点

- 主需求 R-21 `right-size budget` 后补“不得覆盖 risk tier”的 Acceptance。
- 主需求 R-12 `风险分级选择 overlay` 中补 fail-safe 规则。
- 主需求 §8.1 Phase 0 说明中补“budget 与 risk tier 的优先级关系”。

### 2.4 暂不按 segment 拆公开入口

#### 问题

跨场景研究讨论了是否需要按公司规模拆公开 skill，例如 `spec-prd-solo`、`spec-prd-enterprise`。这看似能降低不同人群的心智负担，但会引入更大的合同漂移风险：两个公开入口很容易各自演化出不同的 closure、readiness、防发明 WHAT 语义，破坏主需求正在建立的单一 spine。

而且“公司规模”不是稳定的 intent 轴。一个 solo 开发者也可能做高治理需求，一个 enterprise 内部小工具也可能只是低风险 quick 需求。按 segment 拆，会迫使入口路由先问“你是什么组织形态”，而不是先理解当前需求的风险、surface、变更范围和 planning 发明 WHAT 的可能性。

#### 为什么现在要并入

主需求已经有足够的伸缩手段：`clarification_view` 处理 surface，`clarification_profile` 处理表达深度，`clarification_risk_tier` 处理风险，`clarification_budget` 处理 ceremony。当前应把“不要急于按 segment 拆公开入口”写成主需求边界，防止后续 plan 直接发明新 skill。

这符合项目的 source/runtime 边界和 Light contract：保持单一公开 workflow spine，复杂度下沉到 trigger-loaded reference、concern-axis internal module 或 optional overlay。

#### 应并入主需求的表达

建议补充：

```text
当前 P0/P0.5 不按 solo/small-team/enterprise 拆公开 `spec-prd` 入口。跨场景差异优先由 right-size budget、clarification_profile、clarification_risk_tier、Push-Right Owner Brief、trigger-loaded reference 和 concern-axis internal module 吸收。segment split 只作为后续 fallback，必须在拆分必要性阈值、样本验证和 drift 风险评估通过后再进入 plan。
```

#### 不应并入的内容

不要在主需求里新增 `spec-prd-solo`、`spec-prd-small-team`、`spec-prd-enterprise` 的候选任务，也不要把 segment split 写进 P0/P0.5 路线图。跨场景研究的 T1-A 尚未定义可判定阈值，T2-D 采纳前提也未验证，现在把拆分写入主需求会过早承诺方案。

#### 建议落点

- 主需求 Non-goals 增加“不按组织规模拆公开 PRD skill”。
- 主需求 R-26 `Light contract` 或 roadmap 中补“segment split 仅为 gated fallback”。
- 主需求风险章节补“公开入口拆分导致 closure/readiness 语义漂移”的风险。

### 2.5 self-decision 最小留痕

#### 问题

如果用户/开发者自己就是 owner，要求外部 owner answer 不成立。但如果完全不留痕，就无法证明关键 WHAT 是被有决策权者显式决定的，也无法给后续 `spec-plan`、`spec-work`、review 或跨会话 AI 提供稳定上下文。

这正是 solo 场景里 `$spec-prd` 的核心价值：不是让一个 PM 审批，而是把原本脑内的 WHAT 决策变成可复用、可审查、可交接的工程证据。

#### 为什么现在要并入

主需求已经强调 Owner Decision Trace、Decision Card、`why planning will not invent WHAT` 和 Handoff Context Slice。self-decision 最小留痕只是这些机制在 owner=developer 场景下的解释，不需要新 artifact topology，也不需要新 checker。

关键是要防止把 self-decision 当成可削减 ceremony。轻量化可以减少长模板、批量问题和多 stakeholder sign-off，但不能删掉 closure 的最低证据。

#### 应并入主需求的表达

建议补充：

```text
当需求决策者与执行者同体时，自决策可以作为 closure 证据，但必须留下最小显式留痕：decision、accepted answer 或 rejected alternative、affected PRD write target、why planning would invent WHAT if not recorded、source/owner basis。self-decision log 是 closure 的最小证据，不是可削减 ceremony。
```

#### 不应并入的内容

不要新增 standalone `self-decision-log.md`、不要新增持久 trace ledger、不要要求每个小需求输出完整 owner packet。最小留痕应复用现有 Decision Card、Owner Decision Trace、Readiness Self-Check 或 Handoff Context Slice。

#### 建议落点

- 主需求 §8.2 Owner Brief 后补 self-owner 退化形态。
- 主需求 §8.1 `可以跳过提问式 grill 的条件` 后补“self-decision 仍需留痕”。
- 主需求完成定义中补“self-owner 场景必须有最小 closure evidence”。

## 3. 暂不并入的内容

### 3.1 `operating_context preset` 不作为正式主链路字段并入

跨场景研究里的 `solo / small-team / enterprise` preset 有价值，但当前仍是研究假设。它涉及默认 profile、交互方式、治理 overlay、receipt 强度和 AI-executable lens 的联动，过早并入主需求会造成新的正交维度和概念负担。

当前主需求只需要吸收它背后的原则：协作拓扑影响交互 ceremony，但不改变 closure/readiness/防发明 WHAT 不变量。

### 3.2 不新增 `self-capped` checker token

`self-capped` 的语义成立，但机器层映射未决。跨场景研究 T1-C 已提出三种方案，doc-review 倾向复用现有 `owner-capped` 并在语义层说明 dev=owner。主需求当前不应承诺新增 token、reason_code 或 checker 逻辑。

### 3.3 不把跨场景样本矩阵作为主方案前置

跨场景样本矩阵适合验证 preset 或拆分方案，不是主需求 P0/P0.5 的准入条件。主需求当前的 P0/P0.5 是让研发澄清链路稳定、避免 `spec-plan` 发明 WHAT；跨场景矩阵应保留为后续优化验证。

### 3.4 不把“独立开发者是最大增量人群”作为 confirmed goal

跨场景研究 T2-D 已指出，这个判断需要真实用户信号验证。当前可以把“提升 solo/小团队可采纳性”作为候选价值方向，但不能把“独立开发者必然采纳轻量 PRD skill”写成主需求 confirmed premise。

### 3.5 不按公司规模拆公开 skill

segment split 是 fallback，不是当前 P0/P0.5 scope。只有当 T2-D 采纳前提为 GREEN、T1-A 拆分阈值可判定、且 drift 风险评估证明单入口无法承载时，才应进入后续方案。

## 4. 已被主需求覆盖、无需重复并入的内容

### 4.1 right-size budget 已覆盖轻重伸缩

主需求 R-21 已要求 `clarification_budget: compact | standard | deep` 和 `review_gate_mode: quick | explicit | degraded`。跨场景研究对 ceremony 降低的诉求，优先通过这里承接，不需要新增公开入口。

### 4.2 Owner Question Packet 已覆盖 decision-ready brief

主需求 R-19 和 §8.2 已要求 owner gap 形成 decision-ready packet，包含 recommended answer、affected write target 和 planning_would_invent。跨场景研究的 Push-Right Owner Brief 不需要重复并入，只需补 anti-rubber-stamp 与 self-owner 边界。

### 4.3 `clarification_risk_tier` 已覆盖风险 overlay

主需求 R-12/R-13 已规定按风险触发 security/privacy/accessibility/reliability/compliance overlay。跨场景研究的补充点是“budget/preset 不得降低 risk tier”，不是另建风险模型。

### 4.4 主链路图已覆盖 Phase 5 closure 分支

主需求 §8.1.1 Mermaid 图已经把 `source_answerable_gap`、`owner_owned_gap`、`too_many_owner_gaps`、`unclear_product_direction` 分开。当前只需在这张图周围解释：这些分支服务于 closure，不等于固定 owner round-trip。

### 4.5 `spec-plan` 消费端复验已覆盖下游防发明

主需求 R-06、R-10、R-22、R-23 已覆盖 receipt/check-only、traceability、downstream sync impact 和 context slice。跨场景研究不需要再引入新的 downstream artifact，只需保持“不能让 plan 发明 WHAT”的同一不变量。

## 5. 推荐回写主需求的最小修改清单

如果后续要把本说明回写到主需求，建议按下面顺序做最小修改：

1. 在 §0 结论或 §8.1 前补一句：`spec-prd` 的不变量是 load-bearing WHAT gap closure，owner round-trip 是协作拓扑下的一种证据形态。
2. 在 R-19 补 anti-rubber-stamp：recommended answer 必须辅助 owner 决策，不能替 owner 默认决定关键 WHAT。
3. 在 R-21 或 R-12 补优先级：right-size 只能降 ceremony，不能降 `clarification_risk_tier`。
4. 在 Non-goals 或 R-26 补：当前不按 solo/small-team/enterprise 拆公开入口，segment split 是 gated fallback。
5. 在 §8.2 或完成定义补：self-owner 场景允许 self-decision closure，但必须复用现有 Decision Card / Owner Decision Trace / Readiness Self-Check / Handoff Context Slice 留下最小证据。

这些修改都不需要新增 checker、runtime mirror、公开 workflow 入口或 artifact topology。
