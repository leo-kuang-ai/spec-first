# spec-prd 跨场景适配研究方案：从大厂复杂协作到独立开发者

## 取证与边界声明

- 本文件是研究方案（research-proposal），不是实现 plan，也不修改 `skills/spec-prd/**` 行为或 generated runtime mirrors。
- 本文件与同目录 `2026-06-28-prd-skill专业化与稳定性优化方案.md` 是 sibling 关系：后者解决 `spec-prd` 的定位修正与稳定性优化；本文件解决「同一个 skill 如何跨组织协作场景优雅伸缩」。本文件不覆盖、不回滚该方案，复用其已确立的护栏与裁决。
- 外部方法论（Kiro / GitHub Spec Kit / Amazon Working Backwards / 敏捷 DoR/DoD / Shape Up / RICE-MoSCoW-Kano）本轮无法在线复证（环境禁用 web 检索与抓取），均为 advisory 参考，不是项目 confirmed truth。需要 confirmed 证据时，由后续样本运行、fresh-source eval 与 doc-review 提供。

## 0. 结论

当前 `spec-prd` 是为 **brownfield 大厂协作** 设计的：owner decision trace、Requirements Grill 一问一答、finalize machine receipt 硬卡、design-source provenance、多 stakeholder 治理。它对独立开发者的**价值更高**（防止 vibe-coding 时让 AI 跨会话乱发明 WHAT），但其**形态（ceremony 成本）过重**，在独立/小团队场景会被直接绕过，从而既得不到价值、也损害采纳。

研究的核心命题：

> 真正 load-bearing 的不变量是「每个 load-bearing WHAT gap 在进入 plan 前必须到达一个 closure」，而**不是**「必须与一个外部 owner 一问一答」。当前链路把这两件事耦合了。把 **closure（不变量）** 与 **owner round-trip（场景条件项）** 解耦，`spec-prd` 就能在所有场景守住 spine，只在交互与治理层伸缩。

由此推出两条架构裁决：

1. **不新增正交维度**。已有 `surface_lens × clarification_profile × clarification_risk_tier` 三维，若再叠加一个正交选择轴会组合爆炸，违反优化方案 §7.5 与 80/20 原则。正确做法是引入一个**轻量 operating context preset**——它是上述三维的**默认投影**，**不是第四个正交选择轴**，只捆绑默认值并调制交互/治理 ceremony，复用已有机制（`clarification_risk_tier`、Push-Right Owner Brief、四个合法停点、finalize），不另立 taxonomy。
2. **operating context 永远 advisory，绝不进 BLOCKING checker**，与 `clarification_profile` 同纪律。

### 关于「技能拆分」（本轮新增研究焦点）

用户提出「必要时技能也要拆分」。本轮把拆分作为**正式候选**研究，而非预先排除。要回答的不是「要不要拆」，而是 **沿哪条轴拆、在什么阈值上拆才必要**，以及哪些差异根本不该用「拆技能」解决（应由 preset / trigger-loaded reference 吸收）。

基于项目既有 split DNA（`spec-write-tasks` 按 pipeline/derived 拆、`spec-app-consistency-audit` 按 intent/concern 拆、`spec-prd` 用 9 个 trigger-loaded references（其中 `evaluation-governance.md` 仅治理/生命周期触发，常规 PRD 流程约 8 个）吸收复杂度——**从不按客户规模拆**，见 §13），**领先推荐**（待 §11 测试与 §6 数据确认/证伪）：

- 保持**单一公开入口** `spec-prd`；
- 沿 **concern-axis（即 §13 split DNA 的 intent/concern 轴）做内部模块化**：把 enterprise 重机械（多 stakeholder 治理、design-source provenance、合规 overlay、RACI）下沉为 **trigger-loaded reference / 可选 internal helper**，让 base 默认对 solo/小团队足够轻；
- advisory **operating_context preset** 决定加载多少 overlay；
- 「按 segment（公司规模）新增兄弟级公开技能（如 `spec-prd-solo`）」作为**对抗候选**被 §12 审判，并保留为 fallback——**仅当 §11 拆分必要性测试通过时才采纳**。

完整复杂度建模、判定测试、候选架构对比见 §10–§13。

## 1. 目标与非目标

### 1.1 Goals

- 让 `spec-prd` 的 load-bearing 价值（防 plan 发明 WHAT、强制澄清、closure、readiness、证据闭环）在独立开发者 / 小团队 / 大厂三类场景都能被采纳。
- 让独立/小团队场景的 ceremony 成本与产物重量随场景下降，而**不退化**核心 closure 完整性。
- 让大厂复杂协作场景保持现有强度（多 stakeholder、design-source、合规 overlay、强 finalize），不被「跨场景化」削弱。
- 在不新增正交 schema 维度、不新增语义 checker、不扩 Core 6 的前提下完成跨场景适配。
- 服务项目使命：扩大 harness 对「AI coding 最大增量人群（独立开发者/小团队）」的可采纳性，并把价值锚定在宿主不提供的「跨场景澄清/证据闭环」层。

### 1.2 Non-goals

- 不新增 `operating_context` 作为第三个正交维度或 frontmatter 必填 schema；只做 advisory preset。
- 不让 `solo` 场景成为「跳过澄清 / 跳过 closure」的逃生口。
- 不改 `spec-prd` 的 load-bearing 不变核（closure / readiness / 防发明 WHAT 三点）。
- 不新增 BLOCKING reason_code；context 缺失、不匹配或推断错误最多 advisory。
- 不在本研究阶段修改 `skills/spec-prd/**`、references、scripts 或 runtime mirrors。
- 不把外部方法论当 confirmed truth 写入 checker 或 confirmed 结论。

## 2. 问题框定：两个场景的真实差异

| 维度 | 大厂复杂协作 | 小团队 / 独立开发者 |
| --- | --- | --- |
| 谁是 owner | PM / 多 stakeholder，与开发者**分离** | 开发者**就是** owner（自己问自己） |
| WHAT 出错成本 | 高（多人返工、合规、排期） | 协调成本低，但 **context-loss 成本高**（自己/AI 跨会话遗忘） |
| 主要失败模式 | plan 违背 owner 意图发明 WHAT | **从没写下 WHAT**，AI 跨会话不一致地瞎补；rubber-stamp AI 的隐性决策 |
| owner provenance 上界 | 真实存在（无法证明 owner 真答过） | **基本消失**（可信任自己的答复），但出现新风险 vibe-drift |
| ceremony 回报 | 高，值得 | 低，过重即被绕过 |
| spec 首要用途 | 跨团队对齐契约 | **AI 实现的可执行契约 + 人机共享记忆** |

两条关键洞察：

1. **「owner round-trip」对独立开发者坍缩**。grill / owner-trace / fidelity 整套机器假设「提问的模型」与「决策的 owner」是两个主体。当人既是开发者又是 owner，机器**目的从「忠实抽取他人决策」变成「逼自己在 vibe-code 前显式化并记录自己的隐性决策」**——同一套机器，不同语义。
2. **owner-answer fidelity（防篡改）在独立场景失效，需换成 anti-rubber-stamp（防盖章）**。独立开发者没有「篡改他人答复」风险，却有「让 AI 替自己决定关键 WHAT、然后顺手接受」的风险。这是 solo 场景**独有的新失败模式**，必须有对应护栏（CR-03）。

## 3. 核心设计：closure ↔ owner round-trip 解耦

当前四个合法停点（`SKILL.md:137`）：`leaf / source-resolved / owner-capped / how-pushdown`，其中 `owner-capped` 隐含外部 owner。解耦后：

| 停点 | 不变量（所有场景） | 场景条件实现 |
| --- | --- | --- |
| leaf | 无更多会改变产品行为/验收/scope 的子决策 | 不变 |
| source-resolved | 源码 / 文档 / 测试 / glossary / prior-PRD 闭合 | 不变 |
| `owner-capped` → **decided** | 由有决策权者拍板 | 大厂 = 外部 owner 答复；独立 = **self-capped**（开发者作为 owner 显式拍板并记录） |
| how-pushdown | HOW 下推 plan，带理由 | 不变 |

这一步是整个方案的理论支点：它让独立开发者的「自我澄清」成为**合法 closure，而不是「跳过澄清」的逃生口**。

术语约定：`decided` 是统一概念名（停点"由有决策权者拍板"），`owner-capped`（外部 owner）与 `self-capped`（dev 自身）是它的两种来源，后文沿用这一区分；下沉到 checker 层的映射策略见 §15 待决 T1-C。

配套 anti-rubber-stamp 护栏（CR-03）：

- `self-capped` 的决策必须是开发者**显式**做出并记录在 run-local self-decision log（owner-* 在 solo 下退化为 self-* 行），不能是模型默认填充。
- 这是当前 checkpoint-as-escape 反模式（`SKILL.md:141`）与 direct-write-after-read 反模式（`SKILL.md:143`）在独立场景的同构变体：把「未真正决定」伪装成「已 closure」。护栏判定与现有反模式一致——closure 必须有可审查的决策痕迹，不能只是断言。
- 这是 producer-side / LLM-owned 语义义务，不是 checker 硬卡（与 owner-answer fidelity 同层，靠 readiness / fresh-source eval / 人审守护）。

## 4. operating context：复用而非新增

operating context preset 是 §11 拆分必要性测试判定「不拆核」之后的**伸缩层**；若测试判定某差异需要拆分，则交由 §12 候选架构处理，**不在 preset 内强行容纳**。在领先推荐下，preset 同时充当「加载多少 concern-axis overlay」的开关。

引入轻量 advisory preset，只捆绑已有字段默认值 + 调制交互 ceremony：

| preset | owner model | 交互方式 | 治理 overlay | finalize 强度 | AI-executable lens |
| --- | --- | --- | --- | --- | --- |
| `solo` | dev = owner | **self-clarification checklist**（自填，非 round-trip 提问） | 全跳过（RACI / 合规 / sign-off 不触发） | receipt 仍跑，轻量 | **默认开**（spec 即 AI 实现契约） |
| `small-team` | 一个可异步触达的 owner / 创始人 | **Push-Right Owner Brief**（批量异步，已存在 `SKILL.md:194`） | 仅 risk-tier 触发 | 标准 | 按 surface |
| `enterprise` | 多 stakeholder 分离 | 当前一问一答 grill + blocking tool | RACI / design-source / 合规全在 | 强（Claude Stop hook 硬卡） | 按 surface |

要点：

- **机器已部分就位**：Push-Right Owner Brief 天然适配 small-team 异步 owner；对 solo 它退化成「自决策清单」。本研究主要是把隐性能力**显式化、优雅化**，不是新建机器。
- **context 选择 advisory，永不 blocking**：用户声明 > 输入信号推断（无独立 owner、个人 repo 等，仅 advisory）> 默认中档；checker 绝不因 context 缺失/不匹配阻断。
- **与 sibling 方案三概念正交且不串台**（CR-06）：
  - `clarification_view`（surface 端族：App/H5-PC/Admin/Backend/CLI/Mixed/Generic）—— 表面。
  - `clarification_profile`（澄清深度/表达：compact / ai-executable / frontend-ux-heavy …）—— 深度。
  - `clarification_risk_tier`（low/medium/high/regulated）—— 风险。
  - `operating_context`（solo/small-team/enterprise）—— **协作拓扑**。它只为上述三者**设默认**（如 solo 默认 compact profile + 跳过合规 overlay），但三者仍可被显式覆盖。

## 5. 逐节点适配分析

| 主链路节点 | 不变核（所有场景必跑） | 随 context 伸缩的部分 |
| --- | --- | --- |
| Classify / Route | route-out 判断、是否值得写 durable WHAT | solo 下「值不值得写」阈值更低（小改也常值得做 AI 记忆） |
| Current-State Evidence | brownfield first、证据标签 | solo 下 source 多为自己代码，confirm 成本低 |
| Requirement Analysis Gate | understanding → uncertainty → write-target map | solo 下 map 可极简（self-checklist 形态） |
| Product Expert Lens | 风险排序、绑 write target | 多视角 stakeholder 主要在 enterprise |
| **Requirements Grill** | **每个 load-bearing gap 到达 closure** | **交互形态**：solo = 自问自填；small = 异步 Brief；ent = 一问一答 |
| Pre-Write Closure | 不先写后补 | prewrite-guard 强度可随 context（solo 仍保留，防 vibe-skip） |
| PRD Write | WHAT not HOW、验收、scope | solo 默认开 Engineering Implementability Lens（喂 AI） |
| Readiness + Finalize | readiness 判断 + machine receipt | receipt **强度**伸缩；fidelity → anti-rubber-stamp |
| Handoff | 防 plan 发明 WHAT + 消费端复验（方案 P0.5） | solo 下 handoff 常是「同一人 + AI 进 spec-plan」，记忆连续性 > 跨人对齐 |

两个最深的发现：

1. **不变核高度集中在「closure + readiness + 防发明 WHAT」三点**，其余几乎都可伸缩——说明 spine 本身健壮，跨场景化主要是**减负**而非重构。
2. **Grill 是唯一需要语义改造的节点**（交互形态随 context 变，但 closure 不变），其余节点只是 overlay 开关。改造面收敛，风险可控。

## 6. 研究 / 验证方法论

1. **跨场景样本矩阵**：取 3–4 个真实增量（含 1 个 solo / AI-coding 典型、1 个 enterprise 多 stakeholder），**每个分别用 solo / small-team / enterprise 三 mode 跑**，对比：
   - `time_to_usable_spec`（首份可用 spec 耗时）
   - `ceremony_cost`（owner round-trip / 提问数）
   - `closure_completeness`（load-bearing gap 是否都到合法停点）——**solo 减负后绝不能退化的硬指标**
   - `plan_invention_reduction`（下游是否仍要发明 WHAT）
   - `ai_implementability_score`（spec 能否直接驱动 AI coding）
2. **双向失败测试（核心实验）**：
   - solo mode 是否被滥用成「跳过 closure」？若 `closure_completeness` 掉，说明 self-capped 护栏不足。
   - enterprise mode 强行用于 solo 场景，量化「不可用 ceremony」成本，证明现状缺口。
3. **fresh-source eval per mode**：用 `docs/contracts/workflows/fresh-source-eval-checklist.md`，每 mode 至少一次，记录 reviewer findings。
4. **anti-rubber-stamp 专项**：构造「AI 主动替 solo 开发者填关键 WHAT」的输入，检验是否被要求显式 self-decide（验证 CR-03 / AE-03）。
5. **指标基线**：无历史数据记 `baseline_unavailable`，从首批样本起 baseline；复用方案 §11.4 指标 + 新增 `ceremony_cost` 与 `time_to_usable_spec`。
6. **可维护性阈值（拆分客观触发信号；plan 阶段操作化，见 §15 待决 T1-A）**：度量单技能在 preset 下的 prose 体量与条件分支密度（如 SKILL.md 行数、context-conditional 分支数、reference 触发条件数）。设一个「过载阈值」——一旦 A 路线下 prose 超阈值且 solo 心智模型不可清晰表达，即为 §12 走 C/D 的客观信号。本研究阶段仅给出候选度量，**具体阈值数值与判定函数留待 plan 阶段操作化**；在阈值定义前，§12 的 A/B/C 裁决不可声称已由本测试得出。
7. **漂移风险模拟（对 B 的定量审判；plan 阶段执行）**：对 segment 拆分（B）显式推演「两份核各自独立演化后 closure / readiness / 防发明 WHAT 语义分叉」的成本与检测难度，与 A/C 的「单核 + overlay」漂移面对比。
8. **路由歧义测试**：用 `skills/using-spec-first/SKILL.md` 路由规则检验——用户在**意图阶段**能否选对 segment 入口（公司规模常不在 immediate intent 中）。若 router 必须在意图前先问公司规模，记为 routing smell，计入 B 的反对证据。

通过标准：三 mode 下 `closure_completeness` 不退化；solo/small-team 的 `ceremony_cost` 与 `time_to_usable_spec` 显著低于 enterprise；fresh-source eval 无 P0/P1，P2 resolved 或 deferred-with-owner；拆分决策可回溯到 §11 测试结论而非公司规模直觉。

## 7. 风险与反模式护栏

| 风险 | 护栏 |
| --- | --- |
| context 变成第三正交维度 → 组合爆炸 | 只做 preset 捆绑，不是新 schema 维度；preset 仅设默认，可被既有字段覆盖 |
| solo mode 成为「跳过澄清 / 跳过 closure」逃生口 | self-capped 是**合法 closure 但需显式 self-decision log**；`closure_completeness` 是硬验证指标 |
| context 进 BLOCKING checker | 永远 advisory，与 profile 同纪律；缺失/不匹配最多 advisory |
| 大厂能力被独立场景「砍没」 | 砍的是 ceremony / overlay，不变核三场景一致 |
| 自动推断 context 出错 | 推断仅 advisory，default 中档，绝不阻断 |
| anti-rubber-stamp 被做成机器 gate | 它是 producer-side / LLM-owned 语义义务，靠 readiness / fresh-source eval / 人审，不脚本化 |
| 违反 deep research 69/69 否决与 §7.5 | 不新增语义 checker、不扩 Core 6、不删 load-bearing 机制 |

## 8. 与项目使命的对齐

## 10. 复杂度建模：用 profile 替代「公司大小」

「小公司 vs 大公司」是表象。真正驱动 ceremony/治理需求的是下面六维 **complexity profile**；它同时驱动 §4 preset 选择与 §11 拆分判断（CR-08）。它是一个**谱**，不是三个离散桶——`solo / small-team / enterprise` 只是谱上的常见落点。

| 维度 | 含义 | 低 → 高 |
| --- | --- | --- |
| `decision_maker_cardinality` | 谁能拍板 WHAT | 1（dev=owner） → N（多 stakeholder） |
| `role_separation` | 角色是否分离 | dev=PM → dev≠PM≠合规≠设计 |
| `governance_need` | 治理/合规/审计 | 无 → RACI / sign-off / 审计留痕 |
| `what_error_cost` | WHAT 出错的协调成本 | 低（自己改） → 高（多人返工/合规事故） |
| `spec_consumer` | spec 主消费者 | **AI 执行** → 人类跨团队对齐 |
| `artifact_longevity` | 产物寿命/可审计性 | 短、私有 → 长、可审计 |

判读规则：

- profile 是 advisory，由用户声明或输入信号推断，**绝不进 checker、绝不阻断**。
- profile **不直接等于** operating_context；它是上游证据，preset 是其默认投影，仍可被 view/profile/risk_tier 显式覆盖。
- 三类常见落点：`solo`（六维全低）、`small-team`（cardinality/role 中、governance 低）、`enterprise`（多维高）。但真实项目可能混合（如 solo 开发者做 regulated 金融工具 → cardinality 低但 governance 高），此时按维度而非按「公司规模」选 overlay——这正是用 profile 替代二元的价值。

## 11. 拆分必要性测试（核心判定）

任一「场景差异」是否值得拆技能，顺序过下面六门；**任一门判否即落回 preset/reference，不拆**：

1. **同核测试**：两场景是否共享同一 core invariant（closure / readiness / 防发明 WHAT）？共享 → **禁止拆核**（拆会复制并使核漂移，正是最坏结果，CR-04）。
2. **变化性质测试**：差异是 ceremony/overlay，还是 artifact-topology / 下游消费者不同？ceremony → preset/reference；topology/consumer 不同才进入拆分候选。
3. **轴向测试**：拆分轴是 intent/concern/pipeline-role（项目认可），还是 customer-segment（不认可）？segment → 对**公开入口**有强反对推定。
4. **渐进披露测试**：trigger-loaded reference 能否吸收这块复杂度？能 → 不新增技能（这是 `spec-prd` 现有的 8-reference 机制）。
5. **入口成本测试**：新公开入口是否迫使 router 在**意图阶段**判定用户判定不了的东西（公司规模）？是 → 反对公开拆分（§6 路由歧义测试供数据）。
6. **80/20 净值测试**：拆分是减少 durable mechanism 总量，还是增加重复/漂移面？净增 → 不拆。

把 solo↔enterprise 差异套进测试：差异（owner round-trip、治理 overlay、finalize 强度、AI-executable 默认）经 §2/§3 分析**几乎全是 ceremony/overlay，且共享同一 closure 不变量**（self-capped 仍是合法 closure）。→ 门 1/2 判「不拆核」，门 3/5 判「segment 不宜作公开入口轴」。**结论：默认不按 segment 拆；走 concern-axis 内部模块化 + preset。**

## 12. 候选架构对比与 segment 拆分对抗审判

| 选项 | 形态 | §11 测试结果 | 主风险 |
| --- | --- | --- | --- |
| **A 单技能 + advisory preset** | operating_context 调制 ceremony（当前 §4） | 通过门 1-3、6；门 4/5 取决于 prose 是否过载 | 条件分支膨胀、prose 过载（§6 阈值监控） |

| **C concern-axis 内部模块化（领先推荐）** | 单公开入口 + enterprise 重机械下沉 reference/internal helper + preset | 通过门 1-6；用门 4 吸收复杂度尾部 | 模块边界设计成本（一次性） |
| **D pipeline/derived 拆分** | 仿 `spec-write-tasks`：核心澄清 vs 派生「企业 readiness/治理」层 | 门 2 可能成立（治理是否真可独立派生待验证） | 可能过度；企业层是否「可派生独立」需数据。约束：若采纳 D，**readiness 必须留在 core 不派生**，仅 governance/compliance overlay 可独立，否则违反 Non-goal「不改不变核」 |

**对 B 的对抗审判**（认真对待用户提案，不绕过）：

- **最强 pro**：solo 的目的发生质变——从「忠实抽取外部 owner 决策」变成「跨 AI 会话自洽 + anti-rubber-stamp」；owner-trace/fidelity 整套机械对 solo 是纯认知负担，一个精简 solo 专用技能可能更快、更少误导。
- **con（待 §6 数据）**：solo 仍满足**同一 closure 不变量**，只是 closure 来源从 owner-answer 变 self-capped（§3 已解耦）→ 差异是 ceremony 不是 core，触发门 1/2 判「不拆核」；segment 轴又触发门 3/5。
- **裁决方式**：不靠嘴辩，靠 §6 样本——仅当数据证实「单技能为兼容 enterprise 而无法给 solo 一个干净心智模型（prose 过载阈值被突破）」时，B 才成立。届时优先考虑 **C 内化版**（solo 走极简 base，enterprise overlay 全部 trigger-loaded），仅在 C 也无法切干净时才升级为 B。
- **若最终采纳 B**：必须共享同一 core 引擎（reference 或 internal helper 持有 closure/readiness/防发明 WHAT），两个公开入口只是薄壳——否则违反门 1。

**领先推荐：C**（单公开入口 + concern-axis 模块化 + preset），B 作为带触发条件的 fallback 保留。最终裁决由 §6 数据闭环给出，本文件不锁死。

### 16.1 探针要回答的核心问题

研究方案的整条立论建立在一个未验证因果链上：「solo 绕过 spec-prd 是因为 **ceremony 太重** → 减负就能提采纳」。探针要在三个竞争假设间做出区分：

- **H1（方案假设）**：障碍是 ceremony 重量。减负（A/C/D）有效。
- **H2（误诊风险）**：障碍是"coding 前要先把 WHAT 显式化"这一动作本身，无论多轻都被拒。减负无效，需改问题为"在 vibe-coding 流里近乎零摩擦地被动产生 spec"。
- **H3**：根本没感到 vibe-drift 痛点 → 价值主张本身不成立。

### 16.2 样本与形式

- 3–5 名真实对象，混合纯独立开发者与小团队 founder/lead；优先重度使用 AI coding 的人。
- 半结构化访谈，每人 15–20 分钟；或等价的异步问卷 + 1 轮追问。
- 诚实限制：这是**定性方向性信号**，非统计显著性；样本少，只用于 go / reframe / kill 决策，不用于参数化设计。

### 16.3 访谈提纲（顺序非诱导）

1. **基线行为**：上次做一个新功能/项目，从想法到写代码，中间有没有"先把要做什么写下来"的步骤？（不预设对错）
2. **障碍性质**：若没有——为什么？没必要 / 太慢 / 没工具 / 其他？（区分 H1 vs H2）
3. **消费者**：若有——什么形式？给谁看：自己 / AI / 他人？（验证 §2「solo 的 spec 主消费者是 AI 执行」）
4. **痛点真实性**：有没有过 AI 写着写着方向跑偏、或跨会话忘了之前定的东西？当时怎么处理？（验证 H3：vibe-drift 痛点是否真实被感知）
5. **ceremony 容忍度**：为避免那种跑偏，你愿意前置花多少时间？0 / ~1 分钟 / ~5 分钟？
6. **轻量假设检验**：如果有个工具 30 秒内帮你把"要做什么"澄清清楚再交给 AI，你会用吗？什么情况会 / 不会？（测 H1）
7. **误诊判别（关键）**：如果它只问你 1–2 个最关键的问题就放行，你会用吗？还是连这个都嫌多？（H1 与 H2 的分水岭）
