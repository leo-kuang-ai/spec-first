Skills Flow：七组情境路径

按“想实现的能力”找入口：每组是一条可执行路径，不只是一个命令。黄色是用户显式入口，蓝色是模型可自动调用、也可由用户显式调用的 skill，虚线框是产物或状态。

这是交互式概览，不是独立规范；请以 调研索引、Engineering 映射 与对应 SKILL.md 为准。

黄色：user-invoked 蓝色：model-invoked（用户也可调用） 虚线：artifact 绿色：判断/出口
主研发 外部入站 Bug 诊断 巨大模糊 架构健康 跨会话辅助 生产力/学习

没有匹配的 flow。换一个 skill 名、产物名或任务关键词试试。

① 主干

主研发 Flow：idea → ship

大多数产品/代码工作走这条：先把想法压实，再决定是否拆票，最后实现、测试、评审和提交。

入口：/grill-with-docs

怎么做这环

有代码库的新需求从 /grill-with-docs 开始；它底层用 /grilling 一次一个问题打穿需求，并用 /domain-modeling 记录术语和 ADR。小且仍在当前上下文的工作可直接 /implement；需要跨会话或并行时， /to-spec 再综合成 spec，接着用 /to-tickets 拆成 tracer-bullet tickets；每张票用 fresh session 跑 /implement，内部尽量用 /tdd，最后 /code-review。

注意

  • grill-with-docs -> to-spec -> to-tickets 尽量保持同一个未中断上下文。
  • 短小工作不必为了走图而先写 spec/ticket；条件满足时可从共同理解直接进入 implement。
  • 每个 implement 应从 ticket fresh start，避免把旧上下文带进实现。
  • to-spec 写前要确认测试 seam；to-tickets 发布前要确认拆分和 blocking edges。
② 入站

外部入站 Flow：raw issue / PR → agent-ready

处理别人提来的 bug、feature request 或 external PR：先分诊，不直接实现。

入口：/triage

怎么做这环

/triage 读取 issue/PR、评论、标签和代码上下文，检查是否已实现或曾被拒绝； 必要时用 /grilling 和 /domain-modeling 把请求打磨成 agent-ready brief。 只有 ready-for-agent 的事项才交给 /implement。

注意

  • /to-tickets 生成的票已经 ready，不要再 triage。
  • triage 评论必须带 AI disclaimer。
  • 只有 rejected enhancement 写入 .out-of-scope/；已实现的 wontfix 不写。
③ 修复

Bug 诊断 Flow：broken → fixed

先拿到能变红的 tight feedback loop，再复现、最小化、假设、插桩、修复和回归测试。

入口：/diagnosing-bugs

怎么做这环

用 /diagnosing-bugs，不要直接猜原因。先构造一个已经跑过、能抓住这个 bug 的命令； 再最小化 repro，列 3-5 个可证伪假设，单变量插桩，最后用正确 seam 写回归测试并修复。

注意

  • 没有 red-capable command，就不要进入假设阶段。
  • 没有正确测试 seam，本身就是发现；修完后交给架构健康环。
  • 所有 [DEBUG-*] 临时 instrumentation 最后必须清掉。
④ 探路

巨大模糊工作 Flow：foggy effort → clear route

用于一个任务太大、太雾，一个 session 装不下：先做地图，不直接冲实现。

入口：/wayfinder

怎么做这环

/wayfinder 先命名 destination，再创建 map issue 和 child investigation tickets。 每张票解决一个 decision：可能用 /research 查资料，用 /prototype 提高讨论保真度，或用 /grilling 继续问清楚。路清楚后才接回 /to-spec 或 /implement。

注意

  • Wayfinder 默认是 planning，不是 deliverable production。
  • 一次 session 只 resolve 一张 ticket。
  • map 是索引，决策详情住在 ticket 的 resolution comment。
⑤ 治理

架构健康 Flow：codebase health → deepening opportunity

不是直接做功能，而是找浅模块、漏 seam、难测区域，把代码库变得更适合人和 agent 操作。

入口：/improve-codebase-architecture

怎么做这环

/improve-codebase-architecture 用 /codebase-design 的词汇扫描代码库，产出一个临时 HTML 报告。用户选一个 deepening opportunity 后，再进入 /grilling 和 /domain-modeling，最后变成 spec 或直接实现。

注意

  • 报告阶段不先设计接口，只展示候选。
  • 判断依据是 locality、leverage、testability。
  • 若用户用强理由拒绝候选，可记录 ADR，避免未来重复建议。
⑥ 辅助

跨会话/辅助 Flow：research / prototype / handoff

这些不是完整研发链，但经常嵌入其他链路：查资料、跑原型、跨上下文窗口交接。

入口：按问题选

怎么做这环

要读官方资料，用 /research 生成带引用的 Markdown；纸上想不清的逻辑/UI， 用 /prototype 写一次性可运行答案；上下文窗口快满或要分支探索，用 /handoff 写临时交接文档，再开 fresh session。

注意

  • /research 必须追到 primary sources。
  • /prototype 的主分支只保留已验证决定；原型本身提交到 throwaway branch，并从 implementation issue 留下 context pointer。
  • /handoff 引用已有 artifact，不复制 spec、ADR、issue、diff。
⑦ 非代码

Productivity / Learning Flow

不一定进入代码库：澄清想法、长期学习、维护 skill 写作质量。

入口：/grill-me / /teach

怎么做这环

没有代码库也想压实想法，用 /grill-me，它只调用 /grilling 并不写文件。想长期学习某个主题，用 /teach，当前目录会变成教学工作区。 要写或改 skill，用 /writing-great-skills 作为写作原则参考。

注意

  • /grill-me 是 stateless；需要 ADR/术语就用 /grill-with-docs。
  • /teach 会维护 MISSION.md、RESOURCES.md、lessons/*.html 等文件。
  • /writing-great-skills 不在研发链路里，是 skill 作者工具。
