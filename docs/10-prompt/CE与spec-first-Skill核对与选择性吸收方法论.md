# CE 与 spec-first Skill 核对与选择性吸收方法论

> 2026-09-10；从 `ce-compound` / `spec-compound` 的对比、修复和终审提炼。适用于后续逐个核对有 CE 来源的 Skill。

**先用 spec-first 当前定位判断能力是否需要，再沿完整行为链确认差异，最后用反例和消费者回归验证修复。** CE 是上游经验来源；上游更新、本地差异、文件拆分都不自动意味着必须迁移或存在缺陷。

本文是 [Skill 设计与优化方法论 v2](./skill-prompt-设计与优化方法论-v2.md) 的专项补充，不新增 canonical、运行时契约或强制状态机。与 [项目角色契约](./结构化项目角色契约.md) 冲突时，以角色契约为准。

## 1. 先确定判断基线

spec-first 当前是 **AI-enhanced SDLC / SDD workflow harness**，连接 `Codebase -> Spec -> Plan -> Tasks -> Code -> Review -> Knowledge`。核对目标是改善这条链路中的意图、上下文、执行边界、证据和知识复用，而非复刻 CE 的全部产品范围。

- **目标：** 识别真实能力缺口、契约漂移、无效约束及值得适配的上游机制，修复已授权范围内的问题。
- **非目标：** 文件布局对齐、机械替换名称、追求相同 prompt 长度、引入无消费者的框架，或顺手重构相邻 Skill。
- **范围：** “比较/终审”默认交付审查结论；“逐项修复”授权必要本地修改与验证。提交、推送、发布及 runtime 维护按实际授权分别判断。
- **权威：** 从当前 `skills/`、脚本、schema、模板及 consumers 确认实现；历史文档与记忆只提供线索。generated runtime 不能反向成为修复源。

历史 [CE 优先迁移方法](../solutions/conventions/ce-first-skill-migration-method.md) 强调行为保真，适合已决定迁移的能力；本文先解决“是否采用、采用到哪个边界”。决定采用后，仍需验证行为完整性，不能用“本地适配”解释无意丢失。

## 2. 冻结证据，沿行为链阅读

开始时记录两个仓库的路径、HEAD、相关 dirty 状态和目标 Skill。存在未提交修改时，HEAD 不能代表当前磁盘内容；评审应注明所读工作树，重要摘录保留路径、行号或内容指纹。避免覆盖其他任务改动。

按下列链路建立能力映射，允许两边一对多、多对一：

```text
入口与触发条件
  -> 按条件读取的 references / prompts
  -> scripts / schema / templates
  -> artifact 与输出报告
  -> caller / downstream consumer
  -> 验证与失败处理
```

| 核对面 | 必须回答的问题 |
| --- | --- |
| 入口与模式 | 谁调用？何时触发？interactive、headless、lightweight 等模式是否保留必要检查？ |
| 能力与读取时机 | 规则在哪里？入口是否真的引用？是否在做决定或写入之前读到？ |
| 输入与上下文 | 输入来自当前源码、历史记录还是推断？有无范围、新鲜度及局限说明？ |
| 路径与执行环境 | CWD、目标仓库、临时候选和最终产物路径是否被区分？ |
| 输出与契约 | 字段、enum、状态、动作名和报告是否在所有生产者与消费者间一致？ |
| 权限与副作用 | 谁拥有写权限？候选生成、验证和持久化是否混同？ |
| 失败与降级 | 无能力、无证据、无权限、输入无效分别如何处理？消费者如何解读？ |
| 复用与维护 | 是否已有等价能力？共享脚本、镜像 schema、其他 Skill 是否受影响？ |

**文件不存在不等于能力不存在，文件存在也不等于能力可达。** 在判定缺失前，先追踪 inline 规则、引用文件、调用者提供的前置条件和共享实现。不要只比较两个 `SKILL.md`。

## 3. 对每项差异作出裁决

| 裁决 | 判断依据 | 处理方式 |
| --- | --- | --- |
| 保留本地边界 | 差异服务当前定位、授权或 source/runtime 纪律 | 说明原因，确认没有连带丢失必要能力 |
| 已有等价覆盖 | 行为、读取时机及出口约束均由已有 owner 承载 | 给出双侧证据；不重复引入 |
| 适配吸收 | 上游机制解决真实缺口，且有本地消费者 | 将行为映射到现有 owner，补最小充分机制 |
| 修复缺陷 | 能复现错误、矛盾、遗漏或错误完成声明 | 明确触发条件、影响与根因，修 owning source |
| 暂缓或不采用 | 超出产品范围、宿主已覆盖或收益证据不足 | 写明理由；暂缓项说明重估触发条件 |

裁决依靠语义和证据，不靠“CE 更新所以更好”或“本地更严格所以更好”。新增 gate 要说明它保护哪个真实出口；新增脚本要说明可确定性验证的不变量；新增 artifact 要说明谁消费它。

## 4. 逐个根因修复，连同消费者收口

1. **写清问题。** 用“在什么输入和环境下，实际行为是什么，为什么违背契约”表达 finding，附当前证据。
2. **找最小反例。** 脚本行为缺陷先构造可复现输入或会失败的回归测试；纯文案问题通过完整调用链说明矛盾，避免新增只复述文案的测试。
3. **确认 owner。** 修复共享根因；搜索同字段、动作、脚本、状态及调用参数的其他生产者和消费者。
4. **实施最小充分修改。** 同步确实共享的契约；不因存在复制文件就顺手引入新的统一框架。
5. **验证相邻边界。** 覆盖修复场景、原本正确的场景和受影响消费者，确认没有用漏报替代误报。
6. **记录真实结果。** 同步必要文档与 CHANGELOG，列清未执行验证及 runtime 影响。只有存在新修改、新失败或未决风险时继续扩大检查。

对于有字节一致要求的本地副本，应同步并验证该约束；没有此要求时，不能只因文件同名就强制一致。Contract 的使用关系决定同步范围。

### Schema 与 enum

- enum 表达稳定分类，优先基于项目职责；具体模块名、provider 名、实现路径放入适当的 `module`、`tags` 或正文。
- 既覆盖 harness 本身，也考虑该 Skill 服务业务项目的需要，避免将所有知识硬塞进治理分类。
- 同时核对 schema、说明、模板、示例、validator、refresh 和检索消费者。
- 明确兼容策略：未修改的历史文档如何读取，新文档按什么规则写入，实质重写是否需要重新分类。
- enum 成员合法只是确定性地板；选择哪个分类、是否准确描述根因仍由 LLM 结合证据判断。

### Vocabulary 与动作契约

- 对齐允许的动作、作用范围、验证方式和报告，不只统一名称。
- 区分同义词折叠与概念退役：fold 保留存续条目、别名并修复范围内引用；删除且无存续条目是不同影响面的操作。
- “没有新增词条”不能推出“没有变更”；refine、fold、scrub 也必须出现在变更报告中。
- 邻域检查应绑定已调查范围和已有证据，不能悄然扩大为整个项目重建词汇表。

### 校验、退出码与降级

Scripts 负责路径存在性、解析、hash 和校验结果等事实；LLM 负责解释历史引用、裁决 FLAG 和判断知识是否值得保留。脚本应暴露原始事实与局限，不能把无法验证写成已确认。

退出码、`FLAG`、`NOTE`、degraded 与调用方处理必须一起检查。它们的精确含义由目标工具契约决定；不要把本次 validator 的约定套到所有 Skill。降低误报时，同时验证真实错误仍能被发现。

## 5. 用对照用例检查边界

| 对照场景 | 要发现的失误 |
| --- | --- |
| 普通 session/content ID vs 明确 commit 引用 | 将普通 ID 误当提交，或将真实错误统一降为 NOTE |
| 同一 ID 先普通、后明确引用 | 去重丢失更强证据及其行号 |
| 仓库内文件 vs 仓库外候选 | 从候选目录错误推断目标仓库 |
| 候选路径 vs 最终发布路径 | 相对链接按临时目录校验，导致误报或漏报 |
| Git 项目 vs 有效非 Git 目录 vs 无效目录 | 能力降级与输入错误混同，或缺 Git 就跳过全部校验 |
| 新文档 vs untouched legacy vs 实质重写 | 兼容路径绕过新契约，或让历史存量无故失效 |
| 无新增条目 vs 已修改既有条目 | 报告宣称无变更，掩盖实际写入 |
| 单个 Skill 通过 vs 共享消费者一致 | 局部测试全绿，但 refresh、caller 或其他副本仍漂移 |
| source 正确 vs runtime 已生效 | 将磁盘修改或旧会话行为冒充宿主加载验证 |

按目标 Skill 选择相关用例即可；这张表不是每次必须全跑的固定矩阵。

## 6. 终审要能推翻前一次结论

终审不是重复确认“已经修好”。重新从当前 source 看实际行为，优先寻找三个问题：原 finding 是否成立、修复是否伤及相邻正确场景、是否遗漏消费者。

本次 compound 核对留下的关键教训：

| 观察与纠正 | 可复用的方法 |
| --- | --- |
| 初看似乎缺少 coherence neighborhood，完整读取后发现 assembly 已内联承载 | 先查行为承载位置，再判断能力缺失；真正需要修的是动作与报告契约一致性 |
| 分类沿用上游应用框架语义，难以表达本项目职责 | 改为适配 harness 的分类 v2，同时保留业务代码分类及旧文档读取路径 |
| 为减少 SHA 误报，将未解析 ID 都降为 NOTE，明确无效 commit 也不再 FLAG | 必须同时测试普通 ID 和明确 commit claims，不能仅验证误报消失 |
| 显式传目标仓库后，有效非 Git 项目退出，丢失文件检查 | 区分无 Git 能力与无效目录，保留可执行检查并收缩证据声明 |
| compound 专项通过后发现 refresh 对 claims 脚本有一致性要求 | 修复完成条件包含共享消费者；搜索脚本名与合同测试，不止运行点名 suite |

## 7. 证据与完成声明对齐

| 验证方式 | 可以证明 | 不能单独证明 |
| --- | --- | --- |
| 源码与静态合同检查 | 引用可达、字段一致、规则存在 | 模型实际遵守规则 |
| 脚本执行与行为测试 | 给定输入下的输出、退出码、副作用 | 所有语境正确、所有消费者已覆盖 |
| fresh-source 语义审查 | 当前磁盘 prompt 的场景表现及可发现矛盾 | 真实宿主投射或现场收益 |
| 真实宿主/模型评测 | 指定版本、环境和样本下的行为 | 任意宿主、未来任务的泛化效果 |
| 真实任务结果 | 当前样本内的返工、可信交付与成本表现 | 无条件的长期收益 |

Skill 行为变更需要语义验证时，按 [fresh-source checklist](../contracts/workflows/fresh-source-eval-checklist.md) 检查当前 source，避免当前会话缓存干扰。未执行或能力不可用时明确记录原因，不将静态测试数量换算成行为正确率。

收口时确认：

- [ ] 每项差异有裁决；每个 finding 有触发条件、影响和证据。
- [ ] 采用的 CE 能力已落到本地 owner，必要读取时机、模式和出口没有丢失。
- [ ] schema、动作、报告、脚本和共享消费者相互一致。
- [ ] 相关失败用例及原本正确场景得到验证；降级没有伪装成成功。
- [ ] 只修改 owning source，交代 generated runtime 是否受影响、是否刷新。
- [ ] 实际验证、未验证范围、交付路径和未完成事项都已写清。

## 8. 可复用提示词

### 只读核对

```text
比较以下两个 Skill：
上游：<ce-repo>/skills/<ce-skill>
本地：<target-repo>/skills/<spec-skill>

立足当前 spec-first 项目角色契约，做只读核对，不修改被审对象。
先记录两侧源码基线与相关 dirty 状态，再沿入口、references、scripts、
schema/templates、artifact/report、callers/consumers、tests 追踪行为。
逐项区分：保留本地边界、已有等价覆盖、适配吸收、修复缺陷、暂缓/不采用。
不要根据文件名、拆分方式或长度推断能力缺失。
优先报告有触发条件和证据的缺陷，再说明差异裁决、最小修复顺序及验证缺口。
每项重要结论给出双侧 source refs；未确认的判断明确标注。
```

### 已授权逐项修复

```text
基于上述核对，逐个根因完成修复。写入范围限定 <target-repo>，CE 只读。
先复核 finding，再构造必要反例，修改 owning source，并追踪共享消费者。
保持当前项目定位、授权、source/runtime 和证据边界；不机械复制上游流程。
enum/schema 要说明历史兼容与实质重写策略；动作、报告、退出码和降级保持一致。
对误报修复同时测试真实错误，对路径修复同时检查 CWD、候选位置与最终位置。
完成后从当前 source 终审，允许推翻原结论，修复实际发现的回归。
只运行与风险相称的验证，同步必要文档与 CHANGELOG。
报告修改结果、实际验证及限制；不将本地修复扩大为提交、推送或 runtime 刷新。
```

每个 Skill 的最小记录可用一段：`基线/范围 -> 差异与证据 -> 裁决及 owner -> 修改 -> 验证及局限 -> 未完成项/重估条件`。无需为普通核对建立新状态系统。

## 9. 何时重新核对

项目定位、上游基线、入口模式、共享消费者、schema 或 validator 信号语义变化时，重新验证相关结论。新宿主投射、实际失败或反例也应触发重查；不能将本次测试通过视为永久证明。

历史升级过程可参考 [上游 CE 同步升级方法](../solutions/architecture-patterns/upstream-ce-sync-upgrade-methodology-2026-04-26.md)，其中路径、宿主和实现判断必须回到当前 source 复核。
