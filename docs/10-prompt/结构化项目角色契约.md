# spec-first 项目角色契约 v3.3

> 让越来越自主的 AI coding agent 更快地产生可信变更，而不是更多代码。

本文件只定义 spec-first 的第一性原理、使命、权威和不可越过的边界。命令、路径、schema、宿主差异与操作步骤不属于本契约；当前实现映射见 [`docs/contracts/`](../contracts/)。

实现与本契约冲突时，默认是 implementation gap / drift，不得为迁就现状削弱原则。

---

## 1. 第一性原理

1. **代码不再稀缺，可信变更仍然稀缺。** 真正受限的是正确意图、有效上下文、可靠反馈、验证能力和人的注意力。
2. **自主性是放大器，不是权威来源。** 能力越强、loop 越长，收益与错误都会被放大，因此自治必须有界、可观察、可停止、可恢复。
3. **事实、判断与授权不可混同。** 事实来自可回源证据，语义由 LLM / human 判断，副作用只能来自明确授权。
4. **信任只能覆盖证据直接支持的 claim。** 输出、共识、测试通过或 artifact 存在，都不能自动证明语义正确或真实效果。
5. **长期价值属于项目，而非宿主。** 宿主 primitive 会商品化；项目应长期拥有 intent、evidence、governance 与可失效 knowledge。

由此得到：

```text
可信变更 = 清晰意图 × 有效上下文 × 有界执行 × 可核验证据 × 可失效学习
```

任一项接近零，更多 prompt、agent、工具或自动化只会更快放大问题。

---

## 2. 使命、权威与边界

spec-first 的使命是治理一次变更的工程与证据循环，缩短 **time-to-trusted-change**，提升 **quality-adjusted throughput**，并让价值可识别、可试用、可评估。

- **Host** 提供 agent、工具、权限与执行 primitive，决定任务如何运行。
- **spec-first** 连接 intent、context、scope、claim、evidence、handoff 与 knowledge，约束能够声称什么。
- **Project / Project owner** 定义价值、授权任务、纠正语义，并拥有长期 artifacts 与 knowledge。

spec-first 应是项目拥有、跨宿主可投射的工程协议；不应成为 prompt / agent 集合、强状态机、中心化流程引擎、通用 agent runtime、硬编码专家系统或宿主 primitive 的重复实现。

权威边界：

- Project-owned source 是 intent、governance 与 durable contract 的权威来源；其中的 evidence、artifact 与 knowledge 仍按 provenance、freshness、claim scope 和验证状态确定权威。runtime projection、cache 与 host-local state 是可重建派生物，不得反向冒充 source。
- Mutation、受限读取、数据外发、凭证使用与外部通信必须分别获得明确授权；环境权限只是执行条件，不构成授权。
- External provider 默认只提供带 provenance、freshness 与 limitations 的 advisory 候选；进入结论、mutation、verification、handoff 或 durable knowledge 前必须回源确认。
- 跨宿主投射追求语义保真，不承诺 feature parity；无法等价表达或强制时必须标记 lossy / degraded，不得静默提升权威或 gate 强度。
- 边界冲突时，停止受影响的副作用与完成声明，记录 gap，再修实现或以新证据修订契约。

## 3. 五项不可违反原则

### 3.1 Light contract

顶层契约只保留会改变决策的 durable invariants；条件流程和实现细节按需披露。上下文追求最高 **decision sufficiency per token**，达到语义充分与证据义务后停止扩张。治理强度随风险、歧义、不可逆性、影响面和 handoff 距离增长；低风险、可逆任务允许短路径，但不得降低与 completion claim 匹配的证据义务。

### 3.2 Deterministic floor, semantic judgment

Scripts / tools 强制可机械判定的不变量并准备事实；LLM / agents 判断意图、方案、风险与语义充分性；human / Project owner 裁决价值、高风险和不可逆取舍。任何一方都不得伪造另一方的权威。

### 3.3 Gate the exits, not the thinking

硬 gate 只守 **mutation、verification claim、source/runtime、handoff/context reset、knowledge promotion**。其余推理保持开放。没有可验证的 blocking primitive 时，只能声明为 loud convention，并说明未强制范围。

### 3.4 Evidence over confidence

证据必须与 claim 匹配；self-check 不等于 independent evidence，verification claim 不等于 field outcome。`Trusted Change` 是 claim-scoped、带新鲜度且可撤销的状态，新反例或依赖变化必须触发降级、纠正或回滚评估。

### 3.5 Bounded autonomy, reversible learning

高影响或长时 agent 工作必须有目标、scope、权限、资源边界、checkpoint、停止条件、恢复点和验证责任。多 agent 只在系统级可信收益高于协调成本时使用。只有已验证、可回源、可复用并带适用范围与 invalidation condition 的经验，才能进入 durable knowledge。

## 4. 演化判断

任何新增能力都必须改善可信变更公式中的明确一项，拥有真实 consumer，并说明 source、authority、失败方式、验证与退役条件。

默认顺序是：宿主已足够则 **Adopt**；价值未证实则 **Experiment / Defer**；只在必须补齐权限、证据、可移植或降级边界时做最小、可撤销的 **Wrap**；真实证据确认存在项目应长期拥有的 durable gap 后才 **Build**；无 consumer、成本高于收益或已被宿主覆盖时 **Thin / Retire**。

发生取舍时，可信证据与清晰边界优先于自动化和功能完整；最小可维护机制优先于完整框架；兑现、验证和简化已有能力优先于继续增加能力；用户真实研发增益优先于架构炫技。

核心判断只有一个：

> 这次演化是否用最小可维护机制，更快地把正确意图变成可信结果，同时没有把隐藏成本转移给审查、验证、集成和未来维护？

---

## 5. 修订纪律

- 本文件只保留当前有效原则；实现映射、操作方法、修订历史与验证记录分别进入 `docs/contracts/`、方法论文档、git history 与 `CHANGELOG.md`。
- 修改使命、价值权重、权威层级或 durable boundary，必须由 Project owner 明确授权，并记录 evidence origin、独立 fresh-source 视角和 invalidation condition。
- 高影响修订必须检查下游 contracts、host instructions、tests 与 consumers；实现冲突本身不是削弱契约的理由。
