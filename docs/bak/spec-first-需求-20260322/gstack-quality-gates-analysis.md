# gstack 质量保障与阶段门禁机制

文档日期：2026-03-22
分析对象：`/Users/kuang/xiaobu/gstack`

## 1. 结论

gstack 确实有“上一阶段进入下一阶段”的质量控制机制，但它不是传统 BPM 系统那种硬编码工作流引擎。

更准确地说，gstack 采用的是三层叠加机制：

1. 角色分段：不同阶段由不同 skill 负责，先定义问题，再审 scope，再审架构，再审设计，再实现、review、qa、ship。
2. 阶段产物传递：上一阶段会产出 design doc、test plan、review 结果、QA 证据等，供下一阶段继续使用。
3. 门禁体系：既有软门禁，也有流程门禁，还有少量真正的硬门禁。

所以它更像：

```text
强约束流程系统
  !=
严格状态机式工作流引擎
```

## 3. gstack 的门禁类型

## 3.1 软门禁

软门禁的特点：

- 系统通常不会直接阻断你继续做下一步。
- 但流程设计明确告诉你“现在继续往下做，质量风险会大幅上升”。

典型位置：

- `/brainstorm` 之后再进入 plan 阶段。
- `/plan-ceo-review` 用于避免产品方向错误。
- `/plan-design-review` 用于避免 UI/UX 规格缺失。

本质上，软门禁防的是：

- 做错问题。
- 做错产品。
- 做出模糊设计。

## 3.2 流程门禁

流程门禁的特点：

- 有“是否已跑过某类评审”的概念。
- 有 review 结果和 readiness dashboard。
- 不只是建议，而是进入下一阶段的重要判断依据。

最典型的是：

```text
Eng Review = required gate
CEO Review = informational / recommended
Design Review = informational / recommended
```

这说明 gstack 对门禁是分层的：

- 工程评审是核心强约束。
- CEO 和设计评审更多取决于需求类型。

## 3.3 近硬门禁

近硬门禁的特点：

- 系统虽然不一定像状态机一样“彻底锁死下一阶段”。
- 但到这个阶段时，你必须面对客观验证结果，否则没法合理往前推进。

最典型的是 `/ship`：

```text
/ship
  -> 先同步 base branch
  -> 跑测试
  -> 检查 diff
  -> 检查覆盖率
  -> 再 commit / push / create PR
```

这意味着：

- 你可以嘴上说“准备发布了”。
- 但真正执行 `/ship` 时，测试和基线同步会把问题暴露出来。

所以 `/ship` 是最终发布前最接近硬门禁的一道关。

## 3.4 真正的硬门禁

gstack 中真正会直接拦截动作的，多数不在“产品阶段切换”，而在“安全控制层”：

- `/freeze`：越界编辑直接 deny。
- `/careful`：危险 shell 命令直接 ask。
- `/guard`：同时做命令破坏预警和编辑越界阻断。

这类门禁是系统级硬门禁，不是流程建议。

## 4. 每个阶段如何保障质量

## 4.1 `/brainstorm`

输入：

- 模糊需求
- 初始想法

输出：

- design doc

质量保障点：

- 先确认真实问题，而不是直接实现表面 feature。
- 强迫用户澄清痛点、替代方案、约束和最小 wedge。

防的是什么问题：

- 一开始就做错方向。
- 需求听起来对，其实产品定义错。

## 4.2 `/plan-ceo-review`

输入：

- design doc
- 初步方案

输出：

- scope 决策
- 愿景扩展或收缩结论

质量保障点：

- 逼问“这是不是正确的问题”。
- 逼问“这是不是足够有价值的产品版本”。

防的是什么问题：

- 认真执行了一个低价值方案。
- 把用户真正要的东西缩成了一个次优 ticket。

## 4.3 `/plan-eng-review`

输入：

- 计划文档
- 设计文档

输出：

- 架构评审结论
- test plan
- 边界条件与失败路径分析

质量保障点：

- 架构、数据流、状态迁移、失败路径、测试策略必须说清楚。
- 这是 gstack 最关键的 required gate。

防的是什么问题：

- 方案看起来合理，实际不可落地。
- 边界条件没定义，后面实现和 QA 都会漏。

## 4.4 `/plan-design-review`

输入：

- UI/UX 相关计划

输出：

- 更完整的设计规格

质量保障点：

- 检查 loading、empty、error、responsive、a11y、信息层级等状态。
- 对设计模糊处做补全或发起决策问题。

防的是什么问题：

- 计划里只有“做个 dashboard”，但完全没有真实状态规格。
- 交互细节缺失，导致实现阶段只能拍脑袋。

## 4.5 实现阶段

输入：

- 已经过 plan 阶段审过的文档和决策

输出：

- 代码

质量保障点：

- 实现理论上应该遵循前面阶段产物，而不是重新发散。

防的是什么问题：

- 实现者偏离计划。
- 重新把已经做过的决策打乱。

## 4.6 `/review`

输入：

- diff

输出：

- 结构性问题
- 风险项
- 修复建议

质量保障点：

- 偏静态、结构化地审代码质量。
- 关注副作用、边界、信任链、容易线上出事的问题。

防的是什么问题：

- 代码能跑，但结构不稳。
- CI 能过，但生产行为危险。

## 4.7 `/design-review`

输入：

- 真实运行中的页面

输出：

- 视觉与交互层修复

质量保障点：

- 真正看页面，而不是只看计划。
- 用截图和交互去验证设计质量。

防的是什么问题：

- 计划看起来合理，实际页面很丑、很乱、像 AI slop。

## 4.8 `/qa` 与 `/qa-only`

输入：

- 真实页面/功能
- test plan

输出：

- QA 报告
- `/qa` 还会输出修复与回归测试

质量保障点：

- 不是只看代码，而是真实跑用户路径。
- `/qa` 还会把发现的问题修掉并补回归测试。

防的是什么问题：

- 代码 review 没看出来的真实行为 bug。
- 交互、数据、状态切换、浏览器行为问题。

## 4.9 `/ship`

输入：

- 已完成 review / QA 的分支

输出：

- PR / 发布动作

质量保障点：

- 必须面对 base branch 同步、测试结果、diff、覆盖率。
- 是“最终发版准备度”校验器。

防的是什么问题：

- 在过期分支上直接发版。
- 测试没跑透就推 PR。
- 发布动作和代码状态不一致。

## 4.10 `/document-release`

输入：

- diff
- 项目关键文档

输出：

- 更新后的文档

质量保障点：

- 让交付结果和 README / ARCHITECTURE / CONTRIBUTING / CLAUDE / CHANGELOG / TODOS 保持一致。

防的是什么问题：

- 功能已经改了，文档还停留在旧世界。

## 4.11 `/retro`

输入：

- 一段时间内的提交与行为数据

输出：

- 复盘
- 趋势观察

质量保障点：

- 它不直接阻断发布，但会在更长时间尺度上纠偏。

防的是什么问题：

- 团队持续低质量重复犯错。
- 测试占比、交付节奏、代码健康趋势没人看。

## 5. 上一阶段如何进入下一阶段

gstack 不只是“上一阶段给建议”，而是会留下阶段产物。

典型产物流如下：

```text
/brainstorm
  -> design doc

/plan-ceo-review
  -> scope 决策与 vision 调整

/plan-eng-review
  -> test plan

/review
  -> review 结果

/qa
  -> bug evidence + regression tests

/ship
  -> readiness / PR / 发布状态

/document-release
  -> doc sync 结果
```

所以“进入下一阶段”并不是完全靠对话上下文，而是靠：

- 文档
- 评审记录
- 测试结果
- 真实验证证据

## 6. gstack 的门禁本质

如果用一句话总结：

```text
gstack 的质量控制 = 阶段分工 + 阶段产物 + review/qa 验证 + 发布前最终闸门
```

它不像 Jira 工作流那样：

- 没点 Approved 就绝对不能下一列。

它更像一个“强治理的软件工厂”：

- 前段防方向错。
- 中段防方案错、代码错、设计错。
- 后段防测试漏、发布漏、文档漂移。

## 7. 最终判断

回答“gstack 如何保障各个阶段的质量，是否有上一阶段进入下一阶段的门禁”：

1. 有质量保障，而且是按阶段分层保障。
2. 有门禁，但多数是流程门禁和软门禁，不是全局硬编码状态机。
3. 真正最强的门禁集中在：
   - `Eng Review` required gate
   - `/qa` 的真实行为验证
   - `/ship` 的最终发布校验
   - `/freeze` `/careful` `/guard` 的系统安全阻断

所以 gstack 不是“谁都能随便跳步骤”的系统，只是它把门禁设计成了更贴近实际研发流程的治理机制，而不是僵硬状态机。
