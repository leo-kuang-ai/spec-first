Grounding Context

Codebase Context

当前仓库已经是一个相当完整的工程 harness：Node.js CommonJS CLI、35 个 canonical skills、241 个 references、134 个 skill scripts、202 个测试文件；六宿主 runtime projection、verification summary、honest closeout、handoff 与 knowledge promotion 都已有明确 owner 和确定性地板。2026-08-02 的系统审计整改恢复了 deterministic baseline，但同一报告仍把 C2 真实宿主、C3 真实任务和 C4 增量价值列为未完成证据路线。

8 月新增的风险驱动 assurance 进一步强化了 Product Contract confirmation、evidence authority、source binding 与 required-proof reconciliation。然而其 RA-01、RA-02、RA-04、RA-07 baseline-vs-candidate Trial 因缺授权的独立 fresh reviewer 或人工 blind review，全部以 not-run 收口。因此“机制已经更强”是 confirmed source fact，“真实任务因此更好”仍不是。

复杂度也继续增长。当前最大的三个核心入口分别为 spec-code-review/SKILL.md 1035 行、spec-plan/SKILL.md 864 行、spec-compound/SKILL.md 768 行。quickstart 已将 doctor probes 与 init 串起来，但源码明确禁止它模拟宿主内 workflow；安装成功与首次可信结果之间仍有明显体验断点。仓库同时缺少 canonical STRATEGY.md，产品方向仍主要散落在 dated strategic-review 文档中。

当前核心张力：deterministic floor 已经很强，field evidence 与 adoption 仍很弱。继续增加合同会扩大 carrying cost，却不能自动提高用户信任或研发产出。

外部信号与这一判断一致。Anthropic 2026 的 agent eval 指南明确区分 transcript 与 outcome，并要求多 trial、capability/regression suites 和 human calibration；OpenAI Harness Engineering 强调 repo legibility、结构性测试与把真实 review/bug 反馈回灌为 tooling；SiriusDeliver 通过真实部署与 A/B 测量交付时间和工程师投入。与此同时，harness-eval、VeRO 与 SanityHarness 表明通用 lint、eval runtime、sandbox 与 candidate optimization 正在外部商品化，spec-first 更应守住项目拥有的 intent、claim、evidence、handoff 与 knowledge 边界。

验证限制：本轮因用户未授权 subagent/并行代理，采用 inline/serial 六视角与 basis self-check；结论有 current-source、测试报告和一手外部资料支撑，但不声称独立 agent 多样性或 fresh-context basis verification。

1. First Trusted Change Adoption Sprint

Experiment置信度 92%复杂度 Medium

Description：用一个真实 brownfield golden journey、2–3 个可复现实例和 5–10 个明确 opt-in 的真实任务，闭合“安装 → 第一次可信变更 → 观察窗 outcome”。每次只记录与决策有关的 task class、首次可信结果时间、人工纠正、verification claim、reopen/rollback 与 owner verdict；新用户默认从已有失败测试、diff review 或小修复进入，而不是被迫走完整 workflow 链。

Axis
Adoption、Strategy 与首次价值；Evaluation 与 field outcome
Basis
direct: src/cli/commands/quickstart.js:7-11,84-89 明确 quickstart 只编排 probes/init，不能运行宿主内 workflow；docs/validation/2026-08-01-full-system-audit-remediation.md:48-50 将 C2–C4 保持为 not-run。external: SiriusDeliver 用真实部署和 A/B，而非功能数量，证明交付时间与工程师投入变化。
Rationale
这是当前最高杠杆动作：它同时验证 onboarding、可信机制、真实任务适配与对外价值表达。没有这层证据，新的 contract、metric 或 host 支持都无法证明值得长期维护。
Downsides
需要真实任务、owner 时间、隐私/脱敏与观察窗；5–10 个案例只支持任务类别内的初步判断，不能宣传普遍效率提升。
Boundary
不做静默 telemetry、用户等级、徽章或无基线的“效率提升 50%”；先使用人工研究记录，只有反复改变决策的字段才考虑 schema。

2. Counterfactual Harness Thinning

Thin置信度 90%复杂度 Medium

Description：对 spec-code-review、spec-plan、spec-compound 三个最大核心入口做 current-vs-thinned fresh-source 对比。按钢筋结构先标记 hot path、triggered reference、deterministic fact、eval evidence，再移除重复治理 prose 或下沉冷路径；同时比较 route correctness、evidence coverage、false pass、context bytes 与 wall time。

Axis
Context、Portfolio 与维护可持续性
Basis
direct: 当前三个入口分别为 1035、864、768 行；仓库已有 Front Controller + Triggered References + Deterministic Gates + Eval Regression、钢筋结构与 with-skill/bare-baseline 方法论。
Rationale
这项优化不需要发明新 runtime，却可能同时降低固定 token 税、判断噪声、source drift 与六宿主投射维护成本；它也是检验“哪些规则真的承重”的唯一可靠方式。
Downsides
压缩可能误删低频但高风险边界；共享 reference 也可能损害 skill-local 可移植性。单一模型/fixture 的 A/B 不能外推所有任务。
Boundary
删除前必须有语义迁移映射与 rollback；行为质量下降立即恢复。目标是减少重复与固定上下文，不是追求任意行数阈值。

3. Assurance Graduation Trial

Experiment置信度 88%复杂度 Low–Medium

Description：停止继续扩写 assurance prose、Agent 或 schema，先按现有计划补齐 RA-01、RA-02、RA-04、RA-07 的授权独立 fresh reviewer 或人工 blind review，并加入至少一个真实任务。裁决只允许 retain-trial、revise、revert 或 not-run。

Axis
Evaluation、Assurance 与 field outcome
Basis
direct: docs/validation/risk-driven-assurance/20260805T184057/trial-report.md:12-14,28-39 显示四个 frozen case 全部因 dispatch_authorization_missing 而未比较；focused contract tests 明确不能替代 Trial。
Rationale
当前 assurance 最大缺口已经不是实现，而是增量证明。完成既定 Trial 能决定这些新增语义是降低 false green，还是只增加低风险任务的 ceremony。
Downsides
需要独立 reviewer 授权与稳定 baseline/candidate identity；少量案例可能有方差，真实 field outcome 仍需更长观察。
Boundary
不新增 assurance public workflow、专用 Agent、runner、manifest 或 artifact family；Trial 结果先止于 maintainer decision，不能自动升级为默认产品承诺。

4. Versioned Host Trust Matrix

Wrap置信度 86%复杂度 Medium

Description：把当前零散的 host receipts 收敛为用户可读的 exact-version trust matrix。只维护会改变 mutation、verification、handoff 或 dispatch claim 的 material canary；每项显示 host/version、capture date、expiry、supported/lossy/degraded 与 limitation。先在一个主宿主完成深证，再复制已证明的 canary。

Axis
Host、Integrity 与跨宿主可信承诺
Basis
direct: 六宿主 projection 已达到 C1，但全系统审计明确不能据此外推 loader/invocation；Claude/Codex worker-dispatch 已有 versioned preflight/journey contract，可作为 receipt 形状参考。
Rationale
它让“支持宿主”从静态名单变为 claim-scoped、可过期、可降级的承诺，解决用户真正关心的“我的版本今天能依赖什么”。
Downsides
宿主版本更新快，实机验证需要环境、授权与清理成本；matrix 仍只能证明被测 canary，不能代表整个宿主。
Boundary
不做全宿主 × 全 workflow feature parity；无 fresh receipt 默认降级为 projection-only。宿主提供可信原生 capability facts 时删除 wrapper。

5. Canonical Strategy and Evidence Roadmap

Clarify置信度 85%复杂度 Low

Description：由 owner 创建 canonical STRATEGY.md，只保留 target problem、target persona、可证伪价值假设、可信指标来源、claim ceiling 与当前 P0/P1 tracks；8 月 dated roadmap 继续作为背景材料，实施 HOW 进入后续 plan。

Axis
Adoption、Strategy 与首次价值
Basis
direct: 当前仓库没有 STRATEGY.md，但 spec-strategy、spec-product-pulse 与 ideation grounding 都把它视为产品方向 source；现有 roadmap 同时包含合理目标与未经验证的徽章、unlock state、行业平均值等实施假设。
Rationale
没有当前策略真相源，adoption、metrics、host breadth 与 capability investment 会继续由 dated docs 竞争。先明确谁的什么问题最值得解决，才能解释何时 Thin、Wrap 或 Build。
Downsides
需要 owner 做真实取舍；一份策略文档不会自动产生用户证据，也可能在无人维护时迅速陈旧。
Boundary
不虚构目标值，不把使用次数当 outcome，不把实现设计或 roadmap 全文复制进策略；每个关键指标必须有 source 或明确 no data。

6. Workflow Portfolio Freeze and Retirement

Thin / Retire置信度 80%复杂度 Medium

Description：设置一个版本周期的“零新增 public workflow”窗口，并对 35 个 skill package 做 consumer audit。没有真实入口、downstream consumer、近期验证或宿主原生能力已充分覆盖的 surface，进入 merge、thin、optional pack 或 retire；新需求必须说明替代了什么以及退役条件。

Axis
Context、Portfolio 与维护可持续性
Basis
direct: 当前 35 skills、241 references、134 scripts，且每个 source surface 都承担六宿主投射、测试、README/docs 与升级责任；角色契约明确“兑现、验证和简化已有能力优先于继续增加能力”。
Rationale
这把 80/20 与 one-maintainer capacity 转化为可执行的 portfolio 约束，防止 capability 数量继续快于 adoption evidence 增长。
Downsides
消费信号目前不完整，容易误退低频高价值能力；退役还涉及 migration、runtime cleanup 与历史文档边界。
Boundary
不按行数或主观喜好删除；必须提供 consumer/eval/field evidence、migration、rollback 与下游检查。internal helper 不因隐藏而自动判死刑。

7. External Harness Integrity Provider Trial

Adopt Trial置信度 68%复杂度 Low

Description：以只读、opt-in 方式运行一次外部 harness-eval comparison，检查 skills、agents、hooks、MCP 与 host settings 的跨组件安全/冲突问题。只有当它发现现有检查遗漏的 material issue，才考虑把其 SARIF/facts 作为 optional Runtime Setup provider 输入。

Axis
Host、Integrity 与跨宿主可信承诺
Basis
external: 2026 harness-eval 已公开 92 条离线规则，覆盖 credential exfiltration chains、confused deputy、hook/skill conflicts、orphan surfaces 与 token blowouts；这些属于外部工具正在商品化的能力。
Rationale
一次 comparison 可以低成本判断 spec-first 是否存在跨组件盲区；若有价值则 Adopt/Wrap，若没有则不增加任何 source surface。
Downsides
外部项目较新、规则可能误报或与 spec-first authority model 不一致；新增依赖会带来供应链、版本与支持成本。
Boundary
provider output 只能是 provider_untrusted advisory facts；不复制其 92 条规则、不设为默认硬依赖、不让 linter 做语义裁决。
Rejection Summary

被合并、暂缓或否决的方向

对抗性结论：不建设自动遥测/徽章平台、用户解锁状态机、统一 evidence graph、新 assurance Agent、全宿主全 workflow 矩阵或自研通用 eval runtime。它们要么把代理指标冒充 outcome，要么重复宿主/外部工具，要么在 consumer 未成立前扩大 contract。
