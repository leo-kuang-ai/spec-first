# 需求文档与技术方案：行业模板对照

核对日期：2026-11-20。直接使用：[产品需求文档模板](prd.md) · [技术方案评审模板](design.md)。两份均为针对中文研发评审整理的试用稿，不是任何公司的原版翻译，也不是 spec-first 的新执行格式。

**结论：两份文档分别服务两次决定。** 需求评审决定「谁的问题值得解决、产品承诺什么结果、怎样算做对」；技术评审决定「哪种改法值得选、谁受影响、怎样证明它能工作并安全上线」。产品要说清“失败时不能发通知”，不必指定查询哪张表；技术要说明“在哪一步阻止发送，为什么选这里，怎么观察确实没发”，不能只复述需求。

## 两份实际提案比空模板多教了什么

- **需求：把痛点写成工作现场。** GitLab #407082 不是只说「支持自定义快捷操作」。提议人说明客服在处理同类请求时，需要在已有 issue 中反复填写相似的风险表；创建 issue 时的模板不能解决后续评论的重复输入。这样的现状足以让人比较替代办法。但该提议的成功衡量栏只有模板提示，没有填写结果。因此可以采纳它的场景写法，不能把它当成完整验收样板。
- **技术：把“保持兼容”写成可观察的旧行为。** TiDB 提案解释为何不复用看似相近的旧表，以及为什么初次引入细粒度权限时仍接受原有 `SUPER` 授权：升级不应使原先能执行的操作突然失败。读者可以据此写出新授权与旧授权两条验例。这里学习的是决定和理由，不是照搬数据库结构。

## 如何选择篇幅

| 情形 | PRD 怎样裁剪 | 技术方案怎样裁剪 |
|---|---|---|
| 单点变化、旧行为清楚 | 用一页写用户场景、前后差异、不变项和验例；可复述的已定事实不单列背景。 | 现状与改法、影响、验法即可；没有技术决策时不另造设计稿。 |
| 普通跨职能功能 | 使用[需求模板](prd.md)，写一条完整用户路径，并覆盖会改变结果的分支。 | 使用[设计模板](design.md)，用一次请求讲总体设计，详细设计只展开变化处。 |
| 跨端、权限、支付、数据迁移或难以撤回 | 补角色、状态、旧版本可见结果及业务侧不可接受的后果。 | 对实际风险补契约样例、版本组合、容量或隐私分析、停止条件与恢复验证；不可逆步骤单列。 |

## 对 spec-first 的建议

1. **PRD：先改读者看到的顺序，不再扩字段。** [当前通用骨架](../../../skills/spec-prd/assets/templates/00-generic.md)已有变更差异、范围、验收，问题背景和成功指标则属于条件章节。普通人读稿可先讲「谁现在遇到什么，做成有什么不同」，详细元数据后置。没有可信基线时直说，不把量化目标变成强制填空。[现有机器字段与交接要求](../../../skills/spec-prd/references/prd-output-template.md)仍有独立用途，不因调整人读稿而删改。
2. **技术方案：保留正在试点的七章，不发明第八套目录。** [现有评审模板](../../../skills/spec-plan/references/technical-design-review.md)已经覆盖现状、选型、详细设计、兼容、验收、上线。优先改善章内内容：选型给出放弃方案的理由；详细设计写清一次真实流程；验收把不同失败原因分开；上线区分可停止、可恢复和不可撤回。评审草稿不等于执行计划。
3. **先验证结构，再验证内容。** 用[现有同正文试读材料](../../plans/2026-11-03-skill-optimization-initiative/reviews/runs/2026-11-19-phase-one/design-layout/README.md)让未参与编写的研发和测试分别定位改动、漏验和上线缺口，不向受试者展示答案。本研究提出的新验例不要提前塞进对照稿，否则无法区分是目录还是新增信息带来的改善。公开模板只能支持试用方向，不能证明真实读者已经更容易理解。

## 放回日常研发：差距在哪里，先改什么

**当前处于优化方案与试点验证阶段。** 反馈指向技术方案的目录结构；它不是对所有 Skill 的可读性裁决。从全程使用看，最影响采纳的是：第一次来的人需要知道内部约定，才能拿到适合这次会议的文档；而已经开始执行的人又确实依赖这些约定。应让用户按用途拿到产物，同一个产品决定或技术决定只在权威来源维护一次。

| 使用时刻 | 现有能力与差距 | 推荐的最小变化 |
|---|---|---|
| 第一次进项目：「我要写需求／给团队评方案」 | [中文入口说明](../../../README.zh-CN.md)主要按需求是否明确引向规划或实施；[产物目录](../../user-guide/10-产物目录.md)把 `spec-plan` 介绍为实施计划的生产者。[实际入口](../../../skills/spec-plan/SKILL.md)已经另有 Markdown 技术评审稿，但要求用途明确。能力存在，常用入口没有同样清楚地介绍它。 | 在快速开始和产物目录展示三句真实请求、所得文档及可否实施：「结合现有系统澄清需求」「写给客户端和服务端评审的技术方案，先不实施」「按已定方案拆解或执行」。不要求用户记 Skill 名、格式词或新增开关。只说“出个方案”时先利用上下文；只有评审与执行的区别会改变交付且无法推断时才问一句。 |
| 产品和研发对齐：「相比现在，用户究竟会看到什么变化？」 | [通用 PRD 骨架](../../../skills/spec-prd/assets/templates/00-generic.md)已有摘要、差异、范围和验收；[输出合同](../../../skills/spec-prd/references/prd-output-template.md)已有轻重分档，也允许给核心章节使用有稳定标记的中文标题。真正的缺口不是少一个“成功指标”字段。[Skill](../../../skills/spec-prd/SKILL.md)可以为已有产品起草增量需求；不代表研发能替产品方批准目标。 | 优先在人能读到的现有摘要中写「谁、现状、这次变化、请决定什么」，紧接一条前后行为例。用现有章节标记试用中文标题，保留需求与验例对应关系；业务效果有来源才写数字。已有事实不再询问，旧系统的实现细节不冒充产品承诺。产品定位未定仍先探索；小修不升级成长 PRD。 |
| 技术评审：「设计是否值得选？出错会怎样？」 | [评审稿](../../../skills/spec-plan/references/technical-design-review.md)已有七章；[正式计划](../../../skills/spec-plan/references/plan-sections.md)也早有面向读者的首段。再加摘要不能解决“去哪里找兼容和测试”。通知样稿还有独立的内容缺口：写了读取失败时不发送，但测试只验证成功读到禁用。 | 纯评审先在现有七章稿中试用。用一条请求穿过各端、一个真正的备选、一个能发现错误的反例；按风险补灰度和恢复。目录同正文盲读与补漏验分两次。若两组都找不到原文未写的东西，应修正文，不能把错归为阅读能力。 |
| 评审后：「就按这个做」 | [拆任务](../../../skills/spec-write-tasks/SKILL.md)和[实施入口](../../../skills/spec-work/references/work-intake.md)按具体章节找范围、实施单元和验证；[代码评审](../../../skills/spec-code-review/references/intent-and-plan.md)再按就绪度和单元核对完整性。草稿、正式计划、已验证结果用途不同。 | 已有正式计划时，先核对评审决定是否已回写：产品变更回需求负责人，技术选型回计划作者；再用当前正式计划交接。只有评审稿时不把草稿改名送去执行。既要评审又要实施时，保留一份权威执行计划，先试用指向原文的读者导航，不默认生成第二份需手工同步的技术方案。 |

**为什么不能两种文档一起换标题？** PRD 校验器[识别章节标记](../../../skills/spec-prd/scripts/check-prd-artifact.js)，可以把机器标识留在中文标题之前。正式计划不同：[Markdown 渲染规则](../../../skills/spec-plan/references/markdown-rendering.md)要求精确标题，[HTML 渲染规则](../../../skills/spec-plan/references/html-rendering.md)也同时要求稳定锚点和可见标题，不是套一层网页就能解耦。此次定向复跑了[中文 PRD 摘要标题](../../../tests/unit/spec-prd-exit-safety.test.js)与[替换正式计划标题后拒绝交接](../../../tests/unit/spec-plan-handoff-judge.test.js)两个用例，均符合预期。前者不代表所有 PRD 机器章节可任意改名；后者是交接判分器的行为，不代表每个宿主都已在运行时拦截。

**推进顺序与退出条件：**

1. **先补可发现性，不动执行协议。** 先用上述三句自然请求检查选到的产物；同时把“已有产品的增量需求可起草、未定业务由产品裁决”在入口与指南讲一致。通过标准是拿到对应产物、知道下一步找谁，且“只评审”不启动实施。源规则写明不等于新宿主实际选对，二者分别记录。
2. **再测两种真实工作。** 纯评审用现有同正文对照；评审后要实施另选一个实际增量需求，追一条业务规则从需求、选型、验收一直到下游任务或直接实施。记录首次错找、错误放行、向作者追问和改写次数，并保留具体原句。尤其检查读者能否区分“设计预期”“已有验例”“实际验证通过”；不以偏好投票、耗时更短或章节数作为成功。
3. **最后才决定是否变更默认。** 如果改入口已经够用，就停在评审试点。如果读者确实受益且正式计划仍反复造成误读，才评估将章节身份与可见标题解耦。先让下游能同时读旧格式和候选格式，再改生产者；分别验证 Markdown 和 HTML、需求稿拒绝执行、上游产品原文保留、旧任务包仍指向原版本、缺验例不能空成功。任何一项失败就保留原默认，不重写历史计划，也不直接改宿主镜像。这些是建议的放行条件，本次没有实施迁移或采集读者结果。
