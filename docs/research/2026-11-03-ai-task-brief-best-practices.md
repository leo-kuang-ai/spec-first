# 如何向 AI 交代任务并获得高质量结果

日期：2026-11-03。类型：advisory。用途：个人与团队的任务委托参考。

证据状态：本次会话已读取 Anthropic、Claude Code 和 Microsoft 官方资料；OpenAI、Google 部分页面访问失败，未成功核验。本报告不代表截至该日期的全行业资料完整覆盖。下述六项框架为综合建议，未进行模型对照实验，不能据此宣称已提高成功率或降低成本。访问日期不等于来源发布日期。

## 1. 核心结论

把任务交代成一份简明的工作说明：明确目标、必要背景、交付物、验收标准和授权边界，让 AI 在真实反馈中自主完成。复杂任务还需要合适的工具、阶段检查和可恢复的进度记录。

优先固定结果和边界，允许 AI 根据证据选择方法；业务上必须遵循的顺序应明确写出。简单任务使用短说明，复杂或高影响任务再增加过程约束。

本报告适用于研究、写作、设计、编程及工具操作任务。它不规定统一的模型、宿主、Agent 数量或固定执行步骤，也不修改 spec-first 的既有 workflow、contract 或 generated runtime。

## 2. 官方实践与适用边界

| 实践 | 来源依据 | 应用方式与限制 |
|---|---|---|
| 提供最小充分上下文 | [1]“The anatomy of effective context”指出 minimal 不一定等于 short；信息仍需充分，并应根据失败补充说明和示例 | 先给关键事实、权威来源与必要示例，其他资料按需读取；不能为缩短提示词删除关键约束 |
| 补充 AI 无法自行发现的信息 | [2]“Tell Claude what it can’t see”强调仓库外决策、隐含流程及具体偏好 | 提供业务背景、历史取舍和成功定义；模型能可靠查到的事实可交给它查证 |
| 提供可执行的检查 | [2]“Give Claude a check to run”列出测试、构建、检查脚本和截图等反馈 | 将验收标准连接到实际证据；单个检查只证明其覆盖范围 |
| 固定业务流程明确步骤 | [3]“Build step-by-step workflows with transitions”要求每步包含目标、动作与转换条件；“Use strict structure”将编号保留给真正有顺序的流程 | 必要业务顺序应明确；不能据此要求所有探索任务走同一固定路径 |
| 检查最终结果 | [4]“The structure of an evaluation”区分 transcript 与 outcome，以订票声明和数据库订单为例 | 检查实际产物或系统状态，不能仅凭 AI 声称完成来验收 |
| 长任务保留可恢复状态 | [5]“Incremental progress”“Testing”记录增量执行、进度文件和端到端验证经验 | 跨会话任务保存完成项、证据和下一步；该案例针对 Web 开发，不能直接外推所有领域收益 |
| 随模型升级复核旧流程 | [6]开篇记录旧模型所需的上下文重置在后续模型上成为额外负担 | 定期检查旧补丁是否仍有价值；依据当前任务表现决定保留或删除 |

上述材料主要属于厂商指南和工程经验，不能当作跨厂商、跨任务的独立效果证明。尤其需要区分两类场景：开放问题更依赖目标、背景和反馈；固定业务流程更依赖明确的动作顺序与转换条件。

## 3. 交代任务的六项框架

| 要素 | 需要回答的问题 | 示例 |
|---|---|---|
| 目标与用途 | 解决什么问题？谁使用结果？支持什么行动？ | 帮助研发负责人决定下季度优先改进的三个环节 |
| 背景与依据 | 已知事实、关键材料、术语和已有决定是什么？来源冲突以什么为准？ | 以附件部门数据为准，行业数据仅用于比较 |
| 交付物 | 最终需要什么产物、格式和完成程度？ | 可直接汇报的分析报告，附原始数据引用 |
| 验收标准 | 怎样判断做对、做全、做得好？ | 每项建议包含证据、成本、风险及试点指标 |
| 边界与资源 | 可以自主做什么？哪些动作另需确认？有哪些时间、预算和工具限制？ | 可查公开资料；外发、付费和修改生产配置前确认 |
| 协作与收尾 | 何时提问与汇报？阻塞怎样处理？如何证明完成？ | 只问影响结果的关键问题，交付时列出验证依据与未完成项 |

小任务通常只需“做什么＋依据什么＋怎样算完成”。六项是检查遗漏的参考，不要求每次填满表格。

最值得细化的是验收标准。“专业、深入、高质量、全面”表达期待，但不足以让 AI 判断何时完成。

| 模糊要求 | 可用于验收的要求 |
|---|---|
| 深入调研 | 核验关键原始来源；覆盖主要方案、反例和适用条件；标明证据缺口 |
| 修好问题 | 原始复现通过；相关正常路径无回归；提供实际运行的验证结果 |
| 做一份好 PPT | 每页支持一个明确论点；数据可追溯；最终导出后检查文字、布局和图表 |
| 给出可落地建议 | 说明适用前提、负责人、投入、第一步和成功判据 |

## 4. 可复制的任务说明模板

```text
请完成【任务】。

目标与用途：
结果将用于【使用者/场景/决定】。
最重要的结果是【目标】；发生取舍时，优先【质量/速度/成本等】。

背景与依据：
已知情况是【关键事实】。
请参考【文件、链接、数据、示例】。
其中【来源】具有最高优先级；其他必要资料可自行查找。

交付物：
最终交付【具体产物、格式、完成程度】。

验收标准：
1. 【正确性要求】
2. 【完整性要求】
3. 【可用性要求】
请用【测试、原始来源、计算核对、实际操作等】验证。

边界与资源：
可以自主完成【授权范围】。
涉及【需要另行确认的动作】时先确认。
资源限制为【适用时填写时间、预算或工具限制】。

执行与收尾：
方法由你判断。先解决会影响结果的关键不确定性。
能从现有材料或工具获得的信息自行查证；
只有无法可靠推断、且会明显影响结果的问题才问我。
发现错误后修正并重新验证。
遇到阻塞时，完成其余可推进部分，并说明缺什么。
最终交付成果、验证依据、重要假设和未完成项。
```

模板的作用取决于填入的信息。“顶级专家”等角色描述可以表达视角，但不能代替领域材料、合格示例和具体判据。

## 5. 执行与验收闭环

推荐的轻量循环：明确结果 → 获取必要信息 → 执行 → 对照标准检查 → 修正 → 带证据交付。

- 事实与研究任务：检查引用是否支持相邻结论、来源是否过期、是否遗漏重要反证。
- 代码与操作任务：检查实际运行结果、系统最终状态和相关回归。
- 设计与写作任务：提供合格示例与评价维度，检查最终呈现；重要产物保留人工判断。
- 跨会话长任务：保存目标、已完成项、证据、当前问题和下一步，恢复时核对状态。

工具负责准备和核验可机械判定的事实；AI 负责解释证据、选择方法、判断语义是否满足要求。高影响取舍由对应负责人裁决。测试通过、自检通过和人工满意分别支持不同范围的结论。

必须保证的权限限制应由运行环境执行。[2]明确区分提示词、项目说明、Skill 等模型自行遵循的指令，与权限、沙箱、脚本等宿主执行机制。配置本身也应核验，不能仅凭写入规则就声称已被强制。

## 6. 常见误区与团队采用建议

| 误区 | 建议 |
|---|---|
| 一次塞入所有资料 | 提供权威入口与关键事实，其他资料按需读取 |
| 为所有任务规定同一套步骤 | 只固定真实业务顺序，探索过程允许调整 |
| 只要求反思或检查三遍 | 自检作为补充，关键结论提供外部依据 |
| 无限优化到最好 | 提前定义足够好的标准、资源预算和停止条件 |
| 长期保留旧模型补丁 | 根据当前表现复核，保留有证据支持的约束 |

团队采用时，从真实任务中选择代表性案例，对比原任务说明与本框架，记录结果正确性、遗漏、返工、人工介入、耗时和成本。比较应尽量保持任务、模型、工具及环境一致；输出有随机性时重复观察，不从一次成功推出普遍收益。

本报告建议先作为任务说明参考使用；经过代表性任务验证后，再决定是否纳入团队规范。模型、宿主、任务类型或工具条件明显变化时，应重新检查适用性。
