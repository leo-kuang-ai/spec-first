# Skill 优化方案 v3：代码质量与需求交付导向

日期：2026-11-03。类型：advisory + execution。状态：Phase 0 可立即启动。

本文件基于**「高质量完成需求交付，产出高质量、可维护的代码」**这一明确目标，重构优化方案。

---

## 最终目标拆解

### 终态目标

**高质量完成需求交付，产出高质量、可维护的代码。**

### 目标拆解

```
需求 → 设计 → 代码 → 验证 → 交付
  ↓      ↓      ↓      ↓      ↓
明确   正确   高质量  充分   完整
完整   可行   可维护  可信   可用
```

| 阶段 | 质量标准 | 对应 Skill | 失败模式 |
|---|---|---|---|
| **需求理解** | 明确、完整、无二义性 | spec-brainstorm, spec-prd | 需求理解偏差、漏需求 |
| **方案设计** | 正确、可行、可演化 | spec-plan | 架构错误、技术选型不当 |
| **代码实现** | 高质量、可维护、符合规范 | spec-work | 代码质量低、边界遗漏 |
| **代码审查** | 正确性、可维护性、安全性 | spec-code-review | 审查遗漏、标准不一致 |
| **问题修复** | 根因定位、彻底修复 | spec-debug | 治标不治本、引入新问题 |
| **提交发布** | 安全、可追溯、可回滚 | spec-commit, spec-commit-push-pr | Git 操作错误、权限越界 |

### 成功标准

| 维度 | 指标 | 目标 | 度量方法 |
|---|---|---|---|
| **需求完整性** | 需求遗漏率 | ≤5% | 验收时发现的遗漏需求数 / 总需求数 |
| **代码正确性** | 功能缺陷率 | ≤2% | 测试/使用中发现的功能缺陷数 / 总功能点数 |
| **代码质量** | 可维护性评分 | ≥4/5 | 按可读性、模块化、注释、测试覆盖率综合评分 |
| **返工率** | 需要重做的任务比例 | ≤10% | 因质量问题需要重做的任务数 / 总任务数 |
| **交付及时性** | 按时交付率 | ≥90% | 按预期时间完成的任务数 / 总任务数 |

## 当前质量债盘点

### 从代码质量视角看 Skill 质量债

| Skill | 质量风险 | 影响 | 证据 |
|---|---|---|---|
| **spec-work** | 代码质量标准不一致、边界遗漏 | **直接影响代码质量** | 需要分析历史 work 产出 |
| **spec-code-review** | 审查标准不明确、遗漏关键问题 | **质量把关失效** | 需要分析历史 review 遗漏 |
| **spec-debug** | 治标不治本、根因定位不准 | **修复不彻底** | S00-S21 中有 debug 相关修复 |
| **spec-plan** | 设计遗漏、技术选型不当 | **下游全部受影响** | 需要分析历史 plan 返工 |
| **spec-prd** | 需求理解偏差、边界不清 | **需求遗漏** | 需要分析历史 prd 变更 |
| **spec-commit/push** | Git 操作错误、权限越界 | **代码库安全** | S04 已发现，S11/S12 待验证 |

### 从需求交付视角看流程缺口

```
需求输入 → spec-prd → spec-plan → spec-work → spec-code-review → spec-commit-push-pr → 交付
   ↓          ↓          ↓          ↓              ↓                    ↓              ↓
理解偏差？  遗漏边界？  设计错误？  质量低？      遗漏缺陷？          操作错误？      不可用？
```

**关键发现**：
- **需求到代码的转化质量**是核心
- **代码审查的有效性**是质量把关
- **Git 操作的安全性**是底线

## Phase 0：代码质量与需求交付现状调研

### 目标

**回答三个核心问题**：
1. 当前产出的代码质量如何？哪些 Skill 产出的代码质量最低？
2. 需求到交付的完整性如何？哪里最容易遗漏？
3. 返工的主要原因是什么？

### 步骤 0.1：代码质量回顾（6 小时）

**方法**：
1. 选择最近 10 个由 spec-work 产出的代码变更
2. 按可维护性评分（1-5 分）：
   - 可读性（命名、注释、结构）
   - 模块化（职责单一、耦合度）
   - 测试覆盖（是否有测试、测试充分性）
   - 错误处理（边界、异常、降级）
   - 文档（README、API 文档、变更说明）

**输出**：`docs/research/phase0-code-quality-review.md`

```yaml
code_quality_baseline:
  sample_size: 10
  average_score: "3.2 / 5"  # 示例
  breakdown:
    readability: 3.5
    modularity: 3.0
    test_coverage: 2.8
    error_handling: 3.2
    documentation: 3.3
  
  low_quality_cases:
    - task: "feature-user-auth"
      score: 2.1
      issues:
        - "缺少边界检查"
        - "测试覆盖率 <20%"
        - "魔法数字未提取为常量"
      skill: spec-work
    
    - task: "refactor-payment"
      score: 2.5
      issues:
        - "职责混杂，一个函数做了 3 件事"
        - "异常处理不完整"
      skill: spec-work
```

### 步骤 0.2：需求遗漏分析（4 小时）

**方法**：
1. 选择最近 10 个完整的需求 → 交付流程
2. 对比初始需求与最终交付，统计：
   - 遗漏的功能点
   - 后期补充的需求（说明初期理解不完整）
   - 边界条件的遗漏

**输出**：`docs/research/phase0-requirement-gap-analysis.md`

```yaml
requirement_completeness_baseline:
  sample_size: 10
  average_completeness: "92%"  # 示例
  
  gap_patterns:
    - pattern: "边界条件遗漏"
      frequency: 6 / 10
      example: "未考虑空输入、并发、大数据量"
      root_cause: "spec-plan 阶段未系统化考虑"
    
    - pattern: "非功能性需求遗漏"
      frequency: 4 / 10
      example: "性能要求、错误处理、日志"
      root_cause: "spec-prd 阶段未明确"
    
    - pattern: "用户体验细节遗漏"
      frequency: 3 / 10
      example: "加载状态、错误提示、成功反馈"
      root_cause: "spec-work 阶段未自查"
```

### 步骤 0.3：返工原因统计（4 小时）

**方法**：
1. 分析 spec-debug 的调用记录
2. 统计返工原因分类：
   - 功能缺陷（逻辑错误、边界遗漏）
   - 代码质量（可读性差、难维护）
   - 需求理解偏差
   - 技术选型不当
   - 测试不充分

## 核心优化方向（基于代码质量与需求交付）

### NEW-01：spec-work 代码质量提升（P0）

**问题**：代码质量不一致，边界检查、错误处理、测试覆盖经常遗漏。

**优化方向**：

1. **增加代码质量检查清单**
   ```markdown
   ## Code Quality Checklist (在 spec-work 完成前自查)
   
   ### 功能正确性
   - [ ] 核心功能符合需求
   - [ ] 边界条件已处理（空输入、极大值、并发）
   - [ ] 错误情况已处理（网络失败、权限不足、资源耗尽）
   
   ### 代码质量
   - [ ] 函数职责单一，长度 <50 行
   - [ ] 变量命名清晰，无魔法数字
   - [ ] 复杂逻辑有注释
   - [ ] 无重复代码（DRY 原则）
   
   ### 测试覆盖
   - [ ] 核心路径有单元测试
   - [ ] 边界条件有测试用例
   - [ ] 错误处理有测试
   
   ### 可维护性
   - [ ] 模块化，低耦合
   - [ ] 易于扩展
   - [ ] 有必要的文档
   ```

2. **增加代码质量自动检查**
   - 调用 linter、formatter
   - 检查测试覆盖率
   - 检查圈复杂度

3. **增加代码质量反馈循环**
   - spec-work 完成后自动触发 spec-code-review
   - review 发现的问题反馈到 spec-work
   - 建立代码质量知识库（常见问题 + 最佳实践）

**快速验证路径**：
1. Phase 0 确认代码质量评分基线（假设 3.2/5）
2. 为 spec-work 增加质量检查清单
3. 在 5 个新任务中使用新版 spec-work
4. 重新评分，目标 ≥4.0/5

**推广门**：
- 代码质量评分提升 ≥0.5 分
- 无功能性回归
- 开发时间增加 <20%（质量提升值得付出）

### NEW-02：spec-code-review 审查有效性提升（P0）

**问题**：审查遗漏率高，特别是边界条件、性能、安全问题。

**优化方向**：

1. **建立分层审查策略**
   ```yaml
   review_strategy:
     always_on:  # 所有变更必查
       - correctness  # 功能正确性
       - boundary     # 边界条件
       - error_handling  # 错误处理
     
     conditional:  # 按变更类型触发
       - security: "when: auth OR sensitive-data"
       - performance: "when: loop OR db-query OR file-io"
       - data_migration: "when: schema-change OR data-transform"
     
     opt_in:  # 需要显式请求
       - architecture  # 架构评审（大重构）
       - accessibility  # 无障碍（UI 变更）
   ```

2. **增加审查发现率度量**
   - 记录每次审查发现的问题
   - 追踪审查后仍遗漏的问题
   - 计算 recall = 发现问题数 / 实际问题数

3. **建立审查知识库**
   - 常见遗漏模式（空指针、并发、边界）
   - 最佳实践（命名、结构、模式）
   - 反例集合（真实的代码缺陷）

**快速验证路径**：
1. Phase 0 确认审查遗漏率基线（假设 40%）
2. 为 spec-code-review 增加分层策略
3. 在 5 个新任务中使用新版 spec-code-review
4. 追踪审查后遗漏，目标遗漏率 <20%

**推广门**：
- 审查遗漏率下降 ≥50%
- 审查时间增加 <30%
- 无误报率上升

### NEW-03：spec-plan 边界系统化（P1）

**问题**：设计阶段经常遗漏边界条件，导致实现时返工。

**优化方向**：

1. **增加边界条件系统化检查**
   ```markdown
   ## Boundary Conditions Checklist (在 spec-plan 设计阶段)
   
   ### 输入边界
   - [ ] 空输入（null、undefined、空字符串、空数组）
   - [ ] 极值（最大值、最小值、负数、零）
   - [ ] 非法输入（格式错误、类型错误、越界）
   
   ### 并发与竞态
   - [ ] 多用户同时操作
   - [ ] 网络延迟或失败
   - [ ] 资源竞争
   
   ### 规模与性能
   - [ ] 数据量大（1000+、10000+、100000+）
   - [ ] 高频调用
   - [ ] 资源限制（内存、磁盘、连接数）
   
   ### 错误与降级
   - [ ] 外部依赖失败（API、数据库、文件系统）
   - [ ] 权限不足
   - [ ] 部分失败的处理
   ```

2. **增加设计完整性验证**
   - 检查是否覆盖所有边界条件
   - 检查是否定义了错误处理策略
   - 检查是否考虑了性能影响

**快速验证路径**：
1. Phase 0 确认边界遗漏占返工比例（假设 44%）
2. 为 spec-plan 增加边界系统化检查
3. 在 5 个新任务中使用新版 spec-plan
4. 追踪实现阶段的边界遗漏，目标占比 <20%

**推广门**：
- 边界遗漏导致的返工率下降 ≥50%
- 设计阶段时间增加 <20%

### O11/O12：Git 操作安全（P0，保留原方案）

已在原方案中定义，不重复。

### O06：spec-debug 根因定位（P1）

**问题**：修复不彻底，同一问题反复出现。

**优化方向**：

1. **增加根因分析要求**
   - 不只修复症状，必须定位根因
   - 记录根因分析过程
   - 验证修复的彻底性

2. **建立问题知识库**
   - 记录已修复的问题及根因
   - 建立问题模式库
   - 新问题先查询知识库

**快速验证路径**：
1. Phase 0 统计同一问题重复修复比例
2. 为 spec-debug 增加根因分析要求
3. 追踪修复的彻底性
