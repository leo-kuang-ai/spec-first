## 1. 项目概述

这篇文章不是讲单一技巧，而是给出一套“决策操作系统”：把复杂世界拆成若干可复用的思考模型，用于看清因果、回归本质、判断边界、规避陷阱、理解长期效应和人性机制。

文章中的 16 个方法论可以分为四组：

1. **因果与系统类**：蝴蝶效应、复利效应、创造性破坏、公地悲剧。
2. **本质与概率类**：第一性原理、奥卡姆剃刀、概率思维、回归均值。
3. **边界与规律类**：能力圈、帕累托法则、边际效用递减、大数定律。
4. **长期与人性类**：二阶思维、社会认同、地图不是疆域、临界点效应。

核心公式可以概括为：

> 思维模型 → 更高质量的判断 → 更少被情绪、局部、短期和表象误导 → 更稳定的长期决策收益。

## 2. 架构分析：16 个模型构成的决策系统

这套模型的价值不在于背概念，而在于形成一套从问题识别到行动选择的完整链路：

```text
复杂现象
  ↓
系统视角：先判断是否存在连锁反应、长期积累、结构性替代、公共资源失衡
  ↓
本质拆解：再回到底层事实、简单解释、概率分布、均值回归
  ↓
边界校准：判断自己是否懂、关键变量是什么、投入是否过量、样本是否足够
  ↓
长期推演：看后续影响、人群行为、认知偏差、突破阈值
  ↓
行动决策：选择更稳、更长期、更可验证的方案
```

可以把它看作四层决策栈：

| 层级 | 解决的问题 | 对应模型 |
|---|---|---|
| 系统层 | 事情为什么会连锁变化？ | 蝴蝶效应、复利效应、创造性破坏、公地悲剧 |
| 本质层 | 这件事的底层逻辑是什么？ | 第一性原理、奥卡姆剃刀、概率思维、回归均值 |
| 边界层 | 我的判断可靠在哪里、不可靠在哪里？ | 能力圈、帕累托法则、边际效用递减、大数定律 |
| 长期层 | 下一步、再下一步会发生什么？ | 二阶思维、社会认同、地图不是疆域、临界点效应 |

## 4. 方法论分组详解

### Part 01：看清因果与系统

这一组方法论强调：不要只看眼前单点，要看系统结构、连锁反应和长期累积。

#### 1. 蝴蝶效应

**方法论定义**：在复杂系统中，一个很小的初始动作，可能通过链式反馈引发巨大结果。

**可操作原则**：

- 对小风险保持敏感，尤其是位于关键链路、关键节点、关键依赖上的小问题。
- 不要因为问题“现在看起来小”就忽略它，要判断它是否可能被系统放大。
- 在产品、工程、组织中，要关注“小 bug、小流程漏洞、小沟通误差”的外溢效应。

**决策提问**：

1. 这个小变化会影响哪些下游节点？
2. 如果被重复、放大或传播，会造成什么结果？
3. 哪些微小动作值得提前纠偏？

#### 2. 复利效应

**方法论定义**：微小但持续的增长，会随着时间积累产生指数级结果。

**可操作原则**：

- 优先选择可以长期累积的事情：知识、信用、产品资产、用户关系、自动化能力。
- 不迷信一次性爆发，而是建设可重复、可沉淀、可迭代的系统。
- 把“每天的小改进”当作长期战略，而不是鸡汤式自律。

**决策提问**：

1. 这件事能否持续积累，而不是做完即消失？
2. 它的收益是否会随时间叠加？
3. 我现在做的小动作，半年后会不会形成结构性优势？

#### 3. 创造性破坏

**方法论定义**：创新会破坏旧行业、旧流程、旧模式，同时催生更高效的新结构。

**可操作原则**：

- 不要只保护既有优势，要主动观察哪些新技术正在改变成本结构和效率结构。
- 评估创新时，不只看它是否“更酷”，而要看它是否真正降低成本、提升效率、改变分工。
- 对个人和组织而言，抗拒变化往往比变化本身更危险。

**决策提问**：

1. 哪些旧流程正在被新工具替代？
2. 我现在维护的是价值，还是惯性？
3. 新技术带来的效率跃迁是否足以重构原有模式？

#### 4. 公地悲剧

**方法论定义**：当资源是公共的，个体为了自身利益过度使用，最终导致资源枯竭或整体受损。

**可操作原则**：

- 对共享资源必须设计规则、边界、产权、配额或反馈机制。
- 团队协作中，“没人负责”的资源通常会被过度消耗或无人维护。
- 公共系统不能只依赖善意，需要机制约束。

**决策提问**：

1. 这里是否存在公共资源？
2. 个体最优是否会导致整体最差？
3. 是否需要明确责任人、规则、成本或激励？

### Part 02：回归本质与概率

这一组方法论强调：不要被表象、情绪、复杂叙事和极端个例误导。

#### 5. 第一性原理

**方法论定义**：把复杂问题拆解成最基本的事实，再从底层逻辑重新推导解决方案。

**可操作原则**：

- 拆掉惯例、经验、路径依赖，先确认不可再拆的事实。
- 对“大家都这么做”的做法保持怀疑。
- 用底层约束重新推导，而不是在旧方案上修补。

**决策提问**：

1. 这件事最基本的事实是什么？
2. 哪些只是行业惯例，不是必然规律？
3. 如果从零设计，我会怎么做？

#### 6. 奥卡姆剃刀

**方法论定义**：在多个解释都能解释现象时，假设最少、结构最简单的解释往往更可靠。

**可操作原则**：

- 排查问题时先看简单原因，再看复杂原因。
- 设计方案时减少不必要的机制、角色、流程和抽象层。
- 沟通时用最少概念表达清楚核心逻辑。

**决策提问**：

1. 有没有更简单的解释？
2. 这个方案是否引入了不必要的复杂度？
3. 我是不是为了显得高级而把问题复杂化了？

#### 7. 概率思维

**方法论定义**：现实充满不确定性，好的决策不是追求绝对正确，而是在概率意义上提高胜率。

**可操作原则**：

- 用概率分布替代非黑即白判断。
- 关注期望收益，而不是单次结果。
- 接受“好决策也可能有坏结果，坏决策也可能偶然成功”。

**决策提问**：

1. 各种结果的概率大概是多少？
2. 如果重复做 100 次，这个选择是否仍然占优？
3. 我是在追求确定性，还是在提升胜率？

#### 8. 回归均值

**方法论定义**：极端的好结果或坏结果之后，往往会逐渐回到正常水平。

**可操作原则**：

- 不要因一次超常发挥就高估能力，也不要因一次失误就低估系统。
- 分析数据时要区分真实趋势和短期波动。
- 对异常值保持谨慎，不急着归因。

**决策提问**：

1. 这是趋势，还是异常波动？
2. 有没有足够数据证明系统能力真的改变？
3. 我是否被最近一次结果影响过度？

### Part 03：判断边界与规律

这一组方法论强调：好判断不是无限自信，而是知道关键变量、投入边界和数据可靠性。

#### 9. 能力圈

**方法论定义**：清楚知道自己擅长什么、不擅长什么，只在理解范围内做高质量决策。

**可操作原则**：

- 对不懂的领域保持克制，不因为机会诱人就盲目下注。
- 能力圈不是固定不变的，可以学习扩大，但不能假装已经拥有。
- 真正重要的是知道边界在哪里。

**决策提问**：

1. 我真的理解这个领域的关键变量吗？
2. 我知道自己不知道什么吗？
3. 这是优势下注，还是认知冒险？

#### 10. 帕累托法则

**方法论定义**：大约 80% 的结果来自 20% 的关键原因。

**可操作原则**：

- 找到少数关键变量，把主要资源投向高杠杆事项。
- 避免平均用力，尤其是在时间、资源和注意力有限时。
- 用数据识别真正贡献结果的因素。

**决策提问**：

1. 哪 20% 的动作带来了 80% 的结果？
2. 哪些事情虽然忙，但贡献很低？
3. 如果只能做三件事，应该是哪三件？

#### 11. 边际效用递减

**方法论定义**：对同一事项持续增加投入，新增收益会逐渐下降，甚至转负。

**可操作原则**：

- 不要把“更多投入”误认为“更好结果”。
- 持续评估新增投入的边际回报。
- 当边际收益下降时，应考虑转向其他高回报事项。

**决策提问**：

1. 继续投入一单位资源，会新增多少收益？
2. 这件事是否已经过度优化？
3. 是否存在更值得投入的方向？

#### 12. 大数定律

**方法论定义**：样本量越大，统计结果越稳定，越能反映真实趋势。

**可操作原则**：

- 不被单个案例、单次反馈、个别成功或失败误导。
- 判断趋势时使用足够大的样本。
- 对小样本结论保持保留态度。

**决策提问**：

1. 我的样本量足够吗？
2. 这个案例是典型样本，还是幸存者偏差？
3. 数据是否稳定到可以支持决策？

### Part 04：思考长期与人性

这一组方法论强调：决策不能只看眼前，还要看人的行为、认知偏差、长期反馈和突破阈值。

#### 13. 二阶思维

**方法论定义**：不只看直接结果，还要继续推演后续结果、连锁反应和长期影响。

**可操作原则**：

- 决策前多问一句：“然后呢？”
- 警惕短期收益带来的长期副作用。
- 好策略通常不是一阶最爽，而是二阶、三阶仍然稳健。

**决策提问**：

1. 这个决定的直接结果是什么？
2. 直接结果之后会引发什么反应？
3. 长期看，这会改变什么激励和行为？

#### 14. 社会认同

**方法论定义**：人们会参考他人的行为、评价和选择来指导自己的选择。

**可操作原则**：

- 产品和品牌需要真实案例、客户评价、口碑推荐来建立信任。
- 在不确定场景下，用户更依赖群体信号。
- 社会认同要建立在真实价值上，不能伪造。

**决策提问**：

1. 用户是否缺少信任信号？
2. 有没有真实案例可以降低新用户决策成本？
3. 现有用户行为能否成为增长资产？

#### 15. 地图不是疆域

**方法论定义**：我们对世界的认知、计划、模型、商业计划书，并不等于真实世界本身。

**可操作原则**：

- 所有模型都只是现实的简化，不要把模型当现实。
- 执行中要持续校准计划与现实的偏差。
- 保持开放和灵活，允许事实推翻原计划。

**决策提问**：

1. 我的认知地图和现实之间有什么偏差？
2. 哪些事实正在挑战原计划？
3. 我是否因为沉没成本而坚持错误地图？

#### 16. 临界点效应

**方法论定义**：当系统积累达到某个关键阈值时，会出现质的飞跃。

**可操作原则**：

- 不要因为早期看不到效果就轻易放弃长期积累型事项。
- 识别关键阈值：用户规模、能力密度、数据量、品牌信任、技术成熟度。
- 在突破前的平台期，需要判断是方向错误，还是尚未达到临界点。

**决策提问**：

1. 这个系统的关键阈值是什么？
2. 当前距离临界点还有多远？
3. 我是在合理坚持，还是无效消耗？

## 5. 关键差异：这些模型各自解决什么问题

这些方法论容易混用，但它们的关注点不同：

| 容易混淆的模型 | 区别 |
|---|---|
| 蝴蝶效应 vs 二阶思维 | 蝴蝶效应强调小变量在复杂系统中的放大；二阶思维强调主动推演后续影响。 |
| 复利效应 vs 临界点效应 | 复利强调连续积累的指数增长；临界点强调达到阈值后的质变。 |
| 第一性原理 vs 奥卡姆剃刀 | 第一性原理用于从底层事实重建方案；奥卡姆剃刀用于在多个解释中选择更简单者。 |
| 概率思维 vs 大数定律 | 概率思维用于不确定决策；大数定律用于判断样本是否足以支撑结论。 |
| 回归均值 vs 边际效用递减 | 回归均值解释极端结果后的正常化；边际效用递减解释持续投入后的新增收益下降。 |
| 能力圈 vs 地图不是疆域 | 能力圈关注自身理解边界；地图不是疆域关注认知模型与现实之间的偏差。 |
| 帕累托法则 vs 边际效用递减 | 帕累托法则帮助找到高杠杆关键少数；边际效用递减帮助判断某方向是否继续加码。 |
| 社会认同 vs 公地悲剧 | 社会认同利用群体行为形成信任；公地悲剧警惕个体行为汇聚后损害公共系统。 |

---

## 6. 知识链收束：如何组合使用

单个模型只是工具，真正有效的是组合成决策流程。

### 6.1 面对复杂问题时

```text
第一性原理：拆到底层事实
→ 奥卡姆剃刀：避免过度复杂化
→ 概率思维：评估不同方案胜率
→ 二阶思维：推演长期后果
→ 地图不是疆域：执行中持续校准现实
```

适用于：战略规划、产品定位、技术架构选择、重大职业决策。

### 6.2 面对增长问题时

```text
帕累托法则：找出关键增长变量
→ 复利效应：建设可长期积累的能力
→ 临界点效应：识别突破阈值
→ 社会认同：把用户信任转化为增长资产
```

适用于：产品增长、内容运营、品牌建设、社区发展。

### 6.3 面对风险问题时

```text
蝴蝶效应：识别小问题的放大路径
→ 公地悲剧：判断是否存在公共资源失控
→ 大数定律：避免被个例误导
→ 回归均值：避免被异常值带偏
→ 二阶思维：评估后续连锁反应
```

适用于：工程稳定性、组织治理、质量管理、投资风控。

### 6.4 面对资源配置问题时

```text
能力圈：确认是否在理解范围内
→ 帕累托法则：找到最关键少数
→ 边际效用递减：判断继续投入是否划算
→ 概率思维：比较不同选择的期望收益
```

适用于：时间管理、预算分配、团队投入、学习计划。

## 7. 分级建议：如何落地使用

### A. 个人决策

建议形成一个 5 问清单：

1. **第一性原理**：这件事最底层的事实是什么？
2. **能力圈**：我真的懂这个问题吗？
3. **概率思维**：不同结果的概率和收益分别是什么？
4. **二阶思维**：这个选择之后会发生什么？
5. **地图不是疆域**：我有哪些假设需要被现实验证？

### B. 产品与业务

建议形成一个增长判断清单：

1. 哪 20% 的用户、渠道或功能贡献最大结果？
2. 哪些能力可以产生复利？
3. 是否已经接近临界点，还是还处在积累期？
4. 有没有真实社会认同可以提升转化？
5. 当前策略是否只是地图，是否被真实数据验证？

### C. 团队与组织

建议形成一个治理清单：

1. 哪些小问题可能被系统放大？
2. 是否存在公共资源被过度消耗？
3. 规则、责任、产权是否清楚？
4. 继续加投入是否已经边际收益递减？
5. 当前组织行为的二阶后果是什么？

### D. AI Coding / Spec-first 场景的迁移

结合当前 spec-first / AI Coding Harness 调研，这 16 个模型可以迁移为工程治理方法：

| 思维模型 | 对 AI Coding / Spec-first 的启发 | 主要作用 skill 节点 | 节点说明 |
|---|---|---|---|
| 蝴蝶效应 | 小的 spec 歧义、agent 指令漏洞、测试缺口会在多代理协作中被放大。 | `using-spec-first`、`spec-prd`、`spec-plan`、`spec-code-review`、`retired-skill-review` | 在入口路由、需求澄清、计划拆解、代码审查和 skill 审计中提前识别小偏差的下游放大路径。 |
| 复利效应 | 可沉淀的规范、技能、测试、复盘会形成 compound learning。 | `spec-compound`、`spec-compound-refresh`、`spec-team-standards-governance`、`spec-sessions` | 把一次问题解决沉淀为可复用知识、团队标准和可追溯历史，形成下一次工作的上下文资产。 |
| 创造性破坏 | AI coding harness 正在替代传统手写流程中的部分低效环节。 | `spec-ideate`、`spec-optimize`、`spec-write-skill`、`spec-mcp-setup` | 用 ideation 发现新机制，用优化实验验证效率跃迁，用 source skill 和 runtime setup 替代一次性 prompt 习惯。 |
| 公地悲剧 | 共享上下文、共享 memory、共享 agent 池需要清晰治理，否则会污染。 | `using-spec-first`、`spec-mcp-setup`、`spec-team-standards-governance`、`retired-skill-review` | 约束共享 runtime、skills、standards 和上下文入口，避免多人/多 agent 共用资源时出现多真相源和无人维护。 |
| 第一性原理 | 设计规范框架时应回到“行为契约、验证、状态真相源”这些底层事实。 | `spec-prd`、`spec-plan`、`spec-write-skill`、`spec-team-standards-governance` | 把问题拆回 WHAT/WHY、HOW、skill contract、standards source-of-truth，再从底层约束推导方案。 |
| 奥卡姆剃刀 | Harness 不应堆砌命令和 agent，而应保持核心工作流简单可验证。 | `using-spec-first`、`spec-plan`、`spec-write-tasks`、`spec-write-skill`、`retired-skill-review` | 用最少入口、最少派生任务和最轻 contract 覆盖真实需求，避免新增无必要 workflow、agent 或 schema。 |
| 概率思维 | AI 输出不是确定性结果，需要用评测、置信度、回滚机制管理概率风险。 | `spec-code-review`、`spec-doc-review`、`spec-debug`、`spec-optimize` | 在 review finding、debug 假设和优化实验中区分置信度、证据等级与期望收益，而不是把单次输出当确定事实。 |
| 回归均值 | 单次 demo 成功不能代表系统稳定能力，需要多轮样本验证。 | `spec-optimize`、`spec-code-review`、`spec-debug`、`spec-release-notes` | 对异常成功或失败保持克制，用重复样本、测试证据和版本记录判断能力是否真的改变。 |
| 能力圈 | Agent 应有明确职责边界，不应让通用 agent 处理所有任务。 | `using-spec-first`、`spec-write-skill`、`retired-skill-review`、`spec-doc-review`、`spec-code-review` | 明确 workflow、skill、reviewer、script 和 LLM 的职责边界，避免 helper 入口外露或跨域误判。 |
| 帕累托法则 | 少数关键规范、测试和工作流可能贡献大部分质量提升。 | `spec-plan`、`spec-work`、`spec-code-review`、`spec-team-standards-governance` | 让计划、执行、审查和团队标准聚焦高杠杆风险点，而不是平均扫描所有可能性。 |
| 边际效用递减 | 继续增加 agent 数量或文档长度不一定提升系统能力，可能增加协调成本。 | `spec-plan`、`spec-write-tasks`、`retired-skill-review`、`spec-optimize` | 判断继续加任务、persona、文档或实验是否还有新增收益，防止治理成本超过质量收益。 |
| 大数定律 | 需要基于大量任务样本评估 harness，而不是凭少数案例判断。 | `spec-optimize`、`spec-code-review`、`spec-compound-refresh`、`spec-sessions` | 通过多样本实验、review 历史、session 回放和 stale learning 刷新来判断趋势，避免个例代表整体。 |
| 二阶思维 | 新增规则、自动化、权限机制要评估对开发者行为和 agent 行为的后续影响。 | `spec-prd`、`spec-plan`、`spec-work`、`spec-mcp-setup`、`spec-team-standards-governance` | 在需求、计划、执行、runtime setup 和 standards governance 中推演规则落地后的行为变化、维护成本和下游消费者影响。 |
| 社会认同 | 开源项目的案例、star、真实使用反馈会影响采用决策。 | `spec-release-notes`、`spec-compound`、`spec-slack-research`、`spec-ideate` | 用真实 release、案例、组织讨论和用户反馈增强采纳可信度；只记录可验证信号，不制造虚假背书。 |
| 地图不是疆域 | spec 文档不等于真实系统行为，需要 living contract / runtime validation 校准。 | `spec-prd`、`spec-plan`、`spec-work`、`spec-app-consistency-audit`、`spec-doc-review` | 把 PRD、plan、task、review 视为地图，通过源码、测试、设计稿和 runtime evidence 校准真实系统状态。 |
| 临界点效应 | 规范、工具、agent、测试、memory 累积到一定程度后，可能形成质变的工程效率。 | `spec-mcp-setup`、`spec-optimize`、`spec-compound`、`spec-team-standards-governance` | 识别 readiness、实验指标、知识沉淀和 standards 覆盖度的关键阈值，判断何时从机制建设进入规模化收益。 |

## 8. 最终沉淀：一页纸方法论卡片

### 8.1 四类模型

- **看系统**：蝴蝶效应、复利效应、创造性破坏、公地悲剧。
- **看本质**：第一性原理、奥卡姆剃刀、概率思维、回归均值。
- **看边界**：能力圈、帕累托法则、边际效用递减、大数定律。
- **看长期**：二阶思维、社会认同、地图不是疆域、临界点效应。

### 8.2 一套通用决策流程

```text
1. 先问本质：这件事最底层的事实是什么？
2. 再看系统：哪些小变量会被放大？哪些长期积累会产生复利？
3. 校准边界：我是否真的懂？数据是否足够？关键少数是什么？
4. 评估投入：继续投入是否仍有边际收益？
5. 推演长期：一阶、二阶、三阶结果分别是什么？
6. 验证现实：我的地图是否符合真实疆域？
7. 坚持或转向：这是临界点前的平台期，还是方向错误？
```

### 8.3 最值得长期内化的三句话

1. **不要只看结果，要看系统。**
2. **不要只看当下，要看复利和二阶后果。**
3. **不要迷信认知地图，要持续用现实校准。**

## 9. 可集成的补充决策模型

在原有 16 个模型之外，业界还有一批更偏“操作流程、证据校验、优先级取舍和组织协作”的决策模型。结合 spec-first 的 AI Coding Harness 定位，建议按“核心集成 / 场景化集成 / 暂不进入核心”分层吸收，而不是一次性全部塞进主流程。

### 9.1 第一批：建议核心集成

这些模型与 spec-first 的 workflow routing、证据边界、计划质量、调试根因、审查置信度、优化实验和治理边界直接相关，适合进入核心决策系统。

| 模型 | 中文名 | 集成优先级 | 放入决策系统哪一层 | 主要作用 skill 节点 |
|---|---|---:|---|---|
| Cynefin Framework | 复杂性情境框架 | 高 | 系统/情境层 | `using-spec-first`、`spec-plan`、`spec-debug` |
| OODA Loop | 观察-判断-决策-行动循环 | 高 | 系统/执行层 | `spec-work`、`spec-debug`、`spec-optimize` |
| Theory of Constraints | 约束理论 / 瓶颈理论 | 高 | 系统/资源层 | `spec-plan`、`spec-work`、`spec-optimize` |
| MECE | 不重叠不遗漏原则 | 高 | 本质/拆解层 | `spec-prd`、`spec-plan`、`spec-write-tasks`、`spec-doc-review` |
| 5 Whys | 五问法 | 高 | 本质/根因层 | `spec-debug`、`spec-code-review`、`spec-compound` |
| Inversion | 逆向思维 | 高 | 风险/审查层 | `spec-plan`、`spec-code-review`、`spec-doc-review`、`retired-skill-review` |
| Base Rate Thinking | 基准率思维 | 高 | 证据/概率层 | `spec-code-review`、`spec-debug`、`spec-sessions` |
| Bayesian Updating | 贝叶斯更新 | 高 | 证据/概率层 | `spec-debug`、`spec-code-review`、`spec-optimize` |
| Pre-mortem | 事前验尸 / 预演失败 | 高 | 长期/风险层 | `spec-plan`、`spec-doc-review`、`spec-code-review` |
| Value of Information | 信息价值分析 | 高 | 资源/取舍层 | `spec-plan`、`spec-work`、`spec-debug` |
| Decision Quality Framework | 决策质量框架 | 高 | 决策出口层 | `spec-prd`、`spec-plan`、`spec-doc-review` |
| Goodhart's Law | 古德哈特定律 | 高 | 评估/治理层 | `spec-optimize`、`spec-code-review`、`spec-team-standards-governance` |

### 9.2 第二批：建议场景化集成

这些模型价值明确，但不适合成为所有 workflow 的默认判断层。更适合在产品探索、复杂根因、组织协作或平台战略场景中按需启用。

| 模型 | 中文名 | 适合场景 | 主要作用 skill 节点 |
|---|---|---|---|
| Jobs To Be Done | 待完成任务理论 | 产品需求、PRD、用户价值判断 | `spec-ideate`、`spec-brainstorm`、`spec-prd` |
| RICE Scoring | RICE 优先级评分法 | 多需求排序、路线图取舍 | `spec-ideate`、`spec-plan` |
| Analysis of Competing Hypotheses | 竞争假设分析 | 复杂 bug、复杂 review finding、根因不确定 | `spec-debug`、`spec-code-review` |
| Disconfirming Evidence | 反证思维 / 寻找反证 | 审查、调试、方案证伪 | `spec-code-review`、`spec-debug`、`spec-doc-review` |
| RAPID | RAPID 决策权责模型 | 多 owner、多团队协作、handoff 权责 | `spec-plan`、`spec-work`、`spec-team-standards-governance` |
| Wardley Mapping | 沃德利地图 / 战略态势地图 | 架构战略、平台能力演化 | `spec-ideate`、`spec-plan`、`spec-team-standards-governance` |

### 9.3 暂不建议进入核心层

这些模型本身有价值，但与 spec-first 的核心工程闭环契合度较低，适合放在附录、场景说明或外部产品/运营材料中，而不是默认进入 workflow 判断。

| 模型 | 中文名 | 暂不进入核心的原因 |
|---|---|---|
| Six Thinking Hats | 六顶思考帽 | 更像会议协作方法，适合 persona review 或团队讨论附录，不适合作为核心决策模型。 |
| Eisenhower Matrix | 艾森豪威尔矩阵 / 重要紧急矩阵 | 偏个人时间管理，对 spec-first 工程治理增益有限。 |
| North Star Metric | 北极星指标 | 对产品增长有用，但不应默认进入 AI Coding Harness 核心。 |
| AARRR / Pirate Metrics | AARRR 增长漏斗 / 海盗指标 | 属于增长运营模型，适合产品/市场分析，不适合 spec-first 核心 workflow。 |
| Scenario Planning | 情景规划 | 对战略规划有用，但粒度偏大，适合作为大型 roadmap 或不确定性分析的附加模型。 |

### 9.4 集成判断原则

是否把一个模型集成进 spec-first，不看它是否“有名”，而看它是否能增强以下任一节点：

1. **入口路由**：帮助判断应该进入哪个 workflow。
2. **需求澄清**：减少 planning 阶段替用户发明 WHAT。
3. **证据判断**：区分 confirmed evidence、advisory facts 和模型推测。
4. **计划质量**：让计划更可执行、更有边界、更能暴露风险。
5. **调试根因**：提升 causal chain 的完整性。
6. **审查置信度**：让 finding 更可证伪、更少靠直觉。
7. **优化实验**：让指标、样本、实验和收敛机制更可信。
8. **知识沉淀**：把一次经验转成可复用、可失效、可刷新知识。

因此，最适合优先并入 spec-first 的不是“更多模型”，而是能直接强化 `Codebase -> Spec -> Plan -> Tasks -> Code -> Review -> Knowledge` 链路的模型。
