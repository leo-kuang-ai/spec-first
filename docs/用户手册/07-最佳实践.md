# 最佳实践

本指南汇总了使用 Spec-First 的最佳实践,帮助你最大化效率和代码质量。

## 🎯 核心原则

### 1. 规划优先

**原则**: 永远不要在没有规划的情况下直接开始编码。

**实践**:
```bash
# ✅ 好的做法
/office-hours    # 先规划
# 然后实现

# ❌ 避免
# 直接开始写代码
```

**原因**: 规划阶段投入 1 小时,可以节省实现阶段的 10 小时。

---

### 2. 渐进式开发

**原则**: 小步快跑,频繁验证。

**实践**:
```bash
# ✅ 好的做法
/office-hours          # 规划核心功能
# 实现核心功能
/qa --quick            # 快速测试
/ship                  # 发布

# 然后迭代下一个功能

# ❌ 避免
# 一次性实现所有功能,最后才测试
```

**原因**: 小步迭代降低风险,问题更容易定位和修复。

---

### 3. 质量门禁

**原则**: 每个阶段都要有明确的质量标准。

**实践**:
```bash
# ✅ 好的做法
/plan-eng-review       # 设计必须通过审查
# 实现
/review                # 代码必须通过审查
/qa                    # 功能必须通过测试
/ship                  # 然后才能发布

# ❌ 避免
# 跳过审查和测试,直接发布
```

**原因**: 质量门禁防止问题累积,降低修复成本。

---

## 🚀 规划阶段最佳实践

### 1. 深度思考,不要表面

**实践**:
```bash
# ✅ 好的做法
/office-hours
# 让 Claude 充分提问
# 挑战你的前提
# 探索不同的方案

# ❌ 避免
# 急于进入实现
# 忽略 Claude 的挑战
```

**提示**: 当 Claude 说 "Let me push back on that" 时,停下来认真思考。

---

### 2. 写下所有决策

**实践**:
```markdown
# 设计文档

## 决策记录

### 为什么选择方案 A?
- 理由 1
- 理由 2

### 为什么不选方案 B?
- 问题 1
- 问题 2
```

**原因**: 未来你会忘记为什么做这个决定。

---

### 3. 识别依赖和风险

**实践**:
```bash
/plan-eng-review
# 重点关注:
# - 外部依赖
# - 性能风险
# - 安全风险
# - 边缘情况
```

---

## 💻 实现阶段最佳实践

### 1. 限制修改范围

**实践**:
```bash
# ✅ 好的做法
/freeze src/auth      # 限制只修改 auth 模块

# 实现功能

/unfreeze             # 完成后解除限制
```

**原因**: 防止意外修改其他模块,保持专注。

---

### 2. 频繁提交

**实践**:
```bash
# ✅ 好的做法
# 每完成一个小功能
git add -A
git commit -m "feat: add user login"

# ❌ 避免
# 一天结束后才提交一个巨大的 commit
```

**最佳**: 每个 commit 应该是一个独立的、可撤销的变更。

---

### 3. 写测试

**实践**:
```bash
# ✅ 好的做法
# 实现功能
# 立即写测试
bun test               # 确保测试通过

# ❌ 避免
# "先实现,有空再写测试" (永远不会写)
```

**原则**: 如果没有测试,代码就不算完成。

---

## 🔍 审查阶段最佳实践

### 1. 不要忽略审查结果

**实践**:
```bash
# ✅ 好的做法
/review
# 认真对待每个问题
# 修复或解释为什么可以接受

# ❌ 避免
/review
# 看到 "3 issues found" 就忽略
```

**提示**: 审查发现的问题,在生产环境会放大 10 倍。

---

### 2. 使用安全保护

**实践**:
```bash
# ✅ 好的做法
/guard                 # 在生产环境操作前

# 或至少
/careful               # 警告危险命令

# ❌ 避免
# 在没有保护的情况下运行 rm -rf 或 DROP TABLE
```

---

### 3. 寻求第二意见

**实践**:
```bash
# ✅ 好的做法
/review                # Claude 审查
/codex review          # Codex 独立审查

# 比较两个审查结果

# ❌ 避免
# 只依赖一个审查工具
```

---

## 🧪 测试阶段最佳实践

### 1. 完整测试,不要偷懒

**实践**:
```bash
# ✅ 好的做法
/qa --exhaustive       # 完整测试

# ❌ 避免
/qa --quick            # 只测关键功能
# "应该没问题吧"
```

**原因**: 边缘情况的 bug 最难发现,影响最大。

---

### 2. 真实环境测试

**实践**:
```bash
# ✅ 好的做法
/qa https://staging.your-app.com    # 在 staging 测试

# ❌ 避免
/qa http://localhost:3000           # 只在本地测试
```

**原因**: 本地环境和生产环境总会有差异。

---

### 3. 自动化回归测试

**实践**:
```bash
# ✅ 好的做法
/qa --regression .spec-first/qa-reports/baseline.json

# 每次发布前对比基线
```

---

## 🚀 发布阶段最佳实践

### 1. 小步发布

**实践**:
```bash
# ✅ 好的做法
/ship                  # 发布小功能
/land-and-deploy
/ship                  # 发布下一个小功能
/land-and-deploy

# ❌ 避免
# 累积 2 周的工作量一起发布
```

**原因**: 小步发布降低风险,问题更容易回滚。

---

### 2. 监控不要偷懒

**实践**:
```bash
# ✅ 好的做法
/land-and-deploy
/canary --duration 30m # 监控 30 分钟

# ❌ 避免
/land-and-deploy
# "应该没问题" 就不管了
```

**原因**: 很多问题只在生产环境出现。

---

### 3. 准备回滚计划

**实践**:
```bash
# ✅ 好的做法
/land-and-deploy
# 如果 /canary 发现问题:
# 1. 立即回滚
# 2. 修复问题
# 3. 重新发布

# ❌ 避免
# 没有回滚计划
# 问题发生后手忙脚乱
```

---

## 📊 效率提升技巧

### 1. 并行运行独立任务

```bash
# ✅ 好的做法
/review &
/benchmark &
wait

# ❌ 避免
/review
/benchmark
```

**节省时间**: 50%

---

### 2. 缓存和复用

```bash
# ✅ 好的做法
/benchmark --baseline  # 建立基线

# 后续对比
/benchmark             # 自动对比基线

# ❌ 避免
# 每次都从头开始测试
```

---

### 3. 自动化重复流程

```bash
# 创建发布脚本
cat > ~/bin/release.sh << 'EOF'
#!/bin/bash
set -e
/review && /qa && /ship && /land-and-deploy && /canary
EOF

chmod +x ~/bin/release.sh

# 使用
release.sh
```

## ⚠️ 常见陷阱

### 1. 过度规划

**问题**: 规划太久,不开始实现。

**解决**: 规划 1-2 小时后开始实现,边做边调整。

---

### 2. 跳过测试

**问题**: "时间紧,先发布,回头再测试"。

**解决**: **永远不要跳过测试**。测试节省的时间远多于它消耗的时间。

---

### 3. 忽略警告

**问题**: 审查发现 10 个问题,觉得 "应该没事"。

**解决**: 每个问题都要修复或明确记录为什么可以接受。

---

### 4. 一次改太多

**问题**: 一个 PR 改了 50 个文件。

**解决**: 拆分成多个小 PR,每个 PR 独立测试和审查。
