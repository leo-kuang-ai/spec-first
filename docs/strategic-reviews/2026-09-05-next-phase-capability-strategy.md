## 第一重审视：定义关键问题与领域

### 1.1 真正要解决什么

核心问题是：**在模型和宿主持续增强的条件下，spec-first 能否以足够低的使用成本，让团队更快交付可接受、可验证、可继续维护的变更？**

这个问题横跨产品战略、软件工程、Agent 系统设计、实验方法和组织工作方式。只看模型分数、Skill 数量或 CLI 功能，会漏掉人工澄清、审查、集成、恢复和后续维护成本。

当前角色契约已将使命明确为 `time-to-trusted-change` 与 `quality-adjusted throughput`，并要求项目长期拥有 intent、evidence、governance 和可失效 knowledge。[L1](./2026-09-05-harness-research-sources.md#对项目证据的回源)

建议用三个层次理解产品：

| 层次 | spec-first 应负责什么 | 对用户的意义 |
| --- | --- | --- |
| 产品定位 | 项目拥有的 AI 研发协作与可信交付层 | 同一需求经过不同会话、人员和宿主仍可接续、审查和验证 |
| 核心能力 | 清晰意图、项目约束、可执行验收、交付证据、经验复用 | 减少解释、漏项、假完成、返工与重复调查 |
| 技术载体 | CLI、Skill、contracts、adapters、脚本与项目文件 | 按需交付能力，保持 source/runtime 边界 |

### 1.2 用户使用中的关键时刻

建议首要用户是负责真实变更的研发人员，采纳决策者是技术负责人，结果消费者包括 reviewer、QA 和下一位接手者。个人重度开发者可作为试点参与者；多团队治理属于后续扩展。

优先验证三种高价值场景：

1. **跨模块修复**：定位共享根因，保护其他调用路径，用复现与回归证据交付。
2. **业务需求到可合入变更**：澄清边界，将业务验收连接到实际实现、测试和评审。
3. **跨会话或宿主接续**：继承目标与取舍，识别新变化，继续已有工作，避免重复实施与旧证据复用。

理想体验是：用户描述目标后，Agent 读取必要项目事实，在已授权范围内持续推进；真正的产品取舍和新副作用才需要用户判断；最后返回可核查结果。高级能力应由任务需要触发，用户不应先学习整套内部分类。

**这一重审视改变了什么：** 优先级从“补全能力目录”转为“完成三个明确用户工作”，后续每项投入必须指出谁在什么时刻获得收益。

## 第二重审视：领域大师理论体系与判断主轴

### 2.1 四个判断工具

| 理论/方法 | 在本项目中的具体用法 | 会排除什么决策 |
| --- | --- | --- |
| Rumelt 的诊断、指导方针、一致行动 | 围绕存量项目可信交付形成少数相互支持的投入 | 把十几个功能并列称为战略 |
| Goldratt 的约束理论 | 观察任务卡在需求、上下文、验证、评审还是集成 | 实施更快却增加 reviewer 排队与返工 |
| Simon 的有限注意力与反馈控制思想 | 按决策需要组织上下文，让环境反馈纠正行为 | 用长指令补所有错误，或让自检声明代替观测 |
| 因果推断、消融实验与总成本分析 | 固定任务、模型和环境比较机制；统计人工与运行成本 | 把模型升级、环境恢复、任务变简单归因于 harness |

以上用于选择证据和判断方式，不以理论名字替代项目实测。

### 2.2 主要矛盾

**主要矛盾是：项目已有较丰富的工程机制，但机制的持续成本与真实用户增益尚未在同一口径下充分对照。**

八宿主、验证摘要、结构化收尾、上下文包、知识晋升和行为评测均已有资产，不能把它们重新提案为从零建设；同时这些资产存在，不证明目标用户已减少返工或审查时间。[L2-L9](./2026-09-05-harness-research-sources.md#对项目证据的回源)

两个次要矛盾是：模型升级会使部分补偿指令过时；跨宿主兼容会增加维护与验收成本。它们应由首要用户场景和证据需求约束。

建议决策轴：**某机制新增的可接受结果与可复用知识，是否超过它新增的输入、交互、运行、验证和维护成本？** 授权、安全、任务正确性与关键验证是不可用成本节省抵消的底线。

**这一重审视改变了什么：** 不按功能数量分配预算；先寻找交付瓶颈，再验证最小机制是否有效，并把减少负担列为研发成果。

### 3.2 Codex 与 Claude 官方实践：共同点和适配边界

| 主题 | Codex 实践 | Claude 实践 | 项目落点 |
| --- | --- | --- | --- |
| 输入 | Goal、Context、Constraints、Done when | 精确输入与可运行验证 | 复用现有 Goal/Product/Verification Contract，减去重复说明 |
| 常驻指导 | 短而准确，反复出错后增补 | 写不能从代码推断的内容，定期删减 | 项目约束常驻，场景方法按需 |
| 规划 | 复杂工作使用原生 Plan mode/持久计划 | 探索、规划、实现，但简单工作可缩短 | 保留统一意图与产物语义，不强制所有任务经历完整链 |

### 3.3 论文之间的张力，比单个分数更重要

**AGENTS.md 研究与 SkillsBench 并不互相推翻。** 前者主要测试已有文档较充分的 Python 仓库任务，泛化概览未普遍改善成功率，成本平均增加超过 20%；后者测试筛选后的专业过程任务，curated Skills 宏平均提高 16.6 个百分点。两者的知识类型、任务选择、工具和评价条件不同。[P3](./2026-09-05-harness-research-sources.md#p3)[P4](./2026-09-05-harness-research-sources.md#p4)

进一步限定：SkillsBench 构建时筛掉无可测分组差异的低信号任务，所以其增益不是任意研发请求的平均效应；AGENTS.md 论文也没有完整评估安全、非功能约束和跨会话治理。合理落点是：**少重复模型与仓库已经知道的内容，多提供项目特有、当前有效、能被实际消费者使用的信息。**

**多 Agent 也没有统一最优结构。** Scaling Agent Systems 在六类 benchmark 中观察到明显的任务与架构交互；Cursor 的大规模实验也暴露锁与协调瓶颈。应先比较单 Agent、生成者加独立 reviewer、必要的并行探索，再决定是否扩大；不从论文拟合分数生成固定派发规则。[P5](./2026-09-05-harness-research-sources.md#p5)[I1](./2026-09-05-harness-research-sources.md#i1)

**长期学习的价值在增量修正。** ACE 的局部更新可以避免反复整体摘要丢失有效细节，但它依赖反思质量。spec-first 可采用“带证据的候选增量”，继续由既有 promotion 边界控制入库，不能把模型对自身经验的 helpful/harmful 标记当成验证。[P6](./2026-09-05-harness-research-sources.md#p6)[L4](./2026-09-05-harness-research-sources.md#对项目证据的回源)

**工具与简单基线仍不可少。** SWE-agent 支持改善 Agent 可用接口，Agentless 提醒复杂编排应与简单可运行方案比较；两者是历史研究，不提供当前宿主排行榜，也不要求本项目照搬其执行结构。[P1](./2026-09-05-harness-research-sources.md#p1)[P2](./2026-09-05-harness-research-sources.md#p2)

### 3.4 真实研发收益需要修正评价口径

METR 2025 年的 16 人、246 任务研究发现用 AI 后耗时增加 19%；但 2026 年后续研究明确说明选择偏差和并发计时，使新的效果估计不可靠。不能把旧工具减速当成今日结论，也不能把主观提速当成测量。[P7](./2026-09-05-harness-research-sources.md#p7)[M1](./2026-09-05-harness-research-sources.md#m1)

2026 年维护者评审研究发现，约一半测试通过的 AI PR 不会被接受；其模型较旧，而且没有按反馈迭代的机会。对本项目有用的是评价设计：保留确定性验证，同时测 reviewer 的接受与修正负担；不是复用一个拒绝率。[M2](./2026-09-05-harness-research-sources.md#m2)

另一种常见偏差是：AI 让人选择做更多以前不值得做的任务。必须同时问“原有工作是否更快”和“新增工作是否被使用、是否值得投入”，不把大规模生成报告、测试或重构自动算成业务收益。[M3](./2026-09-05-harness-research-sources.md#m3)

### 3.5 当前项目能力与缺口

| 能力面 | 当前证据 | 下一阶段缺口 |
| --- | --- | --- |
| 定位与原则 | 角色契约、演化方法论明确 | 转为少数真实任务的可见收益 |
| 宿主交付 | 八宿主注册；部分 live journey | 深化主宿主关键旅程；preview 保持证据分层 |
| 输入与知识 | context-bundle、summary-first、recall/promotion | 验证信息是否相关、及时、改变决策，并减少人工补充 |
| 验证收尾 | verification-run-summary、honest-closeout | 更可靠地连接真实执行、最终 source、验收与结果消费者 |
| Skill 质量 | 既有跨引擎套件和路由资料 | 减少只测宣告/入口的盲点，补全长链路与实际接受 |
| 现场价值 | 存在局部实测；本轮读取的 CE field 对照链为空 | 建立代表性、可比较的真实任务结果 |

两个会影响战略的具体证据问题：

1. **“零指导已经饱和”尚不足以成立为全项目结论。** 本地 `benchmarks/agentic/run.py` 将工作区放在仓库内，保留 `--setting-sources project,local`，各组还共享 NO_RUN 并限制 Bash。一份 baseline 原始输出引用了项目 Changelog 要求。这支持“需要复核输入隔离”的判断，不能证明完整 harness 无增益。它测的代码生产范围，也不足以代表真实交付循环。[L7](./2026-09-05-harness-research-sources.md#对项目证据的回源)
2. **高准确率不等于覆盖完整。** 本轮按已有重判标签重新汇总：Claude 220/220，Codex 184/186；Codex 34 次环境错误中有一个类别完全没有有效样本。应分别报告有效样本准确率、任务类别覆盖与环境健康；不能以有效样本率推断缺失类别通过。本轮未独立重判全部原始输出。[L6](./2026-09-05-harness-research-sources.md#对项目证据的回源)

验证摘要合同将 recorder 明确为真实命令结果的薄记录器，弱于进程级监督；honest-closeout 检查结构化 claim 与证据关系，不自动证明业务正确性。这是已声明的能力上限，下一阶段应该按实际 claim 提升证据来源，而非增加完成措辞。[L3](./2026-09-05-harness-research-sources.md#对项目证据的回源)

### 3.6 综合判断模型

建议把变化分成两类，以不同方式演化：

- **应长期稳定的项目责任**：产品意图、权限范围、source ownership、验收标准、证据来源、可失效知识。
- **应定期验证的模型补偿机制**：提示冗余、探索深度、任务颗粒度、审查角色数量、context reset、路由提示与工具组合。

宿主原生能力承接执行；项目规则表达真实约束；现有 workflow 将意图传到结果；评测与现场反馈决定哪些补偿机制仍值得保留。脚本产生可验证事实，LLM 判断语义充分性，owner 裁决价值与关键取舍。

**这一重审视改变了什么：** 不接受“全部精简”或“继续加厚”两种笼统结论；形成“稳定边界、按需知识、动态验证补偿机制”的项目演化方向。

## 第四重审视：反方压力与结论前提辩证分析

| 最强反方 | 什么时候成立 | 本规划因此采取的动作 |
| --- | --- | --- |
| Codex/Claude 原生能力已经够用，spec-first 是额外负担 | 相同任务中宿主原生+项目必要规则已达到同样结果 | 保留原生基线；无收益机制 Thin/Retire，不以“治理更完整”抵消额外成本 |
| 团队只需要 AGENTS.md、CI 和既有 review | 项目简单、上下文稳定、几乎无交接损失 | 不把完整 harness 推给所有用户；首要试点选择真实跨边界任务 |
| 更多 gate 会拖慢日常开发 | 确认重复、路由后停顿、文档维护超过风险收益 | 记录无效打断和主动人工时间；在已授权范围内连续推进，保留真正出口边界 |
| eval 最终是在训练 Agent 说出正确入口名 | 缺少最终状态、业务行为与非法副作用检查 | 将路由合规作为过程诊断，独立验证 outcome 与权限边界 |
| 自动学习会让错误经验反复传播 | 来源失效、同一次生成/自评循环互相背书 | 知识默认 advisory，回源后使用；候选更新通过既有 promotion 才发布 |
| 专业 Skill 成为新的包袱 | 仅有漂亮评分，没有下游任务持续受益 | 最多先做少数现有场景增强；跨任务 holdout 和 consumer 复用决定扩大 |
| 只测任务耗时会错过更大的新价值 | AI 改变任务组合或让过去无法做的工作可行 | 固定任务效率与新增价值分账，后者由真实使用和 owner 评价确认 |

前提尚未验证的部分包括：最痛的用户场景、愿意持续使用的团队、可观测的人工时间、可用试点资源与商业化目标。本报告不据此承诺用户规模、预算或提效比例。

重新评估触发条件：新模型/宿主重大版本、试点持续出现无效打断、维护成本增长、上下文召回造成错误、真实回归或 reviewer 负担增加。

**这一重审视改变了什么：** 为每条方向设置停止与退役路径；允许“宿主已足够”和“此用户不需要 spec-first”成为有效结论。

## 第五重审视：全貌理解与可验证收束

### 5.1 三条投资主线，五项能力方向

战略主线限定为三条：**可信交付与收益验证、低打扰的任务上下文、可迁移的工程知识。** 下表是候选能力优先级，不是已批准的开发任务包。

| 优先级 | 能力方向 | 用户实际获得什么 | 复用的现有资产 | 最小下一步与证据 |
| --- | --- | --- | --- | --- |
| P0 | 可执行验收与可信收尾 | 能判断需求做到哪里、测了什么、哪些仍不确定 | verification profile/run summary、honest-closeout、work/debug/review | 从跨模块修复或业务 feature 选一条链，连接验收、最终 diff 与真实命令结果；复用 CI/宿主回执，验证过期证据不会被当成最终结果 |
| P0 | 真实任务评测与机制消融 | 默认路径的投入有依据，升级后不积累过时机制 | skill-up 套件、agentic benchmark、field protocol | 先校准输入隔离、环境错误与类别覆盖；比较原生、当前 spec-first、单项候选改动 |
| P1 | 按任务提供项目上下文 | 少重复介绍项目，减少漏读关键依赖和陈旧知识 | context-bundle、project-rules、CodeGraph/Graphify、learnings recall | 在一个真实模块验证“相关约束+代码入口+验收入口+历史决策”最小输入；统计补充次数与错误决策 |
| P1 | 低打扰接续与首次可信变更 | 安装后能完成真实工作；切会话后继续已有进展 | quickstart、using-spec-first、spec-handoff、原生 resume/worktree | 完整走查主宿主的首次任务和一次接续；观察不必要的确认、重建时间、重复修改、丢失的约束 |
| P2 | 项目专业经验与跨宿主复用 | 新任务少重复踩坑，换宿主仍保留有效工程知识 | spec-compound/refresh、docs/solutions、现有领域 Skill | 从多次实际失败提炼少量候选条目或场景增强，在后续不同任务中验证复用与失效处理 |

为什么 P0 是这两项：第一项提供直接用户价值，第二项防止我们把开销或评测噪声当成改善。两者应在同一试点任务链上推进，避免先做一个没有消费者的指标平台。

### 5.2 技术落点与 ownership

1. **验收与收尾**：scripts 记录 command、exit、source identity、日志引用等事实；LLM 解释验收覆盖和风险；owner 确认业务接受。优先消费现有 CI/宿主事实，确需补充时才设计最薄 capture；不把 recorder 升格为全知监督器。
2. **上下文**：项目文档与源码是权威；图工具只定位候选；LLM 选择并回源。不让脚本按关键词裁定业务影响，也不新建默认向量平台。
3. **接续**：沿用 summary/source refs/freshness/limitations，宿主负责执行与 resume；恢复后重新检查相关工作树和证据。能力不足明确 degraded，不承诺所有宿主语义完全等价。
4. **知识**：候选经验留在现有候选 surface，经过机械检查与语义判断再进入 docs/solutions；保留 invalidation condition。不能把 transcript 或自评当成 promotion 依据。
5. **投射**：实施时修改 `skills/`、`templates/`、`src/cli/` 与相关 source contracts；需要更新 runtime 时由 `spec-first init` 投射。策略实验不直接改宿主镜像。

如果 schema/contract 必须变化，先指出 producer、consumer、版本与兼容路径，再做最小扩展和 downstream tests；不以战略报告提前创建统一事件总线、中央控制器或跨 Skill 状态机。

### 5.3 验证设计：把“有没有用”测清楚

**第一组：机制增量。** 在隔离环境内比较同一模型、工具、权限和任务条件下的三种方案：

| 方案 | 输入 | 要回答的问题 |
| --- | --- | --- |
| A：宿主原生基线 | 必要项目事实与安全约束；无 spec-first 补偿机制 | 现有宿主本来能做到什么 |
| B：当前 spec-first | 同样任务条件，加冻结版本的当前配置 | 整体增量与成本是多少 |
| C：单项候选变化 | 在 B 基础上只改变一个机制 | 精简或增强是否产生稳定净收益 |

不在用户真实项目中移除安全策略来制造“零指导”。对照应使用 owner 授权的隔离副本、固定必要约束，记录实际加载链。先做 A/A 排查环境与测量噪声，再对困难或高风险任务采用更严格对照。

任务集同时包含易任务、普通任务、困难任务与失败反例；不可只保留 candidate 有收益的任务。模型、source、工具、timeout、资源、重试和缺失规则预先固定；缺失样本单列并检查类别覆盖，不把未执行计成模型成功或失败。

**第二组：交付结果。** 保留业务验收、回归测试、越权/范围检查和 final-tree evidence；用真实 reviewer 校准语义评价。评测允许多种正确实现，不把内部步骤名称当成唯一正确答案。

**第三组：持续价值。** 观察同类新任务中的人工成本、返工、缺陷、接续与自愿复用；新出现的任务单独记录真实消费者和采纳结果，不将生成数量计入价值。

建议初始规模为 2-3 个愿意参与的团队、三类场景、每类 6-10 对任务，总计约 18-30 对；仅用于探索和发现大问题，不承诺统计效力。是否扩大由方差、缺失、预期效应与成本决定，不能用固定小样本证明罕见安全风险为零。

### 5.4 五项核心指标

| 指标 | 定义与来源 | 如何使用 |
| --- | --- | --- |
| 可信变更周期 | 从任务确认到必要验证完成且 reviewer 接受；记录墙钟时间及排队/返工分段 | 对匹配任务看中位数、长尾和未完成数，避免只统计成功任务 |
| 主动人工投入 | 澄清、操作、review、纠错、恢复所花时间；试点轻量记录 | Agent 等待与并发工作分开计时，不用 token 代替人工时间 |
| 交付接受与回归 | 首次接受、后续修改轮数、约定观察窗内的缺陷/回滚 | 任何关键质量退化阻止推广，不被速度抵消 |
| 证据与边界失误 | 假完成、旧证据、缺失验证、越权与范围偏离，按严重度记录 | 检查实际状态与权限结果，不只扫描文字；零观测不等于零风险 |
| 持续有效复用 | 团队自愿继续使用、经验被回源后用于后续任务、错误召回与修正负担 | 区分“打开/调用过”与“任务结果受益” |

`quality-adjusted throughput` 用上述结果解释：只计被接受且通过必要质量约束的变更，并同时披露返工、人工和运行成本。暂不制造一个加权总分掩盖质量退化。

在基线建立后再由 owner 冻结目标。可作为试点讨论起点的是可信周期下降约 20% 或主动人工投入下降约 25%，且质量和边界不退化；这些是候选决策阈值，不是实测收益或既定承诺。

### 5.5 建议的 90 天顺序

这是实施次序建议；未假定团队编制和排期承诺。默认同时推进最多两条实质性实验线。

| 阶段 | 工作重点 | 可审阅交付物 | 扩大投入的条件 |
| --- | --- | --- | --- |
| 第 1-2 周 | 确定首要场景；校准 baseline 与缺失口径；识别真正待收口的验证债 | 场景清单、冻结的实验协议、当前机制/证据状态表 | 各比较组环境可比，任务可以运行且 reviewer 标准明确 |
| 第 3-6 周 | 在主宿主上打通一条“需求/缺陷到可信收尾”链，完成最小对照 | 若干完整任务证据、审查反馈、人工时间与成本对照 | 真实交付有净收益；没有不可接受的边界或质量回归 |
| 第 7-10 周 | 针对主要瓶颈改进按需上下文与接续；逐项消融开销 | 候选前后对照、接续案例、误召回/重复操作记录 | 收益在新任务上仍存在，未转移成本给 reviewer |
| 第 11-12 周 | 决定默认化、继续 opt-in 或退役；发布可复核案例 | 能力处置表、版本化使用说明、匿名化成功/失败案例 | 代表任务、主宿主和新 source 上验证；owner 接受推广范围 |

建议职责：研发负责人拥有目标与取舍；工程 owner 维护验收/证据链；评测 owner 保证比较与统计口径；真实开发者和 reviewer 确认实际工作质量。同一人可以兼任，但产出、自检和独立结果不能因此混为一层。

### 5.6 暂缓的建设

- 新增宿主数量优先级低于现有主宿主完整旅程；已有 preview 继续诚实标记并维护必要兼容。
- 不以默认大规模 Agent 团队、中央调度器或全局状态机作为下一阶段主线。
- 不先建统一指标平台、向量知识平台或 Skill 市场；使用现有文件与实验工具完成价值验证。
- 不将泛化最佳实践持续扩写为更长的根指令；不为了 token 指标删除必要业务知识。
- 不把近邻路由完全正确作为唯一产品目标；同时衡量任务完成、打断、授权和交付质量。

### 5.7 继续、降级与停止

当变化提高可信交付或扩大有真实消费者的任务边界，且未增加不可接受的成本时继续；只有个别模型/任务获益时保持定向 opt-in；经过可比较试验仍无收益，或宿主已覆盖时精简或退役。

出现反复环境失败，先暂停对应效果 claim 并修复测量条件；出现产品取舍、授权范围或语义验收分歧，交由 owning producer/owner 决定。不要以扩大 timeout、追加更多 Agent 或增加 prose 自动消化所有失败。

**这一重审视改变了什么：** 方向被收束为有消费者、有现有落点、有对照和退出条件的五项能力；第一步是完成一条真实交付链并测量，而不是启动全面重构。

## 最终判断

**我建议将下一阶段定义为“可信交付兑现阶段”。** 核心使命保持稳定，研发重心转向三个可被用户验证的结果：一次变更更容易被接受，复杂任务更容易接续，后续工作更少重复踩坑。

长期竞争力应来自项目独有知识的质量、验收与证据的连接、跨宿主接续的可靠性，以及真实任务上的持续收益。CLI 与 Skill 是交付载体；其复杂度应随模型进步而被重新证明。

最值得先做的是：**选择一类真实业务变更，复用当前 work/debug/review 与验证资产，让“意图、最终实现、验收、实际结果、审查反馈”完整闭环，再通过宿主原生对照确定应该加强什么、删除什么。**

## 本轮验证与限制

- 已读取当前角色契约、方法论、README、关键源码、合同、既有报告与指定原始证据；外部结论基于实际取得的一手页面，版本与局限在来源账本逐项记录。
- 已按现有 JSON 标签确定性重新汇总路由样本数、环境错误与缺失类别；未重新人工裁决全部路由原始记录。
- 本轮仅形成战略研究文档；没有运行新增模型 eval、现场任务、产品测试或论文复现，不能据此宣称候选改进已经生效。
- 没有使用多 Agent 独立审查；反方分析为当前研究者的显式压力检验，不伪装成独立评审。
- CodeGraph 用于初始源码定位并回到 current source 确认；发现 `.graphify/` 与 `graphify-out/` 同时存在，前者仅见 `needs_update` 标记，未进行刷新/迁移或将图状态当作 readiness 证据。
- 用户群体、资源和商业目标尚未现场验证；本报告没有覆盖所有仓库文件或全部行业资料，也不把检索未找到的信息推断为不存在。
