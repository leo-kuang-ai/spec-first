# 产物目录

本文说明 `spec-first` 常见产物由谁生成、谁读取、是否应提交，以及哪些目录是 generated runtime assets。它的重点是边界，不是把 workflow 固化成状态机。

## 核心原则

- 长期协作知识写入 `docs/` 下的 ideation、requirements、plans、tasks 和 solutions。
- CLI、skill、template 的 source truth 位于 `src/cli/`、`skills/` 和 `templates/`；agent prose 一般在 `skills/**/references/agents/`（不是仓库根目录独立 `agents/`）。
- `.claude/`、`.codex/` 和 `.agents/skills/` 是 generated runtime assets，可由 `spec-first init` 重建，不应作为 source truth 手改。
- `.spec-first/` 下多为 runtime/control-plane facts，通常不提交到 Git。
- 脚本负责确定性事实和格式校验，LLM 负责需求、取舍、实现和评审判断。
- 公开 workflow / standalone skill 清单见 [公开入口与 Skill 目录](./24-公开入口与Skill目录.md)。

## Workflow 文档产物

| 路径 | 主要生成者 | 主要读取方 | Git 边界 | 说明 |
| --- | --- | --- | --- | --- |
| `docs/ideation/*-ideation.md` | `spec-ideate` | `spec-brainstorm`、后续维护者 | 通常提交 | 候选想法、批判、排序和拒绝理由；用于选择一个方向继续成型，不是 requirements、plan 或代码 |
| `docs/plans/*-plan.md`（`artifact_readiness: requirements-only`） | `spec-brainstorm` | `spec-plan`、doc review、后续维护者 | 通常提交 | requirements-only unified plan，记录问题、范围、非目标和成功标准 |
| `docs/brainstorms/*-requirements.md` | `spec-prd` | `spec-plan`、doc review、后续维护者 | 通常提交 | 研发侧 clarified requirements / planning-readiness artifact，兼容使用历史字段 `artifact_kind: prd-requirements`，记录产品 PRD 或需求材料进入研发前的 current-state evidence、Change Delta、owner 决策追踪、优先级、验收、Evidence And Assumptions；不替产品写 PRD，不新增 `docs/prds/` |
| `docs/plans/*-plan.md` | `spec-plan` | `spec-work`、`spec-write-tasks`、code/doc review | 通常提交 | 实施计划，是执行前的主要决策上下文 |
| `docs/tasks/*-tasks.md` | `spec-write-tasks` | `spec-work` | 视团队协作需要提交 | 从 plan 派生的 executable handoff，依赖 source plan 和 hash freshness |
| `docs/solutions/**/*` | `spec-compound` | 后续 brainstorm、plan、work、debug、review 会话和维护者 | 通常提交 | 解决问题后的可复用经验，不是当前需求或计划的替代品 |
| `docs/dogfood-reports/*-dogfood.md` | `spec-dogfood` | 维护者、后续 polish / work | 通常提交 | 分支/PR 浏览器 dogfood 场景、修复与 readiness |
| `docs/ai/project-rules.md` | `spec-rule-miner` | 后续 plan/work/review 会话 | 通常提交 | 从代码证据沉淀的 AI coding 约定；`AGENTS.md`/`CLAUDE.md` 可放 pointer |
| `docs/architecture/**` | `spec-project-rules` | 后续 plan/work/review 会话 | 通常提交 | 从代码证据沉淀的多端架构边界知识库（端职责/依赖方向/复用契约/高价值约定）；`AGENTS.md`/`CLAUDE.md` 可放 pointer |
| `STRATEGY.md` | `spec-strategy` | 产品与研发规划 | 通常提交 | 产品方向与 persona / metrics 等策略文档 |
| `skills/**`（source） | `spec-write-skill` | `spec-first init`、后续 skill 消费方 | 提交 source | 项目拥有的 Agent Skill package；generated runtime mirror 不手改 |
| `CHANGELOG.md` | 执行变更的 agent / 维护者 | reviewer、release、用户 | 提交 | 本仓库要求任何源码或文档变更都同步记录 |

## Review、debug 与验证产物

| 产物形态 | 主要生成者 | 主要用途 | 边界 |
| --- | --- | --- | --- |
| 结构化 findings / residual risks | `spec-code-review` | 合并前发现 bug、回归和测试缺口 | 以当前 diff、计划和测试为范围，不替代实际验证 |
| `<os-temp>/spec-first/spec-code-review/<run-id>/` | `spec-code-review` 的 interactive、autofix、headless mode | 当前 run 的 reviewer JSON、detail enrichment、safe_auto 结果和 residual handoff | 临时 session/orchestrator handoff，不提交；实际路径由当前 OS temp root 解析，例如 macOS/Linux `$TMPDIR` 或 Windows `%TEMP%`；长期保留只写 PR Known Residuals 或 `docs/residual-review-findings/<branch-or-head-sha>.md` concise summary |
| App consistency audit report | `spec-app-consistency-audit`；headless 自动化下亦可直接调用 `node skills/spec-app-consistency-audit/scripts/run-audit.js mode:headless base:<ref>` | 在移动 App 运行时验证前审查 PRD、Figma、source、route、architecture、analytics 和 i18n 一致性，并通过 `issue_synthesis_status` 三态(`not_run` / `llm_provided` / `fixture_provided`)区分确定性产物与 LLM / fixture 注入的语义 issue | `.spec-first/app-audit/` 是执行产物；Figma ref 不等于 materialized evidence；runner v1 仅支持 `mode:headless` |
| Workspace advisory summaries | `spec-runtime-setup` | 父 workspace 下查看 child repo 候选、per-child setup 结果和只读 graph target 建议 | `.spec-first/workspace/` 是 advisory control-plane，不是 child repo canonical truth |
| root cause / fix / verification notes | `spec-debug` | 解释失败原因并证明修复 | 优先复现，再收敛最小修复 |
| test output / command output | shell、npm scripts、CI | 提供确定性验证事实 | 不应由 LLM 伪造；失败要保留真实限制 |

这些产物不一定每次都落成单独文件。是否写入 docs 取决于对应 workflow 的职责和当前任务价值。

## Generated runtime assets

| 路径 | 生成方式 | 是否 source truth | 是否手改 | 说明 |
| --- | --- | --- | --- | --- |
| `.claude/commands/spec-*.md` | `spec-first init` | 否 | 否 | Claude Code `spec-*` command runtime |
| `.claude/skills/` | `spec-first init` | 否 | 否 | Claude standalone / internal skill runtime |
| `.claude/spec-first/workflows/` | `spec-first init` | 否 | 否 | Claude command-backed workflow skill copies |
| `.claude/agents/` | `spec-first init` | 否 | 否 | Claude agent runtime |
| `.codex/agents/` | `spec-first init` | 否 | 否 | Codex agent runtime |
| `.agents/skills/` | `spec-first init` | 否 | 否 | Codex `spec-*` workflow、standalone 与 internal skill runtime mirror |

如果这些目录漂移，修复方式是重新运行对应宿主的 init，而不是直接编辑 runtime copy。

## Source truth 资产

| 路径 | 角色 | 修改后通常需要 |
| --- | --- | --- |
| `src/cli/` | CLI 行为、命令实现、contract 校验 | 单元/集成/smoke 测试，必要时 build |
| `skills/` | source skill 定义和脚本 | source 文件检查、contract 测试，必要时 fresh-source eval |
| `skills/**/references/agents/` | source agent / persona 定义（挂在对应 skill 下） | source 文件检查、contract 测试，必要时 fresh-source eval |
| `templates/` | runtime 生成模板 | init / smoke / governance contract 测试 |
| `docs/` | 协作文档、计划、手册和长期知识 | Markdown link、内容 contract 或相关文档测试 |
| `tests/` | 回归和 contract 保障 | 对应测试命令 |

## `.spec-first/` control-plane facts

`.spec-first/` 下的目录用于 setup、App consistency audit、verification 和 quality gate 的机器事实。更完整的 control-plane 映射见 [Workflows 与产物地图](./04-workflows-artifacts-map.md)。

常见目录：

- `.spec-first/config/`
- `.spec-first/workspace/`
- `.spec-first/audits/`
- `.spec-first/app-audit/`
- `.spec-first/workflows/`

这些目录回答“当前机器事实是什么”，不是长期手工维护知识库。若事实 stale、blocked 或 degraded，下游 workflow 应说明限制，并回退到 bounded direct repo reads、git diff、tests/logs 或用户提供证据。

父 workspace 的 `.spec-first/workspace/` 只保存 advisory summaries，例如 `project-config-bootstrap-summary.json`、`runtime-setup-summary.json`、`mcp-verify-summary.json`。它帮助选择 bounded candidate repos 或理解批量维护结果，但不替代 child repo 内的 `.spec-first/config/` 或当前源码。

## 选择与维护建议

- 想让 AI 先生成、批判和排序多个方向：写 `docs/ideation/`。
- 已选一个方向并需要记录需求：用 `spec-brainstorm` 写 `docs/plans/*-plan.md`（requirements-only）。
- 产品或 owner 已给出 PRD / 需求材料，需要研发侧澄清与计划准入判断：仍写 `docs/brainstorms/`，兼容使用历史字段 `artifact_kind: prd-requirements`。
- 需要执行前共识：写 `docs/plans/`。
- 计划很大、需要交接或并行执行：从 plan 派生 `docs/tasks/`。
- 问题已经解决且经验可复用：写 `docs/solutions/`。
- 分支/PR 需要浏览器 dogfood：写 `docs/dogfood-reports/`。
- 需要沉淀项目 AI coding 约定：用 `spec-rule-miner` 更新 `docs/ai/project-rules.md`。
- 需要建立或回写多端 monorepo 架构边界知识库：用 `spec-project-rules` 更新 `docs/architecture/`。
- 产品方向文档：`STRATEGY.md`（`spec-strategy`）。
- 创建/修改项目 skill 包：改 `skills/**` source（`spec-write-skill`），再 `spec-first init` 投影 runtime。
- runtime 看起来坏了：先判断 source truth 是否正确，再用 `spec-first init` 并选择目标宿主 重建。
- 不确定某个产物是否该提交：优先提交 durable docs 和源码资产，不提交可重建 runtime/control-plane facts。
- 父 workspace 下不确定该写哪个 repo：先回到 plan/task scope，让文档写明 `target_repo` 或 per-unit/per-task `target_repo`；不要让 workspace summary 替你做语义选择。
