# 核心概念

Spec-First 是面向 Claude Code、Codex、Kiro 与 Qoder 的 **AI Coding Harness**：脚本产出可信事实，LLM 做语义判断，证据作为持久 artifact 留在仓库里。Kiro 与 Qoder 支持当前是 opt-in preview；Kiro native Specs 与 Qoder native rules 仍由宿主拥有。

CLI 入口（与 `spec-first --help` 一致）：

| 命令 | 作用 |
| --- | --- |
| `spec-first doctor [--claude\|--codex\|--kiro\|--qoder]` | 自动检测或显式检查环境、runtime asset manifest 和受管运行时状态 |
| `spec-first init` | 交互式安装 workflows、skills、agents 和开发者身份（多选宿主 → 确认姓名 → 选语言 → 预览 → 确认）。可选非交互 flag：`--claude` / `--codex` / `--kiro` / `--qoder` 显式指定并覆盖默认宿主集合；`-y` 默认仍保持 Claude/Codex，不自动选择 Kiro/Qoder；`-u <name>` / `--lang <zh\|en>` 预置身份与语言 |
| `spec-first update` | 升级 CLI 包到 `@latest`，成功后自动启动 fresh `init` 刷新本地 runtime；刷新失败或 scope 不明时输出可复制 fallback |
| `spec-first clean (--claude\|--codex\|--kiro\|--qoder)` | 移除当前项目里 spec-first 受管资产 |
| `spec-first repair-worktree` | 预览失效 worktree pointer 的修复指引（`--dry-run` 仅预览，不删除 `.git`） |
| `spec-first tasks <subcommand>` | 对派生 task pack 做 hash / validate 确定性校验 |
| `spec-first session <subcommand>` | opt-in 的多 actor 会话 advisory（register / list / heartbeat / unregister） |

## 运行模型

当前版本采用 `npm CLI + project-local runtime assets` 模型。

这意味着：

- 公开 workflow 入口统一写作 `spec-*`
- 宿主 runtime delivery 是内部投射细节，不改变用户侧 `spec-*` workflow 名称
- Claude Code 内部投射到 `.claude/commands/spec-*.md` 与 `.claude/spec-first/workflows/`
- Codex 内部投射到 `.agents/skills/spec-*/SKILL.md`；`spec-first init` 不会生成 `.codex/commands/spec/`
- Cursor 内部投射到 `.cursor/skills/spec-*/SKILL.md`，当前仍是 opt-in generated-runtime preview
- Kiro 内部投射到 `.kiro/skills/spec-*`；P0 不占用 Kiro native `/spec` namespace
- Qoder 内部投射到 `.qoder/commands/spec-*.md`，同时也生成 `.qoder/skills/*/SKILL.md`
- `spec-ideate` 是前置 ideation 入口，用于在 brainstorm 之前发散候选和筛选方向
- Claude command-backing workflow runtime copies 来自项目本地 `.claude/spec-first/workflows/`
- standalone skills 来自项目本地 `.claude/skills/`、`.agents/skills/`、`.cursor/skills/`、`.kiro/skills/` 或 `.qoder/skills/`
- agents 来自项目本地 `.claude/agents/`、`.codex/agents/`、`.kiro/agents/` 或 `.qoder/agents/`
- agent support files 来自项目本地 `.claude/agents/`、`.codex/agents/`、`.kiro/agents/` 或 `.qoder/agents/`
- `.claude/spec-first/state.json`、`.codex/spec-first/state.json`、`.kiro/spec-first/state.json` 或 `.qoder/spec-first/state.json` 负责记录受管资产状态；当前 schema 会显式跟踪 `commands / skills / workflowSkills / agents / agentSupportFiles`
- `.claude/spec-first/.developer`、`.codex/spec-first/.developer`、`.kiro/spec-first/.developer` 或 `.qoder/spec-first/.developer` 负责记录项目级开发者身份和初始化版本
- `spec-first init` 会交互式多选宿主 runtime，并收集开发者姓名与语言；姓名默认值会优先回退到已选宿主的项目级 `.developer`，再回退到全局 `~/.spec-first/.developer` 和 `git config user.name`
- `.kiro/settings/mcp.json` 是 Kiro workspace MCP 配置输出；`~/.kiro/settings/mcp.json` 只有在 `--user-scope` / `KIRO_USER_SCOPE=1` 显式 opt-in 后才写入
- `.kiro/specs/**` 是 Kiro native artifact，只在用户明确命名时作为 advisory input；它不是 spec-first source-of-truth，也不会被 `spec-first init` 生成
- `.qoder/settings.local.json` 是 Qoder local MCP 配置输出；`~/.qoder/settings.json` 只有在 `--user-scope` / `QODER_USER_SCOPE=1` 显式 opt-in 后才写入
- `.qoder/rules/**` 是 Qoder native optional rules，只在用户明确命名时作为 advisory input；它不是 spec-first source-of-truth，也不会被 `spec-first init` 生成

当前升级策略是 hard-cut：

- 如果检测到 legacy managed state，唯一受支持的升级入口是重新运行 `spec-first init` 并选择目标宿主
- `init` 会先执行 managed hard reset，再按当前版本全量重建运行时
- `spec-first clean` 不承担 legacy state 迁移，只清理当前受管集合

发布包运行时资产清单由 `src/cli/contracts/dual-host-governance/skills-governance.json`、`templates/claude/commands/spec/*.md` frontmatter、`skills/`（含 skill-local agent/persona）在 CLI 内生成；Claude runtime 会把模板投射为 `.claude/commands/spec-*.md`，`.claude-plugin/plugin.json` 不再作为源码或发布包真源。

## 三层工程概念

Spec-First 把 AI 工程拆成三层：

- `Prompt Engineering`
  关注如何发出更清晰的指令。
- `Context Engineering`
  关注模型能看到什么信息，以及信息如何组织。
- `Harness Engineering`
  关注整个系统如何运行，包括约束、反馈回路、工作流控制和持续改进。

## 五阶段闭环

![Spec-First 五阶段工作流](../assets/svg/spec-first-workflow.svg)

五阶段主链路是：

`Brainstorm -> Plan -> Work -> Review -> Compound`

### 1. Brainstorm

- 目标：明确要做什么
- 输入：问题、想法、需求描述
- 输出：`docs/brainstorms/YYYY-MM-DD-<topic>-requirements.md`

### 2. Plan

- 目标：明确怎么做
- 输入：requirements 文档
- 输出：`docs/plans/YYYY-MM-DD-NNN-<type>-<name>-plan.md`

### 3. Work

- 目标：按计划完成实施
- 输入：plan 文档
- 输出：代码、测试和必要实现记录

### 4. Review

- 目标：输出结构化评审结论
- 输入：实施产物
- 输出：findings、问题清单和通过结论

### 5. Compound

- 目标：沉淀长期可复用知识
- 输入：评审通过的产物
- 输出：`docs/solutions/<category>/<filename>.md`

## 当前工程闭环

五阶段主链路是最小心智模型。当前 spec-first 实际支持的工程闭环更完整：

```text
Codebase -> Spec -> Plan -> Tasks -> Code -> Review -> Knowledge
```

对应到公开入口：

```text
runtime-setup
  -> ideate / brainstorm / doc-review
  -> plan / write-tasks
  -> work / debug / optimize / polish
  -> code-review / app-consistency-audit
  -> compound / compound-refresh / write-skill（skill 包治理）
```

这些入口不是刚性状态机。脚本和 CLI 准备 deterministic facts，LLM 根据当前目标、证据、scope 和风险决定下一步。

## Supporting Workflows

除五阶段主链路外，spec-first 还提供若干 **supporting workflows**，在特定场景下为主链路提供辅助能力。它们不属于五阶段的任何一步，而是独立运行的工具型工作流。

### spec-runtime-setup（required harness runtime 准备入口）

**入口：** `spec-runtime-setup`

用于安装和验证 required harness runtime、MCP servers 和 helper tools。它写入 setup-owned facts，不替代后续 planning / review 的语义判断。

主要产物：

```text
.spec-first/config/runtime-capabilities.json
```

多仓工作区中，`spec-runtime-setup` 从父 workspace 无参数运行时默认处理所有 child repos；`--repo <child>` 用于收窄到单个 child repo，`--all-repos` 是显式等价入口。`spec-first init` 的 target contract 不同：默认在父 root 创建 instruction、`.gitignore`、缺失时的 `CHANGELOG.md` 与 selected host runtime/state；`spec-first init --repo <child>` 只初始化指定 child；`spec-first init --all-repos` 初始化父 workspace 和所有发现的 child repos。父 workspace 的 init-owned bootstrap 和 advisory `.spec-first/workspace/*summary.json` 可以共存，但 child repo 的 canonical setup/readiness facts 必须写在 child repo 内。

旧内置图 CLI、旧上下文路由和静态文档注入链已移除，不再作为当前可用入口。需要当前代码证据时，workflow 应使用 bounded direct source reads、`rg`、ast-grep、git diff、tests/logs 和用户提供证据；影响面无法直接证明时，在 Coverage 中披露限制。

### 公开入口分层（skill / agent）

用户侧能力分三层（完整表见 [公开入口与 Skill 目录](./24-公开入口与Skill目录.md)）：

| 层 | `entry_surface` | 例子 | 用户怎么用 |
| --- | --- | --- | --- |
| 公开 workflow | `workflow_command` | `spec-plan`、`spec-work`、`spec-write-skill` | 宿主内直接调用 `spec-*` |
| Standalone skill | `standalone_skill` | `using-spec-first`、`spec-explain`、`spec-pov` | 按意图直接调用；部分仅用户显式触发 |
| Internal helper | `internal_only` | `spec-worktree`、`spec-commit` | **不作为用户主入口**；由公开 workflow 委托 |

**Skill** 是能力包（`skills/<name>/SKILL.md` + 可选 scripts/references）。**Agent helper** 写在 `skills/<name>/references/agents/*.md`，由 workflow 在需要时委派给宿主 subagent，不是第二套用户 slash 清单。权威治理投影：`src/cli/contracts/dual-host-governance/skills-governance.json`。

### spec-write-skill（source skill 治理入口）

**入口：** `spec-write-skill`

用于创建、修改、迁移项目拥有的 Agent Skill package，或在用户明确要求时对现有/外部 package 做**零执行**的只读 readiness / 结构校验。

常用意图：

```text
spec-write-skill  # 说明要 create / revise 的 skill 与目标 repo
spec-write-skill  # 对 skills/<name> 做 validate-only readiness 检查
```

确定性校验脚本（在 skill package 内，no-follow、不执行目标 lifecycle）：

```bash
# SKILL_DIR 解析为当前 spec-write-skill package root
node "$SKILL_DIR/scripts/validate-skill.cjs" skills/<name> --json
```

协作规则：

- source-of-truth 是仓库内 `skills/`（或项目约定的 skill source），不是 `.claude/` / `.agents/skills/` 等 generated mirror
- 修改 source 与 `skills-governance.json` 后，用 `spec-first init` 刷新宿主 runtime；禁止手改 mirror「修好」漂移
- 外部/未知 package 默认只 `validate-only`，不执行其 scripts、hooks、binaries
- 一次性问答、普通 code review、纯第三方 skill 安装不走本入口

### spec-app-consistency-audit（App 一致性审查入口）

**入口：** `spec-app-consistency-audit`

用于在模拟器、真机、打包或 QA 前，对移动 App 的 PRD、Figma、源码、页面路由、KMP / Clean Architecture、组件复用、埋点、i18n、工程质量和行业规则做静态一致性审查。

常用方式：

```text
spec-app-consistency-audit prd:<path> figma-context:<path> source:<path>
```

需要从代码评审或自动化父流程中只返回 compact 结果时，可以使用：

```text
spec-app-consistency-audit mode:headless base:<ref> source:<path>
```

主要产物：

```text
.spec-first/app-audit/runs/<run-id>/metadata.json
.spec-first/app-audit/runs/<run-id>/preflight.json
.spec-first/app-audit/runs/<run-id>/impact-facts.json
.spec-first/app-audit/runs/<run-id>/app-audit-context.json
.spec-first/app-audit/runs/<run-id>/issues.json
.spec-first/app-audit/runs/<run-id>/audit-report.json
.spec-first/app-audit/runs/<run-id>/app-consistency-audit.md
```

协作规则：

- `.spec-first/app-audit/` 是 gitignored 执行产物，不是 source truth。
- `figma-context:<path>` 是可抽取 evidence；`figma-ref:<id-or-url>` 只是 reference。
- Figma MCP 属于宿主可选能力，只能在默认交互模式下 materialize 本地 JSON；它不进入 `spec-runtime-setup` required baseline。
- 缺 PRD、Figma 或行业 profile 时应记录 degraded mode，并限制结论范围，不能把缺失输入直接升级为 confirmed issue。
- 脚本负责 preflight、contract extraction、evidence gate 和 artifact 校验；LLM 专家负责语义判断、严重性解释和报告取舍。

## 当前代码证据的正确分层

当前 workflow 的代码证据来自 bounded direct source reads、`rg`、ast-grep、git diff、tests/logs 和用户提供材料。脚本可以写 setup-owned facts 或执行产物，但具体工程判断仍由 LLM 基于当前源码、当前 diff 和验证结果完成。

协作规则：

1. 用户可见知识沉淀写入 `docs/solutions/`，由 `spec-compound` 管理。
2. workflow 需要当前代码事实时直接读取 source 或运行聚焦验证，不读取旧文档包。
3. 父 workspace 的 `.spec-first/workspace/` 只保存 advisory summaries，不是跨 repo 的 source truth。
