## 1. 背景与目标

高手的经验不能只留在高手手里。本次审查要判断这些 Skill 是否把优秀研发人员的隐性经验，转化为普通开发者与 AI 能够理解、执行、验证并复用的工程方法。

审查以软件研发的共同规律为基础，不按 App、H5、Admin、Java、Python 或其他端与语言划分质量等级。重点是问题定义、约束识别、架构取舍、实现正确性、验证策略、风险控制、协作交接和持续维护。

每个 Skill 必须回答：

1. 定位是否清晰、合理，是否解决有价值的研发问题？
2. 正文及其依赖是否提供了足够的专业方法，支撑执行者完成目标？
3. 哪些结果已有证据支持，哪些只是设计意图，哪些存在缺口？
4. 如何以最小可维护改进提升研发质量，而不是增加流程和文档负担？
5. 与不加载该 Skill 相比，它在哪些场景带来可观察的增益，代价是什么？（第 3.8 节）
6. 作为写给模型的指令，它是否只写了模型不知道的内容，是否在多个模型和宿主上都成立，是否会因模型更强、更字面而产生新问题？（第 3.9 节）

模型能力在快速提升，Skill 的价值正在从“教模型怎么做”转向“告诉模型项目的事实、边界和验证方法”。因此本次审查的改进建议既可能是补充，也可能是删减；两者都要有证据和验证方式。

### 2.2 通用工程视角与专项边界

通用 Skill 应表达与技术栈无关的判断方法，并根据项目上下文选择具体工具与验证手段。专项 Skill 可以保留平台能力：例如浏览器测试和 Xcode 测试分别按自身适用场景评估，不要求 Xcode 支持 Java，也不因平台专属性直接判为缺陷。

通用性审查关注：是否把局部习惯误写成普遍要求；能否识别不适用场景；缺少工具时能否正确降级或移交；专项证据是否被错误外推为整体质量。

### 2.2.1 S00 `spec-runtime-setup` 的审查定位

`spec-runtime-setup` 不在研发链路的需求到知识环节中，而是这些环节的运行前提。它准备宿主与工具的确定性就绪事实（MCP server、代码图谱、Graphify、浏览器等辅助工具），写入 setup 自有的项目事实，并报告具体的下一步；源码自述不提供代码理解权威。最先审查它有两个原因：

1. **后续行为证据的前提：** 其余各项的行为场景依赖这些工具是否可用、是否过期以及降级状态。就绪事实不可信时，后续场景中“工具不可用”“索引过期”“降级执行”的判断都无法区分是 Skill 的问题还是环境的问题。
2. **副作用最集中：** 它会安装第三方工具、修改宿主配置和项目文件，是这批对象中越权、破坏和供应链风险最直接的一项。

审查时按其职责调整重点，不套用研发链路 Skill 的需求理解或方案设计要求：

- **事实与判断的分工：** 脚本产出的就绪事实、reason_code 和退出状态是否确定、可复现；哪些结论属于建议而非已确认；有没有让脚本做语义判断，或让模型声称执行过未执行的检查。
- **副作用与授权：** 每种模式（检查、预览、安装、修复宿主配置、刷新、清理）的写入范围是否明确；是否先预览后写入；是否只改 setup 自有的条目，保护用户已有配置；推送、全局安装等高影响动作是否需要独立确认。
- **幂等、中断与回退：** 重复执行是否收敛到相同状态；中途失败时是否留下可识别的部分状态并能恢复；是否能清理自己写入的内容。
- **多宿主一致性：** 8 个受支持宿主（以 `getSupportedPlatforms()` 为准）的投射差异、缺失能力与降级说明是否明确，不把一个宿主的结果外推到其他宿主。
- **供应链与环境安全：** 安装来源、版本固定与校验方式；网络不可用、权限不足、已存在冲突版本时的行为。
- **下游消费：** 下游 Skill 读取的是哪些事实、以什么形式读取，事实过期或缺失时下游能否识别；对照 [project-graph-consumption](../contracts/project-graph-consumption.md) 检查项目情报的就绪与新鲜度边界。

审查深度为完整深度。研发视角以安全与隐私、可靠性与运行反馈、交付与协作、研发效能为主，其余视角说明适用性即可；第 3.6 节只检查“私有代码知识与大型仓库检索”中项目情报的就绪与降级部分，其他环节标为不适用并说明理由；不参与第 3.7 节共同场景；第 3.8 节基线对照只做静态判断，说明下游 Skill 缺少可信就绪事实时会承担什么风险。

**执行安全约束：** 行为场景必须在隔离环境中执行（临时 HOME、临时项目目录或 fixture），不得为完成审查修改审查者本机或当前仓库的真实宿主配置、全局安装工具或刷新真实项目图谱；需要真实环境证据时，先取得独立授权。已有的 `skills/spec-runtime-setup/evals/` 与 `npm run test:mcp-setup` 可作为复用资产，复用前按第 4 节核对适用性。

### 2.2.2 S00 的模型指令检查重点

S00 的 SKILL.md 中“必须/禁止/不得/严禁”类措辞较多（2026-11-01 统计 49 处，见调研记录第 3.1 节，正式审查时重新取数）。按第 3.9 节逐条判断：哪些是真正的出口约束（副作用授权、写入范围、确定性事实不能伪造），哪些是可以改为说明原因的一般指导。在指令遵循更强的模型上，过多绝对措辞可能造成过度停顿或过度询问，需要用场景检验，不能只凭计数下结论。

### 2.4 范围决策

`skills/` 下共有 38 个 source skill。用户授权项目负责人按项目目标自主决定其余 14 项是否纳入。

**决策依据：** [项目角色契约](../methodology/结构化项目角色契约.md)把使命定为缩短 time-to-trusted-change、提升 quality-adjusted throughput，核心价值链是 `Codebase → Spec → Plan → Tasks → Code → Review → Knowledge`。契约还要求“兑现、验证和简化已有能力优先于继续增加能力”，并且治理强度与风险相称。据此用三个问题判断是否纳入：

1. 它是否直接承担主链路某个节点或主链路的可信性入口？
2. 它的质量问题是否会直接造成不可信变更，例如路由错误、行为被改坏、越权？
3. 只把它作为已纳入对象的上下游依赖来读，是否已经足以覆盖相关风险？

前两问为“是”且第三问为“否”时纳入。其余不纳入，并写明重新评估的条件，避免审查规模膨胀到无法完成。

| 决策 | Skill | 理由 | 安排或重新评估条件 |
|---|---|---|---|
| 纳入 S20 | `using-spec-first` | 它是所有工作的入口，决定请求进入哪个 Skill 或直接处理。路由错误会让下游 Skill 的质量失去意义，也会让小任务承担不必要的流程成本，直接拉长 time-to-trusted-change。按 `AGENTS.md`，它在实质性工作前加载，是每次都要付的上下文成本。第 3.9 节的指令优先级与冲突问题在它身上最集中，基线对照问题也最直接：不加载它时，模型能否选对入口 | 完整深度，排在 S00 之后、试点之前 |
| 纳入 S21 | `spec-simplify-code` | 它承担主链路 Code 节点中的行为保持重构。在既有系统中，这是“最小充分、复用已有能力”原则最常落地的地方，风险是在“简化”名义下改变行为。现有清单只覆盖新增实现（work）和缺陷修复（debug），没有覆盖重构 | 聚焦深度，并入“实施与审查”批次。重点是行为未变的证据、复用判断和范围控制 |
| 不纳入，作为依赖读取 | `spec-dogfood` | 它与 S19 的关系可以通过读取调用方合同覆盖；分支级自测的验证能力由 S11 `spec-test-browser` 承担，dogfood 是在其上的自主编排。作为完整对象纳入会增加一项完整审查，收益主要和 S11、S19 重叠 | S19 审查时必须读取 `spec-dogfood` 中调用 `spec-worktree` 的部分，S11 审查时读取它委派浏览器执行的部分。若这两项审查发现与 dogfood 相关的 P0/P1，再把它纳入 |
| 不纳入 | `spec-pov` | 技术选型判断在 S04 `spec-plan` 的方案取舍和第 3.6 节新依赖判断中审查。pov 是独立的第二意见入口，不在主链路上 | 若 S04 审查发现 plan 把选型判断委托给 pov 且依赖其结论，再纳入 |
| 不纳入 | `spec-optimize` | 性能优化频率较低；它的行为保持和测量问题与 S21、S10 有重叠 | 若团队实际使用频繁，或 S21 审查发现行为保持机制与它共享，再纳入 |
| 不纳入 | `spec-prototype` | 一次性原型服务产品探索，产物不进入主链路代码 | 无 |
| 维持排除 | `spec-project-rules`、`spec-rule-miner` | 用户最初明确排除。它们产出的约定与架构知识是“有效上下文”的来源，但本次审查的问题是主链路 Skill 能否正确消费这些上下文，这在第 3.6 节“团队约定的消费”和“私有代码知识”中已覆盖。审查它们的产出质量是另一件事 | 审查报告注明其产物质量不在本次范围。若主链路审查发现关键缺陷的根因指向这些上游产物，单独立项审查 |
| 不纳入 | `spec-explain`、`spec-strategy`、`spec-product-pulse`、`spec-promote`、`spec-riffrec-feedback-analysis`、`spec-polish` | 不承担主链路节点：分别是教学、产品战略、产品数据、推广文案、录屏反馈分析和界面打磨 | 无 |
| 不纳入 | `spec-sweep`、`autoresearch` | 不在主链路上。`spec-sweep` 会在来源处做外部写入，`autoresearch` 会自主循环修改代码，越权风险值得关注，但这属于各自的安全审查，不属于本次研发链路专业能力审查 | 记录为本次范围外的已知风险面。若要评估，按第 3.9 节和第 2.2.1 节的副作用审查重点单独立项 |

### 2.4.1 S20 与 S21 的审查重点

**S20 `using-spec-first`：** 它不产出研发产物，价值体现在把请求送到正确的 owner、让小任务走短路径。审查时以路由正确性和成本为中心，不套用需求或方案设计要求：

- **路由正确性：** 覆盖 `AGENTS.md` 的入口硬规则，包括失败、报错或修复意图必须进入 `spec-debug`，以及显式点名 workflow、PR 反馈、一条龙到绿 PR、外部技术裁决和跨会话交接的强制入口。还要覆盖 Direct Lane 的适用与禁止条件、低置信时最多问一个问题，以及活跃 workflow 中不重新路由。
- **成本与短路径：** 小任务是否能直接处理而不被拖进重流程？路由本身消耗多少上下文和轮次？与不加载它相比，模型自己选入口的正确率和成本如何（第 3.8 节）？
- **规则层级与冲突：** 它与 `AGENTS.md`、`CLAUDE.md`、宿主 steering 和各 Skill 描述之间是否一致？出现冲突时能否说明依据（第 3.9 节）？
- **授权边界：** 路由结果不产生 mutation、验证声明或交接授权。
- **治理文本的事实准确性：** `AGENTS.md` 顶部引用 2026-08-20 基线报告，写的是“零指导正确率 100%、与加载指令无差异”，但该报告已于 2026-09-20 勘误。这段文本每个会话都会加载，可能让模型低估 Skill 的作用，或者让用户误判项目价值。审查时把它作为已知问题 K-01 记录，判断影响和修复位置。修复要改 source `CLAUDE.md`，再按仓库流程派生 `AGENTS.md`，另行承接。

**S21 `spec-simplify-code`：** 重点是行为未变的证据，包括执行前后同一组测试和刻画测试的结果，以及无测试覆盖时的处理。还要检查：复用判断是否核对语义而不只看名字相似；是否守住“近期变更”的范围，不顺手改无关代码；发现缺陷时是否移交 `spec-debug` 而不是在重构中顺带修复。

## 3. 逐项审查要求

### 3.1 先深入理解每个 Skill 的定位与目标

逐项审查必须先形成有源码依据的详细定位说明，不能只复制 frontmatter、名称或清单中的一句话简介。说明应让未参与项目的人理解该 Skill 为什么存在、承担什么研发责任、要把什么输入转化成什么结果，以及怎样才算高质量完成。

每项必须明确：

- **服务对象与问题：** 谁在什么研发情境下需要它，当前痛点是什么，成功后解决什么问题。
- **链路职责与边界：** 在研发链路中的责任、适用与不适用场景，与相邻 Skill 的分工，以及何时直接完成、降级或移交。
- **目标层次：** 核心目标、支撑核心目标的必要子目标、明确非目标；将结果目标与执行步骤区分，不能把“生成文档”或“跑完流程”本身当成价值兑现。
- **输入与前提：** 所需事实、项目上下文、授权、工具及上游产物；哪些缺失可以合理补齐，哪些会使目标无法可靠达成。
- **输出与使用价值：** 交付物包含什么，谁会如何使用，消费者在什么条件下可以据此行动而不必重新猜测关键意图。
- **高质量完成标准：** 各核心目标对应的正确性、完整性、可执行性、可验证性及维护成本要求；按职责解释质量维度，不机械套用所有标准。
- **失败与能力上限：** 哪些现象意味着目标未达成，哪些仅为部分完成，以及现有工具、宿主或证据带来的限制。

区分“源码声明的定位与目标”“实现实际支持的定位与目标”和“专业研发视角建议的定位与目标”。三者不一致时记录差异与影响，不把优化建议写成既有事实，也不能通过降低目标来迁就实现。

### 3.2 建立专业能力基准

每项先根据目标研发角色、使用场景与消费者需要，建立“定位目标 → 必备能力 → 合格产物标准”，再与现有 Skill 正文及实现逐一映射。可以先核实声明定位，但不能仅从现有内容反推必备能力，也不能因为源码没有提到某种能力就把它排除在审查之外。

基准须说明每项能力为何必要、适用条件和判断依据；依据可来自项目约束、真实失败案例、可核验的工程资料或审查者明确标注的专业判断。外部资料是参考，不自动成为项目强制规则。定位本身不合理时应明确提出修订建议，不能通过缩小定位掩盖能力缺口。

例如，故障诊断应检查可复现事实、竞争假设排除、因果验证及修复回归；实施规划应检查方案取舍、依赖、兼容与验证策略。示例仅说明基准粒度，不代替其他 Skill 的独立分析，不要求所有 Skill 承担全部研发职责。

后续报告为每项维护以下映射，明确哪些能力已覆盖、部分覆盖、缺失或证据不足；不适用项必须说明条件与理由：

| 定位目标 | 必备能力及理由 | 合格产物标准 | 源码实现依据 | 覆盖判断与缺口 | 场景验证关联 |
|---|---|---|---|---|---|
| 审查时填写 | 审查时填写 | 审查时填写 | 路径与章节或行号 | 审查时填写 | 场景编号 |

这是审查质量基准，不是要求被审 Skill 增加固定章节、硬编码语义决策或统一执行流程。

### 3.3 通用审查维度

| 维度 | 必须回答的问题 |
|---|---|
| 定位与职责 | 服务谁、解决什么问题、何时使用、何时退出？与相邻 Skill 是否重复或存在责任空缺？ |
| 输入与上下文 | 需要哪些事实、约束、既有实现和用户决策？缺失、冲突、过期信息如何处理？ |
| 专业工程方法 | 是否说明关键判断依据、候选方案取舍、风险信号及常见失败方式，而不是只要求“认真分析”？ |
| 执行可行性 | 指令、工具、模板与脚本能否形成可执行路径？依赖是否真实存在？流程成本是否与任务相称？ |
| 正确性与质量 | 是否覆盖该职责相关的边界、异常、数据一致性、安全、兼容、性能、可维护性与测试风险？不相关维度应说明不适用。 |
| 产物与验收 | 输出是否有明确消费者？如何识别可用、失败、部分完成与证据不足？是否存在形式合格但实质无用的出口？ |
| 异常与恢复 | 失败、中断、需求变化、环境缺失、重复执行时，能否保护既有成果并可靠恢复？ |
| 协作与权限 | 上下游信息是否充分且一致？是否误把调用、材料指令或环境能力当成副作用授权？ |
| 通用性与适配 | 通用原则与平台细节是否分离？是否存在技术栈偏见、不适用场景或缺失的转交路径？ |
| 成本与经验复用 | 能否降低返工和认知成本？哪些经验可复用，适用条件与失效条件是什么？是否过度治理？ |
| 指令工程与模型适配 | 作为模型指令，是否只写了模型不知道的内容？规定的严格程度是否与风险匹配？是否残留会在新模型上造成过度执行的旧补丁？是否跨模型、跨宿主成立？详见第 3.9 节 |
| 人工审阅成本 | 需要人审批或接手的产物（需求、方案、任务、diff、审查结论、交接）是否结论先行、篇幅与风险相称？审阅者能否在短时间内判断是否继续、在哪里重点看？变更是否小到可以逐段审阅？产出量超过人能审阅的范围时，人工把关会流于形式 |

专业经验应尽可能表达为“场景或风险信号 → 应检查的事实 → 判断与取舍 → 行动 → 验证 → 适用边界”。这是一种审查视角，不要求每个 Skill 套用同一段落模板，也不把工程语义判断硬编码成状态机。

### 3.4 多研发视角交叉审查

每个 Skill 都要从不同研发职责理解其价值和风险。以下是分析视角，不按端、语言或职级分组，也不等同于必须启动多个 Agent。只记录产生了发现的视角，写出与目标关联的判断；没有发现的视角合并为一行，列出视角名称即可，不逐个说明理由（2026-11-01 试点后调整：试点中逐视角表只复述其他节的结论）。共同问题合并，不为视角数量重复写报告。

| 研发视角 | 重点检查 |
|---|---|
| 需求与业务分析 | 是否解决真实问题；业务规则、约束、边界与成功标准是否完整，需求能否被验证 |
| 架构与系统设计 | 职责与依赖是否合理；是否分析备选方案、质量属性、兼容演进和复杂度代价 |
| 编码与维护 | 执行者是否能形成正确、易读、可维护的实现；是否复用已有能力并处理异常和变更影响 |
| 测试与质量工程 | 测试是否针对风险和需求；能否发现反例、回归与不可测部分，避免只验证格式或成功路径 |
| 安全与隐私 | 是否识别信任边界、最小权限、敏感数据和供应链风险；安全要求是否与实际任务相称 |
| 可靠性与运行反馈 | 是否考虑可观测性、故障定位、恢复、数据完整性与变更可逆性；运行反馈能否回到研发判断 |
| 交付与协作 | 上下游交接、版本控制、集成验证和变更说明是否充分；消费者能否可靠接手 |
| 研发效能与知识传递 | 是否减少认知负担、等待、返工和重复劳动；新人能否理解专家判断依据，经验能否正确复用 |

各视角只能检查该 Skill 的职责或相关交接责任。例如，运行反馈视角可以要求计划说明迁移或回滚约束，但不能因此把部署编排、生产运维全部纳入该 Skill 的职责。

视角之间发生冲突时，记录具体取舍、项目条件、受影响目标与验证办法，由审查者结合证据裁决。不能以多数意见、角色数量或“某专家建议”替代结论依据。单一审查者切换视角不构成独立复核。

### 3.5 结合业界最佳实践建立对照

逐个 Skill 选择与其核心目标直接相关的工程实践，与源码、产物和场景表现对照。实践用于发现专业能力缺口和改进机会，不能仅罗列知名框架名称，也不能将业界建议直接提升为本项目必须遵守的规则。

可检索的候选来源包括：SWEBOK 的需求、设计、测试与维护知识，Google Engineering Practices 的代码审查实践，Google SRE 的可靠性与故障复盘实践，OWASP 与 NIST SSDF 的安全研发实践，以及 DORA、SPACE 的交付与研发效能研究。这些是候选研究方向；已核验的相关章节（三轮共 R1–R25，含 DORA 2025 公告、OWASP LLM Top 10 2025 的两项，以及 Anthropic、OpenAI 的 Skill 与提示工程官方指引）及未核验来源（SWEBOK、SPACE、NIST SSDF 实践条目、DORA 完整报告）见[调研记录](2026-11-01-ai-assisted-brownfield-research.md)，后续只能引用实际核验的内容，并检查其新鲜度。允许使用其他更贴合目标的一手资料，不要求每项 Skill 对照全部来源。

实践对照必须满足：

1. **可追溯：** 优先使用官方标准、原始研究、维护者文档或公开的一手工程经验。记录名称、发布者、版本或日期、链接、访问日期及具体章节；无法核验时标为待核验，不用模型记忆冒充已读取来源。
2. **有适用条件：** 区分规范性要求、实证研究、经验建议和审查者推断；说明实践解决什么问题、依赖什么组织或技术条件、有哪些限制。不能将特定公司或大规模团队的做法默认套用所有项目。
3. **有本地映射：** 每项至少形成一条与核心目标直接相关的已核验实践对照，写明对应能力、当前源码证据、已有覆盖或真实差距。找不到合适来源时记录检索范围及原因，保留该对照待补证，不为凑数引用无关材料。
4. **有工程取舍：** 对候选实践给出保留现状、直接采用、适配采用、暂缓或不采用的建议，解释预期收益、引入成本、适用边界和验证方式。现有等价机制满足目标时无需照搬外部形式；缺少某个术语本身不构成缺陷。
5. **结论有边界：** 业界证据不能直接证明本项目收益。团队级效能研究不能外推成某个 Skill 的已实现效果，也不能用于评价单个开发者。资料冲突时呈现适用条件与取舍，不挑选支持预设结论的材料。

后续审查报告记录“实践及来源 → 适用条件 → Skill 目标 → 源码现状 → 差距或等价实现 → 采用建议 → 验证办法”。多个 Skill 可以复用同一已核验来源，但必须各自说明适用关系。最佳实践对照未完成时，应单独标明覆盖缺口，不能宣称已完成包含业界对照的全量审查。

### 3.6 AI 辅助企业既有系统研发的专项审查

本次默认关注已有业务、架构、模块、数据和用户的增量开发，不以从零生成一个可运行演示作为主要能力标准。应判断 AI 能否在现有工程中理解正确、设计适配、实现可靠、验证充分并持续接续工作。新建项目场景可以保留，但不能替代既有系统场景。

依据见[调研记录](2026-11-01-ai-assisted-brownfield-research.md)。其中 R1—R25 是已读取资料的索引（R13、R14 仅读摘要；R17—R25 主要用于第 3.9 节），以下内容是结合本地源码的工程判断，并非外部来源原文逐条要求。此表是审查责任映射，不代表已确认各 Skill 当前充分实现这些能力。

| 环节与主要承接 Skill | 必须理解和审查的能力 | 高质量结果与典型反例 | 调研依据 |
|---|---|---|---|
| 需求理解：`spec-brainstorm`、`spec-prd`；`spec-ideate` 负责方向探索 | 还原用户目标、业务流程、领域规则、权限与数据边界；区分现状、期望增量、必须保持的行为和未知事项；用实例与反例消除歧义 | 关键业务行为与验收条件明确，后续无需猜测。反例：把旧实现的缺陷视为业务真相，或将 AI 推测写成已确认需求 | R1、R5 |
| 需求切片与任务拆分：`spec-prd`、`spec-plan`、`spec-write-tasks` | 区分业务范围切片、方案实施单元和派生任务；按可验证结果拆分，说明依赖、接口、责任、验收与集成顺序；识别可并行和必须串行的修改 | 每个切片能形成有效反馈，整体覆盖需求；共享基础确需先行时有理由和最早验证点。反例：只按文件拆分，全部局部任务结束但链路不可用 | R1、R5；本地 Work |
| 现有系统理解：`spec-plan`，`spec-work`、`spec-debug` 按职责核验 | 读取真实入口、模块 owner、调用链、数据流、配置、错误处理、依赖、测试与历史决策；识别代码、文档和运行事实的冲突 | 对受影响边界有可回源解释，阅读范围足以支持决策。反例：只看目录或同名函数就声称理解架构 | R1、R2 |
| 技术方案：`spec-plan`，`spec-doc-review` 审查，`spec-work` 检查当前适配 | 比较复用、扩展、组合和新建；判断语义、生命周期、错误合同及依赖方向是否相容；解释模块落点、备选方案、质量属性和迁移风险 | 在现有架构正确位置形成最小充分方案；需要新边界时有真实需求。反例：复制已有能力、为复用强塞错误模块，或无消费者先造通用框架 | R1、R2；本地 Work |
| 编码与集成：`spec-work` | 按小步可验证变更执行，保持业务规则、模块合同和现有习惯；发现计划与源码漂移时评估影响，范围变化返回 owning workflow；保护并行修改 | 功能通过真实调用链接入，可维护且无孤立代码。反例：新增实现未被任何入口调用，测试却直接调用新增函数并通过 | R2、R5 |
| 单元测试：`spec-work`、`spec-debug`，`spec-code-review` 核验质量 | 从需求、合同和不变量推导断言；覆盖适用边界、错误和状态变化；选择真实实现或适当替身，避免期待值由被测实现生成；复用或强化已有测试 | 测试能在目标行为错误时失败，纯内部重构时保持有效。反例：全 mock、空断言、只测私有调用顺序、改弱断言换取绿灯 | R2、R3 |
| 自测与跨层验证：`spec-work`，按需 `spec-test-browser`、`spec-test-xcode` | 以用户或真实调用者入口检查验收路径、异常路径和受影响旧行为；覆盖必要的接口、序列化、权限、持久化、异步回调及配置；记录环境和执行版本 | 明确实际验证过什么。反例：单测通过即宣称功能可用，或截图存在即宣称整个业务链正确 | R2、R3；本地 Work |
| 审查与修复：`spec-code-review`、`spec-resolve-pr-feedback`、`spec-debug` | 评估反馈是否成立，区分症状与根因，比较竞争假设；在恰当 owner 修复，补足回归并复跑；检查同根影响及修复副作用 | 原问题与受影响行为有证据闭环；不能复现则限定判断。反例：仅吞异常、无界重试，或修改测试让错误实现通过 | R2、R4 |
| 完成总结：当前执行或审查 owner | 对照需求总结变更、方案取舍、实际验证、未覆盖风险、残留问题和下一步；不把执行流水账当结果 | 后续维护者能判断可用范围。反例：只有“已完成、测试通过”，没有对应版本或验证范围 | R2、R5；本地 Work |
| 问题沉淀与更新：`spec-compound`、`spec-compound-refresh` | 提取经验证且值得复用的因果经验、判断方法与防复发措施；保留适用条件、失效条件及证据；更新已有记录，避免重复或过期知识 | 下一次可检索、可理解并能正确应用。反例：未经验证的猜测进入知识库，或每次改动都机械生成文章 | R4；本地 Compound |
| 多对话交接：`spec-handoff`；workflow 内交接由原 owner 负责 | 保留最新用户意图、目标、决策及理由、已做和未做、验证位置、当前分支与未提交状态、阻塞和有界下一步；恢复时核对新鲜度 | 新会话可恢复工作且不重复有副作用动作，不依赖丢失的本地文件。反例：只传聊天摘要，恢复后执行过期计划或相信历史完成声明 | R6；本地 Handoff |
| 整体编排与交付辅助：`spec-lfg`、`spec-commit`、`spec-commit-push-pr`、`spec-worktree` | 维持各阶段责任、验证版本与授权范围，保护提交内容及隔离目录，处理部分成功和恢复，不越过未满足的完成条件 | 局部成功不掩盖整体缺口，外部动作结果可核验。反例：旧树测试结果用于新提交，或重复恢复造成第二次推送/发布 | R5；项目职责与证据边界 |

#### 企业既有架构与复用的重点

对 `spec-plan` 的方案能力及其下游消费，至少检查以下内容是否按风险得到处理：

- **业务与架构现状：** 需求映射到哪段业务流程、领域边界、模块和权威数据源；已有相似能力实际在哪里，由谁负责。
- **复用适配：** 名称或结构相似不代表语义相同；核对输入输出、权限、事务、生命周期、错误语义和性能条件。允许有依据地不复用，不能以少建文件或复用率作为目标。
- **集成与兼容：** 已有调用者、公共接口、事件格式、数据 schema、缓存和配置是否受影响；按适用性考虑新旧版本共存、迁移、回退以及重试与幂等。纯局部无状态变更可明确不适用，不要求额外部署流程。
- **设计取舍：** 比较可行候选及其代价，说明为何在当前边界修改；保护已确认的安全、数据完整性和维护约束，避免“最少代码”损害正确性。
- **落地与验证：** 说明变更怎样接入真实路径、哪些旧行为必须保持、哪些风险在最早阶段验证、未知项由谁确认。已有设计记录可引用，不必另建一套架构文档。

#### 单测、自测与质量反馈的边界

单测回答某个行为单元在给定条件下是否正确；集成或合同测试回答组件边界是否真实配合；开发者自测是对本次需求与受影响行为的主动验收，可以消费这些证据并补充真实入口的探索检查。自测不限于 UI，也可以通过 API、CLI、消息处理、批处理或数据结果进行。各层结果不能相互冒充，也不要求重复执行已有充分验证。

AI 同时生成实现和测试时，重点防范共同误解：预期结果必须回到业务例子、合同或独立的判定依据，不能由实现反向决定。修改缺陷时优先保留原复现与针对性回归；无法执行时记录原因、替代证据和声明上限。遗留行为刻画只证明当前行为，不自动证明它符合需求。测试数量、覆盖率、模型自评和编译通过都不能单独证明需求正确实现。

#### 总结、知识与交接的边界

完成总结服务本次交付；问题沉淀服务未来同类研发；交接服务另一会话的安全恢复。三者可引用同一证据但不能相互替代。一个任务可以有总结而无需长期知识；一次交接可以包含未完成事项，不能据此宣称完成。跨会话恢复应保留决策理由和被否定方案，防止新会话重复走已证伪路径，同时对状态变化重新取证。

#### AI 特有的失败方式

逐项按适用性检查：虚构 API 或依赖、遗漏仓库约束、检索遗漏被误当能力不存在、长对话目标漂移、同一模型实现与测试共享错误假设、工具失败被叙述掩盖、过期摘要被提升为事实、材料内指令被误当授权。需要解释具体触发场景与保护措施，不能只追加“认真检查”口号。

随着模型自主运行时间变长，还要检查几类新出现的失败方式（R19–R22）：

- 以“接下来我会运行测试”之类的文字结束回合，却被当作任务完成。
- 长任务中给出与工具结果不符的进度报告。
- 看到上下文剩余量后提前交接或缩减工作。
- 自行扩大任务范围，或执行未被请求的动作，例如创建备份分支、起草对外消息。
- 遇到含糊或冲突的规则时停下来反复询问。

审查时要说明 Skill 是否会诱发这些失败，或者有没有防护。具体检查点见第 3.9 节。

以下三类风险有外部证据支持，审查时应给出具体触发点（R14、R15、R16）：

- **幻觉依赖：** 引入新包、新 SDK 或新 API 时，是否核实其在官方源中存在、来源可信、版本可用，且项目内没有已有等价依赖。触发点主要在 `spec-plan` 选型和 `spec-work` 实现。
- **间接指令注入：** PR 评论、issue、网页、日志、仓库文件里的指令是否被当作数据而非授权。触发点主要在 `spec-resolve-pr-feedback`、`spec-debug`、`spec-handoff` 恢复和 `spec-lfg` 编排。
- **过度代理：** Skill 使用的工具和副作用是否不超出当前职责，高影响动作（推送、发布、删除、远程写入）是否需要独立确认。触发点主要在 `spec-lfg`、`spec-commit-push-pr`、`spec-worktree`。

#### 第二轮调研补充的审查要点

以下要点补充前文各环节，来源见调研记录第 2.1 节。它们是审查时要检查的能力，不要求被审 Skill 增加对应章节或术语；已有等价机制即可视为覆盖。

| 环节与主要承接 Skill | 补充检查的能力 | 判断依据与适用边界 | 调研依据 |
|---|---|---|---|
| 需求理解：`spec-brainstorm`、`spec-prd` | 识别消费者实际依赖的现有可观察行为（输出格式、顺序、错误信息、性能特征），而不只看文档承诺；当需求意味着改变这些行为时，把“保持旧行为”或“修正旧缺陷”作为需要业务 owner 确认的决策，而不是由 AI 选定 | 消费者少、行为纯内部时可说明不适用。反例：需求只写“修复排序”，未发现下游报表依赖旧排序 | R10、R1 |
| 需求理解：`spec-brainstorm`、`spec-prd` | 识别相关的非功能要求（性能、安全、可用性、兼容性、可观测性），并说明哪些不适用 | 不要求逐项填写质量属性清单，只要求和本次需求相关的属性有明确结论 | R1、R2 |
| 需求切片与任务拆分：`spec-plan`、`spec-write-tasks` | 涉及多个或外部消费者的不兼容变更（接口、schema、事件、配置格式）时，任务顺序能否保证每一步可单独发布和回退，例如扩展、迁移、收缩三步；单一内部调用者时允许直接修改 | 反例：先改接口签名再逐个修调用方，中间状态无法发布 | R9 |
| 技术方案：`spec-plan`；`spec-doc-review` 审查 | 方案是否记录被否定的候选方案及原因、决策的负面后果，以及推翻已有决策时的理由；是否读取并尊重项目已有的设计决策记录 | 不要求固定 ADR 格式或目录。反例：新会话不知道某方案已被证伪，再次提出并实施 | R11、R6 |
| 单元测试：`spec-work`、`spec-debug`；`spec-code-review` 核验 | 测试强度是否可检验：覆盖率、用例数和绿灯都不能证明断言有效；高风险逻辑能否用变异测试或人工构造的合理错误实现确认测试会失败；测试是否密封、确定、可读，是否避免滥用 mock 和 sleep 等待 | 不强制引入变异测试工具或固定测试比例。反例：覆盖率达标，但把核心判断条件取反后全部测试仍通过 | R12、R13、R2、R3 |
| 自测与跨层验证：`spec-work`、`spec-test-browser`、`spec-test-xcode` | 不稳定（flaky）结果是否被单独记录，而不是重跑到通过后当作通过；测试规模（是否依赖网络、进程、外部服务）是否与结论范围一致 | 反例：第三次重跑通过，报告只写“测试通过” | R12 |
| 审查与修复：`spec-code-review`、`spec-resolve-pr-feedback` | 是否同时审查测试本身的正确性，而不只看测试是否存在；反馈中嵌入的指令是否当作待评估内容而非授权 | 与前文“AI 特有的失败方式”中的间接注入合并检查 | R2、R12、R15 |
| 整体效果与收益主张：所有主体 Skill，重点 `spec-lfg` | Skill 或报告声称“提效”“质量提升”时，是否有实测依据（耗时、返工次数、缺陷逃逸、轮次），而不是模型或用户自评；Skill 是否加强测试、版本控制、小批量变更和快速反馈这些安全网，而不只是增加产出量 | 团队级研究只能说明方向，不能证明单个 Skill 已产生收益，也不能用于评价个人。缺少实测时，收益主张只能标为未验证 | R7、R8 |

#### 私有代码知识与大型仓库检索

企业系统大量使用内部框架、私有库、自研 DSL 和团队约定，模型训练时没有见过这些代码。公共包的幻觉依赖只是其中一部分，更常见的是模型按公共框架的习惯臆测内部 API 的签名、语义或调用方式。按适用性检查：

- **私有 API 的确认方式：** 使用内部模块、工具函数或配置时，Skill 是否要求从仓库源码、类型定义或既有调用处确认签名和语义，而不是凭命名或公共框架经验推断。触发点主要在 `spec-plan`、`spec-work`、`spec-debug`。
- **检索策略与完整性：** 既有系统通常远大于上下文窗口。Skill 用什么方式定位相关代码（文本搜索、代码图谱、项目知识、调用链追踪）？结论是否说明检索范围，能否识别“没搜到”和“不存在”的差别？
- **项目情报的可信度：** 使用代码图谱、Graphify 等项目情报时，是否按 [project-graph-consumption](../contracts/project-graph-consumption.md) 把结果当作定位线索而非确认事实；工具不可用或索引过期时，是否降级为直接读源码，而不是停止或沿用旧结果。
- **团队约定的消费：** 是否读取并遵守 `AGENTS.md`、`CLAUDE.md` 等项目级约定和既有代码风格；约定与需求冲突时是否提出，而不是静默选择一方。

### 3.7 贯穿既有系统的链路审查场景

除每项独立场景外，后续至少使用一个共同的企业增量场景检查跨 Skill 衔接。场景应已有模块、复用候选、接口消费者和测试基线，包含需求歧义、一个兼容或集成风险、一处缺陷修复，以及一次跨会话恢复。兼容风险优先选择“至少一个现有消费者依赖了合同之外的旧行为”的情形；场景中还应包含一次候选新依赖的引入判断，以及一条嵌有指令的外部反馈（例如 PR 评论），用于检查第 3.6 节第二轮补充要点。可以选择现有合适验证资产，不要求新建大规模演示系统；静态推演和实际执行分别报告。

场景须追踪“业务规则与验收 → 技术方案及复用决策 → 可验证任务 → 实现与测试 → 审查修复 → 总结及必要知识 → 交接恢复”。知识无复用价值时允许明确不沉淀；不适用的专项工具不强行参与。成功标准是各环节保留同一业务意图、关键约束和证据，消费者无需猜测，且恢复后不将局部完成误当整体完成。场景不能替代 22 项全量审查，也不能以合成任务成功宣称真实企业收益。

### 3.8 相对基线的增益与成本

前面各节回答“Skill 能否高质量完成目标”，还需要回答“与不加载 Skill 相比多带来什么”。模型能力在变化，某项 Skill 写得再充分，如果模型不加载它也能稳定做到，它的价值就只剩防护或一致性，同时仍有上下文和执行成本；反过来，Skill 也可能在某些任务上带来损失。

项目已有的证据很有限，不能作为任何方向的结论。[2026-08-20 基线报告](../../benchmarks/agentic/REPORT-20260820-sonnet5-saturation.md) 的原结论“零指导与加载指令无显著差异”已于 2026-09-20 勘误：复算后 baseline 21/21、spec-work 12/12、spec-debug 19/22，未做统计检验，只覆盖 5 个小任务和两个 Skill。`AGENTS.md` 顶部的提示仍沿用原结论，本次审查不得引用该提示作为依据。

每个主体 Skill 都要给出基线对照判断：

1. **对照设计：** 基线组使用相同任务材料、仓库和工具，但不加载该 Skill；对照组加载当前源码版本的 Skill。两组的评判标准在执行前确定。
2. **选择有区分力的场景：** 优先选择没有指导时模型容易出错的场景（例如第 3.6 节列出的 AI 失败方式、隐式行为依赖、需要停止或移交的边界），而不是任何组都能做对的简单任务。全部场景都饱和时，只能说明这些场景没有区分力，不能推出 Skill 没有价值。
3. **同时记录成本：** 记录上下文规模、轮次、时间或费用，以及多余动作（无关文件修改、过度询问、越权尝试）。
4. **结论分四类：** 有可观察增益、无可观察差异、有损、证据不足。必须写明样本数、模型与宿主，样本少时不声称统计显著。
5. **无差异时的处置建议：** 说明 Skill 在该场景防护的是哪种失败；没有可说明的防护目标时，建议精简、合并或改为按需加载。处置只是建议，实施另行承接。

6. **跨模型覆盖：** 两家厂商都要求用目标模型实测 Skill（R17、R22）。行为对照优先覆盖两个模型，并跨越厂商或能力档位（例如一个 Claude 模型和一个 GPT 模型，或同一厂商的高档和低档模型），因为在高能力模型上多余的指导，可能正是低档模型需要的。第二个模型经 S00 就绪事实基线确认不可用时，允许只测一个模型，但结论要标注“仅对该模型成立”，并记录不可用的原因与证据。就绪状态区分“命令存在、调用未验证、调用失败、评测可用”：版本或 dry-run 仅证明命令或配置可检查；评测可用须有经授权的最小真实调用及当前 Skill 加载证据，并绑定模型、引擎、环境和时间。调用失败须记录错误及受支持替代路径的检查结果，不能把一次暂时失败直接判为模型不可用。未执行、费用未获授权或数据外发未获授权均记为未验证／受阻，不满足单模型豁免条件；真实探测可在后续授权后补做并回填 S00 基线。
7. **按 Skill 类型解读：** 先判断 Skill 主要是“提升模型能力”还是“记录团队流程偏好”（R26）。前者无差异时，可能说明模型已经会了，可以按第 5 条建议精简。后者无差异时，不能据此判定多余，要检查它对团队流程、边界和出口门禁的忠实度。

没有执行基线对照时，结论只能写“未与基线对照”，不能写“有增益”或“已被模型内化”。内部依赖（S17–S19）可以只做静态判断：说明调用者依赖它提供的哪些确定性保护，以及缺少它时调用者会承担什么风险。

### 3.9 面向模型演进的 Skill 工程审查

前面各节审查 Skill 的研发方法是否专业，本节审查 Skill 作为写给模型的指令是否写得对。依据是 Anthropic、OpenAI 的官方指引和开放 Agent Skills 标准（调研记录 R17–R25）。两家厂商的建议方向一致：

- 模型越强，Skill 越应该只写模型不知道的内容：项目事实、不变量、边界和验证方法。
- 指令遵循越来越字面，为旧模型写的强调和补丁会变成新问题。
- 自主运行时间变长，越界、虚构进度和停止时机成为主要风险。
- 模型更新很快，Skill 必须跨模型、跨宿主成立。

这些建议描述的是厂商自己的模型，只作为审查线索，不自动成为项目规则。它们与项目原则冲突时，按项目角色契约取舍并写明理由。最典型的冲突是 OpenAI 建议“偏向行动、减少审批”，而项目要求外部副作用需要授权。

每个审查对象按适用性检查下表各项。检查的是效果和风险，不要求 Skill 采用固定写法；已有等价机制即视为覆盖。

| 检查点 | 要回答的问题 | 典型反例 | 依据 |
|---|---|---|---|
| 增量知识 | 正文和 references 中，哪些是模型不知道的项目知识、不变量、边界或验证方法，哪些是模型已经会的通用工程常识？通用常识是否占了大部分篇幅？ | references 用数千行解释通用的需求分析或代码审查方法，项目特有的约束只有几行 | R17、R20、R24 |
| 自由度与风险匹配 | 固定步骤、确定性脚本和绝对措辞是否只用在正确性、安全、权限或真正脆弱的操作上？开放判断是否给出目标、判断依据和边界，而不是规定步骤？脆弱操作是否交给脚本，脚本是否自己处理错误？ | 对代码审查规定固定的十步流程；对 git 推送只写一句“注意安全” | R17、R24；项目“脚本负责确定性地板，模型负责语义判断” |
| 历史补丁与过度执行 | 是否残留为旧模型写的强调措辞、反偷懒提示、“拿不准就用某工具”、显式自我复查或“用子代理验证”这类步骤？在当前模型上，它们是否造成过度触发、过度验证、过度提问或范围扩大？ | 每个非平凡任务都强制一轮额外验证，小改动也跑全量测试 | R18、R19、R22 |
| 字面执行与过滤 | 是否有会被字面执行而丢失信息的过滤指令，例如审查时“只报高置信或高严重度问题”？是否应改为先报全、再单独过滤或分级？ | 审查 Skill 要求保守报告，真实的中等问题被丢弃 | R19 |
| 硬约束与验证要求的区分 | 能删掉的是“提醒模型再检查一遍”这类思考指令；必须保留的是项目的出口门禁：完成声明要有证据，副作用要有授权，交接要带新鲜度。审查建议删减时，要说明被删内容是哪一类 | 为了减少过度验证，把“声称测试通过必须附命令结果”也删掉 | R19、R20；项目“gate the exits, not the thinking” |
| 指令优先级与冲突 | Skill 与用户当前指令、`AGENTS.md`、`using-spec-first` 及其他 Skill 之间有没有冲突或含糊？是否写明用户指令优先？Skill 让模型暂停、提问或偏离用户意图时，能否指出依据的是哪个文件的哪条规则？ | 两份规则对同一情况给出不同要求，模型停下来反复询问 | R22 |
| 停止、询问与续跑 | 只在会改变结果的信息缺失、或动作不可逆/有外部影响时才停下询问吗？询问前是否先完成已授权的工作，让用户批准的是一个具体可审的结果？无人值守运行中，文本结束的回合是否只被当作进度报告，是否有未完成清单和有上限的续跑？ | 一开始就问五个问题；或无人值守流程在“我接下来会运行测试”之后停止，被当作完成 | R20、R21、R22 |
| 进度声明取证 | 长任务中的状态报告、完成声明和交接摘要，是否要求与实际工具结果逐项核对？ | 交接文档写“测试已通过”，但会话中没有执行记录 | R20；项目“transcript 中的声明不是证据” |
| 子代理与独立验证 | 是否说明什么情况值得委派、什么情况直接做，以及并发或数量上限？需要独立验证时，是否使用新上下文的验证者，且不把预期答案或已有结论交给它？是否在重建宿主已经提供的能力？ | 简单的 grep 也派子代理；独立评审拿到了作者的结论草稿 | R19、R20、R22、R24 |
| 推理外显 | 是否要求模型在回复中逐字写出或按固定格式写出推理过程？这类要求在 Claude 新模型上可能被拒绝（reasoning_extraction）。要求简短说明理由或依据不受影响 | personas 或模板中要求“完整写出思考过程”字段 | R19、R20、R21 |
| 描述与可发现性 | description 是否写明做什么和何时用，并把关键用途和触发词放在前面？只在容易误选时才写排除条件吗？Skill 很多时，宿主会缩短或省略描述，这批 Skill 的描述总长是否会触发这种情况？内部辅助 Skill 是否会被宿主在没有调用方授权时隐式选中？ | 描述开头是长串免责声明，被截断后只剩“不要用于……” | R17、R23、R25 |
| 渐进披露与引用深度 | 入口是否短到足以快速判断方向，同时保留关键约束？关键门禁和授权规则是否在 SKILL.md 或一级引用中？二级及更深的引用是否承载了必须读到的内容？长引用文件是否有目录？ | 授权边界只写在三级引用中，模型只读了前 100 行 | R17、R25 |
| 时效与模型绑定 | 正文是否写死了模型名、宿主版本、工具行为或日期，而这些会过期？针对某个模型的调优是放在可移植的 Skill 正文里，还是放在宿主适配层？ | Skill 写“Claude 会过度委派，所以禁止子代理”，换模型后失去意义 | R17、R18 |
| 外部内容标记 | 把 PR 评论、issue、网页、日志或用户粘贴的内容交给模型或子代理时，是否明确标出这是外部数据？ | 把 PR 评论原文直接拼进子代理指令中 | R21、R15 |
| 评测设计 | Skill 自带的 evals 测的是可观察行为还是措辞、标题和正则匹配？是否有无 Skill 基线和多模型结果？是否记录模型实际读了哪些文件，从未被读取的引用能否删除？ | eval 只检查输出中是否出现某个章节标题 | R17、R24 |

调研记录第 3.1 节有一组 2026-11-01 采集的确定性统计线索：行数、references 体量、嵌套引用、描述总长、强制措辞计数、内部辅助的调用策略。正式审查时要重新取数并绑定版本。这些数字只提示从哪里看起，好坏由审查者判断：计数高不等于写得差，计数低也不等于没有问题。

**删减建议的要求：** 模型能力提升后，有效的改进常常是删除。建议删除或精简某段内容时，要写明：这段内容原本防护什么失败；当前模型在不加载它时是否已不再出现这种失败（引用第 3.8 节的基线证据或说明未验证）；删除后用哪个场景验证没有退化。出口门禁类内容不能仅因“模型已经会”而删除。

## 4. 源码范围与证据规则

1. 对全部 22 项逐个完整阅读 `SKILL.md`，并完整读取影响其目标、执行、产物和验收的引用、模板、脚本与合同。沿引用追踪相关共享依赖及真实上下游消费者，不以抽查代替逐项覆盖。
2. 为每项建立阅读清单：路径、依赖类别、作用、读取状态、关联结论与版本标识；条件依赖标明触发条件。清单至少包含正文、直接行为依赖、相关共享合同和真实上下游消费者中影响该 Skill 合同的部分。按正文引用、脚本调用和产物读写关系发现依赖；新增相关引用必须回填，不能只按目录或显式链接判断范围。**阅读范围（2026-11-01 试点后调整）：** 必须完整阅读 `SKILL.md` 和各 Phase 或步骤明确要求必读的 reference；只在授权派发时加载的 worker 提示（如 `references/agents/`）和只决定输出格式的渲染文件，在与当前判断相关时才读，并在阅读清单中逐项记录不读的理由。脚本按其承担的出口约束（授权、写入范围、校验）优先阅读，其余可以用测试断言和场景结果作为证据，并在清单中注明。排除项记录不影响本项目标判断的理由。共享文件在版本相同时允许一次完整阅读、多项引用；无关消费者实现不要求递归展开。只有影响定位、执行、产物和验收判断的依赖均已覆盖、没有待解析的相关引用时，才能标记阅读完成。未读或不可用的关键依赖必须记录为覆盖缺口；输出截断须补读。
3. 使用 `skills/`、`templates/`、`src/cli/` 与现行合同作为实现依据；宿主运行时镜像仅用于识别投射差异，不作为修改源。
4. 记录读取时间、审查时的 commit 和相关未提交状态。干净的已跟踪文件以 commit 与路径标识；实际作为结论依据的已修改、暂存或未跟踪文件必须记录所读内容的 SHA-256，不能用 HEAD 或“已修改”状态代替内容版本。读取前后发现版本变化时重新读取并绑定结论；交付前核对相关文件版本，仅对变化影响的结论复核。hash 用于识别版本，不能还原内容；若结论必须支持历史重放，则在许可范围保留对应内容快照或差异。无需冻结整个仓库，不改动其他任务工作树。
5. 每个关键结论提供具体路径、章节或行号，并解释“实现事实 → 研发影响 → 判断”。判断缺失能力时必须说明已检查的相关范围，避免由未搜索到推断不存在。
6. 区分四种证据：结构与合同、行为与语义质量、运行成本、真实任务效果。脚本通过、模型自评或文档存在，只能支持对应范围的结论。
7. 脚本负责路径、schema、hash、命令退出状态等确定性事实；审查者负责定位合理性、方案取舍和语义充分性。不能用关键词命中替代质量判断。第 3.9 节使用的统计（行数、references 体量、引用深度、描述长度与总长、强制措辞计数、调用策略字段）属于脚本可采集的事实，正式审查时用可复跑的命令重新采集，记录命令与版本；这些数字只用于定位检查重点，不能直接作为“写得好或差”的结论。
8. 已有测试必须核对实际断言、运行版本和覆盖范围。没有执行的验证标为未执行；fixture、模拟环境和真实宿主结果分别记录。
9. 行为证据还要绑定模型（含版本）、推理强度或 effort 设置、宿主和可用工具（例如是否有 subagent、MCP、浏览器或 XcodeBuildMCP），只对记录的组合成立。厂商说明同名 effort 档位在不同模型上对应的思考量不同（R21），跨模型对照时不能只按档位名称对齐。每项结论写明重新评估的条件，至少包括更换模型、更换宿主、关键工具不可用和 Skill 源码变化。
10. 复用已有验证资产：`docs/validation/`、`benchmarks/` 与 CHANGELOG 记录的既往验收试验可以作为场景输入、评判标准或对照起点。复用前核对其绑定的源码版本、模型和宿主是否仍适用，记录复用、需重做或已失效的判断；历史失败和历史限制一并保留。复用资产可以减少重复工作，但不能把历史“通过”直接当作本次结论。

## 5. 审查过程与场景检验

后续按“核实定位 → 选择研发视角并核验相关业界实践 → 建立专业能力基准 → 完整阅读与依赖覆盖 → 多视角能力映射与充分性分析 → Skill 工程检查（第 3.9 节） → 场景推演或验证 → 基线对照 → 上下游核对 → 记录结论”推进，并即时更新审查报告总表。本需求中的清单保持范围基线，后续进度以审查报告为准。

### 5.1 试点、分批与审查深度

本需求的全部要求同时作用于 22 项，工作量很大，容易退化为机械填表。执行顺序如下：

1. **最先审查 S00 `spec-runtime-setup`：** 按第 2.2.1 节完成审查，产出后续场景可以引用的就绪事实基线：在隔离环境中各工具的就绪状态、降级行为和已知限制。S00 存在 P0 问题时，先报告并等待处置决定，再开始后续批次；存在 P1 问题时，后续依赖相应工具的行为场景须标注该限制。
2. **然后审查 S20 `using-spec-first`：** 它决定后续场景中请求是否能进入正确的 Skill。试点前完成静态审查、场景设计和路由评测能力确认；能力尚未实测时标明待验证，不声称路由正确率已确认。S20 此时标为“静态完成，行为评测待执行”。预算与必要授权确定后补齐行为及基线对照，在依赖实际入口路由的链路行为场景之前完成；试点可直接加载 S04 当前源码评测，不能将其结果当作入口路由证据。整体完成前 S20 必须达到行为完成。S20 存在 P0 问题时同样先报告。
3. **试点：** 先用 S04 `spec-plan` 完整走一遍。它承接需求理解、既有架构适配和复用决策，覆盖第 3.6 节多数环节。`spec-plan` 的 references 体量最大、嵌套引用最多，也适合检验第 3.9 节的增量知识和引用深度检查是否可操作。试点结束后评估：哪些要求产生了实际发现，哪些只增加了篇幅，单项实际耗时多少。S00 和 S20 是前提对象，职责与研发链路 Skill 不同，不作为方法校准的试点。需要调整本需求时，修改内容和理由记入变更记录，不在后续审查中静默降低标准。
4. **分批：** 试点后按链路分批推进。建议顺序是主线上游（S01–S05）、实施与审查（S06、S21、S07、S10、S13）、知识与交接（S08、S14、S15）、编排与专项（S09、S11、S12、S16）、内部依赖（S17–S19）。每批结束时完成该批的链路衔接核对。
5. **审查深度分两档：**
   - **完整深度：** S00（按第 2.2.1 节调整重点）、S20（按第 2.4.1 节调整重点），以及主线 S01–S08、S10、S13、S14、S16。执行本需求全部要求。
   - **聚焦深度：** S09、S11、S12、S15、S21 和内部依赖 S17–S19。完整阅读、能力基准、三类场景、业界对照和结论要求不变；研发视角只分析适用项，可不参与第 3.7 节共同场景，基线对照可以只做静态判断。
   
   默认分档可以按试点结论调整，调整时说明理由。聚焦深度不是抽查，不能跳过阅读覆盖或场景记录。
6. **单项完成分两级：** “静态完成”要求定位说明、能力基准映射、阅读清单、三类场景（允许静态推演）、问题与建议和设计充分性结论齐备；“行为完成”还需要实际执行的场景证据和基线对照。总表分别标注，不能用静态完成代替行为完成。
   - **最低行为覆盖：** S20、S04、S06、S07、S10 必须达到行为完成。这 5 项分别承担入口、规划、实施、审查和诊断，没有它们的行为证据，第 1 节第 5 问就没有实测答案。确实无法完成时，写明原因与补证路径，整体审查不得标为完成。
7. **资源上限与停止条件：** 试点结束后，按实测定出每项预算（审查时长和评测运行次数），写入审查主文档；整体总预算在试点后再次确认。单项超出预算的 1.5 倍时停止扩张，从三种处理中选一种：降为聚焦深度、拆到下一批，或回到本需求重新取舍。选择和理由写入审查主文档。
8. **评测用例先审后用：** 行为评测前，先按结果、过程、风格、效率四类成功标准（R27）和第 3.9 节“评测设计”检查点审查所用用例。只匹配输出措辞的用例不作为行为证据。

### 5.2 关键结论的独立复核

以下结论必须经过一次独立复核后才能定稿：P0、P1 问题；“存在关键缺口”的设计结论；以及基线对照中“有损”或“无可观察差异且建议精简”的判断。

复核按 [fresh-source eval checklist](../contracts/workflows/fresh-source-eval-checklist.md) 进行，由未参与原审查的新上下文读取当前源码和原结论依据，独立判断结论是否成立。记录复核者上下文、读取版本、同意或不同意的理由；意见不一致时保留双方依据，由审查者结合证据裁决并写明理由。宿主无法派发独立复核时，结论标为“待复核”，不能作为已定稿结论进入实施建议排序。

### 5.3 场景检验

每项至少检验三个与其定位相符的场景：正常路径、关键信息缺失或冲突、失败或中断恢复。按风险补充小任务短路径、复杂跨模块变更、高影响副作用等场景；不机械要求每项覆盖所有技术栈。

第 3.9 节的检查点需要行为证据时，可以在已有场景中加入以下变体，不要求额外增加场景数量：

- **小任务短路径：** 检查是否过度验证、过度提问、扩大范围或委派过多。
- **规则冲突：** 用户指令与 Skill 或 `AGENTS.md` 的要求冲突，检查是否按优先级处理并指出依据。
- **长任务或无人值守中断：** 检查进度声明是否与工具结果一致，停止和续跑是否恰当。
- **嵌入指令的外部内容：** 检查是否当作数据处理。

场景推演或执行前，先依据能力基准确定预期结果；不能在看到输出后反向调整合格标准。每项至少有一个反例，用于区分“形式合规”与“专业正确”，可纳入上述三类场景，无需为数量额外造例。例如，故障诊断只让失败测试变绿却未排除同根问题，或计划章节齐全却遗漏必需的兼容约束，不能据此判为专业能力充分。

每个场景记录以下内容；任何预期变更须保留原判据及变更理由：

| 记录项 | 要求 |
|---|---|
| 场景编号与能力关联 | 对应哪项定位目标和必备能力 |
| 输入与关键约束 | 具体任务材料、上下文、前提和权限边界 |
| 预期行为与产物 | 应作出的关键判断、动作及可供消费者使用的结果 |
| 不可接受行为 | 即使格式合规或局部检查通过，也不能接受的错误 |
| 结果判据 | 能区分符合、不符合和证据不足的可观察事实，不以套话或自评为准 |
| 证据类型与结果 | 静态推演或实际执行、对应版本、证据位置、实际观察及限制；未执行不得填写为执行通过 |

静态推演与实际执行分开记载。行为验证需要时采用当前源码的新上下文评估或等价独立验证；实际评测遵循 `skill-upper` 的适用指引。不能运行时记录缺失能力、未验证的具体主张和最小补证方法。对远程写入、发布等场景先核对独立授权，不为完成审查产生真实外部副作用。

单项完成后核对链路衔接，尤其是需求到计划、计划到任务或实现、实现到审查、问题到修复、结果到知识、会话到交接，以及内部 Git 辅助与调用者之间的责任边界。需求覆盖、测试策略、迁移兼容、安全和可观测性等跨阶段责任应检查是否有明确归属，避免各 Skill 局部完整而整体遗漏。

## 6. 后续审查报告的交付结构

后续在 `docs/project-reviews/` 建立一份审查主文档，引用本需求，集中维护总表及逐项分析。必要的原始证据可单独存放并链接，不要求复制全部源码。

每个 Skill 的分析必须包含：

- 详细定位与目标说明：覆盖第 3.1 节全部要素，并区分声明目标、实际支持范围和建议目标。
- 专业能力基准、合格产物标准及逐项源码能力映射。
- 产生发现的研发视角、关键发现及冲突取舍（第 3.4 节）；明确是否经过独立复核。
- 已核验业界实践的来源、适用条件、本地对照、采用建议和验证方式，以及未完成的对照项。
- 源码版本与未提交依据文件的 SHA-256、完整阅读清单、依赖排除理由及覆盖缺口。
- 场景输入、预期、反例、结果判据、证据类型与实际观察。
- 企业既有系统专项能力映射：按第 3.6 节记录职责、现有机制、关键缺口与质量判断；关联第 3.7 节的链路场景，不用重复表述替代取证。
- 已具备的专业能力及依据。
- 问题、触发场景、影响、源码依据与反例。
- 可保留的设计、最小优化建议及其验证方法。
- 逐目标达成分析：将每个核心目标和必要子目标关联到专业方法、源码支持、产物质量标准、场景证据及剩余缺口。
- 设计充分性结论、行为证据状态、真实任务证据状态和剩余限制，并直接回答“在什么前提下，现有 Skill 能否高质量完成其目标，判断依据是什么”。
- 基线对照：对照设计、场景、样本数、模型与宿主、成本记录、四类结论之一及无差异时的处置建议；未执行时写明“未与基线对照”。
- 审查深度档位、完成级别（静态完成或行为完成）、关键结论的独立复核状态，以及复用的既有验证资产及其适用性判断。
- 第 3.9 节 Skill 工程检查：逐项适用性与判断、重新采集并绑定版本的统计事实，以及删减建议的防护目标、基线依据和验证场景。

问题统一编号，记录所属 Skill、严重程度、根因、建议改动位置、预期收益、复杂度、依赖和验收方式。共享问题合并根因并保留全部受影响 Skill 映射，避免重复建设。

审查进度使用“未开始、进行中、已完成、受阻”。设计结论使用“充分、条件充分、存在关键缺口、证据不足”，必须给出理由；行为与真实任务证据另列。不得用一个总分掩盖关键缺陷或证据缺失。

目标达成结论必须说明关键缺口是否阻断核心目标。存在阻断缺口时，不能因其他维度表现良好而给出整体充分结论；缺少实际行为证据时，只能判断设计是否足以支持目标，实际达成能力保留未验证。优化建议必须关联受影响目标，说明补齐后如何验证质量提升。

建议优先级按影响排序：P0 为越权、破坏或虚假完成等严重风险；P1 为核心定位目标无法可靠达成；P2 为质量、衔接或恢复能力不足；P3 为低影响表达与维护改进。优先级需有具体场景支持，不按文档篇幅或个人喜好排序。

第 3.9 节发现的指令工程问题同样按影响定级，而不是按“写法是否符合厂商建议”定级。例如：
- 规则冲突或含糊导致越权动作、虚假完成，或内部辅助在未授权时被隐式调用，属于 P0。
- 关键门禁放在可能读不到的深层引用中，导致核心目标在实际运行中不可靠，属于 P1。
- 历史补丁造成过度验证、过度提问或成本明显上升，属于 P2。
- 措辞、篇幅和格式的改进属于 P3。

没有场景证据时，指令工程问题最高定为 P2，并注明“待场景验证”。

### 6.1 审查本身的价值检验

审查报告不能只以“已完成”作为价值证据。每条 P0、P1 建议都要写明落地后的验证方式：用哪个场景、对比哪个版本、期待什么可观察变化。建议实施后（另行承接），按这些验证方式复测，并在审查主文档中回填结果：问题是否消失、是否引入新问题、Skill 成本是否变化。没有回填前，这些建议只能视为预期收益，不能视为已兑现的改进。

试点结束后，还要记录审查自身的投入与产出：耗时、发现的问题数量与级别，以及哪些审查要求没有产生任何发现。这些数据用于调整后续批次的审查深度。

## 7. 验收标准

### 7.1 本轮需求文档

- 明确用户目标、跨技术栈审查视角及专项边界。
- 包含完整的 16 个主体 Skill、3 个内部依赖、运行时前置对象 S00 `spec-runtime-setup`、入口路由 S20 `using-spec-first`、行为保持重构 S21 `spec-simplify-code` 及可访问源码入口，并明确 S00 最先审查、S20 其次。
- 明确逐项审查方法、证据要求、报告结构和完成条件。
- 全部审查状态保持未开始，不预填结论，不冒充已经执行审查。
- 包含相对基线的增益判断（第 3.8 节）和面向模型演进的 Skill 工程审查（第 3.9 节），外部依据均可在调研记录中追溯到已读章节，未读部分有标注。
- 第 2.4 节对其余 14 个 Skill 逐项给出纳入或不纳入的决策、依据和重新评估条件；纳入的 S20、S21 已进入第 2.1 节范围表、第 5.1 节批次与深度安排。
- 文档可访问，并明确本轮不包含 Skill 修改或审查执行。

### 7.2 后续整体审查

- 22 项全部逐项处理，总表与详细分析一一对应，无静默遗漏或抽查替代。
- S20 在 S00 之后、试点之前完成静态审查和场景设计，并记录路由评测能力的确认结果或待验证限制；行为及基线对照在预算与必要授权确定后、依赖实际入口路由的链路行为场景之前完成，覆盖第 2.4.1 节重点，已知问题 K-01 有影响判断与修复建议；第 2.4 节中“不纳入、作为依赖读取”的部分在对应审查项的阅读清单中可追溯；任何触发重新评估条件的发现都已回到范围决策。
- S00 `spec-runtime-setup` 最先完成审查，覆盖第 2.2.1 节各项重点，行为场景均在隔离环境执行或注明未执行；产出的就绪事实基线被后续依赖工具的场景引用，S00 的 P0/P1 问题对后续场景的影响已标注。
- 每项均有详细定位与目标说明，覆盖第 3.1 节全部要素；不能以简介复述代替理解。
- 每个核心目标及必要子目标都有质量标准、能力与源码映射、场景证据和达成判断，不能遗漏不易验证的目标。
- 每项均按第 3.4 节记录产生发现的研发视角及其分析和取舍，其余视角合并列名；不得把多视角分析表述为独立多方验证。
- 每项至少有一条与核心目标相关的已核验业界实践对照；来源、适用条件、源码映射与采用建议可追溯。未完成项保留待补证状态，不能将整体业界对照标为完成。
- 每项均有独立于现有内容建立的专业能力基准、合格产物标准和源码映射；缺失能力不能因正文未提及而免审。
- 每项结论明确回答能否高质量完成目标、适用前提、判断依据及限制；目标阻断问题不得被其他维度的优点抵消，缺少运行证据不得声称实际能力已验证。
- 每项阅读清单覆盖所有影响目标判断的相关依赖，排除理由可检查，共享阅读可追溯，没有未解析的关键引用。
- 作为结论依据的未提交文件均绑定所读内容的 SHA-256；交付前完成版本核对及受影响结论复核。
- 每项至少有三类场景记录，覆盖具体输入、约束、预期行为、不可接受行为、结果判据与证据类型；其中至少一个反例能区分形式合规与专业正确。
- 关键结论可回源；问题可定位、可解释影响，建议可实施、可验证。
- 明确单项与链路中的责任缺口、重复责任及交接不一致。
- 第 3.6 节各研发环节均有责任归属与能力判断；重点核验既有架构与复用、单测与自测、修复闭环以及总结/知识/交接的差异，不能用从零演示或格式检查代替。
- 第 3.6 节“第二轮调研补充的审查要点”逐行有责任归属和判断，包括隐式行为依赖、不兼容变更排序、决策理由留存、测试强度检验、flaky 结果处理、幻觉依赖、间接注入、过度代理和收益主张证据；不适用时说明理由。
- 完成至少一个第 3.7 节的共同增量场景，记录需求、设计、任务、验证与恢复的实际衔接或推演结果；明确尚未实际执行的部分。
- 每项都区分设计充分性、实际行为证据和真实任务结果，保留失败与未验证事实。
- 每个主体 Skill 都有第 3.8 节的基线对照结论或“未与基线对照”的明确标注；无差异结论写明场景的区分力和 Skill 的防护目标，不以场景饱和推出 Skill 无价值。
- 试点已完成并记录对本需求的调整及理由；每项标明审查深度档位和完成级别，总表不混用静态完成与行为完成。
- 第 5.2 节规定的关键结论均已完成独立复核，或标为“待复核”且未进入已定稿的实施排序。
- 行为证据均绑定模型、宿主与可用工具，并写明重新评估条件；复用的既有验证资产均有适用性判断。
- 第 3.3 节“人工审阅成本”和第 3.6 节“私有代码知识与大型仓库检索”在适用的 Skill 上有判断。
- P0、P1 建议均有落地后的验证方式；试点记录了审查投入与产出。
- 每项都完成第 3.9 节检查表的适用性判断；指令优先级冲突、历史补丁造成的过度执行、内部辅助的隐式调用风险有明确结论。删减建议都区分了思考指令和出口门禁，并附防护目标与验证场景。
- 行为对照覆盖至少两个模型；第二个模型经 S00 就绪事实基线确认不可用时，结论标注只对单一模型成立并记录原因与证据；仅有版本或 dry-run、尚未调用或尚未取得必要授权，不满足豁免条件，跨模型验收保持未完成（第 3.8 节第 6 条）。
- S20、S04、S06、S07、S10 达到行为完成，或写明原因与补证路径且整体审查未标为完成；资源预算与超限处理记录在审查主文档（第 5.1 节第 6、7 条）。
- 如有关键源码覆盖阻塞，整体审查保持未完成；如仅缺实际运行证据，可完成静态审查，但不得声称能力或实际效果已获验证。
- 汇总建议的实施顺序、依赖和补证要求；实施另行承接，不通过审查报告自动授权修改。
