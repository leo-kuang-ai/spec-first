# From request bytes to a visible entry

A `POST /entries` changes shared state only when its request stream emits
`end`, its accumulated body parses successfully, and the handler reaches
`entries.push(...)`. A subsequent `GET /entries` serializes that same
in-memory array. The POST response acknowledges the append; it does not
make the entry durable.

This explanation comes from static inspection of the supplied fixture.
The application and tests were not run. Source references below use the
repository-relative fixture root:

`docs/validation/ce-skill-optimization-2026-10-29/remaining-27-acceptance/wave1/fixtures/explain/`

The implementation is `src/server.js`; the accompanying description is
`README.md`.

## The request lifecycle

The server listens on port `3000`. Its request callback selects routes by
exact method and URL equality: `POST /entries` appends, `GET /entries`
lists, and other requests receive `404` with `not found`. A URL such as
`/entries?limit=10` does not match either route because the code compares
`req.url` directly rather than extracting its pathname.
(`src/server.js:5–6`, `16–25`)

```mermaid
sequenceDiagram
    participant P as POST client
    participant H as HTTP request handlers
    participant S as Shared entries array
    participant G as GET client

    P->>H: POST /entries
    Note over H: Create request-local body string
    P->>H: data events
    Note over H: Append each chunk to body
    P->>H: end event
    H->>H: JSON.parse(body or "{}")
    alt Parsing and property extraction succeed
        H->>S: Push generated id, amount, note, timestamp
        H-->>P: End response with "ok"
        G->>H: GET /entries
        H->>S: Read and JSON.stringify entries
        H-->>G: application/json response
    else Parsing or property extraction throws
        Note over H: No local catch; append and "ok" are not reached
    end
```

The successful branch has five steps:

1. **Allocate a body buffer for this request.** `let body = ''` runs
   inside the POST branch. Concurrent POST requests therefore have
   separate buffers. (`src/server.js:6–7`)
2. **Collect incoming chunks.** Each `data` event appends its chunk to
   that request’s string. Receiving a chunk does not append an entry.
   (`src/server.js:8`)
3. **Wait for `end`, then parse.** The `end` listener parses the complete
   accumulated string, substituting `'{}'` only when the string is empty.
   It extracts `amount` and `note`. (`src/server.js:9–10`)
4. **Append to shared state.** The new object receives an ID from the
   current array length plus one, the two extracted fields, and a
   timestamp from `Date.now()`. (`src/server.js:11`)
5. **End the response.** `res.end('ok')` follows the mutation.
   (`src/server.js:12`)

The `return` at line 14 exits the initial routing callback after
registering the listeners. It prevents the request from falling through
to the other routes; it does not cancel the listeners or perform the
append itself.

## Ownership determines what survives

| Value | Owner and lifetime | Consequence |
|---|---|---|
| `body` | One POST handler invocation | Bytes from different requests are not intentionally combined. |
| Parsed `amount` and `note` | One `end` callback | These values become fields of the appended object. |
| `entries` | Module-level array, shared by this server’s handlers | Later GET handlers see prior successful appends in the same running instance. |
| `id` and `ts` | Generated by the server at append time | Client-supplied `id` and `ts` are not copied into the entry. |
| Response | The individual request’s `res` object | Ending a response is distinct from storing state. |

The shared ownership is visible at `src/server.js:3` and `5–18`.
`README.md:6` also explicitly says data is kept in memory.

For a first successful POST with this body:

```json
{"amount":12.5,"note":"Lunch"}
```

the appended object has `id: 1`, `amount: 12.5`, `note: "Lunch"`, and a
numeric timestamp generated during the append. A later GET emits an array
containing that object. Its response explicitly sets
`content-type: application/json`; the POST success response is the text
`ok`, with no explicit status or content-type assignment in that branch.
(`src/server.js:10–12`, `16–18`)

There is no database, file write, or reload path in the supplied server.
Starting a new instance initializes `entries` to `[]`. Nothing here
establishes shared state across multiple server processes.

## Visibility follows callback execution, not arrival order

The decisive event is execution of `entries.push`, not arrival of the
POST headers or its first body chunk.

A GET handled while a POST is still collecting data serializes the array
before that POST’s append. A GET handled after the append includes the
entry, provided it reaches the same running instance. The POST’s
parse–push–response sequence contains no `await` or other asynchronous
handoff, so another request callback does not run between those statements
during ordinary JavaScript execution. (`src/server.js:9–12`, `16–18`)

Two overlapping POST requests are ordered by execution of their
successful `end` callbacks. A request that arrives first can finish its
body later and receive the later ID. The IDs express append order in the
current array, not necessarily request arrival order.

GET immediately calls `JSON.stringify(entries)` and passes the resulting
string to `res.end`. An append after that serialization cannot alter the
already-created response body. Network delivery may happen later; that
does not make GET a live view. (`src/server.js:18`)

## Malformed JSON fails before mutation

The critical sequence is short:

```js
const { amount, note } = JSON.parse(body || '{}');
entries.push({ id: entries.length + 1, amount, note, ts: Date.now() });
res.end('ok');
```

Source: `src/server.js:10–12`.

If the body is malformed JSON, `JSON.parse` throws before `entries.push`.
This request therefore adds no entry through this path and does not reach
the `ok` response. The fixture supplies no `try/catch`, error response, or
exception handler for this failure. It does not implement a controlled
`400` response. In ordinary standalone Node.js execution, an uncaught
exception can terminate the process; the fixture provides no evidence of
an external handler or supervisor that changes this outcome.

Successful JSON parsing is also not input validation:

| Body | Consequence in this handler |
|---|---|
| Empty body | Parses the fallback `{}`; appends an entry with undefined `amount` and `note`. |
| Whitespace only | Does not use the fallback; parsing throws. |
| `{"amount":12.5}` | Appends with `note` undefined. |
| `null` | Parses successfully, but destructuring `null` throws before the append. |
| `{"amount":"twelve","note":false}` | Appends those values without type checks. |

When GET serializes an object, fields whose values are `undefined` are
omitted. Thus an empty-body POST can produce a GET entry containing only
`id` and `ts`, even though the pushed object was constructed with all four
property names. The server checks neither required fields nor types, and
does not inspect the request’s content type. (`src/server.js:6–12`,
`16–18`)

## Cancellation and recovery have narrow guarantees

**Before the append, there is no new entry.** If a request never reaches
its `end` callback, the only append site cannot run for that request.
However, the server has no explicit `aborted`, `close`, or `error`
listeners, cancellation token, or timeout policy. The fixture alone does
not establish the precise event sequence or client-visible outcome of
every disconnect. (`src/server.js:7–13`)

**After the append, losing the response does not undo it.** There is no
rollback code. The client could lose its connection after the entry is
stored but before it receives `ok`. A missing acknowledgement therefore
does not prove that nothing changed. (`src/server.js:11–12`)

**Retrying can duplicate the expense.** Every successfully handled POST
appends a new object; there is no idempotency key or duplicate check.
Resending a request after an uncertain response can create another entry
with a new ID. A GET can reveal the current array, but the POST response
does not return the generated ID and the request has no stored unique
correlation token, so identical submissions can remain ambiguous.
(`src/server.js:10–12`, `18`)

**Recovery after process loss is not implemented.** A restart creates a
fresh empty array. There is no persisted log to replay, and IDs can start
again at `1`. An uncaught malformed-body failure may therefore affect
previously stored entries through process loss, even though the failing
request itself never reaches the append. (`src/server.js:3`, `10–11`)

These are source-derived boundaries, not observations from disconnect,
crash, or recovery experiments.

## What the evidence says about rationale

The README calls MiniLedger “a tiny personal expense-tracking demo app”
and documents its two endpoints and in-memory data.
(`README.md:3–6`) That establishes the stated purpose.

The implementation’s causal relationships are also clear: collecting
chunks provides the string parsed at `end`; sharing one array allows GET
to expose successful POST appends; placing the response after the append
makes `ok` follow the mutation.

Neither the source nor the README records why the original author chose
in-memory storage, length-based IDs, or omitted validation and recovery.
Those choices have observable consequences, but attributing them to
performance goals, deliberate reliability trade-offs, or a particular
design philosophy would go beyond the evidence.

The README’s statement that adding an entry requires “five fields typed
by hand” (`README.md:8`) does not establish this HTTP handler’s input
contract. The supplied server extracts only `amount` and `note`, generates
`id` and `ts`, and enforces no required fields.

## Check yourself

1. A POST has delivered half its body when a GET is handled. Does that GET
   include the pending expense?
2. A client sends malformed JSON, then retries with an empty body. Are
   these equivalent failures?
3. A client receives no `ok` and retries. Can it assume that only one entry
   will exist?

---

**Answers**

1. No. Receiving body chunks changes only the request-local string. The
   shared array changes later, when the `end` callback successfully reaches
   `entries.push`.
2. No. Malformed JSON throws before the append. An empty body becomes
   `{}` and can append an entry whose `amount` and `note` disappear from
   the JSON representation. This assumes the server is still running;
   the malformed request has no local exception handling.
3. No. The first append may have succeeded before acknowledgement was
   lost. With no rollback or idempotency mechanism, a successful retry can
   append a second entry.
