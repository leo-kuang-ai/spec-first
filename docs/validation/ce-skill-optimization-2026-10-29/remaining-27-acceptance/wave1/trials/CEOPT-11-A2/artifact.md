# How a POST becomes visible through GET

**The write happens when the POST request emits `end`.** The server parses the accumulated body, appends one object to a shared in-memory array, and then ends the response with `ok`. A GET handled after that append serializes the updated array.

This explanation is based on static inspection of the supplied fixture. The application was not executed or tested. Runtime disconnect behavior and deployment recovery were not verified.

## Follow the ownership

The server has two distinct kinds of state:

| State | Owner and lifetime | Why it matters |
|---|---|---|
| `entries` | Module-level array, shared by requests handled by this server instance | POST writes here; GET reads the same array. |
| `body` | Local variable created for each matching POST, captured by its callbacks | Each POST accumulates its own incoming data. |
| `req` and `res` | The current HTTP request and response | Request events trigger processing; response calls report its result. |

The array is initialized at module load, outside the request handler. There is no database, file write, or persistence adapter in the supplied implementation. [S1, lines 1–9]

## Follow the events

```mermaid
sequenceDiagram
    participant P as POST client
    participant H as HTTP handler
    participant B as POST-local body
    participant E as Shared entries array
    participant G as GET client

    P->>H: POST /entries
    H->>B: Initialize body = ""
    Note over H: Register data/end listeners, then return
    loop Incoming data events
        P->>H: Body chunk
        H->>B: Append chunk
    end
    P->>H: end event
    H->>B: Read accumulated body
    alt Parsing and destructuring succeed
        H->>E: Append {id, amount, note, ts}
        H-->>P: res.end("ok")
        G->>H: GET /entries
        H->>E: JSON.stringify(entries)
        H-->>G: JSON response containing the appended entry
    else Parsing or destructuring throws
        Note over H: No append and no "ok"; no local error handler
    end
```

1. **Routing starts the process.** The condition requires both `POST` and an exact `req.url` value of `/entries`. It registers listeners and returns from the request handler. That return does not end the HTTP response; the later `end` callback does. [S1, lines 5–15]

2. **Chunks build the input, not the ledger.** Each `data` event appends to the POST-local `body` string. Receiving a partial body does not append an entry. [S1, lines 7–9]

3. **The `end` callback performs the write.** Parsing and destructuring must succeed before `entries.push(...)` runs. The ID is the current array length plus one; `amount` and `note` come from the parsed value; `ts` is generated by `Date.now()` at insertion time. [S1, lines 9–12]

4. **GET exposes the shared array.** It sets `content-type` to `application/json` and passes `JSON.stringify(entries)` to `res.end`. This produces a snapshot at serialization time, not a live subscription to future writes. [S1, lines 16–19]

The decisive code is short:

```javascript
// Parsing must succeed before shared state changes; the response follows the append.
const { amount, note } = JSON.parse(body || '{}');
entries.push({ id: entries.length + 1, amount, note, ts: Date.now() });
res.end('ok');
```

For example, starting with an empty array, the body `{"amount":12,"note":"Lunch"}` produces an entry with ID `1`, amount `12`, note `"Lunch"`, and a server-generated timestamp. A later GET includes that object. This is a source-derived example, not an observed execution.

## Ordering determines visibility

**The append is the visibility boundary.** In the shown callback, parsing, appending, and calling `res.end('ok')` are synchronous statements, with no intervening `await`. Ordinary request callbacks in this server do not interleave those statements. [S1, lines 9–13]

A GET handled while a POST is still receiving its body sees the array before that POST's append. A GET handled after the append sees the new entry, even if the POST client has not yet received the response.

Across multiple POST requests, **arrival order is not a promised insertion order**. A request that starts first can finish receiving its body later. IDs follow the order in which append operations execute, not when clients began sending requests.

The POST response contains only `ok`; it does not return the newly created ID or object. Calling `res.end` also does not prove that the client received the response. [S1, lines 11–12]

## Malformed JSON never reaches the append

**There is no local error response for malformed JSON.** If `JSON.parse` throws in the `end` listener, control does not reach `entries.push` or `res.end('ok')`. The source has no `try/catch` around that work. [S1, lines 9–13]

Do not translate this into “the server returns 400.” No such response is implemented. An uncaught exception can terminate a Node.js process under normal default handling, but the supplied fixture does not establish an external supervisor, process-level handler, or observed client result.

The empty-body fallback is narrower than validation:

| Input body | Consequence in the shown code |
|---|---|
| `{"amount":12,"note":"Lunch"}` | Parsed fields are appended. |
| Empty body | `body || '{}'` supplies `{}`; an entry is appended with undefined `amount` and `note`. |
| Whitespace only | The string is truthy, so no fallback applies; JSON parsing throws. |
| `{"amount":` | JSON parsing throws before mutation. |
| `null` | Parsing succeeds, but destructuring `null` throws before mutation. |
| `{"amount":"twelve"}` | No type validation rejects it; the string value is appended. |

When GET serializes an entry whose object properties have `undefined` values, those properties are omitted from the JSON output. Thus an empty-body POST can yield a GET entry containing only `id` and `ts`. Successful parsing alone does not establish a valid expense.

## Cancellation and recovery have limited guarantees

**The code defines neither a cancellation policy nor a recovery protocol.** There are no request `aborted`, `error`, or `close` handlers, rollback operations, retry logic, or persistence writes. [S1, lines 1–25]

What the source supports:

- If processing never reaches a successful `end` callback, this POST does not append through the shown code path.
- Once the append executes, the implementation contains no operation that undoes it because a client disconnects.
- A lost response can leave the client uncertain: the write may have happened even though the client never saw `ok`.
- Retrying a completed write can create another entry. There is no idempotency key or duplicate check.
- A fresh process initializes `entries` to `[]`; the fixture contains no mechanism to restore earlier entries. IDs therefore are not durable identities across restarts.

What the source does **not** establish is the exact event sequence for every transport failure, whether any particular interrupted request reached `end`, or whether a hosting system restarts the process. “Client cancelled” is insufficient evidence for either “nothing was saved” or “the write definitely completed.”

## What rationale is actually evidenced?

The README describes MiniLedger as a **tiny personal expense-tracking demo**, explicitly states that data is kept in memory, and names the add/list endpoints. Those statements support explaining the code as a small demonstration of an in-memory ledger. [S2, lines 3–6]

The shared array makes the mechanism direct: POST and GET need no separate storage service to communicate state. That is an observable design consequence. The fixture does not document why the author chose it, why validation is absent, or whether durability was intentionally deferred.

The README also says adding an entry requires five fields typed by hand. The supplied server only extracts `amount` and `note` and generates `id` and `ts`; no supplied client explains that five-field statement. It cannot be treated as an evidenced API requirement. [S2, line 8; S1, lines 10–11]

---

**1. No.** The write is triggered by the `end` callback, after parsing. Received chunks only modify the request-local body string.

**2. No.** The append precedes the response call, and client receipt is not guaranteed. The code has neither rollback on disconnect nor deduplication for retries.

**3. The fallback checks string truthiness, not JSON validity.** An empty string becomes `'{}'`; whitespace remains the original string and fails parsing. Neither path provides meaningful expense-field validation.
