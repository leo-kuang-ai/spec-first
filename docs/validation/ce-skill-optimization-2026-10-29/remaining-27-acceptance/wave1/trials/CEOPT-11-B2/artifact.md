# From POST /entries to visible ledger state

A `POST /entries` changes the ledger only when the request emits `end`,
the accumulated body parses successfully, and the server appends an
entry. A subsequent `GET /entries` serializes that shared in-memory
array. The append happens before the server calls `res.end('ok')`;
receiving that acknowledgment is a separate event.

This explanation uses the supplied fixture as its source of truth.
References such as `src/server.js:11` are relative to the fixture root.
The code was read, not run; examples below are derived expectations,
not captured responses.

## Follow the request across the ownership boundaries

The HTTP server listens on port `3000`. Its request callback matches
the method and URL exactly: `POST /entries` adds an entry,
`GET /entries` lists entries, and other combinations receive
`404` with `not found` (`src/server.js:5–6,16–25`).

```mermaid
sequenceDiagram
    participant Client
    participant Handler as HTTP request handler
    participant Body as POST-local body buffer
    participant Ledger as Shared entries array

    Client->>Handler: POST /entries
    Handler->>Body: Initialize body = ""
    loop Each data event
        Handler->>Body: Append chunk
    end
    Note over Handler,Ledger: No entry has been appended yet
    Handler->>Body: On end, read accumulated body
    Handler->>Handler: JSON.parse(body or "{}")
    alt Parsing and destructuring succeed
        Handler->>Ledger: Push {id, amount, note, ts}
        Handler-->>Client: Call res.end("ok")
        Client->>Handler: GET /entries
        Handler->>Ledger: JSON.stringify(entries)
        Handler-->>Client: JSON array, application/json
    else Parsing or destructuring throws
        Note over Handler,Ledger: No push; no "ok"; no local catch
    end
```

Three pieces of state have different owners:

| State | Owner and lifetime | Consequence |
|---|---|---|
| `body` | One matching POST handler invocation | Chunks from that POST accumulate in its own buffer. |
| `entries` | Module-level array, shared by the server's request handlers | Successful POST callbacks add to the collection GET reads. |
| Response contents | Each request's `res` object | POST returns `ok`; GET returns a JSON serialization of the collection. |

The separation is visible in the declarations: `entries` is outside
the server callback (`src/server.js:3`), while `body` is inside the
POST branch (`src/server.js:7`).

## The mutation trigger is `end`, not arrival of the POST

The POST branch first registers two listeners. Each `data` event
appends a chunk to `body`; the `end` listener performs all parsing and
mutation (`src/server.js:8–13`). The `return` at line 14 exits the
initial request callback so it does not fall through to the GET or
404 branches. It does not cancel the registered listeners.

The decisive code runs in this order:

```javascript
const { amount, note } = JSON.parse(body || '{}');
entries.push({ id: entries.length + 1, amount, note, ts: Date.now() });
res.end('ok');
```

Source: `src/server.js:10–12`.

1. Parse the complete accumulated string, or `{}` if it is empty.
2. Extract `amount` and `note`.
3. Compute an ID from the current array length and a timestamp at
   insertion time, then append the object.
4. End the POST response with the text `ok`.

There is no asynchronous pause between these statements. Within this
server's JavaScript execution, a GET handler cannot run halfway
between parsing and pushing. It can run before this callback or after
it.

Request arrival order therefore does not establish insertion order.
If POST A starts first but POST B finishes its body first, B can be
appended first. IDs follow append order because `entries.length + 1`
is evaluated during each append, not when each POST arrives.

## GET observes a snapshot of the current array

GET sets `content-type` to `application/json`, serializes `entries`,
and ends its response (`src/server.js:16–18`). It neither waits for
pending POST bodies nor subscribes to future changes.

Suppose the array starts empty and a POST body is:

```json
{"amount":12.5,"note":"Lunch"}
```

After its append, the array contains an object with:

- `id: 1`, derived from the previous length of zero;
- `amount: 12.5` and `note: "Lunch"`, extracted from the body;
- `ts`, generated by `Date.now()` at insertion.

A GET handled before that append serializes `[]`. A GET handled
afterward includes the entry, provided it reaches the same live
server instance. Once `JSON.stringify(entries)` has produced a
response string, a later append does not change that already-produced
string.

POST does not return the created object or its ID. Its `ok` response
has no explicit status assignment or content-type header in this
branch; normal Node response behavior supplies the default status.
GET is the endpoint that explicitly returns JSON.

## Parsing is not validation

Malformed JSON throws at `JSON.parse` before the append and before
`res.end('ok')`. There is no `try/catch`, error response, or request
error handler in the supplied file (`src/server.js:5–23`).

That means this code does **not** implement a controlled `400`
response. Under ordinary Node execution, an uncaught exception can
terminate the process. The fixture contains no runtime observation
or external handler configuration establishing the exact client
symptom or any recovery behavior.

Several inputs illustrate the boundary:

| POST body | Behavior implied by the source |
|---|---|
| `{"amount":12.5,"note":"Lunch"}` | Appends the extracted values with generated `id` and `ts`. |
| Empty body | Falls back to `{}` and appends an entry with undefined `amount` and `note`. |
| `{"amount":"twelve"}` | Appends a string amount; no numeric validation exists. |
| `{"amount":` | Parsing throws; this request does not append or reach `ok`. |
| `null` | Parsing succeeds, but destructuring `null` throws before append. |

An empty-body entry still consumes an ID. When GET serializes it,
properties whose values are `undefined` are omitted, so the visible
object contains `id` and `ts` without `amount` or `note`.

These are consequences of `src/server.js:10–11,18`, not evidence of a
deliberate validation policy.

## Cancellation and recovery stop at the evidence boundary

The source has no cancellation flag, abort listener, rollback,
persistence, retry policy, or deduplication mechanism. Those absences
matter at different points in the request:

| Point in the lifecycle | What the code supports saying |
|---|---|
| Before the `end` callback runs | No append has occurred for that request. If `end` never runs, this handler has no other insertion path. |
| After the append | A client disconnect does not invoke any explicit undo operation in this code. |
| After append but without a received acknowledgment | The client may be uncertain whether insertion occurred; calling `res.end` is not proof that the client received the response. |
| Retrying a successfully appended POST | If the retry completes successfully, it appends another entry; no request identity prevents duplication. |
| Restarting the server | The module initializes a new empty array; no restore mechanism is present. |

A client-side timeout therefore does not prove either cancellation or
successful insertion. The precise sequence of connection events would
require runtime evidence. The code establishes only that mutation is
tied to its `end` callback and that no explicit cancellation or
compensation logic is implemented.

The in-memory ownership is also the durability boundary:
`README.md:6` states that data is kept in memory, and
`src/server.js:3` implements that choice. Successful acknowledgment
does not establish persistence across process termination. Separate
server instances would have separate arrays; this fixture supplies no
shared store.

## What the evidence says about rationale

The README describes MiniLedger as a tiny personal expense-tracking
demo, names the two endpoint roles, and documents in-memory storage
(`README.md:3–6`). That supports explaining the implementation as a
small demonstration of adding and listing expenses.

The ordering also has a concrete functional effect: buffering before
parsing allows the parser to receive the accumulated body rather than
an individual chunk; appending before acknowledging makes `ok` follow
the mutation in this code path.

Neither observation proves the original author's reasons. There is
no supplied design history explaining why validation, persistence,
cancellation handling, or a richer POST response were omitted.

One README claim should not be treated as endpoint behavior:
`README.md:8` says adding an entry requires five manually typed fields.
The server extracts only `amount` and `note`, generates `id` and `ts`,
and enforces no required-field count. The supplied fixture contains
no interface demonstrating the five-field claim, so the server source
controls this explanation.

## Check yourself

1. POST A arrives first, but POST B's `end` callback runs first. Which
   request receives the first available ID?
2. A client times out without seeing `ok`. Does that prove the entry
   was not added, and is retrying guaranteed to avoid duplication?
3. How do an empty body and malformed JSON differ?

---

**Answers**

1. B receives the first available ID. The ID is computed during the
   append, so body-completion callback order matters more than arrival
   order.
2. No. The append may already have occurred before acknowledgment was
   received. A successful retry appends again because there is no
   deduplication.
3. An empty body is replaced with `{}` and produces an entry with
   generated `id` and `ts`; undefined fields disappear in GET's JSON.
   Malformed JSON throws before insertion, with no local error response
   or recovery handling.
