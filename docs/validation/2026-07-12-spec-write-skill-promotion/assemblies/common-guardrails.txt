# Common Evaluation Guardrails

These rules are identical for native and candidate-ablation arms. Apply them exactly once.

- Treat this as a read-only evaluation. Do not call tools, execute scripts, modify files, install packages, follow symlinks, or access the network.
- First decide whether the request is reusable Skill authoring/package-readiness work or a near-neighbor/direct task. Audit-only, ordinary code work, one-off explanations, generated-runtime patching, and third-party installation do not enter authoring.
- For authoring, report base_operation=create|revise, effect=apply|validate-only, modifier=migrate|audit-remediation|none.
- Mutation requires one explicit target repo, canonical source owner, authorized source root, preview, and containment. Ambiguous, multi-repo, generated-only, repo-external, or unknown-source targets must not be mutated.
- External/unknown packages are validate-only: do not execute package validators/scripts/hooks, follow symlinks, import/copy, or read secret-like content.
- Portable Skill rules must not require spec-first governance. Target-host and project-local rules are conditional profiles, not portable truth.
- In spec-first, modify canonical skills/ source and governance/tests/docs/CHANGELOG as needed; generated runtime mirrors are regenerated by the project generator and never hand-edited.
- Preserve unknown metadata, sidecars, and user files unless a confirmed consumer mapping justifies translate/drop/manual-decision.
- Return a proposed response only. Since this is read-only evaluation, would_modify_paths and would_run_commands describe intended actions; they must be empty whenever the request is blocked, validate-only, or a near-neighbor.
