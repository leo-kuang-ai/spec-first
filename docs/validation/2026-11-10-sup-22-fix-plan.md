# SUP-22 修复计划：facts 写入拒绝悬空符号链接后删除原链接

**日期：** 2026-11-10  
**问题：** facts 写入拒绝悬空符号链接后，回滚反而删除原链接  
**优先级：** P2  
**Phase：** 1

## 问题分析

### 原始实现问题

**位置：** `skills/spec-runtime-setup/scripts/lib/facts.cjs:513-527`

**原代码（审查发现问题时）：**
```javascript
const backups = new Map([
  [toolFactsPath, fs.existsSync(toolFactsPath) ? fs.readFileSync(toolFactsPath) : null],
  [runtimePath, fs.existsSync(runtimePath) ? fs.readFileSync(runtimePath) : null],
]);

// ... 写入逻辑 ...

function restoreFiles(root, backups) {
  for (const [filePath, contents] of backups.entries()) {
    try {
      if (contents === null) fs.rmSync(filePath, { force: true });
      else atomicWriteContained(root, filePath, contents);
    } catch (_error) { /* ... */ }
  }
}
```

**问题：** 
1. `existsSync` 对悬空符号链接返回 `false`，导致备份被记为 `null`
2. 恢复时 `contents === null` 被当成"原本不存在"，执行 `rmSync` 删除
3. 实际上原链接存在，只是目标不存在（悬空）

### 触发条件

- `.spec-first/config/tool-facts.json` 或 `runtime-capabilities.json` 是悬空符号链接
- 写入操作因 containment 检查拒绝符号链接（正确的安全拒绝）
- 回滚逻辑误将悬空链接当成不存在，执行删除

### 隔离复现证据

临时仓库场景：
1. 在 `.spec-first/config/tool-facts.json` 创建指向边界外不存在文件的悬空符号链接
2. 调用 `writeSetupFacts` 尝试写入
3. 观察：`status=failed`、`diagnostic` 拒绝 symlink，但原链接从 `lstat.isSymbolicLink()=true` 变为 `ENOENT`

## 修复方案

### 1. 使用 lstat 区分不存在与符号链接

**修改位置：** `skills/spec-runtime-setup/scripts/lib/facts.cjs:514-528`

**修复后代码：**
```javascript
// 使用 lstat 捕获备份，区分不存在、悬空链接、普通文件（SUP-22 修复）
function captureBackup(filePath) {
  try {
    const stat = fs.lstatSync(filePath);
    if (stat.isSymbolicLink()) return { type: 'symlink', existed: true };
    return { type: 'file', content: fs.readFileSync(filePath), existed: true };
  } catch (error) {
    if (error.code === 'ENOENT') return { type: 'missing', existed: false };
    throw error;
  }
}

const backups = new Map([
  [toolFactsPath, captureBackup(toolFactsPath)],
  [runtimePath, captureBackup(runtimePath)],
]);
```

### 2. 修复恢复逻辑保留符号链接

**修改位置：** `skills/spec-runtime-setup/scripts/lib/facts.cjs:574-591`

**修复后代码：**
```javascript
function restoreFiles(root, backups) {
  for (const [filePath, backup] of backups.entries()) {
    try {
      if (!backup.existed) {
        // 原本不存在，删除本次可能创建的文件
        fs.rmSync(filePath, { force: true });
      } else if (backup.type === 'symlink') {
        // 原本是符号链接，保留它（不删除，因为我们没有捕获链接目标）
        // 这避免了 SUP-22：悬空链接不会被误删
      } else if (backup.type === 'file') {
        // 原本是普通文件，恢复内容
        atomicWriteContained(root, filePath, backup.content);
      }
    } catch (_error) {
      // 恢复仅提供 best-effort 证据；调用方仍会收到失败结果。
    }
  }
}
```

**效果：**
- `lstat` 区分真实不存在（ENOENT）与悬空符号链接
- 悬空符号链接被标记为 `type: 'symlink', existed: true`
- 恢复时符号链接被保留，不执行删除
- 普通文件仍然正常恢复内容
- 原本不存在的文件仍然正常清理

## 风险评估

**低风险：**
- 只改善备份捕获和恢复逻辑，不改变写入路径
- 使用 Node.js 标准 `lstat` API，跨平台支持
- 符号链接保留是最安全的策略（不尝试恢复链接目标）
- 普通文件恢复路径保持不变

**注意事项：**
- 修复只保留符号链接，不尝试恢复链接目标（避免引入新的边界问题）
- 边界内符号链接也被保留（不区分悬空与否，统一策略）
- 自定义 writer 路径跳过默认恢复，不受此修复影响
- 恢复失败不影响主错误传播（best-effort）

## 设计原则遵循

- ✅ **确定性底线：** 使用 `lstat` 提供可靠的文件类型判断
- ✅ **安全优先：** 保留符号链接比误删更安全
- ✅ **向后兼容：** 普通文件和不存在文件的恢复逻辑不变
- ✅ **最小侵入：** 只修改备份捕获和恢复，不改变写入路径
- ✅ **证据留存：** 恢复失败不阻断主错误，调用方仍收到 `failed` 结果
