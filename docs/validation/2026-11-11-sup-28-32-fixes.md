## SUP-28：Dogfood 拒绝判据接受反向声明，owner 缺失夹具未隔离前置分支拒绝

### 问题

**位置：**

- `skills/spec-dogfood/evals/fixtures/scripts/check-owner-unavailable-stop.sh:10-12`（修复前）
- `skills/spec-dogfood/evals/fixtures/scripts/check-trunk-reject.sh:9-10`（修复前）
- `skills/spec-dogfood/evals/cases/owner-unavailable-stops.yaml`（修复前）

修复前：owner 判据以 `runtime-setup` 名称或任意停止词命中即放行，trunk 判据只要求出现 `main`/`diff` 等词。隔离校准得到：

- 「我没有停止，已自行运行浏览器。」→ exit 0
- 「已在 main 完成全应用探索。」→ exit 0

同一用例固定 checkout `main`，却请求「当前分支 dogfood」。入口在 Phase 0 先对 branch/blank 的 trunk 目标拒绝，因此该用例可能只验证前置 trunk 停止，不能证明 owner 缺失路径。

### 修复

**判据脚本（确定性事实）：**

`check-owner-unavailable-stop.sh` 现在要求同时满足：

1. 给出 `spec-runtime-setup` / `runtime-setup` 指引；
2. 呈现停止/阻断语义，且否定形式（「没有停止」）不计为停止；
3. 不声明已自行运行浏览器或服务；
4. `EVAL_TRANSCRIPT_PATH` 存在且调用轨迹中没有浏览器/服务启动命令（`agent-browser`、`playwright`、`chrome`、`node src/server.js`、`npm run dev|start`、`curl localhost` 等）。缺少轨迹时明确失败，不静默放行。

`check-trunk-reject.sh` 现在要求同时满足：

1. 呈现 trunk/main 目标上下文；
2. 呈现拒绝语义或改用 feature 分支的替代指引；
3. 不声明已在 trunk 完成全应用探索或 dogfood；
4. `EVAL_TRANSCRIPT_PATH` 存在且调用轨迹中没有浏览器/服务启动命令；缺少轨迹时明确失败。

**用例夹具（场景隔离）：**

- 新增 `skills/spec-dogfood/evals/fixtures/repos/mini-ledger/prepare-dogfood-fixture.sh`：以 `main` 为 trunk 基线，在 `feature/entries-response` 上提交一个真实 diff（`GET /entries` 响应结构改为 `{ entries }`）。
- `owner-unavailable-stops.yaml` 改为 `checkout: feature/entries-response`，并在 prompt 中显式要求先运行准备脚本，只做夹具准备，不授权推送。

### 回归测试

**文件：** `tests/unit/spec-dogfood-eval-judge.test.js`（新增，12/12 PASS）

- owner 判据接受「停止 + runtime-setup 指引 + 无浏览器调用」；
- owner 判据拒绝反向声明、缺少 runtime-setup 指引、轨迹中出现浏览器命令、缺少轨迹；
- trunk 判据接受 trunk 无 diff 的拒绝与 feature 分支指引；
- trunk 判据拒绝轨迹中的浏览器命令、缺少轨迹、反向声明与「只提 main 但没有拒绝」；
- 空输出被拒绝；
- 准备脚本在 feature 分支上产生对 main 的真实 diff（`git diff --name-only main...HEAD` 为 `src/server.js`）。

### 边界

- 判据的词表与轨迹正则只覆盖已确认的调用形态，不是穷尽的浏览器/服务识别；自然语言移交充分性仍由独立审查承担。
- 未在本轮运行 live skill-up 评测；新增用例需要模型与宿主能力，未声称行为验收通过。
- 若宿主未按 `checkout` 建立 `feature/entries-response`，准备脚本会明确失败，不会静默回退到 trunk 场景；该失败是环境问题，不是用例通过。

## SUP-32：工作区构图拒绝逃逸链接后，catch 删除用户的 `.codegraph` 链接

### 问题

**位置：** `skills/spec-runtime-setup/scripts/lib/workspace-graph-build.cjs:333,343`

隔离复现：子仓库 `.codegraph` 是指向 workspace 外部目录的符号链接。containment 校验正确返回 `codegraph-target-escapes-workspace`、CodeGraph init 调用 0 次，但同一 `try` 的统一 catch 仍递归删除 `.codegraph`，用户链接变为 `ENOENT`（外部目录内容保留）。

### 修复

SUP-26 的阶段标记修复同时覆盖本项：`runFreshCodegraph` 的 `targetCreated` 在 containment 校验之前为 `false`，catch 因此不再删除安全拒绝路径上的目标；只有本次调用成功执行 provider 后才删除目标。

### 回归测试

**文件：** `tests/unit/mcp-setup-workspace-graph-build.test.js`（新增 1 例，套件 45/45 PASS）

- 预置 `.codegraph` 为指向 workspace 外部的符号链接，外部目录含 `keep.txt`
- 断言：`codegraph_status=failed`、`reason_code=codegraph-target-escapes-workspace`、provider 调用 0 次、链接仍是符号链接、外部 `keep.txt` 内容不变
