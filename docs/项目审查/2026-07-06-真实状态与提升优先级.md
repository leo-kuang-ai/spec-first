# spec-first 真实状态与提升优先级（2026-07-06）

## 1. 项目实际规模

| 维度 | 数据 |
|---|---|
| CLI 核心代码（`src/cli/`） | ~23,000 行 JS |
| Skill prompt 文本（`skills/**/*.md`） | ~36,000 行 Markdown（38 个 skill） |
| 测试 | 179 个 test 文件 / ~54,000 行 |
| Run evidence（`.spec-first/workflows/spec-work/`） | 52 条 `run.json` |
| Knowledge docs（`docs/solutions/`） | 28 个 |
| Agent profiles | 51 个 |
| Skill 脚本 | 30 sh + 12 py + 52 js |

## 2. 核心发现

项目代码质量好：atomic write 有 Windows retry、adapter 层清晰、state 管理有 schema validation、honest-closeout 有结构化 claim/verdict。问题不在代码质量，在以下几个方面。

---

## 3. 五个提升方向（按优先级排列）

### 3.1 最高优先级：Skill Prompt 膨胀

**现状**

| Skill | 行数 |
|---|---|
| `spec-code-review/SKILL.md` | 1,241 行 |
| `spec-compound-refresh/SKILL.md` | 717 行 |
| `spec-compound/SKILL.md` | 646 行 |
| `spec-work/SKILL.md` | 579 行 |
| `spec-plan/SKILL.md` | 460 行 |
| **38 个 skill 合计** | **10,628 行** |

**问题**

- 每次 workflow 调用，skill prompt 全量注入 LLM context，占掉 8-10k tokens
- 加上 plan doc、source 文件、test context，留给 LLM 做判断的 context 窗口被严重挤压
- skill 中大量是防御性规则（anti-rationalization red flags、recall trust boundary、capability-class evidence boundary、workspace repo scope...），80% 的普通任务不会触发
- 对比 Superpowers 每个 skill 通常 50-100 行，只做一件事

**提升动作**

1. 把 skill 拆分为 core（workflow 骨架，<150 行）+ references（按需 on-demand 加载）
2. `spec-work` 已有 `references/` 目录但利用率不够——大量本该在 references 的内容仍在主 SKILL.md
3. 目标：主 SKILL.md 控制在 150 行以内，让 LLM 把更多 context 分给用户实际代码

**预期收益**

- 直接提升 LLM 输出质量（更多 context 给用户代码）
- 零外部依赖，纯内部重构
- 减少 "LLM 被约束规则困住" 导致的 not-run 情况

---

### 3.2 高优先级：Run Evidence 消费层

**现状**

52 条 `run.json` 验证状态分布：
- 26 条 passed（50%）
- 18 条 not-run（35%）
- 5 条 failed（10%）
- 3 条 degraded（6%）

这些数据已经存在，但**没有任何代码或 workflow 在消费它们**：
- 没有 `spec-first stats` 或 `spec-first report` 命令汇总 workflow outcome
- 没有 workflow 查询"上一次类似任务跑得怎样"
- knowledge recall（`docs/solutions/`）与 run evidence 之间没有闭环

**提升动作**

1. 加 `spec-first stats` 命令：聚合 `.spec-first/workflows/` 下的 run artifacts，输出 pass/fail/degraded 趋势、平均 changed_files 数量、top-N 失败 reason_code
2. 让 `spec-compound` 在沉淀 learning 时关联 `run_id`，追踪 learning 实际复用率
3. 这比新建 "outcome ledger" 概念更务实——已有 52 条数据，差的只是消费层

**预期收益**

- 用已有数据证明 workflow 价值
- 为 Evaluation Harness 从 aspirational 推向 confirmed 提供真实数据基础
- 35% 的 not-run 比例暴露 task-pack validation 过严或 prompt 规则过重

---

### 3.3 高优先级：首次体验 5 分钟闭环

**现状用户路径**

```
npm install -g spec-first       # 1 分钟
spec-first doctor               # 1 分钟
spec-first init                 # 3 分钟（交互式）
重启宿主                        # 1 分钟
理解入口概念                    # 5+ 分钟 ← 断点
第一次 spec-brainstorm          # 不确定在哪输入
看产物、理解含义                # 5+ 分钟
```

**断点分析**

- 用户不确定 `spec-brainstorm` 是终端命令还是宿主内命令
- 不同宿主 invocation 方式不同（Claude Code 是会话里说、Codex 有 command palette、Kiro 有 chat）
- 没有 `spec-first run brainstorm "xxx"` 的统一 CLI 入口让用户在终端验证

**对比竞品**

- Superpowers：安装 → 正常聊天 → AI 自动触发 → 用户感觉 AI 变好了。5 分钟
- OpenSpec：3 命令（propose/apply/archive），概念极简
- SpecKit：slash commands 直接在 IDE 里用

**提升动作**

1. `spec-first init` 完成后输出精确 copy-paste 指引（在哪个 UI 位置输入什么文字）
2. 考虑 `spec-first try` 或 `spec-first demo` 命令，自动生成一个 brainstorm artifact 到 `docs/brainstorms/`，证明管道通了
3. 首次 init 可选 `--quick` 模式，只生成最核心 3 个 skill（brainstorm/plan/work），跳过 51 agent 和 20+ skill

**预期收益**

- 直接影响用户留存
- 降低"概念面太重"的学习成本

---

### 3.4 中优先级：Deterministic Floor 下沉

**现状矛盾**

项目哲学："Scripts enforce deterministic invariants"
实际：workflow 关键路径（task-pack hash 校验 → 是否允许执行）完全靠 LLM "读 SKILL.md 里的 prose 规则然后自觉遵守"

证据：
- `spec-first tasks validate` CLI 命令已存在并能做确定性 hash 校验
- 但 `spec-work/SKILL.md` 仍用 100+ 行 prose 重复描述同样校验逻辑
- 52 条 run 中 35% 是 not-run——可能是 LLM 被过度约束后选择放弃

**提升动作**

1. SKILL.md 中的校验逻辑精简为：`run spec-first tasks validate <path> --json; proceed only if exit 0`
2. 不要在 prompt 里手写 hash 比对规则——那是脚本的活
3. 其他确定性可判断的规则（source/runtime boundary check、workspace scope）同理下沉到 CLI 输出

**预期收益**

- 减少 not-run 比例（预期从 35% 降到 <15%）
- 让 SKILL.md 更专注于语义判断（需求理解、架构取舍、review 判断）
- 真正兑现 "deterministic floor" 哲学

---

### 3.5 中优先级：Windows Workflow Helper 迁移

**现状**

- npm install 和 CLI 层已跨平台（CI 覆盖 Windows）
- 核心 workflow helper 仍有 bash-only 依赖：
  - `spec-code-review` 的 base detection 依赖 `.sh`
  - `spec-polish-beta` 有 4 个 shell 脚本
  - `spec-optimize` 有 shell 脚本
  - 合计 30 个 `.sh` 文件在 `skills/` 下

**提升动作**

1. 优先迁移 `spec-code-review` base resolver 到 Node（核心 review workflow）
2. 其他 helper 做 closure matrix（逐项标注 closed/deferred/degraded）
3. 保证安装 → 核心 workflow 的体验不断层

---

## 4. 不做什么

- **不新增 skill/agent**：38 skill + 51 agent 能力存量已溢出，边际收益低
- **不扩展宿主数量**：5 个宿主中 3 个还是 preview/degraded
- **不新增 contract/schema**：已有 schema 足以覆盖当前需求
- **不做重型 outcome ledger 新概念**：用已有 52 条 run evidence + 简单 stats 命令即可

---

## 5. 行动顺序建议

```text
第 1 步：Skill prompt 瘦身（spec-work → <150 行 + references）
         ↓ 验证：LLM context 利用率提升，not-run 比例下降
第 2 步：spec-first stats 命令（消费已有 run evidence）
         ↓ 验证：能看到 pass/fail/degraded 趋势
第 3 步：首次体验闭环（init 完成后精确指引 + 可选 demo）
         ↓ 验证：新用户 5 分钟内看到第一个 artifact
第 4 步：Deterministic floor 下沉（task-pack validation prose → CLI）
         ↓ 验证：not-run 比例从 35% 降到 <15%
第 5 步：Windows helper 迁移（spec-code-review base resolver）
         ↓ 验证：Windows PowerShell 下 code-review workflow 可运行
```

## 6. 与项目角色契约的对齐

| 角色契约原则 | 本报告建议的对齐点 |
|---|---|
| "Light contract" | Skill 瘦身 = 让 contract 更轻 |
| "Scripts enforce deterministic invariants" | Deterministic floor 下沉 = 真正兑现这个哲学 |
| "能力建设 ≠ 已兑现使命" | Stats 命令 = 用数据证明已有能力有效 |
| "可信证据 > 自动化便利" | 消费已有 52 条 run evidence > 新建 outcome 概念 |
| "用户真实研发增益 > 架构炫技" | 首次体验闭环 = 直接面向用户增益 |
| "当再加一个能力与让已有能力可被采纳冲突时选后者" | 不新增 skill，优先让现有 workflow 更轻、更可验证 |

## 7. 竞品对标对齐

| 竞品优势 | spec-first 当前差距 | 本报告提升动作 |
|---|---|---|
| Superpowers：5 分钟感知提升 | 30+ 分钟才能跑通第一轮 | 首次体验闭环 |
| Superpowers：每 skill <100 行 | 平均 280 行/skill | Skill 瘦身 |
| OpenSpec：3 命令极简心智 | 概念面重，入口多 | --quick 模式 |
| SpecKit：GitHub 官方 OSS 信号全 | COC/CODEOWNERS/ROADMAP 缺 | 维持 003 plan |
| 所有竞品：无 evidence 机制 | 有 52 条 evidence 但无消费层 | Stats 命令 |

---

## 8. 一句话结论

> 项目当前最大杠杆不是加功能，是**减 prompt 重量**和**让已有证据说话**。38 个 skill × 平均 280 行 = 10,000+ 行 prompt 文本注入 LLM，这本身就在损害你想保护的工程质量。
