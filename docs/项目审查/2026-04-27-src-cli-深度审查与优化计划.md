# 2026-04-27 src/cli 深度审查与优化计划

## 1. 审查定位

本报告聚焦 `src/cli/`，审查对象是当前磁盘状态下的 CLI 控制面，包括已有未提交变更中的 `src/cli/commands/specs.js` 与 `src/cli/index.js`。

审查基线按 `docs/10-prompt/项目角色.md` 校准：spec-first 的长期演化应坚持 **Light contract / Explicit boundaries / Let the LLM decide**。CLI 应负责确定性执行与事实准备，LLM 应负责语义判断与方案取舍。

本报告不是 PR/diff 评审，而是面向后续演化的架构审计与可执行整改计划。

## 2. 当前全景

`src/cli/` 当前约 7922 行，主要模块如下：

| 区域 | 文件 | 当前职责 |
| --- | --- | --- |
| 根命令路由 | `index.js` | `doctor/init/clean/tasks/specs` 分发，版本提醒，help/version 输出 |
| Runtime 生命周期 | `commands/init.js`、`commands/clean.js`、`state.js` | runtime asset plan/apply、受管状态、清理、drift hard reset |
| Diagnostics | `commands/doctor.js` | Node/Git/host CLI、runtime asset、developer profile、bootstrap、CRG native/graph、workflow evidence 汇总 |
| Asset 分发 | `plugin.js`、`adapters/*` | manifest/governance 加载、host 过滤、source asset copy/transform/inspect |
| Task helper | `commands/tasks.js`、`task-pack.js` | task-pack hash/validate，确定性 handoff 校验 |
| Specs helper | `commands/specs.js` | spec-standards proposal run 写入与校验 |
| 治理块 | `lang-policy.js`、`instruction-bootstrap.js`、`coding-guidelines.js`、`claude-settings.js` | AGENTS/CLAUDE managed block 与 Claude SessionStart 管理 |
| 身份与 changelog | `developer.js`、`changelog.js` | developer profile 解析、changelog author 解析与 bootstrap |

核心调用链：

1. `bin/spec-first.js` 对 `crg` 延迟加载，其余命令进入 `src/cli/index.js`。
2. `init` 读取 adapter、manifest、skills governance 和 bundled assets，构造 operation plan，写 runtime assets、developer profile、state、AGENTS/CLAUDE managed blocks。
3. `doctor` 重新读取 runtime、source truth、graph/evidence，输出事实诊断。
4. `clean` 基于 managed state 删除 spec-first 管理过的资产，并保留用户自定义资产。
5. `tasks/specs` 是窄 helper：面向 task-pack 与 standards proposal 的确定性校验/写入。

## 3. 总体判断

`src/cli` 的方向总体正确。它把 runtime 安装、资产同步、状态文件、doctor 检查和 helper 写入都放在脚本层，符合“确定性执行归脚本”的原则。`tasks` 与 `specs` 也没有尝试判断任务质量或规范内容质量，而是只做机器可验证的边界检查。

主要风险不是方向错误，而是少数中心文件继续吸纳过多确定性细节：

- `plugin.js` 同时承担 source discovery、governance validation、host delivery filtering、runtime sync planning、direct sync、integrity inspection、high-value anchor 检查。
- `doctor.js` 同时承担 check 定义、check 编排、health 汇总、workflow runnability 推导、JSON/text 渲染。
- `init.js` 同时承担参数解析、asset plan、drift 判断、legacy reset、rollback、metadata 写入和用户输出。
- 新增 `specs.js` helper 边界清晰，但已经开始出现 CLI parser、writer、validator、redaction、path resolver 同文件增长趋势。

这些不是立刻阻断发布的 P0 bug，但会提高后续每次新增 workflow、host、helper 或 governance contract 的修改成本。

## 4. 主要优点

### 4.1 确定性控制面清晰

`init/clean/tasks/specs` 都是确定性控制面：

- `init` 通过 operation plan 写 runtime assets，而不是让 agent 手工改 `.claude/` 或 `.codex/`。
- `clean` 依赖 managed state，只移除受管资产，保留自定义资产。
- `tasks validate` 只校验 identity、freshness 和结构，明确不判断任务拆分质量。
- `specs write-proposal` 只写 proposal run artifact，不 promote 到 `docs/specs/**`。

### 4.2 双宿主 delivery 有真源

`src/cli/contracts/dual-host-governance/skills-governance.json` 与 `.claude-plugin/plugin.json` 组合提供了 workflow/skill delivery 的机器真源。`plugin.js` 的 `validateSkillsGovernance()` 会校验 entry surface、host scope、host delivery、manifest command 之间的一致性，避免只靠文档约定。

### 4.3 Runtime drift 诊断有真实价值

`plugin.js` 的 integrity inspection 与 `doctor.js` 的 runtime checks 能发现 missing/drifted command、skill、agent、support file，以及高价值 anchor 缺失。这使 `doctor` 不只是“文件存在检查”，而是能发现 runtime/source drift。

### 4.4 新 helper 的写入策略偏保守

`specs write-proposal` 使用 run-local tmp 目录，完成后 `renameSync` 到最终 run dir；payload 先做 schema、路径、frontmatter、redaction 风险检查；同名 run fail closed。这是正确的 deterministic writer 形态。

## 5. 主要风险与改进建议

### R1. `plugin.js` 已成为 asset control plane 的过重枢纽

证据：

- `plugin.js` 约 1164 行。
- `validateSkillsGovernance()` 覆盖 governance schema 语义、manifest 交叉校验、host delivery 规则。
- `buildFilteredAssetSet()` 同时过滤 command、workflow skill、standalone skill、internal skill、agent support。
- `plan*Sync()` 与 `sync*()` 同时存在，形成 plan/apply 与 direct write 两条执行路径。
- integrity anchors、Codex path rewrite drift、Claude agent reference drift 也集中在同一文件。

风险：

- 每次新增 host、delivery type、asset kind 或 integrity rule，都容易继续往 `plugin.js` 追加分支。
- direct `sync*()` 与 plan-based `plan*Sync()` 容易出现行为漂移。
- `plugin.js` 同时做事实发现和策略判断，模块边界开始变钝。

建议：

1. 拆出 `asset-discovery.js`：只负责 manifest/governance/source files 的读取与枚举。
2. 拆出 `asset-delivery.js`：只负责 governance -> platform asset set 的纯函数过滤。
3. 拆出 `asset-plan.js`：只负责 source -> operation plan。
4. 拆出 `asset-inspection.js`：只负责 installed runtime -> drift report。
5. 将 direct `syncBundledAssets/syncCommands/syncSkills/syncAgents` 标记为兼容层，内部改为调用 `plan* + applyOperationPlan`，最后逐步删除。

边界要求：

- 不引入新的 workflow 状态机。
- 不让 CLI 判断 skill 内容质量，只检查机器 anchor、路径 rewrite、frontmatter 和 source/runtime 一致性。
- 保持 governance JSON 是 delivery 真源，不把同一规则复制到 adapter。

### R2. `init.js` 是高价值但过厚的事务编排器

证据：

- `runInit()` 从参数解析、平台选择、legacy state、drift hard reset、asset plan、metadata plan、dry-run 输出、rollback 到最终日志全部串在一个函数链中。
- legacy reset 与 current runtime drift 的 dry-run 分支重复构建 hard reset、post reset、init write plan。
- 只有 destructive reset 分支显式创建 rollback backup；普通 preSync + initWritePlan 失败时仍可能产生部分写入。

风险：

- 后续新增 host 或 runtime side effect 时，`runInit()` 会继续膨胀。
- 普通 re-init 如果在 prune/remove 后写入失败，用户可能看到部分 runtime 被更新、state 未完成的中间态。
- dry-run 与 apply 虽然都基于 plan，但场景分支多，未来容易遗漏某条路径。

建议：

1. 拆出 `init-session.js`：`inspect -> assess -> plan -> apply -> report` 五个纯阶段。
2. 将 legacy/drift/no-drift 都归一成一个 `InitAssessment`：
   - `reset_kind: none | legacy_state | current_runtime_drift`
   - `reset_plan`
   - `pre_sync_plan`
   - `write_plan`
   - `rollback_required`
3. 所有非 dry-run apply 都走统一 `applyWithRollback(projectRoot, plans)`。
4. `runInit()` 保持薄：解析参数、调用 session、渲染结果。

### R3. `doctor.js` 需要注册式检查

证据：

- `doctor.js` 约 1108 行。
- check 定义、平台编排、health summarize、workflow_runnability 推导、JSON/text rendering 都在同一文件。
- `buildDoctorCommonChecks()` 是硬编码数组；平台 checks 也在 `buildDoctorReport()` 内直接组装。

风险：

- 新增 helper、host 或 evidence source 时容易改动中央编排函数。
- 单项 check 难以隔离测试。
- `doctor` 容易从事实报告器滑向中心控制器。

建议：

1. 拆出 check registry：
   - `doctor/checks/common.js`
   - `doctor/checks/runtime-assets.js`
   - `doctor/checks/host.js`
   - `doctor/checks/graph.js`
   - `doctor/checks/verification-evidence.js`
2. 每个 check 返回统一 shape：`{ id, level, name, message, fix, tags }`。
3. `buildDoctorReport()` 只负责运行 registry、聚合 health、生成 JSON contract。
4. 渲染拆成 `doctor/render-text.js` 与 `doctor/render-json.js`。

原则边界：

- `doctor` 可以报告事实、证据、freshness 和 fallback reason。
- `doctor` 不应自动修复、不应触发 init/update、不应做 workflow 入口语义选择。

### R4. CRG native check 仍不够本地源码友好

证据：

- `checkCrgNativeModules()` 使用 `spawnSync('spec-first', ['crg', '--help'], { shell: true })` 检查 CRG CLI。

风险：

- 在源码 checkout 中运行 `node bin/spec-first.js doctor` 时，如果全局 `spec-first` 未安装或版本不是当前 checkout，doctor 结果可能反映全局安装而非当前源码。
- 这会降低 dogfood 和本地开发诊断可信度。

建议：

1. 优先使用当前 package 的 `bin/spec-first.js`：
   - `spawnSync(process.execPath, [path.join(REPO_ROOT, 'bin/spec-first.js'), 'crg', '--help'])`
2. 只有在 packaged/global 环境无法定位本地 bin 时，再 fallback 到 `spec-first` shell wrapper。
3. JSON report 中增加 `check_source: local_bin | global_wrapper | fallback`。

### R5. Direct sync API 与 operation plan API 并存

证据：

- `plugin.js` 暴露 `syncBundledAssets/syncCommands/syncSkills/syncAgents`。
- `init` 主链使用 `planBundledAssetSync()` + `applyOperationPlan()`。
- `agents.js`、`skills.js` 仍包装 direct sync。

风险：

- 直接写 runtime 的 API 绕过 dry-run、summary、rollback、operation reason。
- 测试或未来调用方可能无意使用 direct sync，导致与 init 主链不同。

建议：

1. 将 direct sync API 改为内部调用 plan/apply，并要求显式 adapter。
2. 对 `agents.js`、`skills.js` 做兼容层审查；若已无外部调用，标记 deprecated 后删除。
3. 单测锁定：所有 runtime 写入必须能先生成 operation plan。

### R6. Adapter transform 依赖正则，需继续收紧 contract tests

证据：

- `CodexAdapter` 使用正则改写 `.claude/*` 路径、`--claude` 参数、`Task spec-*()` 形态和 agent 名称引用。
- `ClaudeAdapter` 会重写 standalone skill name，把 `spec-*` 变为 bare name。

风险：

- 文案稍变可能绕过 rewrite。
- markdown code block、引用路径、自然语言示例都混在同一转换流中，误改/漏改都可能造成 runtime drift。

建议：

1. 为 adapter transform 建 fixture-based golden tests：
   - source skill fixture
   - expected Claude runtime fixture
   - expected Codex runtime fixture
2. 把正则 rewrite rule 单独命名并逐条测试。
3. `doctor` 的 drift check 继续作为运行时回归，不替代 source transform 单测。

### R7. `specs.js` helper 边界正确，但需要尽早拆 parser/writer/validator

证据：

- `commands/specs.js` 已包含 CLI parser、write proposal、validate run、payload validator、frontmatter parser、redaction pattern、path resolver 和 markdown file walk。
- 当前约 581 行，仍可控，但增长趋势明显。

风险：

- 后续 standards MVP-B 如果加入 promote/apply/check，就会把 helper 推向过厚。
- Redaction、path safety、artifact schema 校验可能需要被其他 helper 复用。

建议：

1. 维持 `commands/specs.js` 为薄入口。
2. 拆出：
   - `specs/options.js`
   - `specs/proposal-writer.js`
   - `specs/proposal-validator.js`
   - `specs/run-validator.js`
   - `specs/path-safety.js`
   - `specs/redaction.js`
3. MVP-B 前先拆，不等新功能叠上去。

原则边界：

- `specs write-proposal` 只写 proposal artifact。
- promote 到正式规范文档如果出现，也必须 preview-first、显式确认，不应成为自动规则引擎。
- CLI 只校验格式、路径、redaction、idempotency，不判断规范内容是否好。

### R8. `task-pack.js` 的验证逻辑健康，但函数体过长

证据：

- `validateTaskPack()` 与 `validateTaskPackContract()` 承担 metadata、identity、hash、contract JSON、task fields、waves、dependencies、file overlap 等多层校验。
- 文件约 711 行，测试覆盖较好。

风险：

- 继续新增 task-pack 字段时，容易把 deterministic validator 变成一个大 if/else 文件。
- 错误码治理会分散在长函数内部，复用困难。

建议：

1. 按校验层拆分：
   - `validateTaskPackMetadata`
   - `validateSourcePlanLink`
   - `validateContractEnvelope`
   - `validateTasks`
   - `validateExecutionWaves`
   - `validateFileOwnership`
2. 把 error code 常量化。
3. 保持 `validity_scope: identity-freshness-structure-only`，不要把任务质量打分放进 CLI。

### R9. Operation plan executor 缺少统一事务策略

证据：

- `state.js` 的 `applyOperationPlan()` 顺序执行 `ensure_dir/write_file/remove_file/remove_dir/remove_empty_root`。
- `writeManagedFile()` 直接 `writeFileSync` 到目标路径。
- `init` 的 destructive reset 有 rollback backup，但普通 apply 没有。

风险：

- 中途失败可能留下半更新 runtime。
- binary support file、mode、目录删除之间没有统一事务记录。

建议：

1. 新增 `applyOperationPlanWithBackup(projectRoot, plan, options)`。
2. 对 `write_file/update_file/remove_file/remove_dir/prune_command` 统一备份目标路径。
3. 对文本写入使用 tmp + rename；对目录写入先写临时目录，再 swap 或至少支持 restore。
4. `init/clean/specs write-proposal` 分别声明自己的事务边界：
   - `init`: runtime asset transaction
   - `clean`: managed asset removal transaction，可先从 dry-run + backup 开始
   - `specs`: run-local artifact transaction，当前 tmp+rename 基本合格

### R10. CLI command registry 可以更数据化

证据：

- `index.js` 手写 if 分发 `doctor/init/clean/tasks/specs`。
- `crg` 在 `bin/spec-first.js` 特殊分支延迟加载。

风险：

- 每新增 package subcommand 都要修改 help、index、tests，容易漏。
- `crg` 是 bin 层特殊分支，普通命令 registry 对它不可见。

建议：

1. 保持 `crg` 延迟加载，但把 help metadata 收进一个轻量 registry。
2. `index.js` 只根据 registry 分发普通命令。
3. help 输出由 registry 生成，避免新增命令时文案漂移。

## 7. 分阶段执行计划

### Phase 0：低风险诊断修复

目标：先修会影响当前开发体验和诊断可信度的问题。

步骤：

1. 修改 `checkCrgNativeModules()`，优先调用当前 checkout 的 `bin/spec-first.js`。
2. JSON doctor report 为 CRG CLI check 增加来源字段或至少在 message 中标明 local/global。
3. 增加单测覆盖：
   - 本地 bin 可用时不依赖全局 `spec-first`。
   - 本地 bin 不可用时 fallback 明确。

Done signals：

- `node bin/spec-first.js doctor --json` 不再被全局 `spec-first` 安装状态污染。
- 相关 doctor 单测通过。

### Phase 1：收口 direct sync 双路径

目标：所有 runtime 写入统一经过 operation plan。

步骤：

1. 找出 `syncBundledAssets/syncCommands/syncSkills/syncAgents` 外部真实调用。
2. 若只剩兼容 wrapper，将 direct sync 改为：
   - build filtered asset set
   - build operation plan
   - apply operation plan
   - return syncedAssets
3. 给 `agents.js`、`skills.js` 增加 deprecation 注释或删除未用 wrapper。
4. 增加 contract test：direct sync 与 plan sync 产物一致。

Done signals：

- runtime 写入路径只有一个 operation executor。
- dry-run/apply/legacy reset 不再有独立实现漂移。

### Phase 2：`init` session 化

目标：让 `runInit()` 回到薄 orchestrator。

步骤：

1. 提取 `parseInitArgs()` 保持现状。
2. 提取 `buildInitContext()`：platform、adapter、manifest、filtered assets、developer。
3. 提取 `buildInitAssessment()`：legacy/drift/normal 三类路径归一。
4. 提取 `buildInitPlan()`：reset、preSync、write metadata、runtime plan 合并。
5. 提取 `applyInitPlan()`：统一 rollback。
6. 提取 `renderInitResult()` 与 `renderInitDryRun()`。

Done signals：

- `runInit()` 主要只剩流程调用，复杂分支下沉到可单测函数。
- legacy state、current drift、normal re-init 三类路径各有最小单测。
- 普通 re-init 失败也能 restore 到执行前状态。

### Phase 3：`plugin.js` 拆分

目标：把 asset 控制面的事实读取、delivery 过滤、计划生成、检查分离。

建议文件：

```text
src/cli/assets/discovery.js
src/cli/assets/governance.js
src/cli/assets/delivery.js
src/cli/assets/plan.js
src/cli/assets/inspection.js
src/cli/assets/integrity-rules.js
```

步骤：

1. 先移动纯函数，不改行为。
2. 保持 `plugin.js` 作为兼容 facade，避免一次性改动所有调用方。
3. 每移动一组函数，运行对应 governance/runtime tests。
4. 最后缩小 `plugin.js` export surface。

Done signals：

- `plugin.js` 降到 facade/组合层。
- governance validation 可独立测试。
- delivery filtering 可用纯输入 fixture 测试。
- integrity rules 可独立测试。

### Phase 4：`doctor` registry 化

目标：让 doctor 成为事实检查管线，而不是中心化控制器。

步骤：

1. 定义 `DoctorCheck` shape。
2. 拆 common/platform/runtime/graph/evidence checks。
3. `buildDoctorReport()` 改为按 registry 收集 checks。
4. 渲染与 report construction 解耦。
5. 锁定 JSON contract 不破坏已有字段。

Done signals：

- 新增一个 check 不需要改中央 if/else 编排。
- 每类 check 可独立单测。
- `doctor --json` 仍兼容现有字段。

### Phase 5：helper 分层

目标：在 standards/task-pack 扩展前先防止 helper 变厚。

步骤：

1. 拆 `specs.js` 的 parser/writer/validator/path/redaction。
2. 拆 `task-pack.js` 的 metadata/source-plan/contract/task/wave/file-owner 校验。
3. 保持 CLI 输出完全兼容。
4. 增加 fixture-based tests，覆盖 invalid path、secret-like payload、wrong chain、stale hash、same-wave overlap。

Done signals：

- `commands/specs.js` 与 `commands/tasks.js` 都只做参数解析与输出。
- helper 实现层可以被 workflow hook 复用，而不依赖 CLI stdout/stderr。

## 8. 建议测试矩阵

## 9. 不建议做的事

1. 不要把 `doctor` 做成自动修复器。
2. 不要让 `tasks validate` 判断 task 拆分质量。
3. 不要让 `specs write-proposal` 自动 promote 到正式规范。
4. 不要为了统一把 `crg`、runtime install、workflow execution 都塞进一个 CLI 状态机。
5. 不要新增第二套 workflow/skill delivery 真源。
6. 不要手改 `.claude/`、`.codex/`、`.agents/skills/` runtime 来验证 prose 变更。

## 10. 推荐下一步

如果只做一个最小闭环，建议从 Phase 0 + Phase 1 开始：

1. 修 `doctor` CRG local-bin 检查，立即提升 dogfood 可信度。
2. 收口 direct sync API，避免未来 runtime 资产写入绕过 operation plan。
3. 再推进 `init` session 化和 rollback 统一。

这条路径最小、可验证、不会改变公开 workflow 语义，也不会引入强编排。
