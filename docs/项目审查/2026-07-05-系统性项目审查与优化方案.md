# spec-first 项目 Review 与优化方案（2026-07-05）

## 1. Executive Summary

**总体判断：spec-first 已从 6 月中旬的“能力完整但外部不可见”，推进到 7 月初的“多宿主、adoption-first、runtime 证据明显增强”。当前最大短板已经不再是入口可见性，而是 outcome evidence、Windows/workflow portability、OSS 治理信号和真实用户采纳证据尚未闭环。**

本次按 `docs/10-prompt/系统性项目审查方法.md` 执行项目级系统性审查。审查同时采用项目负责人、架构负责人、开源负责人三重视角，并遵守角色契约中的 `Light contract + Explicit boundaries + Deterministic floor, LLM semantic judgment`。

| --- | --- | --- |
| 定位 | README 首屏已统一为“面向 Claude Code、Codex、Kiro、Qoder 与 Cursor 的 AI Coding Harness”，比 6 月 15 日的“四源漂移”明显改善。 | confirmed |
| 多宿主 | CLI adapter 已覆盖 `claude/codex/cursor/kiro/qoder`，但 Cursor/Qoder/Kiro 仍有 preview/degraded loader 语义。 | confirmed + degraded |
| Evidence/Eval | `honest-closeout`、`verification-run-summary`、AI dev quality gate、eval fixtures 均在场；但多数仍是 contract/shape/evidence-runner 层，未证明真实 workflow outcome。 | confirmed + advisory |
| Onboarding | README 变成 adoption-first，含 90 秒路径、first artifact、Windows install 基础说明；但独立 demo repo、真实案例和 ROI 仍缺。 | confirmed |

优先方向：

1. **P0：建立 dogfood outcome ledger 和真实用户摩擦样本。** 把“机制存在”推进到“真实 workflow 结果可复盘”，避免 Evaluation Harness 长期停在 aspirational。
2. **P1：收口 Windows/workflow portability。** 当前安装层已有正向证据，但 `spec-code-review`、`spec-polish-beta`、`spec-optimize`、`spec-sessions` 等 helper 主路径仍显式依赖 `.sh`。
3. **P1：补齐 OSS/采纳治理信号。** 低成本补 `CODE_OF_CONDUCT`、issue templates、CODEOWNERS、root ROADMAP，并把 release notes/roadmap 面向外部读者表达。

## 4. 核心优势

1. **source/runtime 边界清楚。** Source 路径与 generated runtime mirror 的边界在角色契约、README、context governance、adapter 实现中一致表达。
2. **多宿主扩展已从双宿主推进到五宿主框架。** Claude/Codex 是主力，Cursor/Kiro/Qoder 进入 opt-in/preview，并保持诚实降级。
3. **Evidence 文化强。** `honest-closeout`、`verification-run-summary`、runtime capability catalog、AI dev quality gate 说明项目持续把“声明”拉回“证据”。
4. **Review/Knowledge 比对标项目厚。** `spec-code-review`、`spec-doc-review`、`spec-compound`、`docs/solutions` 和 rule maturity 形成了 review→learning→candidate standard 的雏形。
5. **自指审查能力强。** 历史审查密集，且本次 `npm test` 暴露审查索引失败，说明项目至少有测试在守护 review artifact 的消费性。

## 8. 不做什么

- 不把 spec-first 做成强状态机或中心化流程引擎。
- 不因宿主支持扩展而追逐 20+ host 数量。
- 不把 generated runtime mirror 当 source 修。
- 不把 Web/Graphify/CodeGraph/agent 输出当 confirmed truth。
- 不在 outcome evidence 之前新增过重 behavior contract source surface。

差异化标签：

1. Repo-backed AI Coding Harness
2. Evidence-first workflow layer
3. Source/runtime same-origin governance

失焦风险：

1. 继续新增 agent/skill，稀释 outcome evidence。
2. 用 preview host 数量替代真实 invocation evidence。
3. 把企业治理写成文档宣传，而不记录可验证运行结果。

## 9. 推荐文案

### 一句话定位

`spec-first` is a repo-backed AI Coding Harness that turns one-off agent conversations into requirements, plans, scoped work, review evidence, and reusable learning.

### 30 秒介绍

`spec-first` 不替代 Claude Code、Codex、Cursor、Kiro 或 Qoder。它给这些宿主加一层项目内工程闭环：先把需求和计划落成 artifact，再让实现、验证、review 和经验沉淀都能回到仓库。脚本只强制确定性不变量并准备事实，语义判断留给 LLM 和 reviewer；完成声明必须带证据，生成 runtime 可以随时从 source 重建。

### 面向不同读者

| 读者 | 表达 |
| --- | --- |
| Tech Lead | 把 AI coding 从“每个人各自和模型聊天”变成可检查的工程过程。 |
| 开发者 | 少在长会话里反复解释背景，让任务变成 repo-local artifact，再执行、验证、review。 |
| 决策者 | 它不是另一个代码生成器，而是一层治理与证据系统：帮助团队知道 AI 做了什么、为什么这么做、验证了什么、还有哪些风险没关。 |

## 10. 最终结论

spec-first 值得继续投入，但下一阶段投入重点必须从“造能力”转向“证明能力”。6 月 15 日的最大问题是能力不可见；7 月 5 日时，README、五宿主 preview、CI、runtime catalog 已经解决了一部分可见性问题。现在最稀缺的是：真实 workflow outcome、真实用户摩擦、Windows 原生 workflow 路径、OSS/企业采纳信号。

本报告的 findings 是 review evidence，不是已拍板决策。P0/P1 finding 已按方法要求建立 origin trace plan：

- `docs/plans/2026-07-05-001-review-closure-outcome-ledger-plan.md`
- `docs/plans/2026-07-05-002-windows-workflow-portability-plan.md`
- `docs/plans/2026-07-05-003-oss-adoption-governance-plan.md`

下一步三件事：

1. 先执行 outcome ledger MVP，收集 10 条 dogfood run，证明或推翻当前 roadmap 优先级。
2. 关闭 Windows P1，避免“安装支持 Windows”与“workflow helper 仍 bash-only”形成体验断层。
3. 补齐 OSS governance surface，让外部评估者能在 5 分钟内判断项目可信度与路线。
