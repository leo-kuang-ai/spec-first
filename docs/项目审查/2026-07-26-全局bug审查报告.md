# spec-first 全局 Bug 审查报告（2026-07-26）

## 0. 结论

对约 2.7 万行 CLI JS + repo scripts + 108 个 skill 脚本做了 11 分区全覆盖审查（每分区独立审查员逐文件通读，P1/P2 经内联对抗核实或只读复现）。**共确认 9 条 P1、约 24 条 P2、约 20 条 P3；无 P0（无主路径数据丢失/安全漏洞），但存在两条数据丢失类 P1 触发条件并不苛刻。** 五大根因模式：① Windows spawn/path 处理系统性缺陷；② 按名删除缺 ownership 检查；③ git 输出 C-quoted 路径不解引号（中文文件名主用例失真）；④ 错误处理断层（null/EACCES/编码/超时未捕获）；⑤ 确定性校验 gate 自身有洞。1336 个单测全绿与这些 bug 并存，说明测试覆盖偏向 POSIX happy path 与契约形状，未覆盖跨平台与边界输入。

## 1. P1 清单（9 条）

1. **`src/cli/adapters/codex.js:626` — init/clean --codex 无条件递归删除用户目录**【已核实】
   `plugins/spec`、`plugins/spec-first`、`.agents/plugins` 作为 legacy 路径被纯按名 `remove_dir`（`state.js:716` 执行 `fs.rmSync(recursive,force)`），无任何 managed 标记/state/内容检查；默认 init 摘要预览还刻意隐藏逐路径删除明细（`tests/unit/init-preview.test.js` 断言）。用户仓库自有 `plugins/` 树即被静默删除。数据丢失类，修复优先级最高。
2. **`skills/spec-optimize/scripts/experiment-worktree.sh:371,432` — printf %03d 八进制解析，破坏性操作打错目标**【已复现】
   `printf "%03d" 010` 输出 `008`（实测）；worktree 展示名本身就是零填充，用户照抄 `cleanup <spec> 010` 会对 exp-008 执行 `git worktree remove --force` + `git branch -D`（含未提交工作）；`008/009` 直接 invalid number 中止。
3. **`src/cli/helpers/spec-work-run-artifact.js:971` — Windows 上 spec-work 证据产物永远写不成功**【已核实】
   `expectedRef` 用 `path.join` 构造（win32 反斜杠），而前置校验（960-964 行）只接受正斜杠 repo-relative ref：正斜杠 ref 过校验但 971 行严格比较失败，反斜杠 ref 直接被拒——两难死锁，`run.json` 证据链在 Windows 全灭。
4. **`src/cli/helpers/verification-run-summary.js:163` — 同根因，record→read 往返在 Windows 断裂**【已核实】
   写侧输出反斜杠 `run_summary_ref`，读侧（237-239 行）拒绝反斜杠并要求 `/verification-run-summary.json` 后缀。与上一条同属 evidence chain 的 Windows 系统性缺陷。
5. **`src/cli/commands/update.js:109,121` — `spec-first update` 在 Windows 完全不可用**【已核实，基于 Node 文档】
   `spawnSync('npm.cmd'/'spec-first.cmd')` 无 shell 选项，Node ≥20.12（CVE-2024-27980 加固，engines 为 >=20）抛 EINVAL。仓库自身 `scripts/lib/npm-cli.cjs` 与 smoke 测试都刻意规避了此模式，唯独 update/run-test-suite 漏改。
6. **`src/cli/commands/update.js:134` — update 的 runtime refresh 用 cwd 而非 git root 检测宿主**【已核实】
   `findGitRoot(root)` 的返回值被丢弃，platform detection 在子目录执行必然为空 → 回退 `init -y` 默认 claude+codex：从子目录 update 会静默安装用户未选择的宿主 runtime，而真实安装的宿主（如 cursor-only）不被刷新——恰好制造该步骤要修复的 drift。
7. **`src/cli/helpers/git-diff-signals.js:141` — git C-quoted 非 ASCII 路径被破坏性改写**【已复现】
   `core.quotepath` 默认开启时任何中文文件名输出为引号+八进制转义；parseNumstat/parseNameStatus/parsePorcelain 不解引号，`normalizeRepoPath` 还把转义反斜杠换成 `/`。本机实测本仓库文件产出 `"docs/10-prompt/GPT-5.6/346/217/220/....md"` 假路径。下游 resource-governance/task-governance 的 large-file 检查、owner-hint、top-dirs 对中文文件名（本项目主用例）全部失真。
8. **`skills/spec-compound/scripts/session-history/extract-errors.py:209` — 平台探测 10 行截断使错误挖掘静默变空**【已核实】
   姊妹脚本 extract-skeleton.py 已因 issue #923 移除该上限（Claude session 前置 10+ 条元数据记录是已证实形态），此处漏同步；误检后 handle_noop 输出 0 错误且 parse_errors=0，与「session 无错误」不可区分。
9. **`skills/spec-app-consistency-audit/scripts/validate-artifacts.js:208` — 被 gate 拒绝的 issue 仍被 strict 校验，整个 headless audit 因此失败**【已复现】
   evidence gate 的优雅降级路径（rejected_issues）对「缺 evidence」这一它存在就是为了吸收的输入不可达；`run-audit.js:562` 直接 `artifact_validation_failed` 中止全程。

## 4. 根因模式与修复顺序建议

1. **Windows 系统性清扫（覆盖 P1 #3/#4/#5 + P2 doctor/run-test-suite）**：全仓 grep `npm.cmd|spawnSync.*cmd` 统一走 `scripts/lib/npm-cli.cjs` 已有的正确模式；repo-relative ref 统一 `path.posix.join` 或 `.split(path.sep).join('/')`。与 `docs/项目审查/2026-07-05-windows-powershell-fix-plan.md` 合并推进，一个 plan 关掉 5 条。
2. **删除类 ownership 检查（P1 #1 + P2 codex.js:598）**：legacy 清理先验 managed marker/state 记录，否则降级为 warning + 显式确认；这与项目自己的 mixed-ownership 纪律一致，属违反自家契约的实现缺陷。
3. **git C-quoted 路径解码（P1 #7 + scenario-fingerprint P3）**：加一个共享的 unquote helper（或 `-c core.quotepath=false` 取数），中文用户主用例立即受益。
4. **确定性 gate 补洞（P1 #9 + task-pack reason_code + check-prd 相对路径 + extract-errors 截断）**：这些是「脚本强制确定性不变量」这层地板自身的洞，比普通 bug 优先——gate 失真会让 LLM 拿到错误事实。
5. **错误处理断层批量修（setup-facts null、graphify EACCES、encoding、TimeoutExpired、KeyError-only）**：同类模式一次 sweep，每处就是几行 defensive 修复。
6. P3 按顺手原则跟随对应文件的修复一起做，不单独立项。

### 6.1 新增 P2（7 条）

1. **`src/cli/runtime-tools-index.js` `removeManagedRuntimeToolsBlock` — 孤立 start marker 后全部用户内容被删（条件触发的数据丢失，第二轮最严重项）**【已复现】

4. **`src/cli/helpers/verification-run-summary.js:489` — `fs.openSync` EACCES 未捕获，破坏 structured-JSON 契约**【核实】
