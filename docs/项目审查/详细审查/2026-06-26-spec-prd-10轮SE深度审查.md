### 第 2 轮 · B1 切面 · 歧义检测脚手架(✅ 完成)

**方法:** 4 专家角色并行独立设计(ambiguity-taxonomist / llm-prompt-designer / boundary-guardian / brownfield-practitioner)+ 对抗综合核验源码事实。约 680k tokens。

**结论:做最小版。** boundary-guardian 的「discovery 侧 over-gate 滑坡」反方基本成立并被采纳为**形态约束**;但其「纯接线零内容增量」主张被证伪——referent-ambiguity 是 `skills/spec-prd/references/product-expert-lens.md` 第 11 行 9 个需求完整性维度、`prd-readiness-lens.md` change-delta、`grill-with-docs-integration.md` 均未覆盖的 brownfield 真空。

**坐实的源码事实:**
- `product-expert-lens.md` 已有完整 Run-Local Interface(`gap -> owner_question_or_assumption -> PRD_write_target -> closure_state`)+ Interface Invariant(强制每个进 grill 的 gap 绑 write target)+ closure_state enum;第 11 行那句 "Detect load-bearing ambiguity" 是**失联 prose**(列了 9 维度却没接到下方已有 interface)。

**最终设计(最小 footprint):**

### 第 3 轮 · B1 切面 · 隐含假设挖掘 + 主动场景外推(✅ 完成)

**方法:** 4 专家角色并行(assumption-elicitor / scenario-generator / boundary-guardian / cost-realist)+ 对抗综合核验源码。约 695k tokens。

**核心裁定:把 B1「读不出的缺失」拆两半,两半结论相反。**

- **场景外推(并发/部分失败/回滚/空态/权限交叉/重复提交)——否决新增。** 源码铁证:Canonical **leaf** 定义(`SKILL.md`:"no remaining sub-decision that would change product behavior/acceptance/scope")在语义上**就是**"不准停在 happy path、必须把会改变行为的分支外推到底"的强制令;branch walking 名单已点名 exception/state/permission;relentless-by-default 本身就是主动场景外推引擎。再加独立 section 是 leaf + branch list 的语义重复(R2 已否决过的 over-gate 重演)。
- **隐含假设挖掘(未言明默认值 / 数据量级 / 并发预期 / 默认失败-回滚-权限行为)——采纳,这是 B1 下半唯一真空。** 注意区分:exception/permission 等**场景**已被覆盖,真空是它们底下那个 owner 因"显然"而从未写下的**默认值与量级前提**。今天要么实现期返工、要么漏到线上(性能塌方、越权),零机制能抓。

**真正的设计增量(范式创新):declare-default 而非 ask-open。** 不问 owner"并发冲突怎么办?",而是替 owner 把"我将默认按 last-write-wins 处理"这句话**说出来**让其一键确认/否决——认知负载更低,即使 owner 不答也有正收益(声明出的默认 + 后果落成 `recommended default`,严格优于被静默烤进 PRD)。这正面回答了 R3 的本质难点:缺失无文本锚、无措辞可嗅,只能靠 LLM 主动外推。

**最小 footprint:** `skills/spec-prd/references/product-expert-lens.md` 第 11 行后 +1 条 responsibility bullet(declare-default,补 tacit-defaults/scale/concurrency 维度)+ Interface Invariants +1 条;**checker 零新增**(缺失无文本锚 ⇒ deterministic checker 嗅不到、强行做必假阳性——R3 特有硬红线,也是 Scripts-prepare-LLM-decides 教科书案例);**readiness 零新增**(未顶出的默认对 readiness 不可见 by design,防 over-gate)。承载复用 Push-Right Brief 行 + 既有 `owner_question_or_assumption` 双分支 + `accepted-assumption` closure_state。

**防噪声三门(全真才顶出,否则静默丢弃):** ① 锚定在 load-bearing 需求的真实变更面;② 合理 owner 可能想要别的值(可争议);③ `planning_would_invent_what`(错了会改 behavior/acceptance/scope/data-authority/permission/source-of-truth)。**关键区分:** owner 真实提出的 gap 绑不上 write target 不丢(carried);model 主动外推的假设绑不上就丢——后者是模型加的,丢掉无损 owner 意图,且 owner 不在场时绝不把"consider X"塞进 PRD body。

**否决项:** 独立 Assumption Mining / Scenario Extrapolation section/schema/字段/reference;任何 checker 缺失检测;场景外推独立维度;穷举场景表/假设矩阵/固定 N/scorecard;外推产物默认写进 body;readiness 新 bullet/gate;新增 closure_state。

**重要事实纠正(综合 agent 核实):** `product-expert-lens.md` 第 11 行**当前磁盘仍是 pre-R2 基线**——R2 与 R3 均为设计探索、**尚未落地**。若 R2+R3 同期落地需协调同段共存(R2 改 ambiguity 分句,R3 加对偶 bullet,互不覆盖)。

**残留验证(留落地轮,不加机制):** owner 不在场时"降级 labeled assumption、不撑 body"这条最易被模型违反——需 fresh-source eval(headless PRD 输入看模型是否克制)验证,**非**加 checker gate。

**B1 整体台账(R2+R3 后 = 设计完整闭环):**

### 第 4 轮 · Blocking-2 切面 · 内容质量地基(✅ 完成,needs-code-verification 轮 / design-only)

**方法:** 4 专家角色并行(testability-architect / checker-engineer / boundary-guardian / downstream-consumer)+ 对抗综合。约 642k tokens。本轮锚定真实磁盘事实(覆盖率 `check:791-792` 纯 regex、占位符 `check:795` 零语义、AC skeleton、readiness:52 五词黑名单 anti-rubric)。

**方法:** 4 专家角色并行(consumer-contract-analyst / map-reduce-fidelity / boundary-guardian / integration-test-strategist)+ 对抗综合核验源码与既有测试。约 721k tokens。本轮换轴——前 7 轮都在 spec-prd **内部**做质量,本轮第一次审 spec-prd 作为 **provider** 把制品交给 spec-plan **consumer** 这条接缝,以及大输入/多源切片时的传真度。

**母结论(反预期,已采纳):接缝已覆盖良好,不是真缺口。** 入场假设是"producer 全绿但 consumer 拿到不可消费的 PRD"会有结构性裂缝,核验后被证伪——可消费性已由**三层**共同承担,无须新增机制:
- **producer 侧确定性 checker:** `check-prd-artifact.js` 的 `CORE_SECTIONS`(`check:13`)锁 PRD 结构完整 + R↔AE 双向 trace(正向 `uncovered_requirements` + R5 设计的反向 `dangling_acceptance_ref`)。
- **consumer 侧 entropy check:** `skills/spec-plan/references/planning-flow.md:73` 已有 "PRD handoff entropy check"——plan 入场显式检 PRD 是否带可规划的确定性,不是裸信任 ready 标签。
- **既有跨文锚点测试:** `tests/unit/spec-prd-contracts.test.js:1080` 已锁 spec-prd 与 planning-flow.md 的跨文一致性。

**逐项裁定:**

| 项 | 裁定 | 理由 |
|---|---|---|
| 接缝可消费性整体 | **基本无缺口** | 三层(producer checker + consumer entropy check + 跨文锚点测试)已覆盖;再加 handoff schema/契约层违反 80/20 |
| (a) producer→consumer token 交集断言 | **DEFER-to-narrow-ADD** | 唯一窄 drift 缝:CORE_SECTIONS 与 planning-flow consumer 期望段名若未来分叉无测试可抓;可加 1 条 R1-safe 单向交集断言,但**前置需先 export `CORE_SECTIONS`(当前未导出)**,改动面外溢,留落地轮权衡 |

**R1 红线全程守住:** 本轮反复确认任何接缝改动**不得**让 spec-prd 产物形态被 spec-plan 反向耦合——producer 不依赖 consumer 内部实现,consumer 消费 source refs / readiness facts / reason_code 而非 producer 内部细节(角色契约系统边界硬约束)。(a) 的 token 交集断言被设计为**单向**(只断言 producer CORE_SECTIONS ⊇ consumer 期望的最小段集),正是为了不把 consumer 期望写回 producer。

**对抗综合纠正:** 两个 persona 误称 `CORE_SECTIONS` 已 export 可直接被测试 require——核验源码 `check:13` 确认其为**模块内常量、未在 module.exports 暴露**;故 (a) 的真实成本不是"加一行断言"而是"先改 checker 导出面",据此从 ADD 降级为 DEFER-to-narrow-ADD。

**否决项(记录拒绝理由,避免后续轮重提):** PRD→plan handoff schema/中间契约层、map-reduce fidelity 检测机制、分片 staleness 检测机制、任何让 producer 形态反向耦合 consumer 的双向契约、新建 reference。

**残留(交落地轮):** (a) 若落地,export `CORE_SECTIONS` 后加单向交集断言,且断言锚点须证明不锁死 consumer 内部措辞、只锁段名最小集;(c) 一行新鲜度边界 prose 若加需 fresh-source eval 确认不退化为 over-gate。

**第 8 轮台账推进:** 接缝从"疑似结构性裂缝"→"经三层覆盖证伪为非缺口";仅留一条 R1-safe 单向交集断言为 DEFER-to-narrow-ADD 候选(前置 export CORE_SECTIONS)+ 一行新鲜度 prose 候选。本轮以 source + 既有测试核验为主,未运行新测试,无代码改动。
